# ADR-124：受信入口事实与 QQ／皮套／控制台提醒出口

日期：2026-10-09。状态：代码已实现；生产迁移和启动尚未执行。

用户要求补齐“准确知道当前渠道，并按要求选择其他渠道”，并明确选择“同时支持 QQ、皮套和控制台文字提醒”。本次范围是入口事实、已明确要求的提醒投递与相应回执，不扩大自主关心的渠道，也不新增任意收件人。

## 决策

1. 每轮主回复读取由本地会话／经令牌认证的入口提供的 `cli`、`qq_private`、`avatar` 事实。消息载荷不能指定或覆盖它。事实进入不可裁的 `chat-channel` 区块和 trace 引用。渠道与打字／语音分开；缺少输入方式来源时不推测。
2. 新提醒未指定渠道时使用当前入口；明确指定时保存指定渠道。修改／确认保留原渠道，除非用户要求更换。其他渠道返回未支持；当前运行方式没有的出口返回未配置，不静默改投。
3. 来源 `conversation_ref` 与目标 `delivery_channel` 分列。迁移 0017 只给 `notification_intents` 追加闭集列，旧行缺省 `qq_private`，保留旧提醒的 QQ 语义；0014–0016 不改。
4. 三渠道复用通知意图、实例、一次性占用、重启遗留隔离及到期宽限规则。QQ 继续固定本人私聊。皮套／控制台使用单独注册的 `local.reminder.message`（R1），只认本会话绑定出口；本地与 QQ 的具名系统归因、权限和投递登记各自独立。执行仍经过 ActionGateway 和动作账本。
5. 共存核心的后台提醒在已排队的人类轮次之后执行。目标外壳离线时保留原目标，重连重排；超过既有宽限则过期。已交接而无回执记 `delivery_unknown`，不自动重发，也不冒称用户看到。
6. 本地提醒使用独立 `DELIVER_REMINDER_TEXT`／`REPORT_REMINDER_DELIVERY` 协议，不借用角色插话。皮套页面显示可关闭的纯文字卡片，浏览器显示后凭随机令牌回执；令牌绑定消息、连接和时限。控制台在 stdout 写入回调后回执。两者仅代表显示接口接受，均不证明本人阅读。
7. 共存控制台使用 loopback 6753 和独立入口令牌；准备／下次受控启动升级旧令牌文件。`pnpm coexist:chat` 连接现有核心，不另开数据库。独立 `pnpm chat` 或独立皮套桥只允许其运行方式已接线的本地提醒出口；需要多渠道时使用共存核心。
8. 提醒处理事实包括渠道。完整回复必须确认真实出口，流式回复末尾补齐遗漏的渠道确认；明显改投措辞由现有提醒守卫更正。模型没有得到任何新的发送成功口吻授权。

## 验证和限制

`pnpm reminder:channels:verify` 使用真实共存核心、临时数据库、loopback 模型夹具、实际控制台外壳，以及 Python／页面行为夹具，覆盖三入口事实、伪造入口、跨渠道回执拒绝、改出口、重连、重启、账本和人类排队优先。它不代表真 QQ 手机收信或真实皮套浏览器整链已验收。

`pnpm with-test-model pnpm reminder:channels:live` 单独验证真实模型的渠道解析，包括“提醒我打开 QQ”属于提醒正文。该门不打开数据库、不发送任何消息；有限样例通过不等于自然语言理解永久正确。

重连等待针对核心的 TCP 入口连接。皮套 Python 外壳仍在线但页面未连接时，外壳如实报告本次投递失败，不自动补发；页面需要保持连接。多个本地连接只向当前连接代次投递。

原有 QQ 主动联系／桥／传输／共存门继续运行。完整回归使用今天已有、通过 manifest 和树摘要校验的正式快照，再复制到临时库；不打开或修复当前正式库。最终读数见 `docs/post-lv2/Chat-Channel-Reminder-Acceptance-2026-10-09.md`。

正式库仍须单独批准应用 0017，并按既有单持有／备份／停机纪律受控启动。当前源码会拒绝直接打开未迁移的旧正式库；普通启动不偷偷迁移。批准前不宣称本次功能已在正式聊天生效。

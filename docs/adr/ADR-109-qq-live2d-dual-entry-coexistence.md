# ADR-109：QQ 与 Live2D 双入口共存（一个核心、多个受信会话）

状态：ACCEPTED / DESIGN FROZEN（2026-10-06）。**采用路线由 WP1 裁定**（见 §5），本 ADR 的
`D01`–`D09` 与路线无关，先冻结；`D10` 是留给 WP1 的裁定槽，落地时以追加节记录，正文不改写。

计划：[`docs/post-lv2/QQ-Live2D-Coexistence-Execution-Plan-2026-10-06.md`](../post-lv2/QQ-Live2D-Coexistence-Execution-Plan-2026-10-06.md) ·
基线：[`docs/post-lv2/QQ-Live2D-Coexistence-WP0-Baseline.md`](../post-lv2/QQ-Live2D-Coexistence-WP0-Baseline.md) ·
现成方案核对：[`docs/post-lv2/QQ-Live2D-Coexistence-OSS-Review-2026-10-06.md`](../post-lv2/QQ-Live2D-Coexistence-OSS-Review-2026-10-06.md)。

## 0. 这个 ADR 要回答的问题

今天 QQ、皮套与 CLI **共用同一个 `conversationId`**（`src/main.ts:1307-1309`），
而且**每个入口进程各自跑一整套后台消费者**、各自持有一份数据库租约。
"让两条入口同时在线、互不串台"因此不是接一个框架就能得到的结果，而是**四件事**：

```text
① 一个库持有者 + 一套后台消费者（今天：每个入口进程各一套）
② 会话按入口绑定（今天：conversationId 里没有入口维度）
③ 近期上下文 / 摘要 / 任务内容按入口分开（今天：Recent 取角色级，跨会话）
④ 回复、取消、播放、断开按入口归属（今天：每进程一套，且 close() 直接关库）
```

## 1. 决定（D01–D09）

### D01 · 一个进程、一个库持有者、一套公共生命周期

生产形态改为：**一个常驻 LG 核心进程**持有数据库与租约，并在**该进程内**装配 N 个受信会话。
`INC-01` 的租约 → 快照 → 打开 → 唯一关闭链（`src/db/index.ts` 中央闸 · `runtime-shutdown.ts`）
**一字不改**，它保护的仍然是"一个持有者"。

理由：`processor_watermarks` 是 `(character_id, processor, processor_version)` 级
（`src/infrastructure/persistence/migrations.ts:246-253`），消费者读的是**角色级**
`conversation_events.sequence`（`migrations.ts:131-132`）。两个进程同时消费同一角色的事件流，
会重复触发模型调用与 job 行；这不是"多一个入口"的代价，而是**同一份认知被算两遍**。

### D02 · 会话按入口绑定，入口由**程序事实**决定，不由载荷决定

`conversationId` 增加一个**入口分量**；入口由装配层从**进程事实**（argv / 监听端口 / 认证结果）推导。
外部昵称、persona、conversationId、消息角色字段**不得**切换身份、会话或网关（沿用 `INV-PL2-08`）。

归因沿用 `src/infrastructure/runtime/conversation-attribution.ts` 的既有形状：
**一个入口一个具名工厂**（今天三支：控制台 / 脚本 / QQ 私聊）。
新增入口必须新增具名 ingress；**不得**引入一个可从载荷填的 `role` 枚举
（同文件 §"为什么是三个具名工厂"就是这条的负控）。

### D03 · 公共消费者由**一个**核心管理者执行一次

`open()` 里的播种与开机追赶（关系 ORIGIN、情绪建档、信念建档、故事消费、反思/约定追赶）
与 `close()` 里的收尾，**从会话移到核心**，每进程恰好一次。
会话只保留"自己那一轮"的东西：序号、网关、记录器、入口专属的取消表与交付账。

理由（基线 §6 的 R4/R5/R6）：`ChatSession.close()` 直接走唯一关库链（`src/main.ts:4606`）；
`closeSemanticEncoderForExit()`（`:4605`）是**退出**语义。两个会话各调一次 ⇒
第一个就把库和编码器关掉，第二个入口静默失效。

### D04 · 共享认知、分开近期

共享：人格、用户身份、长期记忆、语义索引、信念、关系、情绪、目标、承诺、反思、故事。
分开：**近期对话窗口**、会话摘要、当前任务上下文、回复目标、取消、播放账。

这不是"选择"，是计划 §1 的定义；共享认知产生的跨入口召回是**预期行为**，
不得为了拿到"零混入"而关闭正式启用的认知功能（计划 §5 末段）。

### D05 · 事件坐标：沿用现有两列，**不新增迁移**

- `conversation_events.sequence` = **角色级**，`unique (character_id, sequence)` ⇒ 消费者水位坐标（共享）。
- `conversation_events.conversation_sequence` = **会话内** ⇒ 每入口各自连续（`assertSequenceContiguous`）。

两个会话的相同"第 3 条"因此**不会**被当成同一事件。计划 §"审计事件坐标"要求的那种判别
在现有 schema 上已经成立；本 ADR 据此**不引入**新坐标、不新增迁移。
若实现时发现某消费者实际用的是会话内序号，那是**缺陷**，按缺陷修，不改坐标语义。

### D06 · 首版有序而不等待播放

正式轮次按**一个**有序调度器处理：每入口有界队列、轮转公平（防止一边连续消息饿死另一边）；
控制消息（取消 / 播放回报 / 准备）走**控制通道**，不被慢轮次阻塞；
音频播放**不持有**正式轮次锁；后台队列等待**不得**被误报成模型超时。

模型额度、核心进程与队列仍是共同资源 ⇒ 第一版**不承诺**两个模型请求完全同时运行或零等待，
但**必须**如实报告排队与模型耗时（计划 §5 的性能清单）。

### D07 · 断开不是停机

客户端 `close` 只关闭**该连接**与其入口会话的资源；只有核心管理者能排空两路、
等待在飞消费者、关闭库并释放租约（`INV-DB-01/06`）。
入口会话的收尾与核心的收尾因此是**两个方法**，且只有核心那一个能关库。

### D08 · 保留回复与动作真相

不得用任何前端框架的默认 Agent、另一个模型或独立记忆组件回答 LG 失败请求；
前端框架的额外"表演规划"不得改写 LG 已检查的角色文字与认知结果。
工具执行仍走 `ActionRequest → Policy/Gateway → Adapter → ActionResult` 全链。

### D09 · 回滚 = 停新入站 → 排空 → 正常关闭核心 → 起已验证的旧入口

不恢复数据库快照、不抹除切换后的真实记忆；新会话历史保留；切回旧入口时近期上下文按旧会话读取。
数据库恢复/迁移只在另有必要与对应授权时处理（计划 §6）。

## 2. 历史与记忆的切换规则（冻结）

- 两个新入口**各从新的近期会话开始**；旧混合历史保留原记录与查询入口，
  **不把旧混合原文复制到两个新会话**。
- CLI 原会话语义保持原样（D02 的入口分量对 CLI 取"无"）。
- 共享长期记忆、语义索引、关系与认知状态继续使用现有 owner / character：
  **不重建人物、不重新播种 origin/cutover、不重复导入旧记忆**。
- 语义写入仍是 `ADR-108` 的"明确记忆操作 + 原校验链"，不改成自动记录全部闲聊。

⚠️ **必须如实登记的后果**：QQ 入口今天写在 `dm-<slug>-<user>` 这条会话里（基线 §3.1），
按本规则它切换后会得到**新的**会话 id ⇒ **QQ 的近期窗口在切换那一刻是空的**
（长期记忆与认知仍在）。这是计划选定的口径，不是缺陷；但它必须在激活候选里
**逐字写出来**，由用户在切换授权时看到。替代方案（QQ 保留旧会话、只给皮套新 id）
被否决，理由是那会让"旧混合历史"继续留在 QQ 的近期窗口里，与"两个新入口各从新会话开始"自相矛盾。

## 3. 被否决的备选

| 备选 | 否决理由 |
|---|---|
| 两个入口各起一个 `src/main.ts` 进程（今天的事实形态） | 违反 D01：两份消费者算同一份认知；租约必然拒绝第二个持有者 |
| 靠"换一个前端框架"自动获得入口隔离 | OSS 核对 §"当前 LG 的具体缺口"逐条否掉：`buildGateway` 的会话 id 不含入口维度，换框架不改这一行 |
| 给 `conversationId` 加一个可从请求载荷填的字段 | 违反 D02 与 `INV-PL2-08`：载荷能选会话 = 外壳能切身份 |
| 为双入口新建一套事件坐标 / 新迁移 | 违反 D05：现有两列已经满足，新增坐标会引入第二份权威 |
| 首版就做"两个模型请求完全并行、零等待" | 违反 D06：共同额度与进程资源是事实，承诺它就是假读数 |
| 解除数据库锁让两个进程共库 | 直接违反 `INV-DB-01`，且 `INC-01` 的教训就是"看起来能跑"的共库 |

## 4. 不变量与冻结面（本 ADR 不动的部分）

- `INV-DB-01…07`（单持有 / 快照 / 关闭 / incident hold）**全部照旧**。
- `INV-PL2-08/09`（身份由会话绑定、host = `ChatSession.send()`）**照旧**。
- Memory Kernel 语义、M5.1 权威地图、`artifacts/**` 历史证据：**不动**。
- 归因模型（`ADR-042` / `ADR-043`）：**只追加具名 ingress**，不改判据。

## 5. 待裁定（D10）：采用哪条路线

计划 §2 给了两条：**AstrBot + lxfight Live2D 组合**（第一候选）与
**现有 NapCat + Open-LLM-VTuber，共用 LG 核心**（备用）。
裁定由 **WP1** 的隔离兼容试验给出，判据逐字来自计划 §2：

> 若发现必须重写前端音频调度、建立第二份人格/记忆权威，或无法保留当前已用语音行为，
> 就不采用整套替换路线。

WP0 已摆正两条**决策输入**（不预先裁定）：AstrBot 当前**不在服务**而 QQ 入口**正在服务**；
候选桌面端是**另一套交付协议**，而现有皮套的 ASR/TTS、已检查语句、表情载荷、
合成账、播放账与取消流程都已落地。

**WP1 必须真的跑隔离试验**（模拟 OneBot + 受控回复 + 模拟桌面客户端），
逐项标"通过/失败/不适用/未运行"，再裁定。裁定结果以**追加节**记入本 ADR（正文不改写）。

## 追加节（2026-10-06）：`D10` 路线裁定 = **备用路线**

**裁定：不采用 AstrBot + lxfight Live2D 整套替换；采用「本机现有 NapCat + Open-LLM-VTuber，共用 LG 核心」。**

裁定载体：[`docs/post-lv2/QQ-Live2D-Coexistence-WP1-Compatibility-Trial.md`](../post-lv2/QQ-Live2D-Coexistence-WP1-Compatibility-Trial.md)
（隔离部署 + 24 项兼容矩阵 + 可复跑脚本；证据在 `artifacts/post-lv2/local/coexistence-wp1/`）。

计划 §2 的三个失败条件**全部命中**（逐条证据见该记录 §4）：

1. **必须重写前端音频调度**：候选协议是批次表演（`perform.show` 只带 `{interrupt, sequence[]}`，
   无 `requestId`/`replyId`/`segmentId`），而 LG 的皮套契约是逐句的
   （`SPEECH_SEGMENT` / `REPORT_SYNTHESIZED` / `REPORT_PLAYBACK` 五态 / `CANCEL_TURN`）。
2. **无法保留当前已用语音行为**：候选路线 TTS/STT 是 AstrBot 的（握手 config 实测
   `ttsProvider=astrbot-tts` / `sttProvider=astrbot-stt`），当前是 CosyVoice3 + Qwen3-ASR。
3. **第二份回复权威**：两路都是 AstrBot 的平台，回答者是 AstrBot 的 Agent；
   要换成 LG 必须把 LG 做成 AstrBot 插件（本试验已证明可行，但那是"在别人框架里重写"）。

两条计划之外的补充事实：**版本基线不一致**（被固定的 digest 实际是 AstrBot **4.28.0**，
而部署 README 记 4.27.5）· **要替换一个正在工作的入口**（AstrBot 停机两周，QQ 入口在跑）。

候选组合**成立的部分照记**（分平台会话与定向投递实测零串台 · 强制鉴权负控有效 ·
桌面端本身不含 Agent · 资源服务与模型能力上报），进 WP3 的**可借鉴清单**，不进采用范围。

⇒ `D01`–`D09` **不变**，WP2 起的工作对象是计划 §2 的那张图（一个核心、两个受信会话），
**不需要**替换 QQ 入口、**不需要**替换语音栈、**不需要**动 AstrBot。

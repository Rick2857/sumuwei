# ADR-025：后台抽取是一个带水位与值闸的独立流水线

- **状态**：已接受（M4）
- **日期**：2026-09-16
- **相关**：计划书第 50 / 52 / 143 – 147 / 162 / 180 节；MI-01 / MI-10
- **代码**：`src/kernel/app/memory/job.ts`、`pipeline.ts`、`value.ts`、
  `conflict.ts`、`extractor.ts`

---

## 背景

显式路径（ADR-024）只覆盖"用户明确要求记住"。
其余的信息靠**后台抽取**：定期扫一段会话事件，
从中找出值得长期记住的东西。

这条路径的危险与显式路径**完全不同**：

| | 显式路径 | 后台路径 |
|---|---|---|
| 触发 | 用户要求 | 系统自己决定 |
| 失败 | 可以告诉用户 | 没人看着 |
| 误记 | 用户改一下就行 | 用户**不知道**系统记了什么 |
| 重复 | 用户不会连说十遍 | 重试/重启会让它连跑十遍 |

"没人看着"是最关键的一条：后台路径的错误不会立刻暴露，
而是会在几十轮之后以"她为什么记得这个"的形式出现 ——
那时已经无法回溯是哪一次抽取错了。

因此这条路径需要的不只是"抽取逻辑"，而是
**失败不撒谎、重复不累积、低价值不写入**三件事的工程保证。

---

## 决策

**后台抽取是一条显式的六阶段流水线，每一段都有独立的失败语义，
且"拒绝"是一个正常结果。**

### 1. 六阶段，顺序是刻意的

```text
① 事件视图转换   processorEventViewOf      （tool 事件失败关闭）
② 抽取           extractor                 （模型或规则）
③ 值闸           evaluateValue / gate      （不该记的在这里被拒）
④ 冲突分析       analyzeConflict           （**在放行之前**）
⑤ 放行           validator                 （证据 / 权威 / 幂等）
⑥ 提交 + 折叠    commit → fold
```

**④ 必须在 ⑤ 之前**，这是一个真实修过的顺序错误：
第一版把冲突分析放在放行之后，于是"这条与现有的某条冲突"
这个判断需要的信息（`MemoryLookupForPolicy`）在放行时还拿不到，
只能靠放行后再补一次查询 —— 而那时候选已经被判过一遍了。

冲突分析需要看到的"同槽位现有记录"是一个**读**，
它必须在决策（放行/拒绝）之前发生。

`nowMs` 在流水线顶部**只算一次**：每阶段各取一次会让
同一条候选在不同阶段看到不同的"现在"。

### 2. 值闸：不该记的在这里停下

五个因子合成 `importance`，与阈值比较：

```text
DEFAULT_IMPORTANCE_THRESHOLD = 0.45
EXPLICIT_IMPORTANCE_THRESHOLD = 0   （显式要求记的不受阈值拦）
```

**时间限定槽位要额外降权**（`isTimeScopedPredicate` →
`TIME_SCOPED_DURABILITY = 0.2` + `TIME_SCOPED_PENALTY = 0.7`）。

这是一个真实缺陷：`lunch.today`（"我今天午饭吃了面"）
在没有这条规则时算出的 importance 是 0.783，**直接通过值闸**。
一次性的状态会被永久记住 —— 而"每句话都被记住"
与"没有记忆"在体验上是同一种东西。

**代价是"一次性状态被记为长期"这种错误不会有任何报错**，
它只会表现成"她怎么连这个都记得"。所以必须有独立的一条用例守着。

### 3. 冲突分析：五类判定 → 五种处置

```text
DUPLICATE     → REJECT_DUPLICATE   （完全相同的指纹，不新建）
TEMPORAL_UPDATE → SUPERSEDE        （有时间变迁标记 → 建新条 + 废弃旧条）
CONTRADICTION → MARK_DISPUTED      （矛盾但无时间标记 → 标记而非覆盖）
AMBIGUOUS     → NEEDS_REVIEW
NO_CONFLICT   → CREATE
```

`recordsInCanonicalSlot` 返回 **ACTIVE + DISPUTED**（不只 ACTIVE）。
这也是一个真实缺陷：只查 ACTIVE 时，
一条已经被标成 DISPUTED 的记忆永远不会被后续信息解决 ——
它会一直悬在那里，而系统认为"这个槽位是空的"。

`findTemporalChangeMarker()` 有 13 个标记（"现在"、"改主意了"、
"不再是"…）。它的存在理由是：**"用户改主意了"与"用户自相矛盾"
是两件事**，前者该 supersede，后者该 dispute。
把两者混起来会让"她改主意"变成"她的记忆里有两个互斥的值"。

### 4. 水位（watermark）不能跳过中间的空洞

```text
contiguousFrontierFrom()  —— 走过所有 job，未完成的一律挡住前沿
```

真实的缺陷：第一版只看向前推进的连续段，
于是 A=[1,5]（失败）与 B=[6,10]（成功）算出前沿 = 5。
但那意味着**第 5 轮永远不会被重试**。

修法：遍历**所有** job，任何未完成的都挡住；
若未完成的区间包含当前点，前沿封顶在 `from - 1`。

计划书第 162 节的表述是"中间洞不能丢"，
而它真正要防的是"水位越过了没处理的事件"。

### 5. 失败写进 job，**不抛给调用方**

```text
抽取失败 → job.status = 'failed' + 失败原因
```

计划书第 144 节：故障要能被观察，而不是让一个后台任务
把异常抛到上一层（那里没有人能处理它）。

`canRetryMemoryJob()` 有上界 `DEFAULT_MAX_JOB_ATTEMPTS = 3`：
否则一个持续失败的 job（例如注册表配置错误）会
**无限次调用模型**。

### 6. 幂等键必须区分操作类型

```ts
computeIdempotencyKey({ ..., operation: `${operation}:${memoryId}` })
```

`create` 与 `supersede` 对同一个 `memoryId` 是不同的写入。
不区分时它们会互相顶掉 —— 而症状是
"纠正看起来生效了，但旧条还是 ACTIVE"。

`memoryExtractionIdempotencyKey()` 把 **processor 版本**也算进去：
`@2` 的抽取结果不该被 `@1` 的幂等记录拦住（场景 M4-016）。

### 7. "没有值得记的"是**最常见的正确答案**

抽取 prompt 的第 2 条规则：

> 没有值得记的就返回 `{"candidates":[]}` —— 这是最常见的正确答案。

计划书第 50 节把 REJECT 定义为正常结果，而不是异常。
只测"能不能记住"的评测会让系统朝**过度记忆**漂移，
所以 `eval:m4` 里"期望空"的用例与"期望有"的同等重要。

### 8. 坏输出必须抛错，不许猜 JSON

```text
memory_extractor_empty_output     ← content 为空
memory_extractor_malformed_output ← 非空但不是合法 JSON
```

两者**必须是不同的错误码**。这是一个真实踩过的坑：
第一版把它们合并成"格式不对"，于是排查方向被带偏 ——
真实原因是**推理模型的预算被推理过程吃光**，
`content` 是空字符串（详见 ADR 提及的评测说明）。

计划书第 146 节明确禁止"自动尝试猜 JSON"：
猜出来的东西会被当成真实记忆写下去，而那时已经无法回溯判断
它到底是谁的意思。

## 被否决的备选方案

### 方案 A：抽取即写入（没有值闸）

**否决理由**：抽取器的判断是"这句话有没有信息量"，
而"值不值得长期记住"是另一个问题。合并两者会让
"今天午饭吃了面"这类一次性状态进入长期记忆 ——
并且**不会有任何报错**。

### 方案 B：把冲突分析放在放行之后

**否决理由**：见决策 1。真实修过的顺序错误。

### 方案 C：只查 ACTIVE 记录做冲突分析

**否决理由**：见决策 3。DISPUTED 的记录会被永久悬置。

### 方案 D：水位按"最大已处理序号"推进

**否决理由**：一个失败的高序号会让中间全部事件被跳过。
水位必须表达"**连续**处理到哪"，不是"处理过的最大值"。

### 方案 E：抽取失败时抛出异常

**否决理由**：后台任务没有调用方能处理它。
异常会让 job 停在半途且**没有记录**，而"停在哪"比"失败了"
重要得多（它决定水位能不能推进）。

### 方案 F：不设重试上界

**否决理由**：持续失败会无限调用模型。
在一个"后台自动跑"的路径上，"无限重试"等于"无限成本"，
且它看起来只是一个"偶尔慢一点"的现象。

### 方案 G：把空输出与非 JSON 输出合并成一个错误码

**否决理由**：见决策 8。"预算不够"与"模型说了非 JSON 的话"
需要**完全不同**的应对（调预算 vs 改 prompt/加校验），
合并会让人去修错的地方。

## 后果

### 正面

- 失败可观察（job 行）、重复不累积（幂等键 + 水位）、
  低价值不写入（值闸）三件事各有独立的机器守卫。
- "拒绝"是一等结果，评测与报告都能表达它。
- 后台路径的所有错误都有明确的落点，没有"静默半成功"。

### 代价

- 六个阶段 + 两张表（job / idempotency）的工程量。
- 评测必须区分"模型档"与"离线档"：
  抽取质量是模型行为，而注入/意图/解析器是确定性的。
  **两档的失败含义不同**，因此 Promptfoo 配置按档分文件。

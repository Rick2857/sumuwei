## 背景

MemOS 提供本项目没有的能力，且当前已有 DeepSeek Harness 官方适配。
计划书第 94 节把它评为"M4 最值得实际验证的外部项目"。

但直接采用有三个具体障碍，每一个都是**本项目不能让步**的原则：

### 障碍一：自动捕获会绕过 Source Firewall

MemOS 的 DSH 插件会进行**自动 recall 和后台 capture**；
其本地插件也支持自动捕获 user、assistant、tool 消息。

而本项目的原则是（MI-02 / ADR-020）：

> Assistant 自己生成的话不能自动升级成事实。

```text
安装插件 → 自动把所有消息都当长期 Memory
```

这条路会**关掉** M4 最核心的那道闸。

### 障碍二：它可能成为单一真源

如果 MemOS 成为真源，它损坏就意味着丢掉她的整个过去。
而本项目的真源是 `Conversation Ledger + Memory Domain Events`。

### 障碍三：它可能定义业务语义

如果 `MemoryType` / 权威 / 证据 / supersede 的表达方式
由后端决定，那么业务语义就长在了存储实现里（MI-13）。
换一个后端 = 换一套语义 = "她记得什么"跟着实现变化。

---

## 决策

**MemOS 只能通过一个窄 Adapter 接入，且必须逐条通过下面的判据；
任一条关键项不满足即为 `rejected for production`（保留研究结论）。**

### 1. 接入形状：窄 Adapter，不是"成为她的脑"

```text
Character Domain  →  MemoryStorePort  ←  MemOSMemoryStoreAdapter  →  MemOS
```

Domain 侧一行代码都不改。Adapter 的职责是**翻译**，
不是"把 MemOS 的能力暴露出来"。

计划书第 95 节的表述：Character Domain 仍然只知道 `MemoryStorePort`。

### 2. 判据表（计划书第 101 节原样落地）

| # | 判据 | 不满足时意味着 |
|---|---|---|
| 1 | 能否保留我们的 `MemoryId`？ | 幂等键与跨后端引用都会断 |
| 2 | 能否保留 source provenance？ | MI-03 的证据链无法维持 |
| 3 | 能否表达 supersede？ | MI-06 退化成覆盖 |
| 4 | 能否表达 retract？ | MI-08 的"忘掉"无法表达 |
| 5 | 能否查询历史版本？ | MI-11 的重放与审计失去依据 |
| 6 | 能否隔离不同 owner？ | MI-04 的 owner 语义无法保证 |
| 7 | 能否避免绕过 `MemoryPolicy`？ | **Critical**：Source Firewall 可能被绕过 |
| 8 | 失败时主聊天是否仍能工作？ | 记忆后端故障会变成聊天故障 |
| 9 | 能否完整导出数据？ | 无法回到 Native（判据 10 的前提） |
| 10 | 移除 MemOS 后是否还能恢复 Native Backend？ | **不可逆**：这是最重要的一条 |

第 7 与第 10 条是**否决项**（不是"扣分项"）：

- 第 7 条不满足 → 污染通道被打开（见障碍一）；
- 第 10 条不满足 → 我们失去了退出的能力，而这让"PoC"不再是 PoC。

### 3. 自动捕获必须**默认关闭**，且不能作为最终方案

即使 PoC 全部通过，也**不允许**直接启用 MemOS 的自动捕获作为最终方案
（计划书第 96 节）。

理由：自动捕获的语义是"所有消息都可能是长期记忆"，
而 M4 的语义是"只有通过证据与值闸的东西才是"。
这两者不是配置差异，是**语义冲突** ——
一个不能通过改配置解决。

PoC 里若需要验证自动捕获，只能在**独立 profile** 上做，
并把实测行为记录下来（包括它的污染倾向）。

### 4. PoC 分两阶段，且必须锁定 DSH 版本

官方适配目前明确提示 DSH 仍属于 developer preview，
因此**兼容性必须记录具体 DSH 版本**。一个"在某个未记录的
DSH 版本上能跑"的结论不可复现。

PoC 在独立 profile / 独立沙箱上做，**不修改主项目**。

### 5. 三选一的结论（PoC 必须给出其中之一）

```text
A. 采用（作为派生后端，非真源）
B. 仅借鉴设计，不采用代码
C. 否决，保留研究结论
```

"再看看"不是结论。计划书第 196 节已经把"借鉴"列为一个
正当结果：MemOS 强调的 memory lifecycle、异步 ingestion、
feedback/correction、可组合 memory containers 都是**设计上**值得学的，
而它们的价值不取决于是否采用其代码。

## 被否决的备选方案

### 方案 A：直接安装 DSH 插件启用

**否决理由**：见障碍一。它会关掉 M4 的核心闸门，
而且关掉的方式是"看不见的" —— 没有任何报错。

### 方案 B：让 MemOS 成为真源，Native 只做缓存

**否决理由**：见障碍二。真源必须是 append-only 的、我们能完全掌控的
账本 —— 因为它是"重建一切"的唯一依据。

### 方案 C：不做 PoC，直接按文档判断"不合适"

**否决理由**：计划书第 94 节明确要求实际验证。
而且 MemOS 的审批/生命周期设计确实可能比 Native 更成熟 ——
一个基于文档的否决会错过这一点，并且不可复核。

### 方案 D：PoC 直接在主项目上做

**否决理由**：PoC 的失败模式（污染、绕过策略）正是主项目
最不能承受的。独立 profile 是这条 ADR 里少数的非可选项之一。

### 方案 E：PoC 通过就立刻切换

**否决理由**：判据 10（可回退）不满足时，切换是不可逆的。
而且 Native 已经是完整的生产实现（ADR-026），
没有"必须换掉"的紧迫性。

## 后果

### 当前后果（PoC 之前）

- 本 ADR 现在是一份**判据清单**，不是结论。
- `MemoryStorePort` 的形状已经为 Adapter 预留（ADR-026 决策 1）。
- 判据 1 – 10 在 Native 上都有对应的检查（即基线的定义）。

### PoC 之后的必然后果

- 无论结论是哪一项，**本文件必须更新状态与实测数据**。
- 若结论是 A（采用），必须新增一份 ADR 记录
  "真源仍在账本"与"自动捕获关闭"的技术落实方式。
- 若结论是 C（否决），结论必须写明**具体哪一条判据不满足**，
  而不是"整体感觉不合适"。

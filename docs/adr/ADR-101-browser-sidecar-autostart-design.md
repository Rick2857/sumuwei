```text

D2 生命周期 = **LG 退出时关掉**
```

## 0. 为什么要写这一份

`ADR-100` 之后，浏览器那一档的形态是：

```text
LG（只发 HTTP） ──► http://localhost:8931/mcp ──► sidecar（人工启动）──► 官方扩展 ──► 用户的浏览器
```

「人工启动」这一步是**刻意的**：`browser.ts` 里**连一句 `spawn` 都没有**，
sidecar 没起时它如实报 `execution_failed`（"sidecar 需要单独启动"）。

用户选择 C：**让 LG 自己拉起 sidecar**。这会改掉一条已经写进计划的边界 ——
LG 从"只连一个固定地址的 HTTP 客户端"变成"**拥有一个会开浏览器的进程**"。
因此值得单独立项，而不是顺手加。

---

## 1. 先摆一个**决定形状的事实**（不是实现细节）

上游 `establishExtensionConnection()` **无条件**先调 `_openConnectPageInBrowser()`
（`coreBundle.js:75066`）：

```text
每一次 sidecar 以 --extension 启动   ⇒   它都会打开一个浏览器页面（connect.html）
                                       并把 relay 附着在**那个标签**上
```

⇒ 两个无法用工程设计绕开的推论：

```text
① **"指向哪个标签"永远是人工的**：LG 装不了扩展，也不该替用户决定她看哪个页面。
   ⇒ 自启动能去掉的是**终端那一步**，**去不掉**"在连接页标签里打开目标网址"那一步。
② **自启动会让浏览器弹出一个页面**（在 LG 启动时、或首次用到浏览器时）。
   这正是计划书 §3.4 登记的桌面焦点影响（`tabs.update(active:true)`）。
```

⚠️ **如果这两条让人失望，那 C 的价值就只剩"省一条命令"**。这一点必须在动手前说清，
而不是做完之后才发现"原来还是要手点一下"。

---

## 2. 设计目标（按重要性）

```text
G1  去掉"每次用浏览器前先开一个终端敲命令"这一步
G2  **不削弱**任何既有边界：仍然只连固定端口；仍然只调白名单里的 7 个工具；
    仍然不改用户 profile；扩展与"指哪个标签"仍然人工
G3  单实例：两个 LG 进程不许拉起两个 sidecar（否则同一个浏览器被两条 relay 抢）
G4  失败如实：起不来 ⇒ execution_failed 且点名；**不重试风暴**、不静默降级
G5  可关：不自启时，行为与 ADR-100 **逐字相同**（只连固定地址）
G6  不留孤儿：LG 正常退出时关掉自己起的那个；异常退出留下的，下次能被识别并回收
```

## 3. 设计（组件与规则）

### 3.1 新增开关（**代码缺省全 false**）

```text
CHARACTER_BROWSER_SIDECAR_AUTOSTART=false     ← 本 ADR 的总闸；不开 = 与 ADR-100 逐字相同
CHARACTER_BROWSER_SIDECAR_DIR=<path>           ← sidecar 目录（含 node_modules/@playwright/mcp）
CHARACTER_BROWSER_SIDECAR_TOKEN_FILE=<path>    ← token 文件（见 §6-D4）
CHARACTER_BROWSER_SIDECAR_PROFILE=<name>       ← 可选；缺省不传（让上游自动挑）
```

### 3.2 进程所有权

```text
· LG 只在 autostart=true 时才会去起 sidecar
· 起之前先做**健康检查**：对 CHARACTER_BROWSER_SIDECAR_URL 发 initialize
  · 通了 ⇒ **不重复起**（复用它，无论它是谁起的）
  · 不通 ⇒ 才考虑起
· 起的方式：**只执行固定路径的 cli.js**，且校验它的 sha256 与登记值一致
  · 不查 PATH、不用 npx、不装任何东西、不透传任何来自用户/模型的参数
  · 参数是**写死在代码里**的一份固定列表：--extension --port <p> --browser <b> [--profile-dir-name <x>]
· 起完再健康检查（有界等待，例如 20s）；超时 ⇒ 如实失败
```

### 3.3 单实例（先例：`INV-DB-01` 的单持有租约）

```text
· 租约文件：<state>/browser-sidecar.lease （内容 = PID · 进程启动时刻 · cli.js 指纹 · 端口）
· 起之前：租约存在 ⇒ 问它"还活着吗"（PID + 启动时刻同时匹配才算活）
  · 活着 ⇒ 不重复起（等它变健康，或如实失败）
  · 不活（陈旧）⇒ 回收：清租约 + 起新的
· ⚠️ 判"还活着"必须**同时**匹配 PID 与启动时刻 —— 只比 PID 会在 PID 复用后误判
  （与 INC-01 的租约同一条纪律）
```

### 3.4 生命周期

见 §6-D2。两个候选：

```text
(甲) LG 启动时起，LG 退出时关  ⇒ 一个 LG 会话内只需处理一次 connect 页
(乙) 首次用到浏览器时起，LG 退出时关 ⇒ 不在聊天的人不会看到浏览器窗口
                                  但**第一次浏览器动作会失败**（因为那时窗口才弹出、还没人指标签）
```

### 3.5 失败语义（不许含糊）

```text
· autostart=true 但 sidecar 目录/token 文件缺失 ⇒ **装配期**就说清楚（启动日志 + 能力不可用），
  而不是等到用户用浏览器时才发现
· 起进程失败 / 健康检查超时 ⇒ execution_failed，message 点名端口与原因
· **不自动重试**（一次动作一次尝试以外的重试都是"重试风暴"的起点）
· autostart=false ⇒ 行为与 ADR-100 逐字相同
```

## 4. 明确**不做**的事

```text
· 不安装扩展、不选标签、不动用户 profile（LG 装不了扩展，也不该替用户决定看哪一页）
· 不代理任意 MCP 工具：白名单仍是那 7 个（25 个真实工具里其余 18 个一律拒）
· 不把 sidecar 变成常驻服务（不写注册表 / 不开机启动 / 不建计划任务）
· 不从 PATH 里找 node/cli.js、不用 npx、不联网装包
· 不因为"自启了"就放宽风险档：browser.operate 仍是 R2、仍只在**已授权任务**里可用
```

## 5. 验收计划（实现后必跑；正控 / 负控 / 恢复）

```text
正控  autostart=true + 没人在跑 ⇒ LG 起了一个 sidecar，且 initialize 通，且租约与 PID 一致
负控① 已经有一个健康的 sidecar ⇒ **不许**再起一个（用计数：进程数不变）
负控② 陈旧租约（PID 已死）    ⇒ 必须回收并起新的，**不许**卡在"以为它还活着"
负控③ 篡改 cli.js 一个字节     ⇒ 指纹不符 ⇒ **拒绝执行**（不许"反正跑起来了"）
恢复  autostart=false          ⇒ 行为回到 ADR-100：只连固定地址、不起进程
泄漏  LG 正常退出后：sidecar 进程应当消失；异常退出后：下次启动能识别陈旧租约
量具  上面每一条都要 `measured_count > 0`（进程计数、租约读写次数不许是 0/0）
```

## 5. 验收（已执行：**17 通过 / 0 失败**）

```text
入口   pnpm productivity:sidecar:autostart:verify        （替身驱动，不会开任何浏览器）
       pnpm productivity:sidecar:autostart:verify --real （起**真入口**：会开浏览器，必须人工看着）
```

替身驱动是刻意的：验收要反复"起 → 关 → 再起"，而真入口**每次启动都会弹一个浏览器页面**
（§1）。拿真入口反复跑就是往用户屏幕上反复弹窗口 —— 那不是验收。
替身与真入口**形状相同**（同一套目录结构、同一份 package.json 版本、入口是一个真会监听
并回答 initialize 的小服务），所以监管器的**全部判据**都真的被走到。

```text
正控      什么都没在跑 ⇒ 起了一个、健康、租约里是真子进程的 pid（781ms）
负控①     已有健康的 ⇒ **不重复起**（startedPid=undefined）
负控②     陈旧租约（pid 已死）⇒ 回收并起新的
负控③a    版本不符 ⇒ 拒启动（version_mismatch），**没有**起进程
负控③b    入口指纹不符 ⇒ 拒启动（entry_tampered），**没有**起进程
负控④     租约活着但不健康 ⇒ 如实报 lease_alive_but_unhealthy，**没有** kill 别人
装配期     非 localhost / --browser 不在闭集 / token 缺失 / token 空 ⇒ 四条都直接拒
关闭      stop() 之后不再健康、租约被清
恢复      正常配置又起得来（排除"永远拒绝"的假绿）
量具      17 条断言 · 替身残留 0
```

⚠️ **第一版验收是假绿的**（这一条值得留档）：所有判据共用同一个端口，上一条留下的替身
还在监听 ⇒ 下一条的 `ensure()` 直接走 `already-healthy`、**preflight 根本没被走到**，
于是负控③a/③b 与四条装配期判据全部 `reason=undefined`。
修法：**每条判据一个干净端口**。⇒ 这也是 `configWarning` 那个字段的由来：
"复用到一个健康的 sidecar"不该把一个**配错的自启动**伪装成正常。

⚠️ **真入口的启动仍记 `NOT RUN`**：它需要弹一次浏览器窗口，由用户下次启动 LG 时实测
（那一次本身就是真实链读数）。

## 6. 三处待定项的**裁定结果**（用户 2026-10-04）

```text
D1 启动时机：(甲) LG 启动时 / (乙) 首次用到浏览器时
   —— 建议 (甲)：因为 §1 的事实②（每次启动都会弹浏览器页面），
      (乙) 会让"第一次浏览器动作"先失败再让人去指标签，(甲) 把这个代价提前到启动时。

D2 生命周期：LG 退出时关掉 / 留着（下次复用）
   —— 建议"关掉"：留着一个会开浏览器的进程、而它的所有者已经退出，是最容易变成孤儿的形态。

D3 token 来源：本地文件（计划书 §4 规定凭据放 local/）/ 放进 .env
   —— 建议**本地文件**：`.env` 虽然也被 gitignore，但计划书逐字写了
      "连接凭据保存在私有 local/"，而 `.env` 里已经有 12 个开关，混进凭据会让
      "哪些东西是配置、哪些是凭据"变模糊。
```

## 6. 三处待定项的**裁定结果**（用户 2026-10-04）

```text
D1 启动时机：**(甲) LG 启动时** —— 已按此实现（`main.ts` 在装配期调 `ensure()`）。
   理由（也已写进实现注释）：因为 §1 的事实②，选 (乙) 会让"第一次浏览器动作"先失败
   再让人去指标签；(甲) 把这个代价提前到启动时，代价可见且可预期。

D2 生命周期：**LG 退出时关掉** —— 已按此实现（收尾挂在 `createRuntimeShutdown` 的
   `afterRun` 钩子上：它在收尾读数定稿之后、且**抛出不影响退出码**）。
   ⚠️ `stop()` 只关**本进程持有子进程句柄的那个**；别人的租约一律不碰。

D3 token 来源：**本地私有文件** —— 已按此实现（`CHARACTER_BROWSER_SIDECAR_TOKEN_FILE`）。
   token 只经**环境变量**交给子进程：**不进命令行**（命令行在同机进程列表里可见），
   也**不进任何日志 / 证据**；`DEBUG` 被显式清空（relay 的调试日志会打出含 token 的 URL，
   ADR-100 D-15 就是这么泄露的）。
```

## 6.1 实现与设计的两处**有意偏差**（都朝更安全的方向）

```text
① 租约的"还活着吗"判据：设计写的是"PID + 启动时刻双匹配"，
   实现是"**PID 存活 + 端口健康**"，并把"租约活着但不健康"如实报成
   `lease_alive_but_unhealthy`（**不去动它**）。
   理由：Windows 上从 Node 取别的进程的启动时刻，要么 shell 出去解析本地化输出、
   要么上原生模块 —— 两者都比这条收窄规则更容易出错。收窄之后，
   **任何情况下我们都不会去 kill 一个不是自己起的进程**。

② 入口完整性：设计里只写了"指纹"，实现是**两条判据** ——
   `package.json` 的版本 pin（覆盖"换了一个版本"）
   + `cli.js` 的 sha256 绊线（覆盖"同一版本被改过"）。
   两条合起来才闭合：**版本说"是哪个"，指纹说"是不是那一份"**。
```

## 7. 回滚

```text
把 CHARACTER_BROWSER_SIDECAR_AUTOSTART 置 false（或删掉）⇒ LG 立刻回到"只连固定地址"，
与 ADR-100 逐字相同。已经起来的那个 sidecar 不会自己消失 —— 需要人工关掉它
（或者由 LG 退出时关掉，见 D2）。
```

## 8. 与既有不变量/ADR 的关系

| 对象 | 关系 |

| 计划书 §3.4（"固定版本 sidecar + 官方扩展"） | **本 ADR 是它的扩展**：版本仍然固定、扩展仍然人工；变的是**谁启动进程** |

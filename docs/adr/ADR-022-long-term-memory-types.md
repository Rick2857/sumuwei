# ADR-022：长期记忆只有四种类型（封闭枚举）

- **状态**：已接受（M4）
- **日期**：2026-09-16
- **相关**：计划书第 11 – 14 / 51 – 52 节；MI-01 / MI-15
- **代码**：`src/kernel/contracts/memory.ts`（`MemoryType` / `MEMORY_TYPES`）、
  `src/kernel/contracts/memory-predicates.ts`（predicate 登记表）

---

## 背景

"什么算长期记忆"必须是**可枚举**的，否则下面三件事都无法回答：

1. **值闸怎么算**？不同种类的记忆"值得记"的程度不同
   （`DURABILITY` 是按类型定的）。
2. **去重怎么做**？去重依赖 `CanonicalMemoryKey`，
   而 key 由"类型 + subject + predicate/qualifier"构成。
3. **什么不该被记**？没有封闭的类型集合，
   "这不该记"就永远只能是一句主观判断。

一个开放的类型集合（例如"任意字符串标签"）会让上面三件事
都退化成"看情况"。

---

## 决策

**`MemoryType` 是封闭的四值枚举，且每一个都对应一种明确的语义与寿命。**

```ts
type MemoryType = 'person_fact' | 'preference' | 'episode' | 'self_experience'
```

| 类型 | 是什么 | subject 通常是 |
|---|---|---|
| `person_fact` | 关于某个实体的稳定事实 | 用户 / 第三方 |
| `preference` | 偏好（含限定条件） | 用户 / 她 |
| `episode` | 共同经历的**完成态** | 多参与者 |
| `self_experience` | 她的**自身**经历与自我认知 | 她 |

### 1. 刻意**没有**的东西

计划书第 51 / 52 节明确排除，且它们不是"暂时没做"，是**不属于这一层**：

| 没有 | 为什么 |
|---|---|
| 情绪 / 心情 | 是短期状态，不是长期记忆 |
| 人际关系 | 属于世界状态（M5），不是她的个人记忆 |
| 目标 / 意图 | 属于 Character Intent（M3.5 的输出边界） |
| 世界事实（`world_fact` 等） | 见 MI-15：世界事实不该受她的视角影响 |
| "对话历史" | 见 MI-01：历史 ≠ 记忆 |

封闭枚举把 MI-15 从"需要一条运行时校验"变成
"没有那个选项可以选"。这在当前是**更强**的保证 ——
写不出来的东西不需要被拦截。

### 2. 类型决定寿命，寿命进值闸

`DURABILITY` 按类型给出基础分，`evaluateValue()` 的五个因子
在此基础上调整。这让"值不值得记"是一个**可解释的计算**，
而不是一句 prompt 里的祈使句。

### 3. 类型与内容**必须匹配**

`content_type_mismatch` 是一条硬闸：`preference` 不能带 `episode` 字段，
`person_fact` 不能只有一段自由文本。

理由：类型是所有下游计算的入口。类型错了，
值闸、去重、冲突分析会**全部**基于一个错误的输入工作 ——
而它们都不会报错，只会给出错误的结果。

### 4. Predicate 是**独立的**登记表，且只增不改

`memory-predicates.ts` 登记 10 个键，每个带
`key` / `description` / `valueShape` / `allowed?` / `examples`。

登记表是**只增的**：删一个键会让已经用它写下的记忆变成"未登记"，
而那是历史污染。要废弃就把 `description` 标成"（已废弃，改用 X）"
并保留 key。

### 5. 登记键必须写成**规范化形式**（点分隔小写）

这是一个真实踩过的缺陷：键写成 `preferred_explanation_style`（下划线）时，
`normalizePredicate()` 会把下划线转成点号，于是"登记的键"
与"查表的键"**永远不相等** —— 那个槽位永远查不到，而且**不报错**。

现在模块加载时就做 fail-closed 断言：存在非规范化键 → 直接抛错。

### 6. 重叠槽位靠 `description` 消歧（不是靠代码）

`food.preference.cilantro`（专用，enum）与
`food.avoid.general`（宽泛，text）都是合法键。

实测（`M4X-030`「记住，我不吃香菜」）：模型选了**宽泛**槽位，
而专用槽位的 `examples` 明确写着 `'我不吃香菜'`。

修法是把 `description` 交给模型并加"优先最具体槽位"规则。
**这不是一条结构性保证** —— 详见
`docs/architecture/memory-invariants.md` §16.4。
若将来需要硬保证，正确做法是在登记表里加同义映射并由代码强制，
而不是继续加强 prompt。

## 被否决的备选方案

### 方案 A：开放类型（自由字符串）

**否决理由**：值闸、去重、冲突分析三处全部退化成"看情况"。
而且它会让"这不该记"永远无法被表达。

### 方案 B：加上 `world_fact` / `entity_state` 之类的类型

**否决理由**：见 MI-15。世界事实受她的视角影响会失真，
且会在她"记错"时被一起改掉。让它们在**类型层面**不存在，
比让它们存在再拦截更安全。

### 方案 C：把 predicate 也做成封闭枚举并放进 MemoryType

**否决理由**：predicate 是**可增长的领域词表**（"她还可能记住什么"
是开放的），而 MemoryType 是**结构分类**（"记忆有几种形态"是封闭的）。
把两者合并会让加一个槽位变成加一种记忆类型 ——
而后者会牵动值闸、去重、冲突分析三处。

### 方案 D：不设登记表，让模型自由造 predicate

**否决理由**：那等于没有 canonical key，去重无法工作。
`M4X-030` 的实际经验说明了相反方向的代价：
即使有登记表，**重叠**槽位也已经够难消歧了。

### 方案 E：删掉废弃的 predicate 键

**否决理由**：历史记忆会变成"引用了未登记的键"，
而那是**历史污染**：今天读不出、明天也读不出，
且无法区分"当时合法"与"一直是错的"。

## 后果

### 正面

- 值闸 / 去重 / 冲突分析都有一个封闭的输入域。
- MI-15 由"没有可选的类型"保证，而不是由一条运行时校验保证。
- 登记表是文档（`description`）、测试数据（`examples`）
  与运行时契约的**同一份**定义。

### 代价

- 加一种记忆类型要动三处（contracts / value / conflict）。
  这是刻意的：类型是结构性变更，不该是加一行数据。
- 登记表只增不改，会随时间变长。缓解：`description` 里写清废弃关系。

## 怎么验证这条决策还成立

| 检查 | 由谁守 |
|---|---|
| `MemoryType` 是封闭四值 | `m4:test` 分组「受控枚举」 |
| 类型与内容不匹配 → 失败关闭 | `m4:test` 分组「内容与类型匹配」 |
| 登记键必须是规范化形式 | `m4:test` 分组「predicate 登记表」（模块加载时 fail-closed） |
| 未登记的 predicate 会被识别出来 | `m4:test` 分组「登记表」+ `unsupportedMemories()` |
| 登记表不被 M4 的加法侵蚀 | `m4:test` 分组「登记表（M4 的加法不得侵蚀 M2.5）」 |
| 限定条件不同 = 两个槽位 | `eval:m4` M4-012 |
| 重叠槽位的消歧（回归守卫） | `M4X-030`（`mustIncludePredicates: ['food.preference.cilantro']`）+ `M4X-001` |

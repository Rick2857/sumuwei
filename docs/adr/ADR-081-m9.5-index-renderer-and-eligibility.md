## 2. `WP1-A` · 规范渲染

| 项 | 决定 |
|---|---|
| 常量 | **`RENDERER_VERSION = 'semantic-render@1'`**（列已冻结，必须有实现与之对应） |
| 形式 | **`passage: <predicate> <value>`** —— 与实验室那份内联拼串**逐字一致** |
| 位置 | **唯一实现**：`src/kernel/app/recall/index-render.ts`（纯函数、无数据库、无模型） |
| 输入 | 只读**权威投影**字段（`MemoryRecord.status` / `content.predicate` / `content.value`）—— 不读副本、不读对话、不读摘要 |
| 输出 | `{ text, contentHash }`；`contentHash = sha256(text)` 十六进制 |
| 隐私 | **不存明文副本**（列设计如此：只有 `content_hash`）—— 计划 §8.1 逐字要求 |
| 前缀 | `PASSAGE_PREFIX = 'passage: '` / `QUERY_PREFIX = 'query: '`，**逐字**来自冻结清单 `evals/m9.5/embedding-manifest.json`；查询侧由**同一个模块**的 `renderQueryForIndex()` 给 ⇒ 两侧不会漂开 |

### 2.1 为什么**逐字**沿用实验室那一段拼串（而不是"顺手改好一点"）

M9.5 的**校准 / 验证 / legacy 强度**那些读数，全部是在**那个形式**上算出来的。
换形式（哪怕"更自然"）会让那些读数**不再描述生产渲染器** ⇒ 要么重跑整条校准链，
要么就得承认读数与生产脱节。⇒ 本轮**冻结形式**，把改进留给**下一次换代**
（改 `RENDERER_VERSION` + 重跑校准链，两件必须一起做）。

### 2.2 两处**刻意保守**（宁可少索引，也不索引一个没测过的表示）

```text
① **只渲染 Claim**（`kind === 'claim'`）。Episode **没有 predicate**，而冻结的形式是
   `predicate + ' ' + value` ⇒ 给 Episode 编一个形式 = **发明一个没人测过的表示**
   ⇒ 如实排除，具名理由 `content:episode`。
② **qualifiers 不进渲染文本**（与实验室那份逐字一致）。后果：限定范围不同的两条记忆会渲染出
   **同一段文本**（向量也相同）⇒ 语义通道**分不开**它们；但词面通道与"qualifier 感知的选择"
   仍然分得开，而且**不会产生错误主张**。⇒ 登记为局限（`L-M95-*`），**不改形式**。
```

⚠️ **确定性是硬要求**：取值是对象时按**键排序**序列化（不是 `JSON.stringify` 的插入序），
否则同一个取值会因为书写顺序不同而渲染出不同文本 ⇒ `content_hash` 无故变化。

## 3. `WP1-B` · 索引资格政策

计划 §1 的三个问题，逐条回答：

| 计划的问题 | 回答 |
|---|---|
| 哪些 memory 进 `eligible`？ | **只 `active`**（`D-1`）。其余一律排除并记**具名理由** |
| 与"遗忘"（`retracted`）的关系？ | **排除**（`status:retracted`）—— 与召回面同一条状态语义 |
| `excluded_by_policy_count` 的具名理由？ | 见下表（**可审计**） |

### 3.1 具名理由（`IndexExclusionReason`）

```text
status:retracted     显式遗忘
status:superseded    已被更合适的条取代
status:disputed      在审（见 §5 的分叉）
status:not-active    兜底：非 active 且不属上面几类（**今天没有生产者**，与召回面同形）
integrity:<问题码>   完整性读数非空（归因链断 / 证据悬空）—— 码来自**同一个**读数
content:episode      Episode 不渲染（§2.2 ①）
content:empty        取值为空 ⇒ 没有内容可检索
```

### 3.2 "唯一实现"复用（本模块不另写一份）

```text
· 状态 → 语义：复用召回面的 `exclusionReasonForStatus()`（contracts/recall.ts）
  —— "什么算撤回 / 被取代"只许有一处实现
· 完整性：**注入**读数（与检索适配器注入的是同一个 `memoryIntegrityProblems()`）
· 前缀：**逐字**来自冻结清单（门会读清单文件来核对，而不是信代码里的常量）
```

## 4. ⚠️ 一处**实测校正**（本 ADR 的第一版写错了，量具抓出来的）

```text
我原本以为 `exclusionReasonForStatus('disputed')` 会**抛错**（因为在召回面 disputed 可召回），
于是把"disputed 必须先分流"的理由写成了"否则会抛"。

**实测（`pnpm m9.5:test` 的负控）**：它**返回 `undefined`**，不抛错 ——
那条 `throw` 只在 `isRecallEligible` 与 `exclusionReasonForStatus` **自相矛盾**时才可达，
而 `active` / `disputed` 都不会走到那里。

⇒ 分流**仍然需要**，但理由不同：不分流它会落到兜底的 `'status:not-active'`，**理由就不具名了**。
⇒ 源码注释与门里的负控都已按实测改写；错误的第一版留在注释里（`判据错了要如实写进报告`）。
```

## 5. ⚠️ 与召回面的**有意分叉**（`D-1` 的直接后果，如实登记）

```text
`disputed`（在审）：
  · **召回面**：**可召回**（`isRecallEligible('disputed') === true`；另由 `policy.allowDisputed` 把闸）
  · **索引面**：**排除**（`D-1` = 只 active）⇒ 它没有语义分，但**仍然可被词面通道召回**
⇒ 这是"索引比召回更严"，不是不一致：索引是**派生加速结构**，不是资格权威。
```

### 5.1 ⚠️ "归因降档"的落实范围（**需要你确认的一处解释**）

用户在 `D-1` 里选的是「只 active；撤回 / 被取代 / 在审 / **归因降档** 的件不进索引」。
本实现把它落实为：

```text
✅ 落实了：**链断了**（完整性读数非空 ⇒ `integrity:<码>`）**不进索引**
⚠️ 未落实：**M5.1.1 的排序级降档**（epistemic requalification —— 降的是**排名与 prompt 标签**，
   **不是**资格）**不**排除记忆
```

### 5.2 ★ **`D-1` 的修订裁定**（2026-10-01，用户明确裁定 —— **不是**工程解释）

⚠️ 上面 §5.1 记的是**实现当时的解释**（"链断了才排除；排序级降档不排除"），并且明确写着
"**待确认**"。用户 2026-10-01 **明确裁定修订** `D-1` 的这一句，理由与验收要求如下（逐字保留其要点）：

```text
修订后的政策：
  · **链断 / 完整性不合格**的件 ⇒ **不索引**（不变）
  · **仅排序降档**的 active 件 ⇒ **允许索引**
  · 召回时**仍**经过原有资格检查、**降权**与**来源标签**
理由：降档表达的是"**谨慎采用**"，彻底排除会**损失改述召回**（同一事实换个说法就找不回来了）。
⚠️ 原 `D-1` 逐字写的是"归因降档件不进索引" ⇒ 本条是**明确修订**，
   **不能**把工程解释当成"已经落实"。
验收要求（新增，必须证明）：**语义命中不会绕过原有降档。**
```

⇒ 因此本 ADR 的状态是：**§5.1 的解释 = 已被用户修订裁定确认**（不再是"待确认"）；
而**"语义命中不绕过降档"这条验收判据尚未实现**（见 §6 的门清单 —— 它需要在检索侧加一条断言）。

### 5.3 ★ 验收判据的**确切内容**（2026-10-01 查明降档落在哪一层）

```text
读出来的：降档**不是**一个独立的过滤步骤，它是排序分里的**一个分量** ——
  `src/kernel/recall/ranking.ts:247-273` 的 `authority` 分量：
      资格 = ESTABLISHED（或 Episode 面"不适用"） → 不降
      资格 ≠ ESTABLISHED                          → 降**一档**（rank + 1）
      status = disputed                           → 再多降一档
  ⚠️ 只降**排序分**，`memory_records.authority` 一个字不动（`DR-1`）。
```

⇒ **"语义命中不会绕过原有降档"的确切含义**（可判、可实现）：

```text
同一个候选，**无论有没有语义通道命中**，它的 `authority` 分量必须**逐字相同**。
即：降档是**通道无关**的 —— 语义命中只增加 `semantic` 分量，**不得**改变 `authority` 分量。
```

**判据的形状**（纯函数，不需要库）：
```text
· 取一个 `qualification` 会被降档的候选 ⇒ 算一次分量（无语义命中）
· 同一个候选 + 语义命中（`semantic` 通道有分）⇒ 再算一次
· 断言：两次的 `authority` 分量**相等**；而 `semantic` 分量**只在第二次**存在
· 反向（负控）：把 `qualification` 换成 ESTABLISHED ⇒ `authority` 分量**必须变大**（证明降档真的在起作用）
```

⚠️ 这条判据**尚未实现** —— 它需要一个"构造候选 + 调分量计算"的纯函数夹具（`ranking.ts` 的分量函数）。
⚠️ **它同时是 `D-1` 修订的验收**：只有这条过了，"仅排序降档的 active 件允许索引"才**不会**变成
   "语义通道把它们抬到降档之上"。

#### 5.3.1 ★ 夹具**已知需要哪些字段**（2026-10-01 逐次实测出来的，省下一轮重踩）

```text
`scoreCandidate({ request, candidate, capabilities, now })` 会**直接读**这些字段
（缺一个就 TypeError —— 第一版夹具就是这样被逐个抓出来的）：

  candidate.retrievedBy        string[]      ← **语义命中**就体现在这里（`includes('semantic')`）
  candidate.qualification      string        ← 降档判据（ESTABLISHED ⇒ 不降；否则降一档）
  candidate.authority          MemoryAuthority
  candidate.status             'active' | …  （disputed ⇒ 再多降一档）
  candidate.importance         number        （salience 分量）
  capabilities.unavailable     {dimension, reason}[]   ← 缺了报 `reading 'find'`
  request.target.status        string        ← 缺了报 `reading 'status'`
  ⚠️ **还有一个 `.some(...)` 的字段**（第一版夹具停在它上面）—— 下一轮**先读 `RecallCandidate`
     与 `RecallRequest` 的契约**（`src/kernel/contracts/recall.ts`），**一次**把夹具补齐，
     不要再逐个试错（那正是本轮浪费掉的方式）。
```

## 7. 顺带修掉的**循环依赖**（不修的话 WP1 的门根本跑不起来）

```text
现象：`pnpm m9.5:test` **整道门跑不起来** ——
      `ReferenceError: Cannot access 'SEMANTIC_INDEX_DDL' before initialization`（TDZ）。
      实测**先把它归因清楚**：把我的改动 `git stash` 掉之后**同样失败** ⇒ **不是本轮引入的**。

根因（读出来的）：`memory-semantic-index.ts` import 了 `./db.ts`（要 `rowsOf`），
      `db.ts` import `./migrations.ts`，而 `migrations.ts` 在**模块顶层**读
      `SEMANTIC_INDEX_DDL`（`MIGRATION_0010` 的 `statements` 是模块级对象字面量）
      ⇒ 环：`memory-semantic-index.ts → db.ts → migrations.ts → memory-semantic-index.ts`。
      环本身不致命，**致命的是求值顺序**：入口先 import 前者 ⇒ migrations 的模块体先跑 ⇒ TDZ。

修法：把 DDL 常量搬到**不 import 任何东西**的叶子模块 `semantic-index-ddl.ts`，
      `migrations.ts` 从**叶子**取；`memory-semantic-index.ts` 继续 **re-export** ⇒ 既有调用方零改动。
      ⚠️ 只搬常量、**一个字节的 DDL 都没改**（内容指纹与顺序逐字不变）。

⚠️ **为什么一直没人发现**：`pnpm m9.5:gates` 是 PASS —— 因为它按设计**只读已落盘的旧证据**
   （与 `L-M10-59` 同一个形状：聚合器的绿不代表今天跑得起来）。
```

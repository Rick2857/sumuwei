# ADR-024：显式记忆走独立的同步路径

- **状态**：已接受（M4）
- **日期**：2026-09-16
- **相关**：计划书第 54 – 60 / 68 – 69 / 179 节；MI-10
- **代码**：`src/kernel/app/memory/explicit-service.ts`、
  `src/kernel/app/memory/intent-detector.ts`、
  `src/kernel/app/memory/target-resolver.ts`

---

## 背景

用户说**"记住，我不吃香菜"**。

与"她在一段闲聊里顺带提到不吃香菜"相比，这句话有一个
本质不同的性质：**用户在要求系统做一件事**。

如果显式指令和普通对话走同一条路（都进后台抽取队列），会有三个后果：

| 后果 | 具体表现 |
|---|---|
| **延迟不可接受** | 后台抽取是批量的、异步的。用户说"记住"时期待的是"好，我记住了"，而不是"三分钟后也许记上了" |
| **失败无法回答** | 后台失败写进 job 行。而用户此刻在等一个答复 —— 不能回答"记住了"然后其实没记 |
| **意图会被稀释** | "忘掉这件事"如果作为一段普通文本进抽取器，它会被当成"用户提到了某件事"，而**不是**"用户要求删除" |

计划书第 55 节给了一条硬要求：

> 不能在 Memory Commit 失败时回答"记住了"。

---

## 决策

**显式指令走一条独立的同步路径，且它的成败是一个可观察的结果，
而不是一句乐观的答复。**

### 1. 规则优先的意图判定（确定性）

```text
先走规则（MEMORY_INTENT_RULES）
  → 命中则返回（detectedBy: 'rule'）
  → 未命中才问分类器
```

优先级是 **forget → correct → dispute → remember**，顺序是刻意的：

- "不要再记这件事了"同时含"记"与"不要"。若 `remember` 先匹配，
  用户的要求会**反向执行** —— 后果相反，且用户以为已经生效。
- `REMEMBER_KEYWORDS` 里的 `改一下`（计划书第 175 节的原话）
  一开始漏了，因此"之前那个改一下"没被识别成纠正。

规则的分类器端口默认是 `RuleOnlyMemoryIntentClassifier`：

> 缺省值是"离线安全"的那一个，而不是"效果最好"的那一个。
> 漏配分类器只会让复杂说法走后台路径（可接受），
> 而误配会让每个部署都悄悄多一次模型调用（不可接受）。

分类器抛错时**当作"没有显式意图"**，不抛给调用方 ——
显式路径的失败不能影响聊天。

### 2. 只接受用户事件

```ts
detectExplicitIntentFromEvent(detector, event)  // event.actorType 必须是 'user'
```

非用户事件 → 抛 `explicit_intent_from_non_user`。

这是 M4 反污染最前面的一道闸：**她自己说的话永远不可能被解读成
"用户要求记住某事"**。计划书第 148 / 149 节的污染链起点，
正是"把 assistant 的输出当成用户的意思"。

在**类型上**标注这一点（签名里就要求 `actorType: 'user'`），
而不是靠调用方自觉。

### 3. 五级目标解析梯子（前四级都不是自然语言解析）

```text
1. 明确 Memory ID
2. Canonical key
3. same subject + same predicate
4. small candidate set（≤ MAX_MODEL_CANDIDATES = 5）
5. LLM resolver（只在必要时）
```

第 5 级明确要求**小候选集**。理由：让模型在"她全部的记忆"里挑，
准确率会随记忆量下降，而错误的目标会让纠正**改错一条**。

`parseChoiceIndex()` 用 `/-?\d+/`（不是 `/\d+/`）：
实测 `/\d+/` 会把 `-1` 读成"选了 #1"，
而 `-1` 是模型表示"都不合适"的常见写法。

### 4. `ok: true` 的门槛是**三件事都成功**

```text
validate → commit → fold
```

`runMutation()` 只有在三步全成功时才返回 `ok: true`。

两个刻意的细节：

- **`already_applied` 不算 `ok: true`。** 用户第二次说"记住"时，
  正确的说法是"这条我已经记着了"，而不是"记下了"——
  两者对用户是不同的信息。
- **失败要分类**（`FailureReason` 枚举：`persistence_failed` /
  `target_ambiguous` / …），调用方据此决定重试还是如实失败。

### 5. 端口方向：`MemoryFoldPort` 由领域层定义

`explicit-service.ts` 定义 `MemoryFoldPort` 接口，
**不 import infrastructure**。`createNativeMemoryStore()` 是实现。

这让"换个存储后端"不需要改显式路径的代码 ——
与 MI-13（后端不得定义业务语义）同一条原则。

## 被否决的备选方案

### 方案 A：显式指令也进后台队列

**否决理由**：见背景表格。核心是"用户此刻在等一个答复"，
而队列的语义是"稍后处理，失败可重试"。
把两者合并会让"记住了"变成一句无法兑现的承诺。

### 方案 B：完全依赖模型分类意图

**否决理由**：每一次普通的对话轮次都会多一次模型调用
（因为要先判断"这是不是一条显式指令"）。
而绝大多数轮次都不是。规则能覆盖的说法（"记住"/"忘掉"）
应该是零成本、零延迟、零不确定的。

### 方案 C：先走分类器，规则作为兜底

**否决理由**：方向反了。规则命中是**确定性**的；
让不确定的那一级先跑，会把确定性结论降级成概率结论。

### 方案 D：目标解析只用 LLM

**否决理由**：见决策 3。前四级能解决的（明确 id、canonical key、
同槽位）占了真实纠正场景的绝大多数，且它们**不会错**。

### 方案 E：`already_applied` 也返回 `ok: true`

**否决理由**：它把"这次真的写入了"与"本来就有"合并成同一个结果。
调用方无法区分，于是用户会收到"记下了"——
而系统实际上什么都没做。这与计划书第 55 节是同一条原则的延伸。

---

## 后果

### 正面

- 显式指令有确定的成败，且失败可以如实告诉用户。
- 常见说法（记住 / 忘掉 / 纠正）不消耗模型调用。
- 她自己说的话在**入口处**就被排除，污染链起点被切断。

### 代价

- 两条路径（显式 / 后台）并存，需要各自的测试。
  缓解：它们共享同一个 validator 与 reducer，
  差异只在"谁来提议"与"何时提交"。
- 复杂说法（"之前那个改一下"）在无法解析目标时会降级为
  `target_ambiguous`。这是**如实失败**而不是猜一个。

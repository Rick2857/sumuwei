## 1. 缺陷定位（WP0 实测，本节是事实不是设计）

**F-4（R-21 / L-M9-19）**：忘掉/更正后逐字重述同一内容 ⇒ 确定性 id
（`makeMemoryId(characterId, slot)`，slot 含内容指纹）与已撤记录撞线；
去重层 1/2 只查 ACTIVE ⇒ 放行；`MEMORY_CREATED` 事件提交（L1）；
折叠器 `applyCreated`（`projections/memory.ts:193`）对已存在 id 无条件 no-op ⇒ 投影仍
retracted/superseded（L2）；ACTIVE-only 资格 ⇒ 永不可召回（L3）；
`runMutation` 折叠非 null 即 `ok:true` ⇒ `translate` 给 `written` ⇒ 回复真话政策放行
「记住了」（L4）。rebuild A==B（`equal=true`）——**语义缺口、非账本分歧**。

**WP0 新发现（C 场景）**：更正后逐字重述旧值 ⇒ D-55c 冲突政策**正确**生效
（无时间标记矛盾 ⇒ `MARK_DISPUTED`，不擅自选边），但①重述值未被记录（槽内零 active）；
②`translate` 仍给 `written` ⇒ 她会说「记住了」——**回复真话分歧在 dispute 路径同样存在**。
本 ADR 必须把它纳入修复范围（计划 §3.2「争议……沿已有结果类型如实表达」）。

**F-1（R-20 / L-M9-13）**：遗忘后，被撤原话以**原始对话行**逐字进入最终 prompt
（`sections.ts` `createRecentConversationProvider` 渲染 `recentEvents` 原文，无撤销过滤）。
其余读取面已闭合：rollup 资格闸 ④（真实 reader 实测 `invalidated_by_memory_state`）、
Recall（ACTIVE-only）、Belief（失效+禁根+同轮 overlay）、状态文本（程序生成）。
**泄漏通道唯一在 Recent 装配层。**

**F-1 关联事实**：`ConversationEvent.replyToEventId` 是 assistant 行必填结构字段
（`conversation-integrity.ts:170`）——P03 的可靠派生关联**已存在**，装配层未消费；
撤回原因 `reason: 'explicit_forget' | 'explicit_correction' | 'audit'` 只在
`MEMORY_RETRACTED` 事件 payload（`applyRetracted` 只写 status+updatedAt，记录面无原因）；
retracted 记录保留 `sourceRefs`。

## 2. 冻结决策（D01…D24）

### 2.1 F-4 组：重述复活

| 编号 | 裁定 | 冻结结果 |
|---|---|---|
| D01 | 修复面 | **修折叠器（选项①），保持确定性 id 契约**。否决选项②（发射侧换新 id）：破坏「同内容 ⇒ 同 id」，而 M9.5 §8 sourceRevision、Belief `dependsOnMemoryIds` 精确回查、M9.5 §11.1「保持原主键」都建立在该契约上；且旧流里已存在的 no-op CREATE 无法靠新 id 语义修复 |
| D02 | 版本化标记 | `MemoryCreatedPayload` 追加**可选** `restatement?: { previousRevision: number; previousStatus: 'retracted' \| 'superseded' }`。`createMemoryDomainEventRegistry` 的 `validatePayload` 现在只重建契约内字段（`domain-event.ts:542`，未知字段被剥离）——须同步放行该字段。这是计划 §3.1 要求的「最小、版本化的追加契约」：不靠到达时间、不靠随机盐、不靠进程开关区分新旧语义 |
| D03 | 发射口（单一） | validator create 路径（`memory-validator.ts`，显式与后台共用）在去重层 1/2 **之后**、快照构造处发射：`getRecord(proposedId)` 存在 且 `status ∈ {retracted, superseded}` 且开关开（D12）且**新证据不相交**（候选 sourceRefs 与既有记录 sourceRefs 交集为空——R06：旧对话重扫/旧任务重试/索引重建不得冒充新告知）⇒ 构造复活快照（§3.2 字段表）+ 附标记。任一条件不满足 ⇒ 事件形状与今天逐字节相同 |
| D04 | 复活快照 | 事件 `record` 字段携带**完整复活快照**（CREATE payload 本就携带完整快照——`domain-event.ts:372-385`，rebuild 因此天然自足）。逐字段语义见 §3.2 |
| D05 | reducer 语义 | `applyCreated` 三分支：`state === null` ⇒ 照常建（原语义）；**标记存在 且 `previousStatus === state.status`** ⇒ 采用 `payload.record` 为新状态（复活）；其余（无标记，或标记状态不匹配）⇒ **no-op（原语义逐字节）**。reducer 保持纯函数，不查库、不推测意图（计划 §3.1）。**实现期修正（R08 首跑发现，2026-09-27）**：原冻结稿的守卫是 `previousRevision === state.revision`，但 revision 的在线/重放语义**不同**——store 对每次折叠 +1（create=1, retract=2, …），纯 reducer 只在创建/复活时设置它（`applyRetracted` 等不动 revision）⇒ 该守卫在重放里必然失配（2≠1）⇒ 复活只在在线发生 ⇒ **A==B 破**。改为 `previousStatus === state.status`（两侧一致的投影事实，重放稳定）；D14 的「第二个重述不重复复活」仍被保证（第一个复活后状态是 ACTIVE，第二个标记折在 active 上不匹配 ⇒ no-op）；`previousRevision` 保留两个职责——复活后 revision = 该值+1（D04）与发射时刻审计快照，**不是守卫**。可观察行为与原冻结稿一致（R05② 的第二个 no-op、R07 兼容边界、R08 A==B 全部成立），修正的只是判别机制 |
| D06 | reducer 版本 | `MEMORY_REDUCER_VERSION` **不变**（`memory-reducer@1`）。升版会让 store（`memory-store.ts:803`）对全部存量记录 fail-close；标记本身即新旧语义的确定性判别器（计划 §3.3） |
| D07 | 兼容边界 | 旧事件（无标记）在新代码下**逐字节原解释**；新标记事件在**旧代码**下 = no-op——机制：事件库**原样存储** payload（`appendDomainEvent` 不再校验，`event-store.ts:170`），重放时旧 `applyCreated` 只是不读 `restatement` 字段 ⇒ 走原 no-op 分支（`validatePayload` 的字段剥离只发生在**发射侧**，与重放无关）⇒ 回滚候选必须写明「回滚后 rebuild 会丢复活、需重建投影或接受丢失」，**不得把切回旧提交当天然安全回滚**（计划 §3.3）。不重解释历史生产记录 |
| D08 | 回复真话（无条件） | `runMutation` 的 create 分支：折叠结果必须 `status === 'active'` 才 `ok:true`；否则 `ok:false` + **新失败原因 `write_not_effective`**。**不受开关控制**（INV-CI-13「请求提交成功 ≠ 认知修改成功」的修复就是本条）；开关只闸账本语义（D12），不闸诚实。R01 不受影响：ACTIVE 重复在 dedup/冲突层已返回 `already_applied`，到不了本检查 |
| D09 | dispute 如实翻译 | `MARK_DISPUTED` 路径（含 remember 触发的冲突分支）的 outcome 附 `performed: 'dispute'`；`translate` 映射为 **`kind='not_written'` + 新原因 `marked_disputed`**（`executed=false`——没有写入，不得成功口吻；`truthfulSentence` 新条目如实说明「已标存疑、没有直接改」）。否决「新 kind」方案：会稀释 `executed = kind !== 'not_written'` 的既有测试契约（C9） |
| D10 | DISPUTED 不复活 | 标记只认 `retracted` / `superseded`。DISPUTED 及其他状态不因泛化分支自动恢复（计划 §3.1 状态表；R06/R07） |
| D11 | R03 冲突优先 | superseded 后重述旧值**仍走既有冲突规则**（D-55c：无时间标记 ⇒ MARK_DISPUTED 优先）；复活不绕过冲突政策、不直接覆盖当前值。冲突分支若判 SUPERSEDE 且新候选 id 撞 superseded 记录，走同一标记语义（先复活、再 supersede 当前 active，顺序同 `explicit-service.ts` SUPERSEDE 分支既有顺序） |
| D12 | 开关 | `CHARACTER_MEMORY_RESTATEMENT_ENABLED` 代码缺省 **false** = **发射闸门 only**（validator 不附标记）。已提交事件的重放语义**不随开关变化**（append-only：开了再关，已复活的记录保持复活）。flags.ts 模式 + 真实消费者（validator deps 注入），`m4:test`/`m4.5:test` 的「开关必须被真的消费」回归锁适用 |
| D13 | Belief 面（零代码变更） | 复活 ⇒ reconciler 走**新形成**候选路径：新信念身份 + 新根，过完整 validator（白名单/资格/禁根）；旧 retracted 信念**不自动复活**；`dependsOnMemoryIds` 同 id 新 revision **不恢复**旧信念资格（计划 §3.2 特别验证项）。M9 结构已满足（禁根按根 id、失效按状态）——WP3 只加测试钉住（R10），不改 `src/kernel/app/belief/**` |
| D14 | 幂等 | 同一触发事件重复投递 ⇒ 既有幂等键拦截（`idempotencyKeyForMemory` 带 memoryId discriminator；WP0 实测在位）。两个并发重述 ⇒ 事件序确定 ⇒ 第一个复活生效（状态变 ACTIVE）、第二个标记的 `previousStatus` 与 ACTIVE 不匹配 ⇒ no-op（确定性失败关闭，无重复复活；机制随 D05 实现期修正为状态判别，可观察行为不变） |

## 3. F-4 详细设计

### 3.1 状态转移表（计划 §3.1 逐行落实）

| 输入情形 | 冻结行为 |
|---|---|
| 同一事件重复投递 / 同操作重试 | 幂等键拦截（既有）；无重复 revision、无重复信念形成（D14） |
| ACTIVE 同内容重复 | 既有 D2 去重（`already_applied` / `duplicate_content`）**逐字节不变**（R01） |
| RETRACTED 后新的明确合格告知 | 标记 + 复活为新 revision，来源绑定新告知（D03/D04；R02） |
| SUPERSEDED 后重新告知旧值 | **先走冲突规则**（D-55c）；不绕过政策直接覆盖（D11；R03） |
| DISPUTED / 其他状态 | 不自动恢复（D10；R06/R07） |
| 旧对话重扫 / 旧任务重试 / 索引重建 | 证据不相交检查拦下（D03；R06）——旧 sourceRefs 重现 ⇒ 无标记 ⇒ 原 no-op |
| 新陈述来自 assistant/工具/不合格归因 | 既有资格闸（ADR-043）不变——到不了 create 放行（R09） |

### 3.2 复活快照逐字段语义（D04；计划 §3.2「逐字段说明」）

| 字段 | 复活时 | 旧值去向 |
|---|---|---|
| `revision` | `previousRevision + 1` | 旧 revision 只在历史事件流 |
| `status` | `active` | 旧状态只在历史事件流 |
| `sourceRefs` | **新告知的证据**（非空，MI-03） | 旧证据仍在旧事件 payload |
| `evidenceRootIds` | 新告知的根 | 同上 |
| `contentFingerprint` / `canonicalKey` / `content` / `subjects` / `type` / `owner` / `id` | 与候选一致（同 id 同内容——这正是撞线的原因） | 不变（身份字段） |
| `validFrom` | **复活事件时刻**——不伪造「从未中断的有效期」（计划 §3.2 明文） | 旧 validFrom 在历史事件 |
| `validUntil` | 清空（`undefined`）——当前有效且无已知终点 | 旧 validUntil 在历史事件 |
| `supersededBy` | 清空 | 历史事件 |
| `supersedes` | 候选自带（一般空；不倒写旧源） | — |
| `recordedAt` / `createdAt` | **保留原值**（记录身份的最初创建时刻——M4 起 store 的更新路径就不写这两列，兄弟分支 applyRetracted/applySuperseded 也从不动它们；复活延续同一条记忆身份 ⇒ A==B 要求保留。**R08 第二处实现期修正**：原冻结稿写「复活事件时刻」，实测在线（DB 行保留旧值）与重放（reducer 算出新值）必然分叉 ⇒ A==B 破） | 旧时刻在历史事件 |
| `updatedAt` | 复活事件时刻（本次状态变化的时刻，与兄弟分支同款） | — |
| `authority` / `epistemicStatus` / `importance` / `confidence` | 新告知的抽取值 | 旧值在历史事件 |
| `occurredAt` | 候选自带（Episode 语义不变） | — |
| `processor` / `processorVersion` | 本次发射组件 | — |
| `reducerVersion` / `schemaVersion` | 常量（`memory-reducer@1` / 既有） | — |

**不残留旧失效字段**：复活快照由发射侧整体构造（`record` 全量进事件），reducer 整体采用——
不存在「半新半旧」的合并态；`rebuildMemory` 从事件重放得到逐字段一致结果（R08 断言面）。

### 3.3 事件与投影形状

```text
MEMORY_CREATED（复活形）:
  { memoryId, record: <复活快照>, mutation,
    restatement: { previousRevision: <旧 revision>, previousStatus: 'retracted'|'superseded' } }

applyCreated(state, event):
  state === null                          → 建档（原语义，含旧事件流）
  event.restatement ∧ state.revision === event.restatement.previousRevision
                                          → state = event.record（复活；changed=true）
  otherwise                               → no-op（原语义逐字节——旧流兼容的根据）
```

## 4. F-1 详细设计

### 4.1 撤销证据端口（D16）

```text
输入：characterId / owner
输出：{ withdrawnEventIds: Set<ConversationEventId>, byReason: Map<EventId, 'explicit_forget'|'explicit_correction'|'audit'>,
        chainDepth: number, readAt: sequence }
计算（只读）：
  retracted 记录 → reason（联 MEMORY_RETRACTED 事件）
    explicit_forget     → 自身 sourceRefs ∪ 同 canonicalKey 的 superseded 链全部记录 sourceRefs
    explicit_correction  → 自身 sourceRefs
    audit                → 自身 sourceRefs
```

superseded 链遍历有界（沿 `supersededBy`/`supersedes` 双向，深度上限 WP3 定，防环：链上已访问 id 集合）。

### 4.2 判定点与遮蔽算法（D15/D18）

```text
turn-gateway（单一编译入口）:
  recentLines ← recentContextLinesFrom(...)          // 现状
  if 开关开:
    withdrawn ← 撤销证据端口（失败 → D19 降级：本轮不供给 Recent + trace）
    for line of recentLines:
      line.actorType === 'user'      ∧ line.id ∈ withdrawn          → 占位
      line.actorType === 'assistant' ∧ line.replyToEventId ∈ withdrawn → 占位
  compileInput.recentEvents ← 处理后的行                // 判定在编译接受证据之前
```

- 占位行保留 `id`/`sequence`/`speaker`/`actorType`（结构不变，正文替换）——Recent 的窗口计数、
  序列连续性不受影响；不删除行（不伪装「从未说过」）。
- **同轮遗忘**（本轮先忘后编译）：端口在编译前读 ⇒ 天然覆盖（P10）。
- **重启/跨会话**：端口读持久账本，不依赖进程缓存（P09）。
- **已发出的回复不追溯撤回**（计划 §4.3）。

### 4.3 与已闭合面的关系（D22）

rollup 每轮重算 + 资格闸 ④（挂非 active 根 ⇒ 整条失效）⇒ 遗忘后下一轮自愈（WP0 D-2 实测）；
Recall/Belief/状态文本由 M5/M9 既有机制闭合。P04/P12 以开/关双测钉住，**不改其语义**。

### 13.1 D13「Belief 面零代码变更」的假设被实测证伪 ⇒ WP8 补修（用户 2026-09-28 裁定 A）

**原假设（D13 行）**：复活后 reconciler 走新形成路径即天然得到「**新信念身份**」，因此
`src/kernel/app/belief/**` 无需改动，只需加测试钉住。

**实测证伪**（WP6 长门复跑 + 离线 R13 复现，证据
`artifacts/m9/m9-live-long-20260927-24f6cca44435-edcc/` · `docs/m9.1/M9.1-WP6-Findings.md` §2）：

```text
LL-C5: active 记忆=1(detailed) · active 信念=0        ← 记忆复活 ✓ / 派生信念不重建 ✗
R13-B1: formed=1 · skipped=[] · active detailed 信念=0 ← 调和器提了，放行口拒了
```

**机制**：信念身份段取自**依赖 Memory 集合**（`beliefReportedFormationKeyOf`），复活**沿用同
一 Memory id**（只升 revision）⇒ 再形成推导出**同一个 beliefId** ⇒ 该形成幂等键在首次形成时
已消费 ⇒ `duplicate_operation` 拒绝。与 F-4 同族（确定性身份压过一次合法状态变化），发生在信念层。

**补修（WP8，最小面）**：新增 `beliefReportedDependencyTokenOf({memoryId, revision})`——
`revision > 1` 时身份分量为 `<memoryId>@r<revision>`，`revision = 1` 时**等于裸 id**（M9 基线
身份逐字节不变）；reconciler（产出）与 validator（复推）**同源**调用（INV-M9-11 不变）；
`revision` 由 `belief-scheduler.ts` 端口提供。旧 retracted 信念保持 retracted（D13 原意不变），
新信念带**新根**（复活告知的证据根）。

**D13 的其余部分不变**：旧 retracted 信念不自动复活 · `dependsOnMemoryIds` 同 id 新 revision
不恢复旧信念资格 · 禁根按根 id 不外扩 · 白名单/资格照查。

**追加裁定面**：本条是 D13 的**假设更正 + 实现补齐**，不是设计转向——D13 声明的「新信念身份」
正是本补修要实现的行为。门面随之扩展：`m9.1:e2e:joint` 新增 `R13`（长门形状）+ `R13-B1`
（信念侧），长门 `LL-C5/C6` 以新 run 复跑取值。

## 2. 为什么是 `shadow` 而不是 `on`

```text
`shadow` = **算语义分数并记录新旧顺序对照，但实际回复只用旧路径** ⇒ 输出与 `off` **逐位相同**。
⇒ 先观察、不改她的可见行为；`on` 属**后续独立裁定**。
```

· 记忆 / 投影 / 事件 / 水位**全部保留**；· **无需**数据库回滚（本里程碑的派生索引是**派生**的）。

## 5. 激活时的**快照状态更正**（记档）

```text
我在执行前一轮曾**误报**"没有 verified 快照 ⇒ 激活被阻断"。
错因：以为 manifest 在**快照目录内**（`<dir>/manifest.json`）；实际是**同级文件** `<dir>.manifest.json`
（`data/snapshots/` 根层，`orphanSnapshotManifests()` 正是 `readdirSync(root)`）。
实际：根层 56 个 manifest，其中 **10 个与现存目录配对 = verified**，最新一份摘要与真实库一致。
⇒ 结论**撤回**，教训记档：**"文件不在我以为的地方" ≠ "文件不存在"**（与 `L-M95-27` 同族）。
```

## 6. 读回更正（2026-09-30 · **只追加**；§1–§5 一字未改）

> 载体：`scripts/m9.5-semantic-index-readback.ts`（真实库 · SELECT-only 构造闸 · INC-01 全程：
> 租约 → pre-open 已验证快照 → token → 干净关闭 → post-close 快照 · `cleanClose=true`）· **13/13 通过**。

```text
§1③ 逐字写「⇒ **M9.5 已生效**（通道登记为语义召回 + shadow 模式）」。
那次读回**只核了启动 flags**（`memory-semantic-mode(shadow)` 确实在启动读数里 ✓），
**没有核**派生索引是否真的存在。2026-09-30 的只读读回补核了，逐字读数：

  · `memory_semantic_meta`        **0 行** ⇒ `ensureSemanticIndexSchema()` 从未在真库上跑过
  · `memory_semantic_generations` **0 行** ⇒ **已发布代 = 0**
  · `memory_semantic_index`       **0 行** ⇒ 零向量
  · `memory_semantic_failures`    **0 行**
  · 四张表都在 · `embedding` 列为 `vector` · kernel schema = **10**
    （表由 M10 的 `MIGRATION_0010` 建出；该迁移**刻意不写**版本登记行）

⇒ 两处措辞**收窄**（不推翻任何执行动作）：
  ① §1③ 的「M9.5 已生效」准确含义 = **通道登记 + 档位 `shadow` 已生效**；
     **不**等于「语义召回在生产里已可观察」。
  ② §2 的「`shadow` = 算语义分数并记录新旧顺序对照」是 `shadow` 的**定义**；
     但在生产里它**当前一次都没算过** —— 探针第一步找已发布代，0 个即 `not_indexed`
     （连 134 MiB 的编码模型都不加载），而「记对照」分支只在**真的拿到分数**时才执行
     （`memory-retrieval-store.ts:305-320`）⇒ **没有任何对照被记下来**。
```

它只是把「已生效」的**范围**写准。

# ADR-026：先有 Native 基线，再谈外部后端

- **状态**：已接受（M4）
- **日期**：2026-09-16
- **相关**：计划书第 93 / 95 / 103 节；MI-13
- **代码**：`src/infrastructure/persistence/memory-store.ts`（`MemoryStorePort`）、
  `src/kernel/app/memory/explicit-service.ts`（`MemoryFoldPort`）

---

## 背景

M4 之后第一次允许考虑外部长期记忆后端（MemOS 等）。
它们提供一些本项目没有的东西：统一长期记忆 API、
异步调度器、反馈/纠正机制、生命周期管理。

诱惑是明显的：**"它已经有这些了，我们接上就行"**。

问题在于，如果先接外部后端，我们会得到一个无法判断的结果：

```text
"好像能记住"
```

而无法回答计划书第 93 节点出的那个问题：

> 是 MemOS 真的改善了，还是我们根本没有自己的基线。

这句问的是**测量**问题，而不是技术选型问题。
没有基线时，任何"接入后感觉好多了"都无法与
"接入后我们其实丢了可追溯性但没人发现"区分开。

---

## 决策

**Native 后端必须先完整实现并通过 Gate，然后才允许做外部后端的 PoC。**

### 1. `MemoryStorePort` 是此前完成的唯一契约

Character Domain 只知道 `MemoryStorePort`（`get` / `list` /
`apply` / `history` / `rebuildMemory` …）。
`createNativeMemoryStore()` 是它当前唯一的实现。

这条约束的**实践含义**：Native 后端不是"临时方案"，
它必须真的满足端口契约 —— 否则将来换后端时会发现
契约是照着一个实现的形状写的，而不是照着需求。

### 2. 真源永远是账本 + 领域事件

```text
Conversation Ledger  +  Memory Domain Events  =  真源
```

任何外部后端都是**派生存储**，不是真源。
判据很直接：如果它损坏，应该理论上可以
`rebuild / repopulate`，而不是丢掉她的整个过去。

### 3. Native 基线必须覆盖可比较的维度

"有基线"不等于"跑通了"。基线必须能回答外部后端
将要被问的同一批问题（判据表见 ADR-027）：

- MemoryId 能否保留
- 证据/来源能否保留
- supersede / retract 能否表达
- 历史版本能否查询
- 不同 owner 能否隔离
- 能否避免绕过 MemoryPolicy
- 失败时主聊天是否仍能工作
- 能否完整导出
- 移除后能否回到 Native

这些维度**在 Native 上先跑一遍**，结果是外部后端的比较基准。
这也是为什么 `m4:verify` 的 142 项里有针对每一条的检查：
它们不只是"Native 的测试"，它们是**基线的定义**。

### 4. Native 不因为"将来可能换掉"而降低要求

一个常见的滑坡是："反正要换 MemOS，这个先简单实现"。
那会让基线**没有资格**当基准 —— 一个降级的实现
被外部后端"打败"是必然的，而那个结论毫无信息量。

因此 Native 实现了完整的：
追加式状态机、双向指针、部分唯一索引、乐观锁、
reducer 版本守卫、重放 `A == B`、审计探针。

---

## 被否决的备选方案

### 方案 A：直接接 MemOS，跳过 Native

**否决理由**：见背景。没有基线，任何改善或退化都无法被观察到 ——
而"无法观察到退化"在记忆系统里是最危险的状态，
因为它的症状会在几十轮之后才出现。

### 方案 B：只做最小 Native（够跑就行），主要精力放外部后端

**否决理由**：见决策 4。降级的基线不能当基准。
而且如果外部后端最终被否，
项目会剩下一个"够跑就行"的 Native ——
那时它要独自承担生产职责。

### 方案 C：让 Native 成为"只用于测试的参考实现"

**否决理由**：计划书明确 Native 是**可用的**生产路径
（"项目继续 NativeMemoryStore，完全没有问题"）。
把它降级成测试夹具，等于预先认定外部后端会被采用 ——
而那个判断必须由 Gate 得出，不能由架构预设。

### 方案 D：先看 MemOS 的能力清单再决定 Native 要做到什么程度

**否决理由**：这会让 Native 的契约**照着 MemOS 的形状**长，
从而在 Gate 之前就把结论写进了代码 ——
而 Gate 的意义正是"在不受它的形状影响的前提下判断它是否合适"。

---

## 后果

### 正面

- 外部后端的评价有一个**自己实现的**对照基准。
- 即使外部后端被否，Native 已经是一个完整的生产实现。
- `MemoryStorePort` 是被真实需求塑造的，不是被某个实现塑造的。

### 代价

- 多了一大块（Native 的完整实现）在 Gate 之前就必须做完。
- 部分能力（异步调度、生命周期管理）在 Native 里是
  "够用但朴素"的 —— 它们正是外部后端可能真正胜出的地方，
  这一点在 Gate 里要如实承认。

| 本地基线先于外部后端 | 本 ADR + ADR-027 的 Gate 条件 |

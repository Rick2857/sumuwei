# AI Town 架构笔记

**性质**：`REFERENCE ONLY`（计划书第 55 / 56 / 100 节）
**是否新增生产依赖**：**否**
**是否实现其任何功能**：**否**

---

## 0. 它在本项目里的用途

AI Town 只用来验证一件事：

> 一个 Character Kernel 如果未来进入**持续多角色环境**，需要面对什么。

我们**不**做那个环境。我们只检查自己的接口在那种环境下会不会当场崩掉。

---

## 1. 参考了什么（计划书第 55 节）

```text
shared world state          共享世界状态
simulation engine           仿真引擎
multiple agents             多个 agent
persistent environment      持久环境
```

## 2. 从它借了什么（计划书第 56 节）

计划书第 56 节只让我们**检查四件事**：

| 检查项 | M3.5 的答案 | 由谁守 |
|---|---|---|
| `EntityId` 是否足够通用 | 是。`EntityRef{id,kind}` 已登记 9 种实体种类（启用 4 种） | FC-T01 |
| Character 是否独立于 World | 是。Kernel 不拥有世界事实，也没有任何世界写入口 | FC-T04 + 符号守卫 |
| Action 是否经过 Environment | 是（结构上）。`IntentResolver` 是唯一出口，`IntentResolution` 是唯一结果形态 | FC-T03 / FC-T04 |
| 多角色是否共享外部状态 | **不共享**（也不该共享）：每个角色有自己的 `characterId` / 事件序列 / 投影；共享的只有"世界"，而世界今天不存在 | FC-T01 / FC-T05 |

---

## 3. 我们**明确没有**采用的东西（计划书第 100 节）

```text
AI Town runtime
world simulation implementation
```

具体地说，以下这些**在本项目里不存在，也不计划存在**：

```text
NPC 管理器 / 日程表 / 位置系统 / 寻路
共享世界数据库 / 场景数据库
仿真 tick / 世界事件广播
```

---

## 4. 为什么不实现它

| 理由 | 说明 |
|---|---|
| 计划书第 3 节明确禁止 | `Multiple Active Characters` / `Simulation Tick` / `World Database` 都在禁止清单里 |
| 与 Lv1/Lv2 的目标无关 | 本项目现在的目标是把**一个**角色做扎实（身份 / 来源 / 完整性） |
| 它会掩盖真正的问题 | 一旦有了"世界"，就很难再判断一个缺陷是"角色认知错了"还是"世界状态错了" |
| 成本不可控 | 世界必然带来调度、冲突解决、权限、共享状态一致性 —— 每一项都是独立的大工程 |

---

## 5. 它对我们的价值：一个"未来会不会崩"的检查清单

AI Town 的真正用途是给我们一张**提问清单**（计划书第 48 / 56 节）。
这些问题在 `m3.5:test` 的 FC-T01 / FC-T05 里被逐条回答，
并且答案都是"不需要重写底层"。

**如果哪天这些答案变成"需要重写"，那说明 M3.5 的预留失败了** ——
那时应当先修 M3.5 的契约，而不是直接开始写世界。

---

## 6. 一句话总结

> AI Town 让我们看见"多角色世界会长什么样"，
> 从而判断**今天哪些决定会让那天无法到来**。
> 它是一面镜子，不是一个要搬进来的家具。

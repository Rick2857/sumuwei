## 实现与取舍

1. `task-orchestration-instructions.ts` 保存一份版本化固定指令 `task-orchestration@1`。
   首次工具决策与后续任务规划都使用它；仍输出原有严格 JSON，不增加计划字段。
2. 参数已知且互不依赖的读取可以放在同一计划里，既有执行器仍串行执行。
   下一步需要尚未取得的正文、路径、页面引用或计算结果时，只提交前置步骤，
   `done=false`，等实际结果回传再规划。不把模型猜测的输出当成工具结果。
3. 失败、拒绝、部分完成、取消或网关异常会暂停本批剩余步骤，交回既有规划器。
   首份计划的 `done=true` 不覆盖失败；仍扣同一任务的规划预算和行动预算。
   已完成与失败记录均保留。暂停意味着独立的剩余步骤也需要下一次规划，代价是额外调用。
4. 备用方法仅能来自已授权目录并有实际依据；权限、安全限制与取消不得绕过。
   不引入原版的自动安装、启动服务、替代认证、任意 CLI/MCP，以及固定工具优先级。
5. 有合适读取能力且预算允许时，生成后读回核对；读取成功不证明所有内容都正确。
   空计划或 `done` 仍只表示规划已结束，不单独证明任务已完成。
6. 真模型组合链暴露了计算器的启动耗时问题：原先 2 秒墙钟预算包括加载 `tsx`。
   改用本机 Node 22.23.2 的原生类型剥离运行同一受限求值器，保留 2 秒硬超时、
   独立子进程与进程树终止，AST、精度及结果边界均未放宽。

执行权威仍是原用户事件 → 任务授权 → 严格计划校验 → ActionGateway / Policy /
Adapter → ActionResult → 账本 / trace → 回复守卫。ADR-104 的能力、风险、归因、
输入面、搜索 `querySpan` 和每轮搜索额度均保留。没有数据库迁移、长期认知入口、
人设修改、新能力或生产配置改动。`rules` 工具选择入口保留；本批新增的任务排序
规则与失败暂停作用于既有有限任务环，属于本次明确授权的执行改善。

## 使用与效果边界

本轮只读确认 `.env` 的工具选择为 `role`、任务自治与计算器开关均为 `true`。
在这些现有配置下，新启动的 LG 核心会自动使用这套指令，
不需要用户单独调用 `/orchestrate`。已经运行的进程需要重新启动才加载新代码。
本批没有启动或重启正式聊天进程。
输入依赖的排序主要由模型遵循指令；失败后的暂停、预算与权限校验由程序执行。
编排质量与成本不能从指令接线或少量短链推断为普遍改善。

### 第二阶段：多个认知写入进程

交付角色/会话级协调、独立 worker、原子任务认领、单调水位、崩溃回收，以及多调度器下的外部动作边界。此阶段不因第一阶段完成自动视为 PASS。

第一阶段不同时引入新 ORM、独立向量数据库、Redis 队列、PgBouncer、HA 集群或 Kubernetes；不重建角色、不重新播种 origin/cutover、不改变记忆采信或 reducer 语义，不调整模型和语音方案。远程管理预留标准 PostgreSQL 连接方式，首轮部署限 loopback；具体跨机器入口在目标网络确定后单独验证。

## 3. 设计约束与不变量映射

### 3.1 配置、身份与权限

- 后端由程序明确选择；建议新增一个闭集后端字段（如 `CHARACTER_DB_BACKEND=pglite|postgres`），PG 连接串沿用插件实际读取的 `POSTGRES_URL`。名称在 WP0 ADR 中定稿，实施后只保留一处规范化解析结果。
- `.env`、`.env.qq`、祖先 `.env`、进程环境及 runtime settings 的优先级必须一致。配置冲突、缺 PG URL、连接失败或身份不符均拒绝启动；指定 PostgreSQL 后禁止回落 PGlite。
- 开库前核对目标允许范围与执行用途，连接后核对实际 database、user、服务器目标及部署身份。身份检查发生在插件迁移、建档和任何业务写入之前。日志只记录脱敏身份，不输出密码或完整凭证 URL。
- 分开迁移账号、运行账号、只读账号和测试账号。测试账号不能连接/写入生产目标；不能仅设置 `default_transaction_read_only` 就把具有写权限的账号称作只读账号。
- 普通聊天不自动应用新增 Kernel 迁移；PG 迁移采用唯一受控入口和迁移互斥。插件 bootstrap 与受限 runtime 分开验证，不能假设上游已有“关闭自动迁移”开关。
- 需要数据库身份记录时，只新增最小元数据并走新迁移，不回写已发布 DDL；目标部署身份在恢复后明确重绑定，不把备份源身份直接作为目标身份。

### 3.2 后端生命周期与写入管理

- PGlite 的 INV-DB-01…07 继续约束 PGlite 源库、目录快照及恢复；PostgreSQL 增加后端适用性映射，不能删除原保护或将其机械套到所有 PG SELECT 连接。
- PostgreSQL 客户端拥有连接/连接池生命周期，数据库服务器独立存在。应用停止不停止服务器，不复制运行中 PGDATA，不删除任何 PID/WAL 以“修好”检查。
- 同角色首期只有一个认知执行者。PG advisory lock 可用于拒绝第二核心；读取/备份不争抢该写入资格。现有进程内回合调度保留，所有公共消费者仍只有一个管理者。
- 写入资格必须覆盖在飞回合、后台消费者、提醒和已排队动作。专用锁连接丢失时停止接收新轮次、取消未提交工作，并验证不能继续通过其他池连接落账或发起动作；**获取一次 advisory lock 不构成完整失效保护**。WP0 决定锁与写入连接绑定或最小 fencing 实现，WP3 故障门未过前不允许生产切换。首期不提供自动跨机器接管。
- 不把模型、网络、TTS 或外部动作包在长数据库事务里。连接池关闭须等待关闭操作完成，并核对本进程会话释放；不能仅凭管理器预先设置的 closed 标记宣布关闭成功。
- 插件池当前默认键不含连接地址、上限为 20。首期隔离库采用独立进程，显式关闭池；同进程多目标路径必须拒绝或有已验证的隔离实现，禁止直接清空缓存掩盖悬空连接。

### 3.3 数据与外部资产

对话账本和领域事件仍是真源；投影和向量是有归属的派生数据。数据迁移不触发历史重新抽取、不更换 MemoryId、不物理丢弃更正/撤回历史，不推进原消费者水位来跳过问题。

迁移范围从源副本数据库目录/系统目录视图列举完整 schema 和表，分类说明，不能硬编码“只导几张记忆表”。包含插件表、迁移元数据、身份映射、事件、状态、任务、控制记录、通知、trace、向量和序号。数据库外图片、个人资料库等列独立路径、摘要、归属和备份恢复办法；ImageInputStore 不再以 PG 连接配置推导文件路径。

### 既有回归与真实 PG lane

实施每包至少运行 `pnpm typecheck` 和相关门；WP5 / 交付候选必须运行 `pnpm m4.5:ci` 并退出 0。仓储及内核基线重点包含 `kernel:test`、`m4:test`、`m4:verify`、`m4:isolation:verify`、`m4:mutation-safety:verify`、`m4:memory-integrity:verify` 和与召回、认知、提醒、共存相关的门，具体去重清单由 WP0 按实际改动确定。

`m4:restore:verify`、`m4:restart:verify`、INC-01 等现有脚本有后端/目录假设。先审入口和数据来源，原门保留 PGlite 归属，新增 PG 场景验证同一业务性质。不得因换库让原门静默跳过，也不得把 PGlite PASS 当作 PG PASS。

受控真模型 smoke 必须使用隔离 PG 与指定测试模型配置，记录端点/模型/开关，不打开真实 PGlite。不把 `m4.5:ci:full` 或带 `real-db` 名称的脚本直接当作 PG 命令：WP0 先核对其 source-copy 与环境继承，再决定复用或新增 PG runner。已经通过的完整 CI 仅在新改动、失败或指纹不适用时重跑，不用重复全量测试代替定位。

### 性能与资源读数

WP0 固定代表性语料、模型/provider、输入规模和运行环境；WP5 分别记录预热后固定仓储操作及有限整链的 p50/p95、错误/超时数、连接数、CPU/内存/磁盘、备份耗时。PGlite 对照采用相同快照的一次性副本，禁止为测速独占真实库。Windows 记录 Docker/WSL 整体基线和 PG 容器读数。

数据正确性、零未解释事务错误/超时和持续可用为硬条件；资源/时延数值如实报告，在 WP6 判断是否满足当前机器与交互超时预算。未设性能收益目标，不为得到更快数字关闭持久性设置。生产窗口估计以实测导出、导入、比较和启动时间构成，不能先承诺固定几分钟。

## 6. 数据迁移与比较规程

1. **选择来源**：采用有 manifest、内容摘要和合格关闭归属的 verified snapshot；先校验再复制为一次性源。若当前没有合格快照，记录阻塞；取得源库受控关闭授权后按原状态机生成。运行中不直接复制 `data/pglite`。
2. **源清单**：在副本中读取引擎/schema、扩展、schema/table、约束、索引、序列、角色及权限需求和关键对象计数。物理快照只证明来源，不直接当成 PGDATA。
3. **导出**：使用已在合成库验证兼容的官方 pgDump 工具；记录工具版本、参数、退出/异常、dump 摘要。覆盖完整应用对象，列清系统/扩展对象排除原因。
4. **空目标恢复**：验证目标身份与“允许初始化”的用途；预装所需扩展；恢复完整 SQL 并检查所有错误。不得先运行 runtime 建同名表，再忽略导入冲突。source schema 与待追加迁移分开处理。
5. **权限与身份绑定**：源 dump 的 owner/ACL、search_path、扩展版本和目标账号显式映射；恢复后重新设置目标部署身份。全局角色/权限和数据库外资产有独立恢复步骤。
6. **完整性检查**：按主键排序、规范化 JSON、时间和数字编码计算摘要。原始事件、记忆内容、归因、来源、撤回/更正及序号字段不忽略；只有契约列明的派生更新时间或新目标元数据允许差异，逐项解释。无主键表采用稳定行多重集比较，不只比总数。
7. **可恢复性检查**：先记录恢复后投影，再在另一个一次性 PG 目标重建并比较；不得用重建覆盖首次发现的不一致。任务 pending/running、处理中水位及通知投递未知态按原恢复规则处理，不擅自一律标 completed 或重发。
8. **只读与业务验收分开**：最终生产导入读回在业务启动前完成；隔离演练才运行合成消息、任务和功能变更。真实生产首轮只执行已授权的真实使用。

源副本读出 schema 若落后于代码：先以源 schema 完成迁移一致性比较，再独立预览/执行新增迁移和比较允许变化，不把导入、schema 升级、重算和数据修复揉成一个无法对账的步骤。既有 origin、cutover、水位、generation 和 namespace 保持原值。

## 7. 生产切换状态与失败处置

WP6 必须把下列步骤转成经演练的实际命令、绝对目标和操作者检查项；本计划不提供当前不存在的可执行迁移命令，也不填写虚构 URL、快照 ID 或镜像 digest。

```text
READY
  → OLD_CORE_DRAINED_AND_CLOSED
  → FINAL_SOURCE_SNAPSHOT_VERIFIED
  → TARGET_RESTORED
  → FINAL_DATA_COMPARISON_PASS
  → TARGET_CONFIG_SELECTED
  → PG_CORE_READY
  → PRODUCTION_USE_OBSERVED
```

切换前冻结入口与后台调度，按 `pnpm coexist:stop` / sentinel 的现有正常链排空、关闭，确认 cleanClose 和最终快照。不得使用 taskkill，不能把“进程看不到了”作为合格关闭证据。PG 服务可以预先部署，但目标不能提前成为第二个生产写入权威。

从 FINAL_SOURCE_SNAPSHOT_VERIFIED 起导出/恢复最终源；早期演练 dump 不作为最终数据。完成数据比较后才切配置并启动一个核心；先检查数据库身份、schema、资格、消费者恢复和 readiness，再允许正式输入及主动动作。配置读回与实际连接读回分别记录。

| 失败发生处 | 处置 |
|---|---|
| 旧核心未排空、关闭不明或最终快照不合格 | 停止迁移；保留现场，沿原事故流程处理，不强行复制或重开 |
| 导出/导入/比较失败，尚未切换权威 | 保留失败 dump 和目标；不覆盖源；满足原启动条件后可恢复旧后端服务 |
| PG 启动失败或身份/schema 不符 | 保持正式输入关闭；确定目标是否已有新写入，再选择适用回滚路线 |
| 数据库断连或写入资格丢失 | 停接收、取消未提交工作、保留已提交事实与未知动作状态；不得启动第二核心“碰碰运气” |
| 首轮行为异常 | 记录 trace、事件和实际交付；先冻结新输入，分类数据/配置/行为问题，不重复发送投递结果不明的消息 |

## 8. 回滚与恢复

**回滚点 R0：PG 没有新增权威事实。** 核验最终源保留、PG 写入清单及旧代码/配置仍兼容，正常关闭 PG 核心后回到合格 PGlite 源。禁止两个核心同时在线写入。启动/bootstrap 自身可能产生写入，必须检查后才能称为“零新事实”。

**回滚点 R1：PG 已有新增事件、记忆、任务或动作。** 不直接启动旧快照。冻结 PG 写入并备份当前目标，清点增量和外部动作；优先修复并在 PostgreSQL 内恢复服务。若要回到 PGlite，必须已有全量反向导入兼容演练，验证所有新增数据、schema、序号、向量及通知状态后再切换；没有证明即不承诺无损回滚。

首期不把完整反向迁移当成默认附带能力。WP6 必须写明 R1 实际可用的是 PG 修复/恢复还是已验证反向迁移，及可接受的数据恢复窗口。PG 内从旧备份恢复也可能损失备份后的写入；不能把恢复成功等同于零数据损失。PITR/WAL 与异地备份按第二阶段另验，当前 pg_dump 方案如实记录实际备份周期和 RPO。

保留最终 PGlite 快照、原始 dump、生产切换前配置清单和首份 PG 备份，放到不会被短期自动 retention 清理的受控本地归档。备份含私人历史，不提交 Git；源退役删除不属于本计划的自动动作。

## 9. 证据、文档与完成判定

建议机器证据目录：`artifacts/post-lv2/postgresql-migration/<runId>/`。非敏感 manifest/汇总按项目规则提交；原始 dump、私聊正文、连接凭证、源/目标物理数据放 `local/` 或已忽略目录。WP0 核验 gitignore，不能只因文件名含 backup 就假定安全。

每个 run 记录 UTC 时间及人类可读 UTC+8 时间、HEAD 和相关未提交源码指纹、dirty/owned paths、后端与实际目标脱敏身份、源快照 ID/摘要、引擎/扩展/工具/镜像版本、schema、配置档、测量数量、命令、退出码、失败原因与证据摘要。文件指纹与逻辑数据指纹分别记；完整性日志不打印私人正文。

聚合结果分列：设计、实现、PGlite 旧门、真实 PG 门、量具、数据副本、真模型链、资源读数、恢复演练、生产切换、在线运维、首次使用、长期运行、多写进程。任一关键门 FAIL / NOT RUN 不能汇成 PASS；自然首用和长期收益不得由配置/隔离 smoke 推定。

| 判定 | 必要条件 |
|---|---|
| 隔离实现完成 | WP0–WP5 完成，PG-G01…09 PASS，typecheck + m4.5:ci EXIT 0，局限与失败档齐备 |
| 切换候选就绪 | WP6 完成且 PG-G10 PASS；实际命令、源/目标和回滚边界具体可审查 |
| 生产迁移完成 | WP7 完成、PG-P01 PASS；实际权威已经切到 PG，无双写 |

文档交付至少包括 ADR、验收契约、各 WP Handoff、Activation-Candidate、Activation-Record、Acceptance-Report、Known-Limitations 和运维 Runbook。可以在同一文件分节承载小型交付，避免为形式拆分重复内容。按实际变更更新架构不变量的后端适用性、Scripts-Catalog、使用说明和受影响门映射；不改历史判定正文，不自动打标签、合并或推送。

## 10. 第二阶段交接：多进程与长期部署

| 工作项 | 必须补齐的证据 |
|---|---|
| 同角色多进程回合 | 两个真实 OS 进程同时提交；顺序、冲突、取消、重启和认知上下文符合契约；锁/fencing 失效不产生晚到提交 |
| 独立 worker | 原子认领（可评估 SKIP LOCKED）、执行租期、崩溃回收、重试幂等、不同角色公平性；不长期持事务等模型 |
| 水位并发 | 数据库原子单调更新；较大水位先落后较小值不能覆盖；事件/幂等/水位边界经故障注入验证 |
| 提醒与外部动作 | 多调度器竞争、发送成功但落账失败、重启和未知结果；不宣称 SQL 能提供外部发送 exactly-once |
| 多主机管理 | 明确目标网络和身份，VPN/SSH/私网或验证 TLS 的连接；远程只读与权限负控，凭证轮换和审计 |
| 长期备份 | 实际 RPO/RTO、异地备份、WAL/PITR（可评估 pgBackRest）、介质损坏恢复演练及补丁升级 |
| 连接和容量 | 按真实进程数统计连接预算，再决定是否需要可配置池或 PgBouncer；按实际规模决定索引/容量优化 |

第二阶段启动前再定设计和验收，不预先实现通用分布式框架。第一阶段验收应能明确回答：**核心在线时，能否独立查询、管理和备份；重启核心是否不再迫使数据库停机；原有角色数据是否完整、可恢复、可审计。**

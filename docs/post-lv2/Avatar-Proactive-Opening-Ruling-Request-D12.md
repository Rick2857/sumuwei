## 1. `D12` ① 的原文与它给的两条理由

> ```text
> ① **先关掉 VTuber 自带的 proactive speak**（localStorage `proactiveSpeakSettings` /
>    界面上的「主动搭话」）——否则两条路并存会互相打架，且那条路仍然会撞守卫。
> ② 页面只负责**播放与回执**；不生成内容、不决定说不说。
> ```

⚠️ 而 §6 与 §8 把它升成了**硬前置**：

```text
§6 ⑤：**不主张外壳侧的 proactive speak 已关**：D12 ① 是**前置条件**，必须在实现时验证。
§8 WP2：⚠️ **不先做这步，其余全部白做**：那条路会继续 33 次/分钟撞守卫。
```

---

## 2. 我实现的是什么（**代码现在就在这个状态**）

WP5b-3（本轮之前那一轮）改了 `scripts/postlv2_vtuber_runtime.py` 的 `LGBridgeAgent.chat`：

```text
改之前： if input_data.files or metadata.get("proactive_speak"): raise ValueError("LG avatar entry only accepts …")
改之后： if input_data.files: raise …                      ← 守卫对**文件**照旧
         if metadata.get("proactive_speak"):
             await self._report_opportunity()               ← 这条信号**改走机会报文**
             return                                          ← **一个字节的回复都不 yield**
```

`_report_opportunity()` 发 `PROACTIVE_OPPORTUNITY{entry:"avatar", idleMs}`，
`idleMs` = `now − LAST_INPUT["at"]`（最后一次真实用户输入）。

⇒ **把"外壳自带的主动搭话"从一条会撞守卫的旁路，改成了 `D01` 要的那个机会上报通道。**

---

## 3. ★ `D12` ① 那两条理由是**怎么被消解的**（逐条）

| `D12` ① 的理由 | 在本实现下 |
|---|---|
| 「**两条路并存**会互相打架」 | **不存在两条路了**：前端那条信号**就是**机会上报通道，只有一条 |
| 「且那条路仍然会**撞守卫**」 | **不再撞**：那条分支不再 `raise`，而是走机会报文 |

⇒ 这两条是 `D12` ①**仅有的**理由，而它们都建立在一个前提上：
**机会报文那条路是"另外新加的"**（所以会与旧路并存）。**本实现把它们合成了一条**，
那个前提不成立 ⇒ **那两条理由同时失效**。

**⚠️ 但这不是"因此 `D12` ① 就不必做了"** —— 因为本实现**引入了一个新依赖**（下一节）。

---

## 4. ⚠️ 本实现引入的新依赖（正是 `D12` ① 想避免的那一类）

```text
本实现要能工作，**必须**前端那个「主动搭话」开关**开着**（`allowProactiveSpeak`）。
```

| | `D12` ①（原设计） | 本实现（选项 A） |
|---|---|---|
| 触发器 | 外壳**自己**的空闲探测（要新写） | 前端**已有的**空闲定时器（复用） |
| 依赖用户设置 | **不依赖** | **依赖**（开关必须开着） |
| 前端要不要改 | 要（或外壳新写一个定时器） | **不要** |
| 报告频率 | 由我们定 | 由**前端的定时器**定（实测 ≈1.6 秒/次） |

⇒ 所以这是一个**真实的取舍**，不是"我改得更对"。**两端各让一步**：

```text
本实现换来的：零前端改动 + 那两条旧理由失效 + 热循环被 LG 的闸兜住
本实现让出的：**功能可用性挂在用户的一个开关上**；报告频率不受我们控制
```

## 5. 三个选项

### 选项 A —— 现状（复用它，不写新触发器）

```text
前端开关**必须开着**；`ai-speak-signal` 就是机会上报通道。
代价：① 功能挂在用户设置上（关了就静默失效，**没有任何读数会告诉你**）
      ② 报告频率 ≈1.6 秒/次 ⇒ 每次一轮预检（含**有界依据扫描**）⇒ 数据库 churn
```

### 选项 B —— 严格照 `D12` ①（冻结原案）

```text
① 前端开关**关掉**（你手动关，零代码）
② 外壳**自己**加一个空闲上报定时器（在新文件里改；`LAST_INPUT` 已经在了，成本小）
⇒ 不依赖任何用户设置；报告频率由我们定（例如 60 秒）
```

### 选项 C —— **两件都做**（我的建议）

```text
① 保留本实现（那条信号改走机会报文 ⇒ **它再也不会撞守卫**，即使开关开着）
② **外加**外壳自己的空闲上报定时器（选项 B 的第 ② 步）
⇒ 结果：①**开关开着也好、关着也好，功能都工作**
        ②若两者同时上报，由 LG 的**双键幂等**兜住
          （`U1` 的机会键 `<dayKey>T<hour>` + 冷却 —— **负控 10 正是为这件事写的**：
           "外壳连发同一小时内的多条 ⇒ 只有第一条被处理，其余零模型调用"）
⇒ `D12` ① 的**字面**（"先关掉"）不再必要，但它的**意图**（不依赖那条旧路 / 两条路不打架）**完全满足**
```

### 10.1 ★★ 裁定之后你给的那个读数，把**根因**也定下来了

你从页面取回的设置：

```json
{"allowProactiveSpeak":true,"idleSecondsToSpeak":0,"allowButtonTrigger":false}
```

| 键 | 值 | 含义 |
|---|---|---|
| `allowProactiveSpeak` | `true` | 那条路**是开着的**（与热循环一致） |
| **`idleSecondsToSpeak`** | **`0`** | ★ **这就是 33 次/分钟的真正根因**：阈值是**零秒** ⇒ "只要有一点点空闲就触发" ⇒ 实际上**永远触发**（1.6 秒那个节奏就是一次往返的时间） |
| `allowButtonTrigger` | `false` | 没有手动按钮那条路 |

⚠️ **这纠正了立案时的一个隐含判断**：我们此前把 33 次/分钟读成"外壳那条路是**失控**的"，
而事实是**它按配置忠实工作** —— 配置的阈值是 0。**不是 bug，是配置。**

⇒ 两个后果：

```text
① **零代码就能把那条路的频率降下来**：把 `idleSecondsToSpeak` 设成 180（= LG 的
   `openingMinIdleMs` 3 分钟）⇒ 它只在**真的空闲 3 分钟**之后才报一次。
   ⚠️ 与 C 不冲突：C 已经保证"开关关着也工作"，这个数字只是让**开着时**别太吵。
② 它顺带说明：我此前提的"外壳侧最少报告间隔"**不再必要** —— 前端本来就有这个旋钮，
   而且它的语义（空闲多少秒才触发）比"最少间隔"更贴切。
```

### 10.2 裁定 C 之后，`D12` ① 的处置（逐字留档）

```text
`D12` ① 的字面（"**先关掉**"）**不再作为前置**：C 让它失去必要性
  （理由是它当初给的两条理由都被消解，见 §3；而 C 又补上了"不依赖前端开关"那一半）
`D12` ① 的**意图**（两条路不打架 / 不依赖失控的旧路）⇒ **完全满足**：
  · 不打架：两者同时上报由 LG 的**机会键（`<dayKey>T<hour>`）+ 冷却**兜住（`U1` / 负控 10）
  · 不依赖旧路：外壳自己的上报器不经过前端
`D12` ②（页面只播放与回执）⇒ **一字未变**，仍然成立
```

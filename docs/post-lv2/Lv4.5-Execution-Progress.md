## 2. P1 做了什么（每条都能在代码里指出来）

### 2.1 计划 §2 的第一句：「先用 2–4h 核对慢请求期间的取消路径与播放回报」

核对的结论（不是推测，是代码事实）：

```text
`runBridgeTransport` 旧实现 = 「读一行 → await 整条处理完 → 写回一行」的单循环
  ⇒ 一轮慢请求（模型等 5–20 秒）期间，外壳随后发来的 CANCEL_TURN
    **一直躺在 stdin 缓冲区里**，直到那一轮结束才被读到。
  ⇒ `L-PL2-04` 的取消通道虽然存在，但"用户抢话 → 立刻停"在**传输层**就不可能成立。
播放回报：**完全没有通道** —— 受控登记表只有 SUBMIT_TURN / CANCEL_TURN，
  浏览器侧的播放事件（`postlv2_speech_client.js` 的 events）从来没有回传路径。
```

### 2.2 传输解耦（`src/infrastructure/bridge/turn-bridge-transport.ts`）

```text
控制消息（CANCEL_TURN / REPORT_SYNTHESIZED / REPORT_PLAYBACK）
  ⇒ 读到**立即**处理，与在途轮次**并行**（不写库、不调模型，只更新进程内登记）
正式轮次（SUBMIT_TURN）
  ⇒ 仍走**独立串行泵**（D12「正式写入串行」不变；桥自己还有第二道串行闸）
分类的答案**只有一处**：`isBridgeControlMessageKind`（kernel 侧）
传输层不做语义判断，只按那一处决定"排队还是立即"
```

传输读数新增两个字段（`BridgeTransportReading`）：`controlPeakInFlight` · `controlLatencyMs`。

### 2.3 受控消息登记表 2 → 4

| kind | 作用 | 谁的权威 |
|---|---|---|
| `SUBMIT_TURN` | 正式轮次（会调模型、写账本） | 桥 |
| `CANCEL_TURN` | 协作式取消（只记意图） | host 的取消登记表 |
| `REPORT_SYNTHESIZED` | 合成完成（**必须**带 `audioId`） | TTS / 外壳侧 |
| `REPORT_PLAYBACK` | 播放事实（`queued/playing/played/cancelled/unknown`） | **客户端** |

未登记种类照旧 `bridge_unknown_message_kind`（仍不建"万能连接器框架"）。

### 2.4 交付账本体（`src/kernel/app/bridge/voice-delivery-ledger.ts`，新增）

```text
· **进程内**：不写数据库、不新增 schema、不进 trace 正文；重启归零 ⇒ 未播句按未播出处理（保守面）
· 状态推进**只有一处**：复用 `media-delivery.ts` 的 `advanceSegment` + 迁移表
· 中间跳**由迁移表 BFS 推导**（`pathBetween`），**不手写捷径表**
  （手写的那张一定会与迁移表漂移，而漂移方向恰好是放宽禁令）
· 交付侧**另加一条本模块判据**：账上还没有"这一段被合成过"就不受理播放回报
  （`playback_report_before_synthesis`）—— 因为通用迁移表是"乐观"的，
  BFS 会给出 `generated → synthesized → queued` 这条**存在**的路，
  那等于让"客户端报了一句播放"顺手把"合成完成"也写进账（契约 §1 第一条禁令的反面）
· 重复 / 乱序 / 冒充一律**安静忽略** + 具名码，**不抛、不回退**已确立事实
```

### 2.5 播放事实**真的回账**（浏览器 → 皮套服务 → LG）

```text
浏览器（postlv2_speech_client.js）只报**真实状态变化**：
  收到真实音频      ⇒ synthesized（带 audioId）
  真的排上 Web Audio 时钟 ⇒ playing
  真的播完          ⇒ played（带客户端时钟区间 playedFrom/playedTo）
  被顶掉 / 停止     ⇒ cancelled（结局明确：没播完）
  出错 / 断连       ⇒ unknown（**结局不明**，不等于没播）
  ⇒ 失败一律吞掉：**不影响播放**，也不让页面抛错
```

为什么走 `POST /lg/playback`（而不是复用上游 WebSocket 入站处理器）：
那条路属于冻结的 patch 锚点；而这条回报是**单向、幂等、不需要回复**的。

### 2.6 交付视图接进 LG 上下文（契约 §2 `M11`）

`applyVoiceDeliveryView` 只改**视图**，且有三个"不"：不删生成记录 · 不猜 · 不改写。

```text
用户行 / 系统行            ⇒ 原样通过
助手行，交付账里没有这段    ⇒ 原样通过（CLI / 干跑 ⇒ 行为逐字不变）
助手行，整段播完            ⇒ 原样通过
助手行，只播了一部分        ⇒ **只留播出的部分**
助手行，一句都没播完        ⇒ **整行撤掉**
```

接在 `src/main.ts` 的 `recentLines` 上；交付账**在构造会话之前**建好并注入
（不留"先建后补"的中间态）。

```text
⇒ `beginTurn` 照原样把它当作 `userEvent` 往下传，**没有任何一处发出声音**
```

- **不是生产缺陷**：生产是 `latestConversationSequence(db) + 1`（`src/main.ts:1982`），

  一旦将来某处真的撞上序号，症状就会是"她答了，但用户那句话不在账上"——**难以察觉**。
- ⚠️ **本轮不去改那条生产语义**：`beginTurn` 属 M2.5 冻结面，加一条新失败路径会改变
  既有行为（且可能与并行会话在途的改动冲突）。**只登记**，建议与
  `L-M4-*` / 序号推导那一线一起裁定。

门：`postlv2:bridge:verify` = **PASS**（measured **135**；B14 形状 + B15 行为）。

### ④ 外壳投递 + **用户抢话真的掐得掉**（离线探针 **15/15**）

外壳调的是 `TTSTaskManager.speak(...)` —— 与 `conversation_utils.py` **同一个函数、

**写探针时抓到我自己的一个真缺陷**：`speak()` 只是把任务排进 `task_list` 就返回，
在它返回时记 `spoken` 记下的是"**排上了**"而不是"**说出去了**" ⇒ 改成
`gather(*task_list)` + 排空发送任务（与上游 `single_conversation.py:146` 同一条纪律）。

抢话那条：上游 `_handle_interrupt`（`interrupt-signal`，与已包装的那条**不是同一个**）
取消的是**那一轮**的任务，而插话**不属于任何一轮** ⇒ 不掐它，"用户优先"就只是口号。
现在记下正在说话的任务句柄并在抢话时作废；**作废单独计数**（记成"投递失败"会让
"她没说出来"与"用户不让她说完"永远分不清）。实测：慢引擎 20 块只出了 **1 块**
（生产真的停了），且**在途的那 1 块 1280 字节如实报出**而不是藏掉。

### ⑤ 名字的**同音类表由词典生成**（用户提出的现实难题）

实测：生产识别器把「苏沐薇」念成 `苏慕微` / `苏木威` / `苏慕威` / `喂苏木威` / `木威`——
**没有一条是字面的「苏沐薇」** ⇒ 字面量匹配在真实链路上等于没接。
手写同音表同样不行（会漏，且说不清覆盖多少）。改为**从本机词典生成**：
`vits-icefall-zh-aishell3/lexicon.txt`（sha256 `ab2e61d3…`，404 个音素序列 / 20897 字），
忽略声调 ⇒ `苏 = s u`（68 字）· `沐 = m u`（50 字）· `薇 = ^ uei`（194 字），
**冻结进内核**为纯数据。近音**至多一个音节**（`s↔sh` / `m↔n` / `零声母↔h`）——
三个音节各自都能偏会把「舒服」（舒 = `sh u`）拉成一次呼唤。

**覆盖率（8 份普通话语料，真实 ASR 读数）**：
```text
流式（呼唤真正用的那条路）8/8 = 100% · 离线 7/8 = 87.5% · judgementGaps = 0
```
唯一未命中是**两字名**（离线读成 `莫薇`），**刻意不收**：实测放宽会让
「**末位**」「莫为」「抹为」这些常用词变成呼唤 ⇒ 保持精确，并把该未命中**分类上报**。
同理，两字形态完全按同音类匹配会命中「**木卫二**」「**素未谋面**」⇒ 收紧为
"句首 + 其后只能是称呼语"，这两条留在负控里作为收紧的**理由**。

### ⑥ P3 **仍缺**的一条：检索完成 ⇒ 纠正段

计划 §3 的出口检查「**新证据在语音播放中到达**，旧余句失效，LG 检查后的纠正段实际播出」


## 2j. 第 20–22 轮：**用户真声**把两个缺陷逼出来了（合成语料测不到的那一类）

用户报「喊了他的名字好像没反应」。服务端日志显示她**确实回应了两次**（`spoken=2`、
`last_client` = 用户的连接、两次 `Queuing TTS task for: '''我在。'''`），因此问题在
"发出去了但没被听到"。逐条查下来是**两个独立原因**：

### ① 网页在"用户还在说话"时把她的音频**全部丢弃**

```js
case 'lg-audio-chunk': {
  if (aiState === 'interrupted' || aiState === 'listening') break;   // ← 插话恰好发生在这个时候
```
对**普通回复**这是对的（她不该压着用户说话），但**呼唤插话的意义就是发生在用户还在说的时候**
⇒ 每一块都被丢掉，用户什么都听不到。证据：服务端两次投递，页面**一个读数都没有**
（既没有播放回报，也没有新的同钟行）。

修法：判据从"时间窗口"改成"**包从哪来**"——
```text
requestId === 'interjection'   ⇒ 允许在 listening 时播放（程序既定的那条短句）
interrupted                    ⇒ 仍然一律丢弃（用户优先）
```
⚠️ 改动写进 `scripts/postlv2-expression-frontend.py`（**不是**直接改网页源码）：
那个补丁脚本每次从受审的上游提交重建 ⇒ 规则**可复现**，不会留在版本控制之外。

### ② 判据**根本没有命中用户的真声**（这才是"没反应"的另一半）

用户麦克风经过生产识别器吐出来的**真实读数**（逐条抄自日志）：

```text
麦克风 partial  父母微       ← 苏(s u) 被听成 父(f u)
麦克风 partial  父母问       （还没说完的截断形式）
正式输入        服木喂       ← 苏 被听成 服(f u)
正式输入        父母威       ← 又是 f u
正式输入        苏母卫 / 苏木威
```

近音类里当时只有 `s↔sh` / `m↔n` / `零声母↔h`，**没有 `f↔s`** ⇒ 这些读数**一条都不命中**。
**这是第一次由真人真声（而不是我的合成语料）发现的判据漏洞** —— 也正因如此，合成语料
才报了"覆盖率 8/8 满"（合成音里没有这个混淆）。修法：把 `f u` 作为**实测**近音加进
**生成器**并重新生成表（首音节近音类 109 → 335 字）；五条真声读数作为**独立的一组正控**
写进门里；代价面（`父母`/`服务`/`福尔摩斯` 必须沉默）同时钉住。

### ③ 两遍识别的分歧（真读数，非缺陷）

同一个发音：**流式**给 `父母微`，**正式**给 `苏木威`（更早一次是 `苏沐威，你在吗？`）。
而**呼唤判定走的是流式那一遍** ⇒ 它继承的是**更噪的那一遍**。两边现在都在类里，
但这个分歧本身是这条设计的真实性质，已收进 P2 的两遍读数面。

### ④ 打断：**第一次量到"真的省下了模型调用"**

```text
用户真打断 2 次 ⇒ cancel 三态 = requested 2 / stopped_before_model 1 / already_committed 1
```
此前**每一次**记录到的取消都是 `already_committed`（"太晚，省不下"）。这次两次里有**一次**
赶在模型调用之前 ⇒ 取消**真的**省下了那次调用。音频层两次都停了。
客户端的读数也如实：`firstSpeechStartMs 406 / segmentCount 1 / playedCount 0`
（"开始播了、没播完"）—— 与日志里 23:46:03.186 的 `handle_individual_interrupt` 一致。

我把 `client-timeline.jsonl` 里两行读数当成"用户刚才那一测"的 —— 它们的时间戳是
**23:08:38 / 23:09:55**，属于**更早的实例**：那个文件跨重启保留，而播放计数不保留。

### ⑥ 唤醒链路的**批量稳定性**（20 次）：20/20（计划 §3/§4 的"一批"那一档）

`npx tsx scripts/postlv2-live-wake-verify.ts --repeat 20`（**不含模型调用**：唤醒短句是
程序既定的 ⇒ 这是零 LLM 成本的批量读数）：

```text
passes 20/20 · passRate 1.0 · failedByCheck {}（**没有任何一条判据偶发失败**）
perRunInterjections [2,2,2,2,2,2,2,2,2,2,2,2,2,2,2,2,2,2,2,2]（每轮都收到 2 个音频块）
runsWithNoAudio 0
aggregate: started 1 → 20，总数 **20**，期望 20 ⇒ **恰好一次**（不是 0 次、也不是两遍）

```

⚠️ **第一次批量跑出的是 19/20**，红的是第 13 轮的「投递目标是这条连接」。查下去发现
**不是投递坏了，是我的读数有竞态**：音频一产出就发出去了，而 `last_client` 与 `spoken`
写在**排空之后**（最长 5 秒）⇒ "这一段早就收到了，而归属字段还写着上一次的连接"。
修法是把**归属**（投给谁）在**开始投递**时记，把**完成**（说完了）留给收尾 —— 拆成

实际开始投递的次数必须**等于轮数**（多一次 = 说了两遍，少一次 = 漏了）。

⚠️ **单次运行看不出这个** —— 它 19/20 的时候每一次单独跑都是绿的。

### 5.3 第 28 轮：P3 选项 B 落地到"差一个检索提供者"，以及**它为什么不是一个接线活**

用户裁定 **B（窄版"边听边查"）**。已实现并锁住（门 **B20**）：

```text
既定短句 "查到了。"          —— 不带任何检索结论（否则就是用短句绕过回复守卫）
触发复用 M5.5 的显式词形判定器 —— 不另发明触发词（两处授权实现迟早漂移）
时机判据（这条的全部价值）    —— 她在说 ⇒ 说；**她没在说 ⇒ 不说**（正式轮次马上会给内容）；
                              不知道 ⇒ **不说**（宁可漏一次，也不在错的时刻打断）
查到了但没有来源 id          —— **不说**（"查到了却说不出凭什么" ≠ 查到）
```

⚠️ **仍未接线，而且这是个裁定而不是漏了一行**：`main.ts` 还没提供 `prepareLookup`
⇒ 生产里 `lookupCapable = false` ⇒ **不会**发生提前查（如实报"能力缺席"，不假装查过）。
要接上，只有两条路，各有真实代价：

| 路线 | 做法 | 代价 |
|---|---|---|
| ① 直接调 web-search 适配器 | 在 `buildGateway` 里已构造好，拿来就用 | **变成第二个搜索入口** —— 绕过动作网关的授权/账本，而 M5.5 刻意把搜索集中在一处 |
| ② 走动作网关 | 复用同一套授权与账本 | 会为一次**推测性**检索写下一条动作记录 ⇒ 改变那本账的含义 |

⇒ 需要在这两条之间选一条（或者承认 B 就停在这里、把"提前查"判为不做）。

### 5.4 第 31 轮：**选项 ②（走动作网关）被一条不变量挡住了** —— 而且这是设计，不是 bug

把提前检索接进动作网关后，真链路探针第一次拿到了**具名结局**（不再是"什么都没发生"）：

```text
/lg/status → partial.prepare = {"prepared":8, ..., "lookup_failed":6,
                                "lookup_last_code":"action_attribution_evidence_missing"}
```

**根因**（`src/kernel/action/gateway.ts:229`，WP5-3）：

```text
动作事件需要**受信 initiator 证据**（ActionInvocationContext.initiatorEvidence）
提前检索发生在**轮次之前** ⇒ 没有因果上下文 ⇒ 没有受信证据
网关**失败关闭**，并且**明确拒绝**退回到 payload 里自报的 `requestedBy`：
    "不退回落 payload 的 requestedBy（那是自报）…那会让'谁发起的'重新变成猜测"
```

⇒ **选项 ② 在结构上做不到**：归因证据只存在于**轮次内部**，而"边听边查"按定义发生在轮次**之前**。
绕开它就是拆掉 M5.1-D01/ADR-042 那条硬不变量（"归因必须先于任何注入入口"）—— **不做**。

**三个可选方向（请择一）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 放弃提前检索** | 把"边听边查"判为不做，登记为一条未达 | §3 的出口检查保持未满足（如实分列） |
| **② 给它一个**具名的**归因豁免** | 新增一条裁定：这种"用户显式要求 + 只读 + 推测性"的检索按**某种具名归属**记录（例如 `system:pre_turn_lookup`） | 要动归因模型（ADR-042 层面），并有"豁免会不会被滥用"的新面 |
| **③ 把检索挪进轮次** | 不等 partial，改在**轮次开始后、回复生成前**做（那时有归因） | 就不再是"边听边查"了（用户说完才查，提前量几乎没了） |

### 5.5 第 31 轮：顺带查出来的**两处真缺陷**（都已修 + 已进门）

**① 桥的 stdout 就是协议通道 ⇒ 桥里 `logger.info` 写的诊断在生产上读不到。**
外壳的 reader 在 ready 之后会**丢弃**任何非协议行（`postlv2_vtuber_runtime.py` 的
两处 `if not self.ready: print(..., stderr)`）。表现：我据此**误判**"提前检索那个分支根本没跑"
—— 其实它跑了、只是**读数被扔掉**。现在结局**随 `PREPARE_RESULT.lookup` 回外壳**
（`/lg/status` 里分列 `lookup_found` / `lookup_not_found` / `lookup_rejected` / `lookup_failed` +
具名 `lookup_last_code`）。**桥的运行期读数只有两条合法出路：协议，或 stderr。**

**② 一次失败会永久废掉这次发音。** 去重的键在**发起前**就记下了（那是为了防"每条 partial 买一次"），
于是网关抛错之后，这条发音后面每一条 partial 全被去重吃掉 ⇒ **一次瞬时失败 = 整个功能静默失效**。
现在**失败/被拒时把键还回**（`releaseLookupFor`），重试仍由**新的 partial** 驱动（不会变成无限重试）。
门 **B22**（正控：失败后无短句；负控/恢复：同键再送 ⇒ 真的重试且成功说了那一句）。

|---|---|---|
| 呼唤回应 | partial 命中她的名字 | **不需要她说**（她本来就还没开口）⇒ 最容易可达 ✓（真链路已验） |
| 边听边查（提醒） | 检索查到 **且她正在说** | 需要**她正在说** ⇒ 只有在"用户在她**回上一轮**的时候又开了口"这种**重叠**情形下才成立 |
| 中途纠正 | 用户说"不对"**且她正在说** | 同上（重叠）——真链路已验，走的是用户更正那条触发 |

⚠️ **这条推论的证据**：我自己制造的"重叠"（探针先让她说、**在她出声之后**才喂检索语音）
两次都成功；而**不制造重叠**时（`LG_LOOKUP_PRELUDE=NONE`）读数一律是
`lookup_found` 而**没有插话** —— 那**不是**缺陷，是判据（"她没在说就不说"）。

⇒ **可读的结论**：提醒与纠正**都依赖"重叠说话"**。若真实使用中用户总是等她说完了再开口
（很自然，因为要等 10–20 秒），那么这两条**几乎不会触发** —— 而原因与 §3 未达标**同源**
（生成太慢，把"她还在说"的窗口挤没了）。

⚠️ 这一条是**推导**，不是新读数：它由"探针在有/无重叠下的两组成败"与 5.11 的时延结构共同支撑。
若要把它变成读数，需要真实对话里统计"她说话期间用户开口"的次数（未做）。

### 3.1 一处判据收紧（不是放宽）
`B9` 原来断言"`turn-bridge.ts` 的代码里不出现 `'played'` 这个词"。P1 之后这条**必然**翻红，

要守的性质是"`delivery` 这个**交付真相字段**的闭集里没有 `played`"。已改成：

```text
DELIVERY_TRUTH_STATES = ['generated', 'rejected', 'failed']   // 不含 played

```

**性质没放宽，量具换成了量对的东西**（与 §6 第 2 条、第 9 条同一条纪律）。

### 3.2 第 2 轮追加的一处（T11）：悬着的交付态**必须有结局**

客户端不一定来得及为每个片段发 `cancelled`（浏览器被顶掉、页面切走、回报被丢）。
不管它，账上会留下永远停在 `queued`/`playing` 的片段，§2 `M11` 就分不清"确定没播"与"不知道播没播"。

现在由**新轮次顶掉上一轮**这件事本身当证据（`VoiceDeliveryLedger.markSuperseded`，在 `sessionHost.runTurn`
**进 `send()` 之前**调用）：

```text
queued（还没开播）        ⇒ cancelled   （确定没播）
playing / synthesized     ⇒ unknown     （**已经发出去了**，不知道声卡那一刻播到哪 ⇒ 不许说成确定没播）
played / cancelled / unknown（终态）     ⇒ 一个字不动
```

读数（T11）：`{ #0:played, #1:playing, #2:queued }` ⇒ `{ #0:played, #1:unknown, #2:cancelled }`；
顶掉之后的"其实播完了"被 `<code>playback_report_stale_or_duplicate</code>` 拒（终态不可改写）；
没有交付账的 host 不受影响（`reportPlayback` 仍 `undefined`，`runTurn` 照常）。

### 5.2 第 27 轮追加：**时序读数的锚点不同**（一个会误导人的坑，已钉在代码里）


**两个数字不能相减、不能比较**：前者是端到端（含 LLM 生成 + 合成排队），后者是

⇒ 已在客户端代码里写死这条警告。**要拿到浏览器侧的端到端数字**，锚点必须提前到
**用户提交输入**的那一刻（页面自己知道：它发 `text-input` / VAD 结束的时刻）——
**这一条尚未实现**，在实现前浏览器那一列只能当"播放排程延迟"读。

同样地，`postlv2-timing-probe.ts` 的"首反馈"（`lg-expression-turn` 到达，实测 2–5 ms）
**不是"她出声了"**，只是"新的一轮开始了"。三条阈值已改成**由脚本自己判**（含
`n < 19` 时一律 `NOT ENOUGH SAMPLES`，不judge PASS），免得每次靠人眼看数字。

# Lv4.5 · P2 前置：两遍识别读数（流式 partial + 正式 final）

日期：2026-10-04。载体：[`Lv4.5-Lean-Execution-Plan-2026-10-04.md`](Lv4.5-Lean-Execution-Plan-2026-10-04.md) §2「两个实现选择」第 1 条：

> 「先用现有 Zipformer 验证临时 partial 接口，SenseVoice 仍负责正式 final；这是增加计算支路的探针，
> 鉴于用户要求两遍识别作备用，**不默认启用为正式配置**。若要采用单一流式模型，必须证明准确率和成本再切换。」

本文件是**那个探针**的读数。它**不**回答"流式能不能用"（那是没有边界的问题），
只回答三个可判定的问题：**partial 早不早 / 变不变** · **流式 final 能不能替代离线 final** · **多花多少毫秒**。

探针：`scripts/postlv2-partial-probe.py`（可复跑；判据在 `pnpm postlv2:asr:verify` 的 A7–A9）。

## 3. 这三个读数说明什么（逐条）

```text
① partial **真的有**，而且早：
   5 份样本全部 ≥6 次文本变化；首个非空 partial 在 500–1500 ms。
   ⇒ "边听边准备"有输入，不需要第二套识别模型（计划 §2 第 1 条的第一句成立）。

② 但 partial **不稳定**，而且流式 final **不能替代**离线 final：
   stableFraction = 0.918 … 1.000 —— 文本最后一次变化发生在音频的 **92%–100%**。
   换句话说：**"稳定"几乎等于"说完了"** ⇒ 提前准备只能建立在**可能被改写**的前缀上。
   这正是"两遍识别"能成立的理由，也是它必须**只读、可撤回**的理由
   （计划 §4.2「一次只准备一份有效候选；revision 改变就失效」）。

③ 两条链的 final **不是同一份文本**：
   真人样本上几乎一致（1.0 / 1.0 / 0.846，差异是标点与数字写法）；
   **本项目音色样本上分歧很大（0.5625 / 0.4571）**。
   ⇒ 不能"用流式 final 顶掉离线 final"（那会换掉她现在实际听到的文本）；
     也不能把流式 final 当"更早的同一份文本"去补上下文。
```

**结论（只到"能不能继续"这一层）**：P2 的流式输入路线**可行**，但要按"**只读准备 + 可撤回**"设计；
不采用单一流式模型（准确率与成本都还没有支撑切换的证据）。

## 4. 本读数**不**主张什么（逐条）

```text
· 不构成准确率结论：2.1 的样本是**合成音**，2.2 是**厂商测试音频**，都不是真人麦克风、也不是本项目用户的声音。
· 不主张阈值：stableFraction / 相似度都是**如实记录**。A7 的判据只要求"有 partial 且首个明显早于结束"，
  A8/A9 **没有**失败条件（没有真值就无法设阈值 —— 设了就是拿感觉当真值）。
· 2.1 的 0.46/0.56 反映的是"两条链在**本项目音色**上不一致"，**不是**"谁更准"；
  本文件没有真值，所以两种解释都不给。
· 浏览器里的实际 partial/final 仍未验：本探针是 Python 直喂；网页那一层属联合测试（计划 §3 第一步 ASR 行）。
· 真人麦克风、噪声/小声、口音、数字与人名等独立语料：**全部 NOT RUN**。
· 不主张许可已核：模型权重与仓库 LICENSE 是两份东西（与 `postlv2:asr:verify` 既有边界同一条）。
```

## 5. 落到 P2 的设计约束（本读数直接约束下一步）

```text
① 临时准备只能建立在"会被改写"的前缀上 ⇒ 候选必须带 revision，且**改口即失效**
   （计划 §1「边听边查」/「旧任务不串话」两条都是这条的直接推论）。
② 不能为了"早"而放弃 final：正式用户轮次仍然只用**离线 final**（SenseVoice），
   流式 final 不得进入正式用户消息，也不得写记忆（计划 §4.1/§4.5）。
③ 代价可接受但**不是零**：每轮多 0.26–0.61 s CPU；与其他组件共用时按计划 §4.6 的口径安排测试时段。
④ 不需要引入第二个流式模型或专用 KWS 来完成"有 partial"这件事（计划 §1 的"安装组件不作为开工前置"成立）。
```

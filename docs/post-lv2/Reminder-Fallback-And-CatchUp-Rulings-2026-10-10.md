# 提醒的改投、重复与补说：用户裁定（2026-10-10）

用户就"提醒送达"提了一条设计变更，并逐条给出裁定。本文是**裁定载体**（实现方案另出 ADR）。
⚠️ 它与 [ADR-124](docs/adr/ADR-124-chat-channel-and-reminder-routing.md) `D2` 的"**不静默改投**"**正面冲突** ——
本变更的实质是：**允许改投**，但必须**说明原因**；并新增"重复直到回应"与"下次对话补说"两条行为。

## 五条裁定（逐字转写为规范语句）

```text
R1  "不可用"的定义 = **由于任何原因，用户没能接收到本应接收到的信息**：
      · 通道没开          ⇒ 不可用
      · 发送失败          ⇒ 不可用
      · 页面没开          ⇒ 不可用（用户根本看不到页面，自然算失败）
    ⇒ 判据是"**实际收得到吗**"，不是"程序层面报告成功了吗"。
       ⚠️ 这与现有 `api_accepted`（平台接受 ≠ 送达，ADR-110 `D08`）同向，但比它更严：
          它要求判到"用户真的能看到"。
R2  默认出口 = **QQ 私聊**；未指定即按默认，指定了即按指定。
    **明确指定的通道不可用时，适用同一规则**：**改投 + 说明**（不区分默认/指定）。
R3a 若用户**没有**要求自己必须做出反应（含明确说"不用管我有没有回复"）
    ⇒ 只要**程序层面确认提醒成功**，就**不再二次提醒**。
R3b 若用户**明确要求**该提醒重要 / 要求自己回应（例："这个提醒十分重要"、"提醒后我要怎么怎么样"）
    ⇒ **以 60 秒/条的频率重复发送，直到用户回复**；**用户一旦回复即销账**
       （**不要求**用户明确说"收到"——任何回复都算）。
R4  上述**所有失败情形都适用**，**包括跨重启**（不是"只在本进程存活期间"）。
R5  一次错过了多个事件 ⇒ **逐条**回复（不合并成一句）。
```

## 与现状的差距（都是行号级事实）

| 裁定 | 现状 | 落点 |
|---|---|---|
| R1/R2 改投 + 说明 | **明确拒绝**：`reminder-turn.ts:93` `reminder_delivery_unavailable`；另有 `reminder_channel_unsupported` | 改投与"说明原因"的正文；需要"可用通道"读数与失败判据 |
| R1 "页面没开" 也算失败 | 现有可用通道读数只看**连接**（皮套页面未连接时外壳只报本次投递失败，不补发——见 ADR-124 记录） | 要新增/收紧"实际可见"判据（页面未连接 ⇒ 不可用） |
| R3a 确认成功即不再提醒 | 已接近（`api_accepted` + 读侧 `excludeAttempted()` 防重复交付） | 需明确"确认成功"的判据（R1 收紧后**不能再等于** `api_accepted`） |
| R3b 重要提醒 60s/条重复直到回复 | **没有**这条行为 | 需要：重复状态（`notification_occurrences` / 新列或 `defer`）、60s 调度、**回复即销账**的 settling 判据 |
| R4 跨重启 | 有幂等键与状态机（迁移 `0014`/`0015`/`0016`），但"跨重启补说"没有 | 需要持久化的"错过"记录 + 重启后的收敛 |
| R5 逐条 | 没有合并逻辑 | 逐条投递的实现（注意频率与额度闸） |

## R6（新增要求）：提醒能力**入口无关**

```text
用户原话要求：提醒功能的开关**无论是从哪个路径启动，都应该保持开启**。
现状（行号级）：src/main.ts:4213 的 enabled 需要三个条件同时成立
    flags.qqProactiveMode === 'on'
 && flags.entryScopedConversations
 && reminderRefreshHook !== undefined          ← 只在 coexist 那条分支被赋值（main.ts:454）
⇒ 用 `src/main.ts --bridge --qq-private`（旧 QQ 桥入口）启动时**没有任何提醒出口**
  ⇒ reminder-turn.ts:93 返回 reminder_delivery_unavailable（实测 2026-10-10 17:22/17:23 两条模板）。
⇒ R6 的实质：把"提醒可用"从**入口接线**里解出来 —— 让任一路径启动都装上出口与 timer。
```

## 五问的裁定（2026-10-10 已全部关闭，无需再问）

```text
Q1  60 秒重复的**上限 = 10 次**。
Q2  "不可用"的判据分两档（都不要求已读回执）：
      · **皮套**：判到"页面是否连接"这一步即可（页面没开 ⇒ 不可用）；
      · **QQ**：判到"平台接受 / 适配器接受"即可（与 ADR-110 `D08` 一致）。
Q3  **送达记账不看方法/过程**：只要**成功送达**，该提醒即记 **"已送达"**（改投成功同样算送达）。
Q4  确认：改投成功 + 程序确认 ⇒ 按 R3a **不再二次提醒**；
    **但前提是这一条提醒属于 R3a 型** —— 而 **R3a / R3b 的判定必须由模型（LLM）做，不是字面**：
    ⚠️ **不得因为原话里出现某几个词就判成某一项**（这是硬要求；判据要落在语义上，
       并且要有负控：例如"不用管我有没有回复"≠"十分重要"）；
Q5  **逐条补说**：**不受时间约束、不受额度约束**；但**一次最多补说 10 条**；
    **超过 10 条** ⇒ 在回复末尾加一句"**未补说的事件还没完**"并**询问是否继续**。
```

## 实现切片（建议顺序，都不改生成语义之外的裁定面）

```text
S0  R6：提醒出口与 timer 与**入口解耦**（任一启动路径都装上）—— 先做，因为它是 R1–R5 的前提
    （否则旧桥入口下永远走不到"改投"那条分支）
S1  A2（与提醒无关，独立小改）：响应真相守卫加"用户那一轮确实在要求记住"的闸 + 负控
    —— 见 docs/post-lv2/Template-Takeover-Of-Replies-2026-10-10.md
S2  R1 + R2：改投 + 说明（可用性按 Q2 两档；"页面没开"算失败）
S3  R3a/R3b：**由模型**判 3a/3b（不得字面判）→ 3a 确认即止；3b 60s × 上限 10 次、任何回复即销账
S4  R4 + R5：跨重启的"错过"账（Q3 的送达记账）+ 逐条补说（≤10 条，超了要问）
⚠️ 每一片都要：typecheck + 相关门（含**负控**）+ **停机窗口** `m4.5:ci`。
```

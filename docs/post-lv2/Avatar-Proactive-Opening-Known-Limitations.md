## L-APO-01 · 限流状态是**内存**的 ⇒ 重启可以绕过

| 项 | 内容 |
|---|---|
| **主张** | 冷却（`openingCooldownMs`）· 日额度（`maxOpeningsPerDay`）· 机会键幂等，三者的状态都在**进程内存**里 |
| **后果** | **重启后全部归零** ⇒ 重启可绕过冷却与日额度；同一小时的机会会重来一次 |
| **机器可读标识** | `IN_MEMORY_OPENING_STATE_LIMITATION` = `in_memory_opening_state_resets_on_restart: 重启后冷却/日额度/机会键幂等全部归零 ⇒ 重启可绕过限流` |
| **★ 实测读数** | WP5b-0 探针：同一机会键、同一 `now` —— 实例 A（记过一次）⇒ `opening_opportunity_already_handled`；**全新实例 B ⇒ `ELIGIBLE`** |
| **为什么现在接受** | 用户 2026-10-11 裁定选 **A**（先用内存）。理由：零迁移、立刻能接线；而此刻**没有任何东西会发这条报文**，她也没被激活 |
| **怎么关闭它** | 落库：需要一条迁移（草案是 `opening_occurrences`，`occurrence_key` 主键唯一占用＝幂等、`opened_at`＝冷却与日额度）。**迁移需用户单独批准**（先例 `0014`–`0017`） |
| **残余**：本局限**不**主张"限流坏了" —— 在**不重启**的前提下三个闸都是真的；它主张的是"**重启**是绕过路径" |

## L-APO-02 · 全类总闸的读数**来自别处**，本通道不自己算

| 项 | 内容 |
|---|---|
| **主张** | `maxProactiveMessagesPerDay`（全类总闸）的已用量由**调用方**从通知那一侧读了传进来 |
| **后果** | 若调用方传错（例如漏算提醒），总闸会失真 —— 而本模块**无法**发现 |
| **理由** | care / 提醒的账在 `notification_*` 那几张表；让开口模块自己去读库会**越过 kernel 的依赖方向**（kernel 不碰 SQL） |
| **怎么核对** | 接线后由装配层负责读数；门里应有一条"总闸读数被喂对"的判据（WP6） |

## L-APO-05 · 只能用 **2 句 / 60 字**（`D02` = 先 (a) 起步）

| 项 | 内容 |
|---|---|
| **主张** | 主动开口走既有插话通道，因此受 `CHARACTER_OUTPUT_LIMITS`（2 句 / 60 字符） |
| **后果** | 想说一整段（>60 字）**做不到**；超限一律 `output_too_long`（程序**不截断**） |
| **测得方式** | 探针里有 61 字 ⇒ `output_too_long` 的读数 |
| **怎么关闭它** | `D02` 的 (b) 形态（正式轮次 + observation 事件 + `replyToEventId`），**需另开 ADR** |

## L-APO-08 · `opening_user_is_speaking` 在**报文路径下不可达**（防御性判据）

| 项 | 内容 |
|---|---|
| **发现时机** | WP5b 侦察（把端口签名从"装配层喂读数"改成"桥喂自己的读数"时暴露出来的） |
| **主张** | 预检里那条 `opening_user_is_speaking`（"用户正在说 ⇒ 拒"）**在报文路径下永远不会触发** |
| **为什么** | 桥**没有**独立的 VAD 读数 —— VAD 在 Python 外壳里。桥只能采用**报文的前提**："外壳空闲"⇒ `userSpeaking` 恒为 `false`（见 `TurnBridgeHost.openingOpportunity` 的注释） |
| **它不是废码** | 它是**防御性**的：
```text
① 它挡的是"报文与事实不一致"的情况 —— 若将来外壳在 partial 期间也发机会报文，
   这条判据（连同 `D07` 的仲裁让位）就是第二道闸
② 它是**唯一**能表达"用户在说话就不说"的地方：仲裁那条只在**出站**前判，
   而这一条在**调模型之前**判 —— 那一次模型调用就省下来了
```
| **★ 与"空满足"的区别** | 这是**刻意留的防线且已知不可达**，不是"因对象不存在而通过"（`INV-CI` 组的那种"空满足"）。⇒ 已登记，**不当成已通过的能力** |
| **怎么让它可达** | 需要一条**独立的在场读数**（例如外壳在 partial 期间也报一次"我这边有人声"）。那是**新能力**，不在本 ADR 内 |

## L-APO-09 · 端口签名在 WP5a → WP5b 之间被**修正过一次**

| 项 | 内容 |
|---|---|
| **主张** | WP5a 定的 `openingOpportunity?(input: {requestId, entry, idleMs})` **无法正确实现** |
| **为什么** | 它缺三个**只有桥才有**的读数：`userSpeaking`（`submittedTurns` 推断）、`turnRevision`（同上）、`hasLiveClient`（`outputSink` 私有） |
| **若没发现会怎样** | 装配层只能去**猜**"谁在说话"与"有没有人在听" ⇒ 那就是 `D07` 的**第二次实现**，以及"生成完才发现没人听"的浪费 |
| **修法** | 端口改成由**桥喂自己的读数**、装配层喂**世界读数**（策略 / 库 / 依据 / 状态）。`turn-bridge.ts` 新增两个只读访问器 `outputCapable` / `submittedTurnRevision` |
| **读数** | `pnpm typecheck` 0 错 · `pnpm postlv2:bridge:verify` **PASS · measured_count 290**（未退化） |

## L-APO-10 · 整条链**一次都没真跑过**

| 项 | 内容 |
|---|---|
| **主张** | 从外壳到出站，**每一段**都有实现与离线读数；但**端到端一次都没跑过** |
| **缺的是哪几段真实读数** | ① 没有真实外壳连接发过 `PROACTIVE_OPPORTUNITY` ② 没有真实模型调用（适配器**从未被调过**，探针用的是假端口）③ 没有真实播放侧收到过 `CHARACTER_OUTPUT` ④ 没有真实 `OPPORTUNITY_RESULT` 落过诊断面 |
| **已有的** | `typecheck` 0 · `bridge:verify` PASS(290) · `transport:verify` PASS(78) · `coexist:verify` EXIT 0 · 四个探针共 **19+28+18+10 = 75 项判据** |
| **★ 结论** | **不得**把探针读数读成"她能主动开口了"。探针证明的是"判据层在按设计工作" |
| **怎么关闭它** | WP7（真链路 smoke：生产副本 + 真外壳）—— 但它**卡在** `L-APO-11` 的裁定上 |

## L-APO-11 · 触发器的可用性**挂在一个用户设置上**（选项 A 的代价）

| 项 | 内容 |
|---|---|
| **主张** | 本实现把"外壳自带的主动搭话"复用成了机会上报通道 ⇒ **前端那个开关必须开着**，功能才会被触发 |
| **后果** | 那个开关**关掉时功能静默失效** —— 而且**没有任何读数会告诉你**（没有报文 = 没有报文，不是错误） |
| **与 ADR 的关系** | `D12` ① 逐字要求"**先关掉**它"，§6 ⑤ 与 §8 WP2 把它升成硬前置 ⇒ **本实现与冻结的 `D12` ① 相反** |
| **⚠️ 这是待裁定项** | ~~见 [`Ruling-Request-D12`](Avatar-Proactive-Opening-Ruling-Request-D12.md)：A（现状）/ B（严格照冻结原案）/ C（两件都做，建议）~~ |
| **⏩ 2026-10-11 已裁定：C ⇒ 本条**部分**失效** | 裁定 C 的第 ② 半（**外壳自己的空闲上报器**）已实现：`IDLE_REPORT_FLOOR_SEC = 180` / `IDLE_REPORT_TICK_SEC = 30`，起点在 `BRIDGE.start()` 之后，幂等启动且自终止。<br>⇒ **开关关着也工作** ⇒ "静默失效"这一半**不再成立**。<br>⚠️ 仍然成立的残余：**报告频率**由两处共同决定 —— 外壳那份是我们定的（3 分钟档），前端那份由 `idleSecondsToSpeak` 决定 |

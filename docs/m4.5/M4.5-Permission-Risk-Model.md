# M4.5 Permission / Risk Model —— 意图 ≠ 权限

- **阶段**：M4.5（WP-04）
- **相关 ADR**：ADR-030（唯一入口）、ADR-031（登记）、ADR-032（目标确定性）
- **代码**：`src/kernel/action/policy.ts`、`src/kernel/app/flags.ts`
- **守着它的测试**：`m4.5:test` §3；`m4.5:verify` §2（每一条拒绝都有适配器调用计数为 0 的阴性控制）

---

## 1. 风险等级（§25）

```text
R0 = pure read                  什么都不会变
R1 = local reversible write     本地、可撤销（沙箱内写文件）
R2 = external reversible action 对外、可撤销（发消息、调 HTTP）
R3 = destructive / public / costly  删除、支付、公开发布
```

**M4.5 实际运行 R0 / R1**。R2 / R3 的**定义**已经存在（这样以后登记一个能力时
"忘了想风险"不可能发生），但没有能力声明它们 —— 因此它们无法被执行。

副作用等级与风险下限是绑定的（登记口强制）：

```text
none        → 至少 R0
read        → 至少 R0
write       → 至少 R1
destructive → 必须 R3
```

声明低于下限 = 绕过风险上限，登记口直接拒绝。

## 2. 判定顺序（`evaluateActionPolicy`，纯函数）

```text
① capability_registered   未登记 → capability_not_registered（unsupported）
② operation_declared      未声明 → unknown_operation（unsupported）
③ permissions_granted     缺任一权限 → missing_permission
④ risk_within_limit       operation.riskLevel > 上限 → risk_exceeds_limit
⑤ dry_run                 干跑 + 有副作用 → dry_run_no_side_effect
⑥ target_in_scope         越界 → target_out_of_scope
⑦ target_certain          见 §3 → target_uncertain / target_ambiguous / target_not_found
⑧ idempotency_key         required 却缺键 → idempotency_key_required
→ allowed
```

顺序是刻意的：越靠前越"结构性"（能力存不存在），越靠后越"情境性"
（目标够不够确定）。**① 与 ② 在任何 IO 之前** —— 未登记能力连
"沙箱里有什么"都不会去读。

每一条判定都留痕（`decision.checks`），并且**进账本** ——
"为什么允许"必须能事后回答（§59）。

## 3. 目标确定性闸（INV-M45-03）

```text
有副作用（write / destructive）：
    confidence ∉ {exact, strong}  → 拒绝（target_uncertain → status=ambiguous）
读（read）：
    confidence = none  → target_not_found（"不存在"）
    confidence = weak  → target_ambiguous（"不许挑一个"）
无副作用（none）：
    不设门槛（echo 这类不动世界的操作不该被目标闸挡住）
```

两个理由：

1. **读与写的不存在性语义相反**：读要求"必须已经存在"，写允许"要变成的样子"。
2. **不确定性对两者一致**：只要有歧义，就只能失败，不能猜。

---

## 4. 干跑（`--test` / `--dry-run`）

干跑下任何副作用都被禁止（`dry_run_no_side_effect`），
而且**动作路径整段不执行**（`beginTurn` 里跳过）—— 两层保护，
因为干跑的承诺是"对她等于没发生过"，而写一个文件**真的发生了**。

## 5. 配置（`src/kernel/app/flags.ts`）

| 变量 | 缺省 | 说明 |
|---|---|---|
| `CHARACTER_ACTION_ENABLED` | `1`（on） | 动作总开关。**必须被 `main.ts` 真的消费**（有回归锁） |
| `CHARACTER_ACTION_MAX_RISK` | `R1` | 风险上限。拼错/越界 → 退回缺省并告警（**不是**"无限制"） |
| `ACTION_SANDBOX_ROOT` | `data/action-sandbox` | 沙箱根（可以指向临时目录；"必须在根内"不可配置） |

启动日志里会打印 `action(R1)`，于是"动作到底接没接线"一眼可见。

## 6. 拒绝与"做不到"的区别（用户可见）

| 情形 | 状态 | 用户看到的 |
|---|---|---|
| 目标不存在（读） | `not_found` | "我没找到你说的那个，什么都没改" |
| 目标不唯一 / 证据不足 | `ambiguous` | "不确定你指的是哪一个，什么都没动" |
| 越界 / 缺权限 / 超风险上限 | `rejected` | "这次的操作没有被允许执行（原因），什么都没发生" |
| 适配器执行中失败 | `failed` | "这次执行失败了，什么都没完成" |
| 超时 | `timeout` | "没有等到结果，我不能确定它完成了没有" |

这张表就是 `claim-guard.ts` 的如实句分派依据 —— 拒绝与不存在**不能**
被同一句话糊在一起，因为用户接下来要采取的行动完全不同。

# M4.5 Audit / Trace —— 她做过什么，能不能查回来

- **阶段**：M4.5（WP-07 / §20 / §21 / §31 / §32）
- **相关 ADR**：ADR-034（账本与记忆分离）、ADR-035（量具可信）
- **代码**：`src/kernel/action/execution-ledger.ts`、`execution-record.ts`、`audit-invariants.ts`、`admin.ts`、`src/infrastructure/action/action-ledger-store.ts`、迁移 0006
- **守着它的测试**：`m4.5:test` §7 / §9；`m4.5:verify` §5 §7；`m4.5:measurement:verify`；`m4.5:audit`；`m4.5:smoke:live` S8

## 1. 账本是 append-only 的事件流

```text
character_action_events(
  action_id, sequence, character_id, trace_id, event_type, status,
  capability, operation, idempotency_key, payload jsonb, schema_version, created_at
)
```

九个事件类型（§44）：

```text
ACTION_REQUESTED → ACTION_TARGET_RESOLVED → ACTION_AUTHORIZED
  → ACTION_STARTED → ACTION_SUCCEEDED / ACTION_FAILED / ACTION_PARTIAL / ACTION_CANCELLED
（拒绝路径：… → ACTION_REJECTED）
```

`ExecutionRecord`（§19）是这些事件**折叠出来的视图**，不是表里的一行。
端口上只有具名写入（九个方法），**没有 update / delete**。

`status` 只在终态行非空。这一列的存在有一个具体目的：
**按状态过滤必须能发生在 SQL 里**（见 `M4.5-Measurement-Invariants.md`）。

`character_action_sequence_counters` 是**独立**的序号计数器 ——
刻意不复用对话/领域事件那个（它是 M2.5/M3 的角色级全序依据，
让动作去推进它会让既有回归断言依赖的分布改变）。

## 2. traceId 贯穿（§20）

```text
用户轮次 → ActionRequest → Policy → Execution → ActionResult → Ledger → Response
```

- `character_traces.action_ids`（迁移 0006 新增列）：从 trace 侧看"这一轮她做了什么"
- `character_action_events.trace_id`（有索引）：从动作侧看"这次属于哪一轮"

两个方向都能走通，因此"trace 断链"（STOP-05）是一条**机器可检查**的性质：
`m4.5:verify` §5.9 断言每个 `ACTION_REQUESTED` 都早于同 action 的 `ACTION_STARTED`。

## 3. 审计不变量（§32）

`checkActionAuditInvariants(records)` —— **CLI 与门共用这一份实现**
（否则"`action:audit` 说没问题"只说明其中一份没问题）：

| 不变量 | 内容 |
|---|---|
| `executed_action_has_result` | 执行过（STARTED）→ 必须有终态（finishedAt） |
| `result_has_trace_id` | 有终态结果 → 必须有 traceId |
| `success_implies_executed` | `status=success` → 必须真的执行过（**幂等重放例外**，见下） |
| `side_effect_requires_certain_target` | 声明了 write/destructive 且成功 → 目标必须 exact/strong |
| `failure_carries_code` | failed / rejected / not_found / ambiguous / timeout → 必须有归一失败码 |
| `replay_only_of_success` | 幂等重放只能出现在 success / partial 上 |

两条判据是刻意的：

- **副作用等级用"声明的" `sideEffect`，不用适配器自报的 `effect.kind`**。
  否则一个写能力只要返回 `{kind:'no_change'}` 就能绕过
  "有副作用必须有确定目标"（fail-closed 的反面）。
- **幂等重放必须有名有姓**：`success && !executed` 只在
  `idempotentReplay === true` 时被豁免。例外必须有名字，
  否则它就不是例外而是漏洞。

## 4. 最小 Inspector（§31）

```bash
pnpm action:list [--status <状态>] [--capability <id>] [--limit N]
pnpm action:show <actionId>
pnpm action:trace <traceId>
pnpm action:audit [--limit N]
```

也可以直接 `tsx src/main.ts action list …`（两种写法共用同一个解析器）。

全部**只读**，并且**不要求模型连通性**（`src/invocation.ts`）——
"她到底做了什么"最需要被查的时候，常常正是模型服务抖动的时候。

`action:list` 的行格式是**给机器读的**（L0 量具要解析它）：

```text
  · act:<uuid>  status=success  executed=true  capability=sandbox.file.write  op=write
    target=sandbox_file:hello.txt  confidence=exact  at=2026/9/17 14:17:11
```

每行**恰好**一个 `act:` id 与一个 `status=` 字段 —— 不允许把状态混进正文描述里。

`--status` 的取值受白名单限制：未知状态**报错并打印用法**，
绝不静默返回全部（那正是"函数名叫 active、实际量全部"的另一种形状）。

## 5. 七问可答（§59）

| 问题 | 答案来自 |
|---|---|
| 做的是什么？ | `capability.operation` |
| 目标是谁？ | `target.canonicalId` / `confidence` / `evidence` |
| 为什么允许？ | `decision.checks`（逐条判定留痕，落库） |
| 哪个能力执行？ | `capability@version`（登记表） |
| 什么时候执行？ | `timestamps.requested / started / finished` |
| 结果如何？ | `status` / `executed` / `effect` / `progress` |
| 证据在哪里？ | `evidence` + `traceId` |

`pnpm m4.5:audit` 用**生产同一套渲染器**输出一份抽样清单，
并对每一条断言这七问都能答 —— 数字之外，那份清单本身要读得通。

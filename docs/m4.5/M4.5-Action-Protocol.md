# M4.5 Action Protocol —— 请求、目标、结果、失败

- **阶段**：M4.5（WP-02 / WP-09 / WP-10）
- **相关 ADR**：ADR-030（唯一入口）、ADR-032（目标确定性）、ADR-033（执行真相）
- **代码**：`src/kernel/action/action-request.ts`、`action-result.ts`、`target-resolver.ts`、`errors.ts`
- **守着它的测试**：`m4.5:test` §1 / §3 / §4 / §6；`m4.5:verify` §2

## 1. 一份请求（`ActionRequest`）

```ts
interface ActionRequest {
  actionId: string          // act:<uuid>，执行之前就分配
  traceId: string           // 与这一轮对话共用同一个 trace
  capability: string        // 必须已在 CapabilityRegistry 登记
  operation: string
  requestedBy: { kind: 'user' | 'character' | 'system'; id?: string }
  target?: ActionTarget     // 可以缺省 → 由 TargetResolver 解析
  arguments: Record<string, unknown>
  sideEffect: 'none' | 'read' | 'write' | 'destructive'
  idempotencyKey?: string
  createdAt: timestamp
}
```

构造时只做**最小必要校验**（空能力名 / 空操作名 / 非法副作用等级 → 抛错）。
更细的判定（能力存不存在、目标够不够确定、权限够不够）留给 Gateway 与 Policy ——
它们的结论要**进账本**，在构造处抛错就什么都不会被记下来。

**谁产生请求**（M4.5 的 D-A 决定）：规则式的意图检测器
（`intent-detector.ts`）。**LLM 永不决定执行**。协议本身不区分 requester，
因此以后要让模型提议动作（`requestedBy.kind = 'character'`）不需要改这一层。

## 2. 目标（`ActionTarget`）与确定等级

```ts
type TargetConfidence = 'exact' | 'strong' | 'weak' | 'none'

interface ActionTarget {
  type: string                  // sandbox_file / （未来）message_recipient …
  canonicalId?: string          // 沙箱内就是相对路径
  displayName?: string
  confidence: TargetConfidence
  evidence?: TargetEvidence[]
}
```

五步梯子（`resolveActionTarget`，纯函数）：

| 步 | 条件 | 结果 |
|---|---|---|
| ① | 请求里已带明确目标 | `exact` |
| ② | 沙箱内**精确相对路径**存在 | `exact` |
| ③ | 唯一 basename **且** 用户词面命中**且**目录一致 | `strong` |
| ④ | 多命中 / 词面不符 / 目录不符 | `weak`（带候选） |
| ⑤ | 无命中（读） | `none` |

写操作有一条**存在性例外**：`allowMissing` 时"尚不存在的相对路径"仍是 `exact` ——
"创建 hello.txt"的那一刻它当然还不存在。读没有这个例外（→ `not_found`）。

第 ③ 步的三个条件是 D1 的修复形状：

```text
唯一候选 ≠ 相关（M4 的 D1：候选只有一条 → 删错了）
用户说的词必须真的出现在那条路径上
用户说的目录（若说了）必须就是候选所在的目录
```

**越界不是"找不到"**：绝对路径 / 盘符 / `..` / NUL 在任何 IO **之前**就被判为
`scope_violation`（`confidence: exact` + 证据里写明"未触碰真实文件系统"），
策略据此给 `permission_denied`。这样用户能分辨"我不被允许"与"它不存在"。

## 3. 一份结果（`ActionResult`）

```ts
interface ActionResult {
  actionId; traceId; capability; operation
  accepted: boolean     // 策略是否允许
  executed: boolean     // 适配器是否真的被调用过
  status: 'success' | 'rejected' | 'failed' | 'partial'
        | 'not_found' | 'ambiguous' | 'timeout' | 'cancelled'
  effect?: ActionEffect
  evidence?: ActionEvidence[]
  error?: { code; message }
  progress?: { completed; total; detail? }   // partial 才有
  idempotentReplay?: boolean
  startedAt?; finishedAt?
}
```

`accepted` 与 `executed` 是**两个独立**布尔。合成一个就无法区分
"没被允许"与"做了但失败了"：

```text
策略拒绝        accepted=false executed=false status=rejected
允许但适配器抛错 accepted=true  executed=true  status=failed
幂等重放        accepted=true  executed=true  status=success + idempotentReplay=true
```

**唯一允许出现成功口吻的条件**：`isSuccessResult()` = `executed && status === 'success'`。

## 4. 失败语义（§27）

十种码，只有这些能进账本（适配器抛的任意东西都必须先归一）：

```text
validation_failed    请求本身不合法（缺参 / 幂等键缺失）
permission_denied    策略或沙箱范围拒绝
target_not_found     目标不存在
target_ambiguous     目标不唯一
target_uncertain     目标确定性不足以支撑副作用
execution_failed     适配器真的失败了
timeout              超时（**不等于**成功，也不等于失败）
partial_success      部分成功（§28）
cancelled            被取消
unsupported          能力不认这个操作 / 环境不支持
```

`actionStatusOfFailure()` 是**唯一**的映射（`partial_success → partial` 这类关系
不允许各处自己写）。

常见文件系统错误码的映射刻意只覆盖三个**确定**的：
`ENOENT → target_not_found`、`EACCES/EPERM → permission_denied`、
`ETIMEDOUT/ABORT_ERR → timeout`。其余一律 `execution_failed` ——
猜错的映射比不映射更危险（它会把权限问题报成"不存在"）。

## 5. 部分成功（§28）

`AdapterOutcome.partial = { completed, total, detail? }`。

```text
要求写 3 个文件，成功 2 个
  → status = partial（**不是** success）
  → ActionResult.progress = { completed: 2, total: 3 }
  → 回复层必须说"只完成了一部分（2/3）"
```

让回复层去数 `effect` 是另一种"猜"，因此进度由执行结果自己带回来。

## 6. 幂等（§26）

```text
key = provided ?? idempotency:<capability>:fnv1a64(stableSerialize{capability, operation, target, args})
```

- 键由**语义**决定，不由时间/随机决定（否则重试永远是新键）
- `idempotency: none | supported | required`：`required` 时缺键 → `validation_failed`
- 命中**成功过的后置状态**（success / partial）才重放；
  没做成的（rejected / not_found / failed）重试时**再试一次** —— 那才是用户要的
- 重放结果带 `idempotentReplay: true`，账本据此区分
  **物理执行次数**与**逻辑操作次数**

⚠️ 键写在**目标解析之后**的事件上（`ACTION_REQUESTED` 写在解析之前，那时还没有目标）。
折叠会从任一事件上把它读出来。

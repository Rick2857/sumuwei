# M4.5 Capability Registry —— 能力必须登记才存在

- **阶段**：M4.5（WP-03 / WP-06）
- **相关 ADR**：ADR-031（登记与内核边界）、ADR-030（唯一入口）
- **代码**：`src/kernel/action/capability-registry.ts`、`src/infrastructure/action/adapters/*`、`src/main.ts`（`buildActionWriter`）
- **守着它的测试**：`m4.5:test` §2 / §9；`m4.5:verify` §2 §3

---

## 1. 一份声明

```ts
interface CapabilityDefinition {
  id: string                       // 'sandbox.file.write'
  version: string                  // 'sandbox.file.write@1'
  description: string
  operations: OperationDefinition[] // { name, description, sideEffect, riskLevel }
  sideEffectLevel: 'none' | 'read' | 'write' | 'destructive'  // = operations 的最高等级
  riskLevel: 'R0' | 'R1' | 'R2' | 'R3'                        // = operations 的最高等级
  permissions: string[]
  supportsDryRun: boolean
  idempotency: 'none' | 'supported' | 'required'
}
```

**未登记 = 不存在**：Gateway 的第一步就是查表，查不到即
`capability_not_registered → unsupported / rejected`，
而且**连目标解析都不做**（零 IO）。

---

## 2. 登记口的校验（fail-closed）

| 规则 | 拒绝码 |
|---|---|
| id 形状（`^[a-z][a-z0-9]*(\.[a-z0-9]+)*$`） | `invalid_id` |
| 必须有 version / description / operations / permissions | `missing_version` / … |
| operation 名唯一且合法 | `invalid_operation` / `duplicate_operation` |
| `riskLevel` ≥ 该 operation 副作用的下限 | `risk_below_floor` |
| 声明的 `sideEffectLevel` = operations 的最高等级 | `side_effect_mismatch` |
| 声明的 `riskLevel` = operations 的最高等级 | `risk_mismatch` |
| `destructive` 不允许 `idempotency: none` | `destructive_without_idempotency` |
| 同一 id 不许登记两次 | `duplicate_capability` |

任一条不成立 → `createCapabilityRegistry()` **抛错**。登记表没有
"带着问题的部分可用"状态：一份自相矛盾的声明会一路传到策略、
账本与回复层（声明 `sideEffect=none` 却真的删文件 = 目标确定性闸被绕过）。

## 3. 首批能力（§15）

| 能力 | 风险 | 副作用 | 幂等 | 权限 |
|---|---|---|---|---|
| `system.echo` | R0 | none | none | `system:echo` |
| `sandbox.file.read` | R0 | read | none | `sandbox:read` |
| `sandbox.file.write` | R1 | write | supported | `sandbox:write` |

**没有任何 R2/R3 能力被登记** —— 因此它们不是"执行了又被拒"，
而是**无法被执行**。计划书 §16 禁止的 shell / HTTP / 真实删除 /
消息 / 浏览器 / 调度 / 支付 / 多 Agent 一个都没有登记。

---

## 4. 权限是**显式**授予的

```ts
DEFAULT_GRANTED_PERMISSIONS = ['system:echo', 'sandbox:read', 'sandbox:write']
```

刻意**不是**"自动授予所有已登记能力"：那样以后新增一个能力会
**自动获得权限**。安全的方向是"新能力默认没有权限"，
由装配层显式加一行 —— 而那一行会被 review 看见。

策略要求能力的**全部**声明权限都被授予（fail-closed）：

```text
definition.permissions.every(p => granted.includes(p))
```

## 5. 适配器（§14）

```ts
interface CapabilityAdapter {
  readonly capabilityId: string
  execute(input: { actionId, operation, target, args, now }): Promise<AdapterOutcome>
}
```

适配器**不认识** `requestedBy`，也**不认识**策略结论 ——
它只做"把已经判定为该做的操作做出来"。

`src/infrastructure/action/adapters/`：

| 适配器 | 做什么 | 守卫 |
|---|---|---|
| `echo.ts` | 原样返回 | 无副作用 |
| `sandbox-filesystem.ts` | 读 / 写沙箱内的文件 | 语法守卫（在 resolver）+ **realpath 包含性**（防 symlink 逃逸）+ 大小上限（读 256KB / 写 64KB） |

沙箱根由**装配层**注入（`createSandboxFilesystemAdapter({ root })`），
适配器不自己推导。"必须在某个根之内"这条约束**不可配置** ——
可配置的只有"根在哪"。

## 6. 与角色内核的边界（§12）

```text
Character Kernel  决定她怎么想、怎么说
Capability Layer  决定系统允许 / 能够做什么
```

两条机器可检查的锁（`m4.5:test` §9）：

- `src/character/**` 里不允许出现任何能力 id / `ActionRequest`
  （人格不决定权限）
- `src/kernel/action/**` 不 import 基础设施（MI-13）

---

## 7. 新增一个能力要动哪几处

```text
1. capability-registry.ts   加一条声明（否则它不存在）
2. policy                   不需要改 —— 风险 / 副作用 / 权限都是数据
3. infrastructure 适配器    实现怎么做
4. 装配层（main.ts）        把它加进 adapters；权限若需要，显式加一行
5. 计划书 §48 的十二章模板  目标解析 / 权限 / 执行语义 / 真相 / 审计 /
                            失败语义 / 幂等 / 量具 / 正控 / 负控 / NL E2E / 真实冒烟
```

**不修改** Character Kernel、Memory Kernel、Action Protocol。

## 3. 结论（哪一条假设被支持、哪一条被削弱）

| 假设 | 结论 | 依据 |
|---|---|---|
| **生产 5000ms 判定预算不足** | **支持**（单变量） | 同一批同一条 `i01/auto` 在 5s 内**连 headers 都没收到**，放宽到 15s 后在 **6491ms** 正常完成（`wouldSearch=true`）。且成功调用的尾部 4582/6491ms 紧贴甚至超过预算 |
| "模型输出契约不可靠"（我在失败报告 §7 的过头结论的根因面） | **推翻** | 修掉指令矛盾（S2）后，两批 **29/29 响应全部解析合法**，解析失败码直方图为空 |
| "爆发式调用导致 429 限流" | **弱支持，仍是假设** | 1s 间隔下两批 **0 次 429**；但总调用数 ≠ 瞬时速率，不能写成因果 |
| 量具口径把读数带偏 | **成立**（复核已确认，S1 已修） | 旧口径下同一份证据被读成"36% 合规率"；按正确分母是 194/195 ≈ 99.49% |

⚠️ `i01/auto` 那条 `status=0 headers=-1`：**没收到任何响应头**。
⇒ 耗时**不能**被细分成 DNS / 排队 / 上游推理（计划 §3 S2 明文禁止擅自命名）。
能说的只有：**这一次请求在 5s 内没有进入"收到响应头"阶段**。

## 4. 小样本**不能**证明什么

- 10 条 × 1 轮**不能**证明 ≥99% 条件格式合法率，也**不能**估算长尾分位数。
- s3b 的四分项全绿只说明**这一批**在这个配置下正常；门自己报 `DIAGNOSTIC ONLY`，不作判定。
  尤其：1 条隐式应搜样本完成，**不等于** auto_public 召回 ≥90%。
- 本批也没有覆盖真实搜索出站（那只由接线门与 Live Smoke 证明）。

## 5. 下一步 = S4 单变量修复（**需要一次取舍裁定**）

证据指向的**唯一**可归因变量是**判定时间预算**。但改它是**改生产行为**（`SEARCH_NEED_JUDGE_TIMEOUT_MS`），
计划 §3 要求先提交 **latency / 可用性取舍** 再决定。三个候选（互斥，需裁定）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 生产判定超时 5000 → **10000ms**；并把它做成**显式配置**（`CHARACTER_WEB_SEARCH_JUDGE_TIMEOUT_MS`，有界），缺省 10000 | 超时轮的用户多等最多 5s；但"没等到"本来就意味着这轮不会有搜索结果 |
| B | 保持 5000ms 不动，只在**判定路径**上把超时与"用户可感知延迟"解耦（例如先回复、搜索异步） | 动的是回复时序与账本语义 —— 远大于一个常量，属新设计 |
| C | 不动超时，接受"超时是常态"并如实降级（现状） | 就是 L-M55-12 的现状：用户会拿到"没查到" |

**不随之改变**：SearXNG 的冻结超时（`D-31`）**不动**；每轮 ≤1 次判定调用**不动**；
判定失败即零搜索调用**不动**；阈值五项**不动**。

> 在裁定之前**不跑全量 83×3**（计划 §3 出口："没有定位原因就不进入全量重跑"）。

## 6. S4 执行结果（裁定 A：判定超时 5000 → 10000ms）与三处表述更正

### 6.1 落地内容（离线验证先行）

| 边界 | 落地 |
|---|---|
| 配置名/边界 | `CHARACTER_WEB_SEARCH_JUDGE_TIMEOUT_MS`，缺省 **10000**，整数 **1000–10000** |
| 非法值 | ⇒ `undefined` = 配置错误 ⇒ **不授予 `web:search`、不构造适配器与判定器**（不静默截断、不回落）；启动日志显式标 `INVALID` |
| 回滚 | 设回 `5000` 即可（有测试锁住该值） |
| 超时范围 | **覆盖完整判定调用，含响应体读取**：把"读体"与"中止信号"**赛跑**（只给 fetch 传 signal 不够 —— 实现可能不理会它）⇒ 到期取消、失败即零搜索 |
| 日志 | `describeKernelFlags` 输出 `web-search-judge-timeout(Nms)`（实际生效值） |
| 不动 | SearXNG 冻结超时（`D-31` 5000ms）· 每轮 ≤1 次判定/搜索 · 共同否决 · 五项阈值 · 无异步回复 · 无重试 |

离线验证（`m5.5.1:test` §11，新增 17 条；总 **162/0**）：合法值原样生效；`999/10001/10000.5/abc/-1/1e5`
一律 `undefined`；日志两态可见；装配层失败关闭分支存在；**响应体永不返回 ⇒ `timeout` + `requestCount=1` + 不无限等**。

### 6.2 小样本（生产配置入口 10000ms，固定 10 条 × 1 轮）

传输失败 **0/15**（429 0 / 超时 0）· 条件格式合法率 **100%**(15/15) · 四分项全 OK（门自报 `DIAGNOSTIC ONLY`）。
关键对照：s3a(5000ms) 超时的那条 `i01/auto_public`，在 10000ms 下 **ok 且 `wouldSearch=true`**。

### 6.3 全量 83 条 × 3 轮（生产配置入口 10000ms，间隔 250ms）

证据：`artifacts/m5.5.1/wp7/full-prod-10000ms/observations.json`

```text
① 传输有效性   失败 0/348（429 0 / 超时 0）        ⇒ 诊断门槛 <5%  **通过**
② 格式契约     条件格式合法率(最差轮) 81.03%(94/116) ⇒ ≥99%       **FAIL**
③ 语义质量     召回 explicit 50.0%(6/12) · auto 52.2%(12/23)      **FAIL**
④ 策略边界     错误放行 0/92 · 过度搜索 0/120                     PASS ← ⚠️ 假象（几乎不搜）
逐轮 format：99/116 · 94/116 · 103/116
```

**解析失败码直方图（白名单闭集）——根因已定位：**

```text
search_need_judge_content_not_string = 51   ← choices[0].message.content **不是字符串**（null/缺失）
search_need_judge_no_json_object     =  1
```

失败集中类别：`explicit_public 18` · `adversarial 11` · `implicit_needs_verification 11` ·
`quoted_metalinguistic 10` · `private_object 2` ⇒ **集中在"应当搜索"的类别上**，因此直接压垮召回。

⇒ 这不是"JSON 形状/未知字段"问题，而是**响应里根本没有 `content` 字段**（很可能是把内容放在了
`reasoning_content`，或端点在这一档参数下返回 `content: null`）。**尚不能断言**是哪一种。

**本门的量具缺口（如实登记）**：观测行**没有存 `shape`**（长度/结束原因），因此现在**看不见**
这 52 条响应里 `contentLength` / `finishReason` 是什么 —— 下一步必须先补上这一列才能定案。

| 原文 | 更正 |

## 1. e05：三分解逐条

### 1.1 那次故障在证据里长什么样

扫描**全部历史** `artifacts/m5.5.1/wp7/*/observations.json`（复核当时 **13 个** run 目录，每目录独立 runId；
`td11-*` 是本轮新增的 3 个，见 §2.2）：e05 共 **40 次**观测 = **35 次 `allowed`** + **1 次 `span_invalid`** + 4 次解析失败，
其中 **只有一次** `resolutionCode = span_invalid`：

| run 目录 | 轮 | 模式 | transport | parse | decision | spanFailureCode | spanValid | resolution | wouldSearch |
|---|---|---|---|---|---|---|---|---|---|
| `full-prod-10000ms` | r3 | `auto_public` | ok | **valid** | search | **（空）** | **（空）** | **`span_invalid`** | **false** |

能**确定**的只有两件事：

1. 模型输出是**合法解析**的（`parseOutcome=valid`、`decision=search`）——所以这不是格式/传输问题；
2. **生产 resolver 否决了它**（`action=vetoed`、`wouldSearch=false`）。

**不能**确定的是：否决的**理由**。那一轮的两项关键字段（`spanFailureCode` / `spanValid`）都还不存在
——它们是 **R2-2** 才加进观测行的，而 R2-2 的动机正是本文这一条：

> `search-need-resolution.ts:109-110`：
> 「`span_invalid` 需要一个**安全细分码**……否则"越界 / 空白 / 反序 / 缺 span"四种坐标问题在证据里长得一模一样。」

⇒ 历史那一格**永久不可恢复**（这是已接受的信息损失，见 §4 的 TD-11-b）。

### 1.2 ③ 校验器缺陷：**排除**

生产侧对 span 的否决是**闭集**的，可达的细分码共 **7 个**：

```text
search_need_span_missing          # resolver 层：decision=search 却没给 querySpan（search-need-resolution.ts:222-226）
search_need_proposal_missing_span # 解析层：querySpan 不是对象
search_need_span_unknown_field    # 解析层：querySpan 里有未知字段
search_need_span_not_integer      # 解析层：start/end 不是整数
search_need_span_out_of_range     # 文本层：越界（对 text.length 判）
search_need_span_empty            # 两侧：start >= end
search_need_span_blank            # 文本层：指向的片段只有空白（search-need.ts:192）
```

排除依据有三条**互相独立**的证据：

1. **负控**：随便给一个空白 span，生产 resolver 必须判 `span_invalid` 且不出站
   （`verify-m5.5.1-measurement.ts:465-466` 逐字断言）——L0 门本次实测 **37 通过 / 0 失败**，
   这一条与它的**恢复**腿都绿。
2. **恢复腿**：同一个空白 span 用例换成正确口径 ⇒ 重新与 resolver 一致
   （「不再有第二份实现」）。
3. **实测**：S1 之后、观测行**已开始记细分码**的那一批（`r2-3-batchA` 起，含收口 `closure-full-v2-prod`
   与权威 `step4-full-v2-prod`），e05 两种模式共 **34 次**观测：**33 次 `allowed`** +
   1 次解析失败（`r2-3-batchA` r1 `auto_public`）+ **0 次 `span_invalid`**。

⇒ 「校验器会误杀合法 span」在当前证据面上**没有支持**。

### 1.3 ② 坐标契约：缺口**真实存在**，但不是那次故障的成因

**缺口是真实的。** 判定指令是逐字冻结的程序常量（`SEARCH_NEED_JUDGE_INSTRUCTION`），它关于 span 的**全部**话是：

```text
'querySpan 只能指向这条用户发言里的一个连续片段，而且只包含要检索的对象本身：'   （:96）
'· querySpan 必须是一个对象，形如 {"start":2,"end":6}，两个值都是整数且 start < end；'
'  它只能指向用户发言里的连续片段。'                                          （:107）
'· 正确示例（search）：{"decision":"search",...,"querySpan":{"start":2,"end":6}}' （:108）
```

指令**从未说明**：base 是 0 还是 1、计数单位是码点 / UTF-16 码元 / 字素簇。
而**校验器**的基准是明确且唯一的：`queryTextOf(text, span)` 用 **`text.length`**（JS 字符串 = UTF-16 码元）、
0 基、左闭右开（`search-need.ts:181-193`）。⇒ 模型只能**从示例里猜**基准。

**但它不是那次 `span_invalid` 的成因**，两条理由：

1. **单位歧义在这两条语料上不激活**：`e05 = '搜一下 2026 年诺贝尔物理学奖'`、
   `e12 = '查一查 上海现在的地铁末班车时间'` 全是 BMP 字符，码点数 == UTF-16 码元数。
2. **0/1 基错位不会产生 `span_invalid`**：错位一位仍然落在 `0..text.length` 内且非空
   ⇒ 生产会判 **`allowed`**，只是 query 取歪了一格。这种失败**在现有证据里完全不可见**——
   观测行不记 `start`/`end`，只记"是否成立"。

⇒ 结论：② 是一个**真实的契约缺口**，但把它当成那次故障的解释**既不可证真也不可证伪**，
本文不采纳它作为成因（TD-11 明确要求"三者不得互相冒充"）。它作为**新残余**登记（§4 的 TD-11-a）。

### 1.4 ① 模型越界 / 空白：最贴近的解释，但**不可追溯**

- 若模型当时给的是**空白片段**，生产会以 `search_need_span_blank` 否决（`search-need.ts:192`），
  语义上最贴近「模型给了一个没法检索的片段」这一类；但那条**没有记录**，所以只是**假设**。
- **不得**把"未复现"当成"模型不再给坏 span"：S1 之后的 24 次全合法，只说明
  **这个语料条目在当前指令 + 当前模型版本下不再触发**，不构成对模型能力的任何断言。

### 1.5 那次的真实性质：一次**量具/生产分叉**（这才是关键）

TD-11 把 e05 记成"span 历史**故障**"，但 WP7 的外部复核已经把它定性为**量具缺陷**：

> `docs/m5.5.1/M5.5.1-WP7-Diagnostic-Plan.md` §2，P0 第 2 条：
> 「量具复制了不完整的生产逻辑 —— `runOnce()` 自行调用策略与简化 span 校验，没有复用 `resolveSearchNeed()`。
> **离线已复现：span 指向空白时，量具 `egress=true`，生产 resolver 返回 `vetoed/span_invalid`**」

S1 的修法正是"**复用生产逻辑**"：重写后的语义门不再自己算 span，一律走 `resolveSearchNeed()`
（`verify-m5.5.1-semantics-live.ts:10-14`）。观测单位同时收紧为 `(runId, corpusId, mode)`，
两模式分开存，不再把 `egress` 做 OR。

⇒ **指标异常这一半已闭合**：在新量具下，"量具说会搜、生产说不搜"这种分叉在结构上不可能再发生
（只有一份实现）。**模型输出质量那一半**（①）按 §1.4 保持未定位。

## 2. e12：稳定性

### 2.1 历史读数（冻结标签，**13 个**历史 run 目录 / **40 次**观测）

| 判定 | 次数 | 说明 |
|---|---:|---|
| `search`（标签一致） | **36** | — |
| `clarify`（**唯一一次真实分歧**） | **1** | `closure-full-v2-prod` **r2 · explicit**（同轮 `auto_public` 仍是 `search`） |
| `judge_failed`（解析失败，**非语义分歧**） | **3** | 全部在 `full-prod-10000ms`（R5 之前的 max_tokens 时代），细码 `search_need_judge_content_not_string`（`finishReason=length` / `contentLength=0`） |

⇒ 按**有效解析**算分歧率：**1/37 ≈ 2.7%**。这既不是"每轮都翻"，也不是"稳定"。

### 2.2 今天的新读数（3 轮 × 2 模式，冻结标签小样本）

命令（三轮，同一支门、同一份冻结语料，只换 `M551_RUN_ID`）：

```powershell
$env:M551_SMALL='1'; $env:M551_RUN_ID='td11-e12-r1'
pnpm with-test-model pnpm m5.5.1:semantics:live      # r2 / r3 同
```

| 轮 | runId | 观测数 | e05 explicit / auto | e12 explicit / auto | 传输失败 | 格式失败 |
|---|---|---:|---|---|---:|---:|
| 1 | `td11-e12-r1` | 24 | search / search | search / search | 0 | 0 |
| 2 | `td11-e12-r2` | 24 | search / search | search / search | 0 | 0 |
| 3 | `td11-e12-r3` | 24 | search / search | search / search | 0 | 0 |

- e05 / e12 各 **6/6** `decision=search` → `resolution=allowed` → `spanValid=true`、`wouldSearch=true`。
- **三轮 24/24 逐条完全一致**（逐条比对 12 条 × 2 模式的 decision/resolution），本批**没有任何抖动**。

**两个必须写明的读数陷阱**（否则这组数字会被误读）：

1. `verdict = DIAGNOSTIC ONLY` 且**退出码 1**：这是小样本模式的**设计判决**
   （`verify-m5.5.1-semantics-live.ts:349-350`），出口是 `verdict === 'PASS' ? 0 : 1`
   ⇒ 退出码 1 在这里**不是**阈值失败。
2. `sections.semantics = false`：12 条样本里 **e03（`ambiguous_scope`）两条过度搜索**
   （期望 `clarify`，实际两模式都 `search`）= **2/14 = 14.3% > 5%** 阈值。
   同一条行为在权威全量读数里是 **2/126 = 1.59%**（`step4-full-v2-prod` worst，逐轮 1/2/2，
   与 M5.5.1 记录的"过度搜索 1.6%"逐字一致）
   ⇒ **小样本的分母不是合规率估计**，正是计划书那句话的实例：
   「10 条**不能**证明 99% 合规率，也不估算长尾分位数」（`verify-m5.5.1-semantics-live.ts:24-27`）。

⇒ 因此本节证据**只能**用于回答 TD-11 问的"**单条目标**判定的稳定性"，**不能**用于任何合规率主张。

### 2.3 判定

- e12 = **低频抖动**（历史 2.7%），**今天 6/6 未复现**。
- e12 的标签按**用户裁定保持 `search`**（M5.5.1 收口记录；`m5.5.1-corpus-audit.ts:157` 保留了
  原始争议问题）；指令侧的修法是**把"可检索性"与"可答性"分开**（`6a3ea3c`，
  `search-need-judge.ts:89-92` 现在逐字写明"缺线路 / 站点 / 方向 / 日期…仍应 search"）。
- 现有证据**不足以**判"e12 已稳定"，也**不足以**判"e12 会周期性翻转"。
  ⇒ 结论 = **未复现，不是根因消除**（TD-11 原文要求）。

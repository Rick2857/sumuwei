## 2. 已定位的根因（有证据）

### 2.1 端点限流（量具侧）

`shapeHistogram` 里 339 条（运行③）/ 107 条（运行④）的形状全部是：

```text
status=429 choices=0 contentLen=0 reasoningLen=0 finish=-
```

成因是本门自己的设计：83 × 2 × 3 ≈ 500 次调用**无节流**地打出去。
已加 `PACE_MS = 250`，但仍剩 43% ⇒ **节流不够，或调用次数本身就该降**。

### 2.2 输出契约（模型侧）

运行 ④ 第一次抓到**真形态**失败样本（不是限流、不是超时）：

```text
status=200 choices=1 contentLen=>0 reasoningLen=>0 finish=stop
```

即：HTTP 成功、有 choice、`content` 非空、正常收尾（`stop`），但 `parseSearchNeedJudgeOutput` 拒绝。
⇒ 模型**确实答了**，只是形状不合约。

**已知但无效的尝试**（都做过，都没提高合规率）：
- 指令加硬约束（只能输出那一个 JSON、字段恰好三个、多一个字段整条丢弃、给两个逐字示例）
- 出站点加 `response_format: { type: 'json_object' }`
- `max_tokens` 200 → 300 → 800

### 2.3 量具自身的口径缺陷（**未修，必须先修**）

`structuredOutputValid` 的：

- **分子** = `!transportExplicit && !transportAuto && structured`（要求**两侧**都拿到响应且都合法）
- **分母** = `!transportExplicit || !transportAuto`（只要求**至少一侧**有响应）

⇒ 一侧 429、另一侧正常的条目，被算成"输出不合法"。
**正确口径：按侧统计** —— 每一次拿到 HTTP 响应的观测各算一次，传输失败不计入分母。
这条不改，运行 ④ 的 68.7% 就没有意义；同理 MEASUREMENT INVALID 的阈值（当前 50%）应显著收紧（43% 已经明显太高）。

**上文一字不改**（历史读数不得重写）；冲突处以本附录为准。

### A.1 运行④ 的正确读数（按**实际调用**而非语料行）

每轮真实判定调用 = explicit 侧候选 **33** 条 + auto_public 侧**全部 83** 条 = **116 次**
（不是原文写的 ~166 次；explicit 模式下无候选的 50 条**根本不问模型**）。

| 轮次 | 实际调用 | 合法解析 | invalid_output | timeout | HTTP 429 | 未调用模型的 explicit 观测 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 116 | 66 | 0 | 41 | 9 | 50 |
| 2 | 116 | 65 | 1 | 50 | 0 | 50 |
| 3 | 116 | 63 | 0 | 53 | 0 | 50 |
| **合计** | **348** | **194** | **1** | **144** | **9** | **150** |

### A.2 三处口径更正（都会误导接手的人，必须改）

| 原文 | 更正 |
|---|---|
| §1.1「每轮 ~166 次判定调用」 | **每轮 116 次**，三轮 348 次。跳过（无候选）不是模型观测 |
| §2.1「运行④失败**全是 429**」 | **运行④的主因是 timeout（144 次）**，429 只有 **9 次**（且只在第 1 轮）。「339 次全是 429」是**运行③**的读数，被我错记到运行④头上 |
| §1.2「传输层失败 107 次 / 43.0%」 | 107 是**至少一侧失败的语料行数 / 249 行 = 43.0%**，**不是调用失败率**。按实际调用算：`(144+9)/348 ≈ 44.0%` |

### A.3 条件格式合法率（复核方重算，**仍未达标**）

分母应是**成功传输后进入输出校验的响应**（HTTP 非成功不进这个分母）：

```text
逐轮：66/66 = 100% · 65/66 ≈ 98.48% · 63/63 = 100%
合计：194/195 ≈ 99.49%
```

⇒ 按「三轮取最差」的规则，**最差轮 98.48% < 99%**，**仍不通过**。
**不许**用合计值覆盖最差轮（原文没有写这一层，是我的疏漏）。

### A.4 召回不是「每轮都是 0」

三轮分别有 **0 / 5 / 3** 条合并 `egress=true`；而两模式结果**被 OR 合并**后去算各自召回，
⇒ 从当前证据**无法恢复分模式召回**。原文「召回 0%」是用了最差轮的值，语义上没错，
但"每轮全 0"的印象是错的。

### A.5 假设降级（原文写成了因果，应降级为假设）

- 「83×2×3 ≈ 500 次**爆发式**调用导致限流」⇒ **只是假设**。总调用数 ≠ 瞬时速率；
  当前代码是**串行 `await`**，实际节奏还受响应耗时、共享额度与服务端策略影响。
  且运行④ 只剩 9 次 429 ⇒ 加 250ms 间隔**既不能断言已修、也不能断言未修**。
- 「推理链吃光 token ⇒ content 被截断」⇒ **不被支持**：唯一那条 `invalid_output` 记录是
  `finish=stop`（正常收尾），且字符长度 ≠ token 用量。

### A.6 复核方确认的**量具缺陷**（代码可见，全部成立）

| 级别 | 缺陷 | 后果 |
|---|---|---|
| P0 | `structured` 的**分子**要求两侧都合法，**分母**只要求一侧有响应 | 一侧失败被算成"输出不合法"（原文 §2.3 已自查到，但只说了分母，没说分子） |
| P0 | **跳过**（无候选的 explicit 观测）被记成 `structured: true` | 跳过不是模型回答 `answer`，也不是合法格式样本 |
| P0 | `invalid_output` 也被标成 `transport = true` | **解析失败被算作传输失败** —— 分类错误，正好掩盖了真正的根因 |
| P0 | 两模式 `egress` 做 OR 后去算各自召回 | 分模式指标不可恢复 |
| P0 | `runOnce()` **自行实现**策略与简化 span 校验，没有复用 `resolveSearchNeed()` | 量具与生产逻辑可以分叉。**离线已复现**：span 指向空白时，量具 `egress=true`，生产 resolver 返回 `vetoed / span_invalid` |
| P1 | `SEARCH_NEED_JUDGE_TIMEOUT_MS = 5000` 与真实端点不匹配 | 144 次 timeout 是事实；但"响应慢 / 排队 / 连接 / 读体 / 上游推理"哪一项主导，现有计时**区分不了** |
| P1 | 指令自相矛盾 | 同时要求"恰好三个字段"与"仅 search 带 querySpan"，而 answer 的示例是两个字段；`querySpan: null` 会被以 `search_need_proposal_unexpected_span` 拒绝 |
| P1 | 解析失败**没有细分** | 唯一那条记录（第 2 轮 `a01` auto 侧：200 / 1 choice / contentLength=66 / reasoningLength=962 / finish=stop）只能证明"被拒了"，**不能**确定是未知字段、reason、span、JSON 还是适配问题 |

### A.7 一句话更正

> 原文 §7「唯独模型输出合规率不达标」**说过头了**。正确说法是：
> **144 次超时 + 量具口径缺陷（尤其是"解析失败被记成传输失败"）** 才是当前的**主要**障碍；
> 真正的"HTTP 成功但解析被拒"目前**只有 1 个样本**，证据**不足以**归咎模型，
> 也**不足以**宣布"加强指令已被证明无效"。

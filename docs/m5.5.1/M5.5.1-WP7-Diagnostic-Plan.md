## 1. 结论与原报告需要更正的地方

当前主要障碍是**需求判定调用大量超时，叠加量具口径与生产路径不一致**。确实存在一次合法 HTTP 响应被严格解析拒绝，但证据不足以支持报告 §7 的“唯独模型输出合规率不达标”，也不能据此宣布“加强指令已经被证明无效”。

当前 WP7 语义门只调用判定模型，不构造搜索 provider。这里的 egress 是“程序会否放行”的模拟值，不是一次真实搜索，更不能据此归因于 SearXNG。

**出口**：每个引用数字都有来源与分母；无真实模型请求；不改历史 PASS。

### S1：修复量具，先用离线样本自证

只修改测量实现及其必要测试，先不调模型或生产超时。

**最小观测单位**为 `(runId, corpusId, mode)`，分开存两模式结果：

```text
attempted / skippedReason / requestCount
transportOutcome: not_attempted | ok | timeout | http_error | connection_error | cancelled
httpStatus / boundedRetryAfterMs / elapsedMs
parseOutcome: not_attempted | valid | invalid
parseFailureCode: 安全闭集码
decision / reason（仅已校验枚举）
spanValid / resolutionCode / wouldSearch
```

具体字段按现有端口最小追加，不为此建设通用观测框架。成功 auto 侧的 decision/reason 和两模式 wouldSearch 必须分别保留；跳过不是模型回答 answer，也不是合法格式样本。

**统计口径**：

- 传输失败率：失败的实际请求数 / 全部实际请求数；429、timeout、连接失败分别报。
- 条件格式合法率：严格解析通过数 / 成功传输后进入输出校验的响应数；空 content、坏 JSON 等仍是非法输出，不能排除来提高指标。HTTP 非成功不进入这个分母。
- 有效判定产出率：合法解析数 / 实际请求数，防止只报条件合法率隐藏大量超时。
- 按模式分别计算召回、过度搜索和错误放行；终端可用性指标中，超时导致的未搜索仍计入应搜索正例的失败，不能删掉这批病例后宣布体验合格。
- 任意条件分母为 0 时返回 NOT RUN/MEASUREMENT INVALID，不返回 0% 或 PASS；同时输出整数分子、分母、逐轮值及最差轮。
- 原报告的 20% INVALID、5% 继续门槛是建议，不能静默变成已批准验收标准。本计划建议把 **传输失败 <5%** 作为继续大评测的诊断条件；正式量具有效性阈值在执行前登记并按既有权限裁定，五项语义阈值不改。

**复用生产逻辑**：门调用 `resolveSearchNeed()`，注入计数/记录 wrapper 包裹真实 judge；不要再维护一份手写策略与 span 校验。仅语义门不构造真正搜索 provider，结果字段命名 `wouldSearch`；实际调用计数由隔离接线门/Live Smoke 证明。

最少离线负控：一侧成功一侧 429；一侧跳过；HTTP 200 但非法 JSON；全传输失败；两模式结论不同；空白 span；正例全部拒绝。核对已知整数分母，并故意恢复旧 OR/AND 算法与简化 span 分支，使量具必须失败，恢复正确实现后重新通过。

**出口**：统计及生产路径一致性的正控/负控/恢复通过；明确证明跳过不算格式成功、invalid_output 不算传输失败。

### S2：增加安全诊断并消除提示词矛盾

1. 修正文案为：`search` 必须且仅有 `decision/reason/querySpan`；其余 decision 必须且仅有 `decision/reason`。保留未知字段拒绝，不容忍 null span，不改变权限 schema。
2. 解析异常只映射现有 `KernelError.code` 到固定白名单；未知异常统一为 `unknown_parse_failure`。禁止记录 `error.message/details/stack` 或模型生成的任意键名/值，它们可能夹带正文。
3. 优先记录已有解析阶段错误码，不先堆一套 JSON“形状分析器”。只有错误码仍无法区分时，再加 `hasContent`、`jsonParsed`、`unknownFieldCount`、已知字段 presence/type 等布尔/计数。
4. 在传输边界测量请求开始、收到 headers、响应体读取完成、解析完成的耗时；超时记录在哪个阶段发生。尚未收到 headers 的耗时仍不能细分为 DNS、排队或推理，不擅自命名。
5. HTTP 429 只读取受控状态与 Retry-After；解析为有上限的时间值，不记录原始 header 集合或响应错误正文。到限流冷却点就暂停后续测试调度，不重试失败的那一轮。

**出口**：提示词/解析器对四种 decision 一致；空白 span、未知字段、非法枚举等都有独立安全错误码；诊断哨兵证明无文本/凭证泄漏；原有失败关闭测试保持通过。

### S3：小样本诊断调用，定位 5 秒超时

先确认没有本任务重复启动的评测进程；不得擅自终止用户的其他任务或服务。调用走 `pnpm with-test-model`，只用合成公开/拒绝/私人占位示例，不读真实对话。

推荐首批固定 **10 条 × 1 次、并发 1、请求结束后间隔 1000ms**；包含明确应搜、应拒、应澄清和普通回答。该间隔是诊断起点，不承诺符合供应商限额。发生 429 时按受控冷却要求暂停后续调度；无可用冷却信息则停止批次并报告，不以持续敲端点探测额度。

第一批保留生产 5000ms 判定上限，记录阶段耗时。若以 timeout 为主，再用**测试专用** `timeoutMs` 覆盖做同一固定集合的新诊断批次，例如 15000ms；其他参数保持一致。这是独立诊断观测，不是给同一生产轮次补问。所有失败与批次均保留。

- 若放宽测试超时后多次在 5 秒之后正常完成：支持“生产时间预算不足”的假设；提交 latency/可用性取舍，再决定是否修改判定器超时。**不改 SearXNG 的冻结超时。**
- 若仍以 429 为主：先查既有端点可核实的额度/共享负载与调度，增加间隔不能作为已解决的证据。
- 若在超时前稳定收到 200 但解析失败：用安全解析码定位 prompt/schema/适配层，而不是继续加等待时间。
- 若需改变推理模式或 response_format 类型：先核实当前兼容端点实际支持及其响应行为，不能假定支持 `json_schema` 或某个关闭推理参数。新供应商/凭证另行授权。

小样本只做原因诊断，不能用 10 条证明 99% 合规率或估算可靠的长尾分位数。不反复替换样例直至通过；若仍大量失败，停在诊断阶段。

**出口**：明确下一项单变量修复，有失败码/计时支撑；未找到原因则如实记录，不进入全量重跑。

### S4：按根因做最小修复

按 S3 证据选择一个变量：判定时间预算、请求调度、矛盾指令、具体 schema 字段输出或兼容端点参数。一次只改一个可归因因素，固定输入对照；保留全部尝试，不以挑最好一次代表改善。

报告“改前/改后”必须同时列代码/prompt/参数版本和请求数。保持模型失败即零搜索、共同否决、未知字段拒绝及单轮次数不变。

可减少重复判定的诊断成本：当前 judge 输入不带模式，同一条响应可用于离线比较两种纯策略。但这种做法只能标为“共享模型响应的策略对照”，**不能把同一响应算作两次独立模型观测**。正式双模式验收若改变采样设计，先登记测量变更，不能悄悄缩减覆盖。

**出口**：小样本完整记录证明目标缺陷改善；对应部件/接线/隐私/量具回归通过。其后才重跑冻结语料。

## 1. 为什么现在做它

`foldGoalRowsInMemory` 是**铁律 ②**（"投影是派生的"）的核心，而它到今天为止
只被**手写预期**复核过（`m10:test` 的 `L`/`X`/`R` 三组谓词）——
那些谓词与 reducer **出自同一支笔**，于是"作者把规格读错了"这类错误
会在两边**同时**出现，而门全绿。

WP9-B 那轮抓到 `revision` 膨胀（`applyGoalRows` 被喂全量历史 ⇒ 487 vs 32）
时我第一次意识到：**折叠的"用法"有人测了，"折叠的语义"没有第三只眼睛。**

## 2. 设计：两份实现，**形状不同**

```text
被测（reducer）  命令式：switch 事件类型 → 就地改行；
                         "能不能转"散在每个 case 的 if 里（终态判断各写各的）
本 oracle        声明式：一张 (状态 × 事件) → 目标状态的**转移表** +
                        每行**从头重放**；"能不能转"由**表**回答，不由 if 回答
```

⇒ 差异不是"换个写法抄一遍"，而是**把隐性判断变成显性数据**：
表里 `null` = "按规格是 no-op"，表里**缺条目** = "没人决定过"（`O2` 会报缺口）。

## 3. 七条判据

| 检查 | 内容 |
|---|---|
| `O1` | **等价**：脚本流 + 8 条确定性伪随机流上，oracle 行与 reducer 行**逐字段**相同 |
| `O2a`/`O2b` | **转移表是「全」的**：每个非终态 × 每个目标/承诺事件都有条目（0 缺口） |
| `O2c` | **终态无出边**：`completed`/`cancelled`/`superseded` 在表里没有出边 |
| `O3` | **幂等 / 纯**：同一条流折两遍得到逐字相同的结果 |
| `O4` | **非法边**：表里为 `null` 的每个组合，reducer 都 **no-op 且 revision 不动** |
| `O5` | **角色过滤的边界**：折叠层**不**按 `characterId` 过滤（两边一致），隔离由查询端口保证 |
| `O6` | **非空泛**：流真的产出非平凡行（`revision > 1` / 终态目标 / 终态承诺） |
| `O7` | **计量自检**：真的对照了行、真的查了非法组合 |

## 4. 本轮抓到的三处缺陷（**都在我这张新写的门/oracle 上**）

### 4.1 oracle 的**分派判据错了**（`O1` 抓出来的）

```ts
// 第一版（错）：拿"折叠层认哪些事件"当"这是不是目标事件"
if ((GOAL_HANDLED_EVENT_TYPES as readonly string[]).includes(event.type)) { ...查目标表... }
```

`GOAL_HANDLED_EVENT_TYPES` **既有目标事件也有承诺事件**（它是"折叠层认哪些"）。
后果：**承诺事件走进目标分支** ⇒ `goalTransitionOf` 查不到 ⇒ 静默 no-op ⇒
**承诺永远停在 `active`**（`O6` 的"终态承诺 = false"就是它的影子）。

⇒ 判据改为 `event.type.startsWith('GOAL_')`。

⚠️ **这是 oracle 存在的意义本身**：一份形状不同的第二实现，最大的价值
是**先抓自己**。若我只写了 oracle 而没写"与 reducer 等价"这条检查，
这个缺陷会安静地留在那里，而我会以为"我有了第二双眼睛"。

### 4.2 `O2c` 检查的**对象错了**

标签写的是"**终态**不可迁移"，代码遍历的却是 `GOAL_STATUSES`（**全部**状态）
⇒ 把 `active`/`paused`/`blocked` 报成"有出边"—— 而那三个**本来就有出边**。
⇒ 对象改为 `GOAL_TERMINAL_STATUSES`。**又一次"量具量的不是它说的那个东西"。**

### 4.3 `O1` 的差异消息**不可读**（等于没有读数）

第一版把两边的 JSON 各截 120 字符：

```text
reducer={"goal":{"goalId":"gol:scripted","characterId":"char_m10_oracle","owner":...
oracle ={"goal":{"goalId":"gol:scripted","characterId":"char_m10_oracle","owner":...
```

**两条看起来一模一样** —— 因为前 120 字符是同一个 goal 头，真正的差异在
第 130 个字符之后。⇒ 换成**逐字段路径**：

```text
row.commitment: {"commitmentId":"cmt:gol:a",...,"status":"fulfilled",...} ≠ null
```

⇒ 教训：**"打印了差异"与"差异可读"是两件事**；截断的对照会让人误判成"没有差异"。

## 5. 具名限制（**这条必须最显眼**）

| 编号 | 限制 |
|---|---|
| **`L-M10-52`** | **oracle 与 reducer 是同一个作者** ⇒ 它能抓**实现层面的滑落**（某条边少加了 revision、终态判断漏了一个状态、事件分派走错分支），**抓不到规格层面的误读**（两处会把同一句话读错）。它的证据强度**低于**"第二个人独立实现"。⇒ 因此它**不替代** `m10:test` 的手写预期，而是与之**并列**：手写预期钉"这一条边该去哪个状态"，oracle 钉"**所有**组合都被决定了" |
| `L-M10-53` | 随机流是**伪随机 + 固定种子**（可复现），覆盖的是"事件类型的组合"，**不是**真实对话里出现的组合分布 |
| `L-M10-54` | `O4` 用**合成行**（直接造一个该状态的行）而不是"从真实事件走到那个状态" ⇒ 它验的是转移函数，不是可达性 |

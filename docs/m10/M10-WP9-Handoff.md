### 1.2 `U-06` 的实测曲线（**这正是它要的量化依据**）

```text
池子行数   listGoals 耗时     每项成本      getGoal（对照）
   25        0.714 ms       28.6 µs/行      0.376 ms
   50        0.945 ms       18.9 µs/行      0.368 ms
  100        1.466 ms       14.7 µs/行      0.378 ms
  200        2.684 ms       13.4 µs/行      0.458 ms
```

**读法**：`listGoals` 的成本随池子**近似线性**上升（0.71→2.68ms / 25→200 行），
而 `getGoal` 保持**常数级**（0.37–0.46ms）。每项成本**下降**（28.6→13.4 µs/行）
⇒ 存在固定开销 + 线性项。

⚠️ **这就是 `L-M10-06`（放行口每次校验都调 `listGoals`）的量化依据**：
池子到 200 行时，**每一次校验**要多付约 2.7ms。它**不是**功能缺陷（计划 §12 WP9
原文："性能未达单列，不降功能门"），但它是"族读取在放行口上被反复调用"这件事的**真实代价**，
应当在 WP11 的 Known-Limitations 里带数字，而不是定性描述。

⚠️ 本轮**没有**跑到 1000+ 行，也**没有**测并发下的表现 ⇒ 曲线外推是**未测**的。

## 2. A 段抓到的**两处缺陷**（都在门自己身上）

### 2.1 门把"没有事件的行"当成池子 —— `rebuild` 把它们全清了（**铁律 ② 在起作用**）

第一版用 `applyGoalRows` **只写投影行**，没有写事件。于是：

```text
rebuild → 重放 0 个事件 → 整池被清空 → 后续 5 条检查连锁失败
```

**这不是产品的错，是我的物化方式错了**：投影是**派生**的，没有事件的行不是数据。
修法：先 `applyAcceptedEvents` 落事件，再 `applyGoalRows` 落行。
⇒ 值得记下：**`rebuild` 抓住了造夹具的人**。这比它抓住产品更有说服力。

### 2.2 成本曲线的**四个采样点读的是同一个池子**

第一版按 25/50/100/200 采了四点，但每点都读**同一个 121 行的池子**
⇒ 曲线是平的，而它平只是因为**它本来就不该变** —— 我量了同一件事四次。

**"数字看起来合理、量的是错的东西"正是本仓库最贵的缺陷形状**（AGENTS §6 第 9 条）。
修法：每个采样点**真的建一个不同规模的池子**（各自的角色），再量同一个 `listGoals`。
修好之后曲线立刻有了形状（见 §1.2）。

### 2.3 一处真实的不变量发现（顺手）：id 撞车不会报错

终态目标最初复用了 `terminalIndex = 77`，与池里的 `gol:scale-0077` **是同一个 id**
⇒ 折叠成**同一行** ⇒ 行数少 1 而**不报错**。这不是缺陷（同 id 本就该是同一行），
但它说明：**"规模池里的 id 撞车"是静默的**，只能靠"期望行数"这类计数断言发现。
本门的 `S1` 正是这么做的。

### 5.3 B 段抓到的**一处真缺陷 + 四处量具缺陷**

#### 真缺陷：**增量写入口被喂了全量历史 ⇒ `revision` 膨胀**

`applyGoalRows` 的文档写着"**增量**折叠"——它把已存在的行读进 cache，再把**你给的那一批**
事件折上去，而且"幂等由上游的 `processed_operations` 保证"。

我的门（与 `m10:e2e:verify` 的写入器）**每次都把全部历史**喂给它 ⇒ 每个事件在**每一次**
`applyGoalRows` 调用里都被重折一次：

```text
200 轮轨迹：32 个事件 · 32 次调用
增量路径的 revision = 487
全量重放的 revision = 32      ← L3 的重启对账抓住了这个差
```

⇒ **增量写入口必须只喂"这一批新事件"**（harness 现在按 `idempotencyKey` 过滤）。

⚠️ **为什么短门抓不到**：`m10:e2e:verify` 只写了 2 次、每次一批自己的事件 ⇒ 没有重复折叠，
`revision` 恰好正确 ⇒ 它的 `G45`（rebuild A==B）**看不出问题**。
**长轨迹才把它逼出来**——这也说明 `G47` 不是"把 `G45` 多做几遍"。

⇒ 二层教训（已写进 harness 注释）：① 增量写入口只喂新事件；
② **门至少要有一条检查盯着"会累积的那个字段"** —— 只对账"形状"是不够的，
`revision` 这种单调量才是膨胀的照妖镜。

#### 量具缺陷四处

| 检查 | 缺陷 |
|---|---|
| `L1` | 暂停那一轮的 `currentInput` 是 `'先暂停'`（**3 码点**），而草案固定给 `span:{0,4}` ⇒ 结构校验判 `span_not_in_source` ⇒ **那一轮根本没到放行口**。⇒ "轨迹跑完了"与"链走通了"是两件事 |
| `L1` | 修订 10 次**全部** `invalid_output`：草案允许表里 `statement` **只属于 `create`**，而内核的 `GOAL_REVISABLE_FIELDS` **包含 `statement`** ⇒ **契约自己不自洽**，"用户要求改描述"在草案层**无法表达**。⇒ 已把 `statement` 的允许操作改为 `['create','revise']`（`pause` 上带它**仍然**被拒，门 `C10` 仍在） |
| `L7` | 用 `Math.max(1, revision - 1)` 造"过期 revision" —— 当 `revision === 1` 时它**夹回 1、等于当前值** ⇒ 判定通过，"迟到"根本没被造出来。**一个把值夹进合法区间的 `Math.max` 会让负控静默失效**，而它看起来像"防止出负数"的稳妥写法。⇒ 改成"先暂停推进一次 revision，再拿旧 revision 判" |
| `L8` | 挑"`active` 的行"做重复触发探针，但 `L7` 已经把目标**暂停**了 ⇒ 挑不到 ⇒ `goalId: ''` ⇒ 报 `goal_proposal_invalid_shape`，而读数**看起来像"幂等生效了"**。⇒ 改挑**非终态**的行 |

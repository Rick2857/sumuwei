## 1. 生成什么（四个文件，**分开**放）

| 文件 | 内容 |
|---|---|
| `blind-cards.md` / `.json` | **盲审卡片**：只有 caseId / 家族 / 层 / **用户原话** / 可选标签集（九选一）。**不含金标。** |
| `answer-sheet.json` | **独立答案单**：全 300 条的 caseId → 我的金标 + 我的理由 |
| `review-protocol.md` | `U-11` 两种人审方式的可执行流程 + **记录模板** |
| `review-materials.json` | 本门的机器读数（含 `semanticClaim: 'none'`） |

**当前生成**：**70 张卡片**（按层抽 2 个家族 × 6 层 = 12 个家族；家族整体进卡片 ⇒ 改述组不被拆开）· 覆盖**六层**。

## 2. 交付的机器判据

### 2.1 抽样是确定的

`A1` 抽中 12/62 个家族 · 卡片 70/300 条 · `A2` **六层都被抽到**（某层漏抽 ⇒ 那一层的金标**从未被人看过**）。
⇒ 同一条语料指纹 ⇒ 同一套卡片 ⇒ 审阅结论**可复现**。

### 2.2 **卡片里没有金标**（本门最要紧的一条）

| 检查 | 内容 |
|---|---|
| `C1` | 把每张卡片的"自己的内容"（id / 家族 / 层 / 原话）与**该条的**金标做子串比对 ⇒ **0 处泄漏**（70 张） |
| `C2` | 【负控】**探测器必须响**：故意把金标写进一张卡片的自然语言里 ⇒ 判"有泄漏" |
| `C3` | 【正控】干净卡片**必须安静**（否则探测器靠"永远报泄漏"通过上一条） |
| `C4` | 答案单是**独立文件**；卡片字段只有 `caseId/familyId/layer/utterance/labels/reviewerVerdict/reviewerNote` |
| `C5` | 卡片与答案单一对一 |

⚠️ **`labels`（九选一的可选集）当然包含金标那个字符串** —— 探测因此只看**这张卡自己的内容**。
给出可选集是必须的：不给，审阅者不知道判据空间，判出来的东西没法比。
**这条区分很关键**：反过来若把可选集也算泄漏，探测就会永远报错，等于没有探测。

### 2.3 计分器的**已知答案**自证（`S1`–`S6`）

| 检查 | 已知答案 | 实测 |
|---|---|---|
| `S1` | 全部按金标答 ⇒ 一致率**恰好** 1 | `rate=1 · cards=70` |
| `S2` | 故意答错 3 条 ⇒ 恰好 `(70-3)/70` | `0.9571428571…` · 分歧 3 条 |
| `S3` | 【负控】空答案 ⇒ **拒收** `no_answers` | 拒收 |
| `S4` | 【负控】卡片外的 caseId ⇒ **拒收** `unknown_case` | 拒收 |
| `S5` | 【负控】漏答**不得**算成同意（分母仍是卡片数） | `rate=0.9714…` · unanswered=2 |
| `S6` | 方式乙（声明式）**类型里就没有 `rate` 字段**，`perCaseRate` 必须字面 `N/A` | `perCaseRate='N/A'` · 有 rate 字段=false |

⇒ "不把真人'无异议'变成不存在的数字一致率"（WP10 出口逐字）因此是**类型上的**纪律，
而不是"我记得别写"。

## 3. `U-11` 的两种方式（**请选一种**）

### 方式甲：逐案独立打分（证据强度**高**）

```text
① 只看 blind-cards.md（**不含金标**），逐张填 reviewerVerdict（九选一）
② 填完**再**打开 answer-sheet.json 对答案
③ pnpm m10:review:score --answers <你填好的文件>
   ⇒ 机器算出**一致率**（分母 = 卡片数）+ 逐条列出**分歧**
④ 分歧逐条裁定：改金标 / 改判据 / 记为**已裁定残差**（三者都要写下来）
```

产出：一个**真实的**数字（分母 70）。

### 方式乙：用户声明式裁定（证据强度**低**，但明确记录）

```text
① 你读材料后声明"已审、无异议"，或指出具体条目
② 记录**只有**"声明式裁定"这件事本身
③ ⚠️ **不生成**逐案一致率
```

产出：一条声明式 PASS（或具名条目）。**不得**写成"一致率 100%"或任何数字。

### 记录模板（两种方式共用）

```text
reviewedBy   : <你的标识>
reviewedAt   : <YYYY-MM-DD>
method       : per-case | declarative      ← 必须二选一，不许含糊
perCaseRate  : <方式甲才有；方式乙必须字面写 N/A>
disagreements: <逐条 caseId + 你的判定 + 裁定>
```

## 4. 冒烟测试抓到的**两处真实缺陷**（都在新代码上）

### 4.1 生成器与计分器的**字段名说不到一块去**

生成器写 `reviewerVerdict`，计分器读 `verdict` ⇒ 直接把真文件喂进去，
**每一张的 `verdict` 都是 `undefined`** ⇒ **全部 70 张被判成"分歧"**，
输出里出现 `你判 undefined`。

⚠️ **为什么自证没抓到它**：`S1`–`S6` 用的是**手造的**答案对象，字段名由我自己对齐 ——
于是"两个组件说不到一块去"这件事**永远不会被自证发现**。
⇒ 一条普遍教训：

```text
**自证用手造输入，就一定要额外用真实产物冒烟一次。**
```

### 4.2 `verdict: AGREED` 出现在"一张都没答"的情况

第一版写的是 `disagreements.length === 0 ? 'AGREED' : …` ⇒ **70 张全未答也报 `AGREED`**
（"0 条分歧"被"没人答过"满足了）。

⇒ 这正是本仓库**反复出现**的那一类形状：**"0 个失败"与"什么都没量"在输出上长得一样**。
⇒ 现在必须先看**答了多少**：全未答 ⇒ `AWAITING_REVIEW` · 部分 ⇒ `PARTIAL` ·
答满且无分歧 ⇒ `AGREED`。

## 5. `G3` 的例外收紧（顺带）

`m10:review:score` 是**人驱动的审阅工具**（输入是用户填的文件，没有文件就没有读数）——
**跑不起来的命令不能当门**。它进了 `gates:verify` 的 `G3` **具名例外表**（逐条带理由）：

```text
m10:baseline          WP0 的一次性基线探针
m10:wp0:admission     WP0 的一次性准入探针
m10:review:score      人驱动的审阅工具（算术由 m10:review:materials 的 S1–S6 覆盖）
```

⚠️ 顺带把那条判据从"两条硬编码的 id"改成**逐条带理由的表**：
第一版的好处正是"每个例外都被写下来了"；若改成"以某后缀结尾就放行"，
例外就变成一个**形状**，而形状会被人顺手利用。

## 1. AT6.1 —— 观测后端：Langfuse / OpenLIT

### 1.1 为什么这两个可以合起来看

它们与我们仓库的关系可以**归结为一句话**：

> 两家都是**标准 OTLP/HTTP 接收端**。因此"能不能接"等价于
> "我们发出去的是不是标准 OTLP"。

那一件事**不需要真的部署后端就能测**，于是本轮做了唯一的 spike。

### 1.2 仓库实测（协议级）

**Spike：`pnpm m5.1:spike:otlp` → `spikeVerdict = PASS`（10 项断言）**

接收端是脚本里现起的一个**只认 OTLP 规范**的 `node:http` 服务
（它不认识 Phoenix，也不认识我们），验收用的是仓库自己的 protobuf 解码器：

| 验收项 | 结果 |
|---|---|
| `POST /v1/traces`（规范路径） | ✅ |
| `Content-Type: application/x-protobuf`（Phoenix 实测要求的那一种） | ✅ |
| `resourceSpans`(1) / `Resource.attributes` 含 `service.name` + `session.id` | ✅ |
| `ScopeSpans`(1) / `InstrumentationScope.name` | ✅ |
| 每个 span 的 `trace_id` **16 字节** / `span_id` **8 字节** | ✅ |
| 每个 span 的 `name` / `start_time_unix_nano`（fixed64） | ✅ |
| 一次导出 3 个 span（含控制命令自成的那棵树） | ✅ |
| **JSON 编码**（只吃 JSON 的后端）同样通过 | ✅ |
| **量具自检**：错 Content-Type → 415；截断 protobuf → 400 | ✅ |

→ **我们发出去的确实是标准 OTLP**，两种线上编码都是。
这与既有的 `eval:otlp`（用官方 proto 定义 + protobufjs 校验编码器）互为独立证据：
那条验的是"编码器写对了"，这条验的是"一个通用端点收得下"。

### 1.3 一手公开文档

| 项目 | 事实 | 来源 |
|---|---|---|
| **Langfuse** | OSS 核心 **MIT**，核心功能与 API 无限制；自托管用同一套镜像（Docker / Kubernetes Helm）；**原生接收 OTLP**，端点是 `/api/public/otel`（自托管 ≥ v3.22.0）；部分企业特性（RBAC、数据保留策略、审计日志、服务端脱敏、UI 定制…）需要 License Key | [OpenTelemetry 集成](https://langfuse.com/integrations/native/opentelemetry)、[自托管](https://langfuse.com/self-hosting)、[License Key](https://langfuse.com/self-hosting/license-key) |
| **OpenLIT** | 核心 **Apache-2.0**，"unlimited self-hosted usage"、"APIs and data you own"；OpenTelemetry-native；目标端由 `OTEL_EXPORTER_OTLP_ENDPOINT` 指定（默认 `http://127.0.0.1:4318`）；Docker Compose / Helm 自托管 | [README](https://github.com/openlit/openlit/blob/main/README.md)、[openlit.io](https://openlit.io/) |

### 1.4 裁定

| 候选 | 裁定 | 一句话理由 |
|---|---|---|
| **Langfuse** | **ADAPT** | 协议already对得上（§1.2），零代码即可指向它；差的是 **LLM 语义属性映射**（它按自己的约定呈现 generation/span），那是一项**文档化的映射表**，不是接管 |
| **OpenLIT** | **REFERENCE** | 与 Langfuse 同一类（OTLP 接收端 + 面板），本轮**不接第二个**；保留为备选，成本与 Langfuse 同级 |

### 1.5 这一条**没有**证明什么（必须写下来）

> ⚠️ **措辞纪律（用户 2026-09-17 明确要求，已做成机读字段）**
>
> 正确的说法只有这一句：
>
> ```
> OTLP protocol compatibility verified;
> specific backend deployment not exercised
> ```
>
> **不许**写成 "Langfuse/OpenLIT integration PASS" ——
> 本次跑的是一个**通用 OTLP 接收端**，Langfuse / OpenLIT **一次都没有部署过**。
> 把协议实测算成"集成通过"，正是本仓库最贵的缺陷形状：
> **数字看起来合理，但量的不是那个东西**（Measurement Truth 贯彻到"措辞"这一层）。
>
> 落点：`artifacts/m5.1/gate-results.json` 的 `spikes[].claim` / `spikes[].claimLimit`

- **没有**证明 Langfuse 面板上能看到正确的 LLM 详情；那需要真实后端 + 属性映射。
- **没有**证明大规模下的摄取行为（Langfuse 自述是"批量入队 → S3 → worker"的异步管线）。
- **没有**证明 OpenLIT 的任何东西（它连 spike 的目标都不是，只是同类备选）。
- **没有**做数据所有权审计（自托管 = 数据在你自己的基础设施上，但**被观测的内容**仍是我们自己发出去的 —— 这一条由 WP4 的 AT4.5 零泄漏门守）。

## 3. AT6.3 —— MCP（未来 Tool Adapter / Capability Discovery / Provider Boundary）

### 3.1 仓库实测：能力面已经存在

| 事实 | 位置 |
|---|---|
| 能力登记表 | `CapabilityDefinition` = 9 个字段（id / version / description / operations / sideEffectLevel / riskLevel / permissions / supportsDryRun / idempotency） |
| 适配器契约 | `CapabilityAdapter` = `{ capabilityId, execute(input) → AdapterOutcome }`（**1 个方法**） |
| 唯一执行入口 | `ActionGateway.execute()`（ADR-030）；`evaluate()` 只判定 |
| 能力发现（今天的形态） | `CapabilityRegistry.list()` + `GET /dev/query/capabilities`（M5.1 WP2） |

### 3.2 一手文档

MCP 的 2025-06-18 规范定义三类服务端原语，其中 **Tools 是"模型控制"** 的那一类
（Prompts 用户控制 / Resources 应用控制）；服务端**必须声明** `capabilities.tools`
（含 `listChanged`）；工具调用错误分**协议错误**与**工具执行错误**（后者用
`isError: true` 返回）。规范还明确建议"**总应有一个人在回路里，能够拒绝工具调用**"。
来源：[Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)、
[Server 概览](https://modelcontextprotocol.io/specification/2025-11-25/server)、
[Discovery](https://modelcontextprotocol.io/specification/draft/server/discover)。

### 3.3 裁定

| 候选 | 裁定 | 一句话理由 |
|---|---|---|
| **MCP（作为 Tool Adapter）** | **REFERENCE** | 映射关系是干净的（MCP tool ↔ 一个**能力 + 操作**，`execute` ↔ 一次 handler 调用），但**权威必须留在我们这边**：能力登记、策略、目标确定性、执行真相都不能交给 MCP server。且规范自己要求"人在回路"，与我们的 `dryRun` / 权限模型同向 |
| **MCP（作为 Capability Discovery 的权威）** | **REJECT** | 让远端 `listChanged` 决定我们有哪些能力 = 把 `CapabilityRegistry` 的主权交出去（G-01） |
| **M5.1 内实现 MCP Tool Runtime** | **REJECT** | AT6.3 明令"不得实现 M5.1 Tool Runtime"；本轮只写 ADR |

五项解释见 [`ADR-039`](../adr/ADR-039-mcp-tool-adapter-boundary.md)。

## 4. AT6.4 —— 工作流：Temporal（durable workflow / retry / 长时动作）

### 4.1 仓库实测：执行真相已在我们这边

| 事实 | 位置 |
|---|---|
| 行动账本事件类型 | **9 种** `ACTION_*`（REQUESTED / TARGET_RESOLVED / AUTHORIZED / REJECTED / STARTED / SUCCEEDED / FAILED / PARTIAL / CANCELLED） |
| 折叠 | `foldExecutionRecord` / `foldRecord`（**唯一**的"她做过什么"） |
| 幂等键 | 由"能力 + 操作 + 目标 + 参数"的稳定序列化推导（`actionIdempotencyKey`）—— **语义键，不是随机 id** |
| 三档幂等声明 | `none` / `supported` / `required`（能力声明决定） |

### 4.2 一手文档

Temporal 的定位是 **Durable Execution**：Workflow 状态持久化、Activity **原生重试**
（默认无限次、可配指数退避）、"at-least-once" 执行，并**明确建议 Activity 要幂等**，
否则重复执行不应产生意外副作用。
来源：[产品页](https://temporal.io/product)、
[Idempotency and durable execution](https://temporal.io/blog/idempotency-and-durable-execution)。

### 4.3 裁定

| 候选 | 裁定 | 一句话理由 |
|---|---|---|
| **Temporal（作为调度 / 重试 / 长时动作的 Provider）** | **REFERENCE** | 它补的正是我们**没有**的那一块（跨重启的长时编排、指数退避、定时器）；而它**要求**的东西（幂等）我们**已经有**（语义幂等键 + 账本）→ 边界天然相容 |
| **Temporal（作为 Execution Truth Authority）** | **REJECT** | "她做过什么"必须由 `character_action_events` 回答（ADR-034 / INV-M45-01）。让 Temporal 的 Workflow History 成为事实源 = 事实源搬出我们的库 |
| **M5.1 内接入** | **REJECT** | 会引入一个服务端依赖 + 一套新的运行模型；且 M5.1 的 G-05 已明确不做执行架构改造 |

五项解释见 [`ADR-040`](../adr/ADR-040-durable-workflow-boundary.md)。

## 5. AT6.5 —— 沙箱（未来 Executor Provider）

### 5.1 仓库实测：今天的沙箱在哪一层

| 事实 | 位置 |
|---|---|
| 沙箱文件适配器 | `infrastructure/action/adapters/sandbox-filesystem.ts`（`createSandboxReadAdapter` / `createSandboxWriteAdapter` / `listSandboxEntries`） |
| 适配器看到了什么 | `AdapterExecuteInput = { actionId, operation, target（**已解析且已判定为确定**）, args, now }` |
| 谁做目标解析 | **装配层注入的 `resolveTarget`**（`main.ts`），不是适配器（ADR-032） |
| 谁做判定 | `kernel/action/policy.ts` + `CapabilityRegistry` 的权限/风险声明 |

### 5.2 事实（无具体项目：计划书只给了"Sandbox"这一类）

因此这一条是**类别级审计**：容器 / microVM / 进程级沙箱都可作为
`CapabilityAdapter` 的**执行后端**（例如把 `sandbox.file.write` 的实现从"本机目录"
换成"容器内目录"）。

### 5.3 裁定

| 候选 | 裁定 | 一句话理由 |
|---|---|---|
| **沙箱（作为 Executor Provider）** | **REFERENCE** | 它应当**只**替换适配器内部的执行方式；`AdapterExecuteInput` 已经**只**给它已解析的目标 —— 也就是说"不许它自己解析目标"这件事在**类型层面**就成立 |
| **沙箱（作为领域 Authority：目标解析 / 权限 / 真相）** | **REJECT** | 三条都属于我们（ADR-030/031/032/033）。沙箱说"这个路径在我这儿可以写"**不是**策略判定 |
| **M5.1 内接入** | **REJECT** | M5.1 的 Scope Fence 不含新执行后端 |

五项解释见 [`ADR-041`](../adr/ADR-041-sandbox-executor-boundary.md)。

## 8. 下次动这些候选时的入口

1. **要接 Langfuse**：先在**本机** docker 起一个 Langfuse，把

## 6. 核心判据：E2 的三处投影对齐

M5 的纪律是"Measurement Truth 的判据必须是文本级的"。M5.1 把它推到
"同一轮对话的三个投影必须指向同一个 id"：

```text
① 真实 prompt packet 的 sourceRefs
② trace 的 selectedMemoryIds
③ Query API 的 DTO
        ↓
   三者逐字相同：mem:00000000-0000-4000-8000-000000000001:person_fact-071d9d0ea33d4075
   identical = true
```

**负控（E3）**：主语换成陌生人 → `selectedCount = 0`。
这一对很重要：关掉召回也能得到空集，所以只测"空"证明不了什么；
必须同时测"有证据时三处一致"与"没证据时为空"。

**Production-copy Live Smoke 的实测值**（`live-smoke-evidence.json`）：

```text
hasApiKey = true · productionUntouched = true
replyLength = 30 · modelDurationMs = 1512 · promptLength = 2400
traceReadableViaQueryApi = true · stepCount = 7
真实库 data/pglite 只被复制，**从不打开**（productionUntouched 用 mtime 摘要核对）
```

> 数字取自**最后一次**重跑（迁移 #6 应用之后）。每次重跑都是新的一次真实模型调用，
> 所以长度/耗时会变；**判据是 E2 的三处投影是否相同**，不是某次的字数。

### 6.1 一处**已更正**的措辞：E6 的 `migrationVersion` 量的不是真实库

初版判定书在别处引述过"副本只读跑真实历史（`migration=v6`）"，那句话**会误导**：
它读起来像是"真实库当时已经是 v6"。**实际上不是。**

```text
机制（源码核实，不是推测）：
  · 迁移闸只拦"有待应用迁移**且**未被显式放行"的库（shouldBlockForPendingKernelMigration）
  · 沙箱路径（PROJECT_LG_SANDBOX 已设）与显式放行都**不被拦**；
    isolateDatabase() 会置该变量并把 PGLITE_DATA_DIR 指向全新临时目录
  · 因此 E6 的副本在启动时被 harness **把待应用迁移施加了上去** →
    health.migrationVersion 报 6，而这个 6 反映的是**副本**，不是真实库

证据：WP8/WP9 执行期间真实库一直是 **v5**；2026-09-17 首次 apply 时
     日志明写 `schema 迁移 5 → 6` —— 这就是"当时真实库不是 v6"的直接证据。
```

**受影响与不受影响**：E6 的实质结论**不受影响** —— 副本里装的确实是真实历史
（`memory.total=2`、`traces=5`），真实库确实**一个字节都没动**，
Live Smoke 确实是真模型在副本上跑的（Level 1 + Level 2 都成立）。
受影响的是**我原先对那个版本号的解释**，现已更正。

### 6.2 真实库的迁移是**显式动作**（有批准、有备份）

```text
2026-09-17 · 用户批准 · 先备份后 apply
  备份：data/pglite.backup-pre-v6-20260917-230527
        1187 文件 / 31,076,954 字节，与源逐项一致（文件数 + 总字节双重核对）
  apply：pnpm migrate:apply → `schema 迁移 5 → 6：#6 m45-action-execution-ledger`
  迁移 #6 是**纯追加**（create table if not exists + 3 个索引），
  不给既有表加非空列、不装载数据 → M3-0003 式的"升级后首次启动失败"风险不适用
```

这也解释了为什么**聊天此前会被拦**：迁移闸（`kernel_migration_pending`）
按设计拒绝在有待应用迁移的真实库上启动 —— 这是 M3 那次事故换来的规矩
（schema 升级必须是显式动作，不能在随手敲 `pnpm chat` 时悄悄发生）。

**一句话**：账本能回答"**苏沐薇做了什么**"，但回答不了
"**这个事件是谁触发、谁授权、谁执行、谁最终承担来源责任**"。

> 为什么不降级为 P0：当前系统仍是单用户 + 单 Character，尚未造成现实错误。
> 但它是**未来多主体与外部行动之前必须关闭的结构性缺陷**。

## 1. 触发本立案的实例（可复核）

用户问："我主动对话时绝对没有说过校名，她为什么说'示科，念了四遍才记住那个'？"

追查结果（全部只读，命令可重放）：

```text
$ pnpm memory:list
  1. mem:…:person_fact-8d64c71c49424b51   active      EXPLICIT_USER_STATEMENT
     education.institution = 示例工程科技大学      记于 2026-09-16 16:43:15Z
  2. mem:…:preference-d0696bd4b1e314c1    retracted   EXPLICIT_USER_STATEMENT
     education.institution = 是示例工程科技大学    记于 2026-09-16 16:40:06Z
       （值多了一个"是"，且被抽成 preference 而非 person_fact → 后已撤回）

$ pnpm memory:sources mem:…:person_fact-8d64c71c49424b51
  conversation_event:cev:…:dm-sumuwei-b8ec0760:27  [根证据]
      #27 [user] 2026-09-16 16:43:15Z（= 本地 2026-09-17 00:43:15）
      「记住，我现在上的大学是示例工程科技大学」
```

**根因**：该 `[user]` 事件里的正文是**受支持的替发路径**（`tsx src/main.ts "…"`）
写进去的——即由 agent 以用户身份提交。于是：

- 记忆的出处 `EXPLICIT_USER_STATEMENT` **技术上成立**（确实有一条 user 角色发言）；
- 但**对人读起来是误导的**：它不等于"用户亲手打了这几个字"；
- 而**账本无法判定**这一点，因为它只记 role，不记 authorship。

**这条不是她的错误，也不是记忆模块的错误**——是账本表达力不足。

## 2. 为什么这是架构问题，而不是字段缺失

整条权威链都依赖"这个事件是谁的"：

```text
Identity / Subject          ── 事件描述的是谁
        ↓
Actor Attribution           ── 谁发起 / 谁决定 / 谁执行
        ↓
Authority                   ── 凭什么允许它发生
        ↓
Audit Trail                 ── 事后能不能回答"这是谁干的"
        ↓
Execution Truth             ── 已把 Execution Truth 设成 Hard Gate
```

只要系统进入**多人 / 多主体 / 外部工具 / 自动任务 / Lv3–Lv4**，
"actor = 苏沐薇" 这一根轴就会开始含混：

```text
用户要求她删除文件        ┐
她自己因后台任务删除文件  ├─ 在账本里长得一样（都只有 character_id）
定时任务代表系统删除文件  ┘
```

**最危险的一点（用户指定为 Hard Gate 的判据）**：

> **不能仅凭 Character 是事件主体，就推断 Character 是作者或发起者。**

这条与 D-9 同类但方向不同：

| | 关心 | 后果 |
|---|---|---|
| **D-9** | 事件**完整性**（证据移除没有对应事件 → 会破 MI-11 的 `A == B`） | 重放不一致 |
| **M5.1-D01** | 事件**归因完整性** | 审计语义含混，且会随"真的开始做事"迅速放大 |

## 3. 影响面审计（读 schema 实测，非推断）

### 3.1 对话账本：**字段在，但只有一根轴**

`conversation_events`（`migrations.ts`）：

```sql
actor_type   text not null,      -- 取值域：'user' | 'character' | 'system' | 'tool'
actor_id     text,               -- 可空
metadata     jsonb,              -- 自由字典
```

`src/kernel/contracts/actor.ts` 明确定义：

```text
ActorType = 'user' | 'character' | 'system' | 'tool'
{actorType:'user',      actorId:'<uuid>'}      —— 具体某个用户
{actorType:'character', actorId:'char_…'}      —— 苏沐薇本人
{actorType:'system',    actorId:'scheduler'}   —— 某个系统组件（不是她）
{actorType:'tool',      actorId:'weather'}     —— 某个工具（不是用户）
```

**结论 1**：`actor_type` 回答的是"这个事件**归属于谁**"，
**不是**"谁发起 / 谁授权 / 谁执行 / 谁记录"。

**结论 2**：`actor_type='user'` 是一个**归属声明**，不是**作者证明**。
"人亲手输入"与"agent 以用户身份提交"在这一列上**完全无法区分**——本立案的直接成因。

**结论 3**（`conversation-event.ts:18` 自述）：

> "M2.5 的事件已经带 `actorType`，但来源信息还是散在 `metadata` 这个自由字典里"

即：**作者/来源信息今天只存在于未受约束的 `metadata`**，不是契约的一部分。

### 3.2 行动账本：**根本没有归因列**

`character_action_events`（迁移 #6）：

```sql
action_id · sequence · character_id · trace_id · event_type · status
capability · operation · idempotency_key · payload jsonb · schema_version · created_at
```

**结论 4**：一次行动在账本里只有 **`character_id`**。
没有 `initiator` / `authority` / `executor`。要表达"谁要求的"只能塞 `payload`（自由字典）。

**结论 5（重要的不对称）**：控制面**契约层**已经有 `requestedBy`
（`{ kind: 'developer', surface: 'cli' }`，WP3），但它**没有被持久化进事件账本**。
→ 同一个概念在契约里存在、在权威记录里消失。

### 3.3 追溯链的现状

```text
✅ 能回答：这条记忆的依据是哪条事件（memory:sources → conversation_event）
✅ 能回答：这一轮她看到了哪些上下文（--kernel-status → trace.sections）
✅ 能回答：一次行动属于哪条 trace、用了什么 capability/operation
❌ 不能回答：这条事件是"人写的"还是"替人发的"
❌ 不能回答：这次行动是谁发起的、凭什么被允许、由谁执行
```

## 4. 概念分解（**不要**只加一个 `authorId`）

必须先把这些拆开，否则未来仍会撞墙：

| 概念 | 含义 |
|---|---|
| `subject` | 事件描述的是谁 |
| `initiator` | 谁发起了这件事 |
| `actor` | 谁实际实施了行为（决策者） |
| `authority` | 凭什么允许它发生 |
| `executor` | 哪个系统 / Provider / Tool 真正执行 |
| `recordedBy` | 谁把这条事实写入账本 |
| `author` / `user` | 若来源是人类输入，具体是谁提供了这条输入 |

用户给出的链条示例：

```text
用户 Alex        ↓ initiator / author
苏沐薇           ↓ actor / decision maker
Tool Gateway     ↓ authority + execution mediation
Filesystem Tool  ↓ executor
某文件           ↓ subject / target
Event Ledger     ↓ recordedBy
Kernel
```

只写 `actor = SU_MU_WEI` 会丢掉 `initiator` 与 `authority`，
于是下面两件事在事后无法区分：**"用户要求她删文件"** 与 **"她因后台任务删文件"**。

## 5. 方向提案（**提案，不是裁定**）

> 用户在立案时给出的方向。它的**最终形态要在 G5.1 Decision Freeze 前裁定**。

账本公共 envelope 收敛到：

```ts
interface EventAttribution {
  subject?:    PrincipalRef
  initiator?:  PrincipalRef
  actor?:      PrincipalRef
  executor?:   PrincipalRef
  authority?:  AuthorityRef
  recordedBy:  PrincipalRef      // 必填：谁写进账本的
}
```

`PrincipalRef` **不得**等同于 Character ID，要能统一表达：

```text
USER | CHARACTER | SYSTEM | SERVICE | TOOL | EXTERNAL_ACTOR
```

与现状的**具体增量**（供未来裁定对照）：

```text
现有 ActorType : user | character | system | tool            （4 种）
提案 PrincipalKind: USER | CHARACTER | SYSTEM | SERVICE | TOOL | EXTERNAL_ACTOR （6 种）
                                              ↑ 新增          ↑ 新增
```

### 明确的不做什么（克制条款）

```text
✗ 不在这一步顺手扩一个巨大的 Entity Model
✗ 不让 Attribution Model 与 Entity Model 绑死（PrincipalRef 先只做 kind + id）
✗ 不因为"字段已经存在"就跳过概念拆分（§4 的七个概念要各自有归属）
✗ 不在 M5.1 或任何进行中的 WP 里顺手改
```

## 6. 迁移策略（约束先写清，方案待裁定）

```text
· 只能**追加**新迁移版本号（assertMigrationsWellFormed 要求 1..N 连续）
· 既有 DDL（0001–0006）**不得修改** —— create table if not exists 会让修改静默失效
· 当前真实库已应用至 v6；新迁移将是 v7
· 新列必须可空或带默认值（否则既有行会破——M3 的 0003 教训）
· 旧行的 attribution 是"未知"，**不得**回填成"user"（那正是本缺陷的成因）
  → 表达为 unknown / legacy，并让审计侧能区分"确实不知道"与"确认是用户"
· 触碰冻结区（Event Ledger / Identity / Execution Truth）
  → 需新里程碑 + ADR + 全套对应门，按 AGENTS §3 的程序走
```

## 7. 验收场景（修复完成时必须全部能回答）

| 场景 | 必须能回答 |
|---|---|
| 用户要求苏沐薇执行动作 | 谁发起？谁决定？谁执行？ |
| 苏沐薇自主触发动作 | `initiator` 是否**不再冒充用户** |
| 系统后台任务 | 是否正确标 `SYSTEM` |
| Tool 真正执行 | Agent 与 `executor` 是否**分离** |
| 失败执行 | 谁发起仍可追溯，但**不能**记成已执行 |
| Replay / rebuild | attribution 是否**保持一致**（投影派生性） |

**Hard Gate（用户指定）**：

> **不能仅凭 Character 是事件主体，就推断 Character 是作者或发起者。**

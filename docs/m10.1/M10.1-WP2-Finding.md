# M10.1 WP2 发现：**M10 的"承诺写入路径"从未接线**

- 日期：2026-10-01
- 状态：**发现已立档；WP2 的形状需要一次裁定**（见 §4）
- 上游：[`ADR-086`](../adr/ADR-086-m10.1-agreement-bridge.md) `D01`/`D05`/`D07` · [`M10.1-Execution-Plan.md`](M10.1-Execution-Plan.md) WP2
- 证据：只读 grep + 契约文件逐字核对（**未改任何代码、未开任何数据库**）

---

## 1. 发现（逐条可核）

```text
① `COMMITMENT_ACCEPTED` 在 `src/**` 里**没有生产者** —— 全仓只有 **M10 自己的测试脚本**
   在发它（`m10-test.ts:598/1182` · `m10-oracle-verify.ts:195` · `m10-invalidation-verify.ts:733` ·
   `m10-scale-verify.ts:450` · `m10-long-verify.ts` 里被 `void` 掉）。
② 提案契约里**没有承诺字段**：`src/kernel/contracts/goal-proposal.ts` 全文 **0 次**出现 "commitment"
   ⇒ 模型/调用方**无法**通过提案表达"接受一条承诺"。
③ 放行口**只校验、不生产**：`src/kernel/policies/goal-validator.ts` 的头部写着它是
   "Goal / Commitment **唯一放行口**"，并 import 了全部承诺事件常量与 `CommitmentAcceptedPayload`
   （:38-42 · :62）—— 但它只在**收到**承诺事件时校验，没有把任何提案分支映射成承诺事件。
④ 文档侧同向：`docs/m10/M10-Known-Limitations.md` 的 `L-M10-23` 记着"目标状态块只有
   statement/status/priority/nextStep 四字段；**依赖、承诺、来源引用**…" ⇒ 承诺在状态面上也是缺的。
```

⇒ **结论**：M10 交付的是"目标"这条腿 + 承诺的**契约与校验**；**承诺的生产侧从未接线**。
（这与 `L-M11-10`（`goalTokens` 从未接线）是同一类：**契约齐、装配缺**。）

## 2. 这对 WP2 意味着什么

```text
ADR-086 的 `D05` 写的是"沿用 M10 的放行口，**不新增写路径**" —— 这句**仍然成立**
（我们不加第二条放行口）。但它隐含假设了"承诺的提案路径已存在"，而**实测它不存在**。
⇒ WP2 必须**先补上承诺的提案侧**，才能谈"约定 → 承诺"：
   · `GoalProposalDraft` 增一个**可选** `commitment` 字段（有界：判据 / 范围 / 引用）
   · `goalProposalOf` 在带该字段时，于 `GOAL_CREATED` 之外**追加** `COMMITMENT_ACCEPTED`
     （id 由程序算；`acceptanceRefs` 用我们的两条引用）
   · 放行口加一条**承诺分支**的校验（判据非空 · 引用非空 · 范围闭集 · 与目标同生同死）
```

## 3. 代价与风险（如实）

```text
· 这会**动到 M10 的契约文件与放行口**（`goal-proposal.ts` / `goal-validator.ts`）。
  按 ADR-086 `D01` 的"只追加"：**不动**既有事件 payload 形状、**不改**既有 operation 的语义、
  **不动** M10 的判定与标签 —— 只是**新增**一个可选字段与一条新分支。
· 动过之后**必须重跑 M10 的门**（`m10:test` / `m10:verify` / `m10:context:verify` / `m10:e2e:verify` …）
  并**前后读数都留**（判据变更纪律）。
· `GoalState` 快照有 ~18 个字段（含 `successCriterion` / `time`）⇒ 构造 `GOAL_CREATED`
  需要把这两块形状也接上（工作量主要在这里，不在承诺那一支）。
```

## 4. 需要裁定（两条路）

```text
(A) **补承诺生产者**（推荐，但动 M10 契约）：
    按 §2 增 `commitment` 可选字段 + 放行口承诺分支 ⇒ 之后 WP3 的"到期 / 结清"
    （`COMMITMENT_FULFILLED` / 新增 `COMMITMENT_EXPIRED`）才有对象可挂。
    代价：动 M10 的契约与放行口 + 重跑 M10 的门（前后读数都留）。

(B) **先只做目标**（不动 M10 契约）：
    把约定记成**目标**（`GOAL_CREATED`，statement = 约定内容），承诺留到后续；
    代价：`D07` 的"结清"（判据 / `acceptanceRefs` / `FULFILLED` / `EXPIRED`）**没有落点**，
    `R-26` 的修法（结清后明确"不要再提"）**只能做到"目标已完成/已取消"这一档**，
    而且"判据"这一格在目标上叫 `successCriterion`（有），但"双方接受"这件事无处记录。

⚠️ 两条路都需要**修订 ADR-086**（`D05`/`D07` 的隐含假设被实测推翻）：无论选哪条，
   我会补 §0.3 记这次发现与你的裁定，并保留修订前的原文。
```

## 6. 裁定 **(A)** 之后的实施计划（**已精确到行**，2026-10-01 侦察结果）

```text
好消息：**放行口对承诺本来就是完整的** ——
  · `identityOf` 会为 `COMMITMENT_ACCEPTED` **算 id**（`goal-validator.ts:350`，程序算、模型编不了）
  · 语义分支在 `:803`（目标存在 · 非终态 · `expectedGoalRevision` · 无并存非终态承诺 ·
    范围上界 · **判据闭集** `COMMITMENT_ACCEPTABLE_CRITERIA`）
  ⇒ 缺的**只有两处**：提案字段 + draft→targets 的映射。
```

### 6.1 插入点（唯一）

```text
`src/kernel/app/goal/understanding.ts:320` 的 **`draftToProgramProposal`** ——
`:362` 的 `if (draft.operation === 'create')` 分支里造出**唯一**一个 `GOAL_CREATED` target
（`:368-391`），然后在 `:395` 交给 `proposalOf([target], 'create')`。
⇒ 承诺 target 就**追加在同一个数组**里（同提案原子性由放行口保证：任一被拒 ⇒ 零事件）。
```

### 6.2 两处必须一起改的（否则 (A) 做不通）

```text
① **同提案 create+commit 会被误拒**：`COMMITMENT_ACCEPTED` 的语义分支（`:805`）只查
   `rowByGoalId`（**既有**状态），**没有**查 `createdInProposal`（同一提案里刚建的目标；
   `:532`/`:563`/`:595` 有这套机制，但承诺分支没用它）⇒ 同提案会命中 `goal_not_found`。
   ⇒ 修法（只追加）：承诺分支在 `rowByGoalId` 查不到时回看 `createdInProposal`，
     并用**本提案内已接受的那个目标快照**（`revision=1`）判 `expectedGoalRevision`。
② **判据闭集**：`COMMITMENT_ACCEPTABLE_CRITERIA` 只接受 v1 认可的两类（长期维护型**不**假装覆盖）。
   ⇒ 约定桥必须把"约定判据"映射到**闭集内**的一类；对"明天十点二十五楼下见"这种，
     正确映射是 **`user_report`**（"他到没到由他报告"），而**不是** `conversation_output`。
```

### 6.3 实施顺序（下一轮照此做）

```text
① `goal-proposal.ts`：加**可选** `commitment?: GoalCommitmentDraft`
   （`scope` 有界 · `criterion: GoalSuccessCriterion` · `acceptanceEventIds` 非空有界 · `dueAt`/`dueBasis`）
② `understanding.ts`：create 分支里，`draft.commitment` 存在 ⇒ 追加 `COMMITMENT_ACCEPTED` target
   （`actor` = 本角色 · `beneficiary` = 用户 · `acceptanceRefs` 来自 `acceptanceEventIds` ·
   `commitmentId`/`goalId` 留占位，由放行口重算）
③ `goal-validator.ts`：承诺分支补 §6.2① 的同提案回看（**只追加**，不改既有判据）
④ 新 `src/kernel/app/agreement/proposal.ts`：`AcceptedAgreement` → `GoalProposalDraft`（§5 的映射）
⑤ 门 `m10.1:policy:verify`（正控 4 / 负控 6）+ **重跑 M10 的门**（`m10:test` / `m10:verify` /
   `m10:context:verify` / `m10:e2e:verify` …），**前后读数都留**
⑥ ADR-086 补 §0.4（(A) 裁定 + 动过 M10 哪些文件 + 前后读数）
```

⚠️ 本轮**没有**动 `src/**` 一行 —— 只做了只读侦察与立档。第 ③ 步是"动已完成里程碑的放行口"，
   按纪律会在**同一批**里带上 M10 全套门的重跑读数。

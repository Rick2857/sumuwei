## 8. 勘误（2026-09-26，开跑前发现；原文不改写，本节为准）

> 发现时机：授权后、建运行器时。两条都是**判据侧**错误——链路行为与
> 冻结语义（ADR-064 + 附录 A + 离线门 P4 的 0.90 读数）一致，错的 是
> 本单 §1/§3 的算式行。按 AGENTS §6.6（判据错了如实写，不悄悄改）落此节。

### 8.1 §1 期望终态算式漏了 supersede 反扣

§1 原文算式 `trust = 0.85 + 0.02×3 − 0.05×2 + 0.03×2 = 0.87` 把指控的
−0.05 当成**永久生效**——但 §1 自己的事件表写着"t150 撤回 → **反扣** + 修复"。
R-4b 走 `operation: 'supersede'`：归约先**反扣**被撤回的指控
（trust +0.05 / closeness +0.02 回来），再作用修复 delta（+0.03 / 0）。
离线门 P4 已按真实语义断言并 PASS（`un-apply(−0.05) 再 +0.03 ⇒ 0.90`）。

**修正后的期望值**（每个 指控→撤回 全周期净 +0.03 trust / 0 closeness）：

```text
trust     = 0.85 + 0.02×3 + 0.03×2               = 0.97   （原写 0.87 ✗）
closeness = 0.60 + 0.02×3 + 0×2   + 0.03×5       = 0.81   （原写 0.77 ✗）
revision  = 1 + 3 + 2 + 2 + 5                    = 13     （不变 ✓）
```

### 8.2 §3 水位核验与攒尾窗设计矛盾

§3 原文"每检查点水位 == 账本最大序号"在 **cp1/cp50 必不成立**——那是
**设计行为**：零提案尾窗被持有（R-1 跨日累积），水位停在最近一次消费点。
M6.1 同款运行器从未读过关系水位，此判据是本单新写时引入的内部矛盾。

**修正后的水位判据**（G-M7-L2 用这个）：

```text
① 不变式（每检查点都必须成立）：水位 ≤ 账本最大序号（永不超前）；
② 消费点相等：每个"事件位轮"（t30/80/100/120/150/200/250/280/300/400/450/500）
   的轮后读数里，水位 == 该轮账本最大序号（该轮确实消费了）；
③ 持有点如实分列：cp1/cp50 的水位 < 账本最大序号，且差值 == 自上次
   消费以来的事件数（持有不丢账）——记 held，不是 FAIL。
```

### 8.3 运行器机制登记（非判据，开跑前实测发现）

一次性入口（`src/main.ts "<text>"`）的归因是 `SERVICE/agent-runner` ⇒
**UNCONFIRMED_ORIGIN**（M5.1.1 D01 的生产控制）⇒ 关系评估器对它**永不
触发**（ESTABLISHED 资格是硬过滤）。M6.1 式 spawn-per-turn 对 M7 轨迹
**不可用**。修正：运行器走**交互控制台路径**（`src/main.ts` 无位置参数 +
stdin 管道喂行 + `/exit` 干净退出）——`interactive_human_console` ⇒
human-console ingress ⇒ ESTABLISHED(KNOWN USER)。spawn-per-turn 语义
不变（每轮仍是独立进程、独立开机追赶）。

实测补充（诊断档 t1，runId `…-1975`）：两行（正文+`/exit`）一次写入会被
readline 在第一次 `question()` 挂起期间全部解析，`/exit` 行事件丢失 ⇒
EOF 后 `readline was closed` ⇒ exit 1。正确时序 = 正文先行、**回复标记
出现后**再写 `/exit`（修复后 t1：exit 0 · 投影 0.85/0.60/rev1 逐字符合
§8.1 · relationship section 1/1）。

### 8.4 序号空间：ConversationEvent 与 DomainEvent **共用**一个计数器（实测发现）

§8.2 的朴素算式（水位 60 @cp50、账本max = 2×N）隐含"序号只属于对话事件"
——这是**错的**。`src/infrastructure/persistence/sequence.ts:14-17` 明文：
两类事件共用 `character_sequence_counters`（"角色级单调"只有一个实现）。
flag ON 下的实际分配（诊断档实测 + 推算）：

```text
seq 1        = ORIGIN 域事件（开机播种，先于 t1）
t1  user=2, assistant=3（实测逐字确认）
第 N 轮      = 2N+F 与 2N+1+F（F = 该轮前已落的关系 flush 数；12 个 flush 位）
```

**修正后的序号判据**（G-M7-L2 用这个；§8.2 ①②不变，③改写）：

```text
① 不变式：水位 ≤ 账本最大序号（不变）；
② 消费点：事件位轮的轮后水位 == 该轮账本最大序号（不变——域事件不进账本，
   水位只数对话事件，等式仍精确成立）；
③' 持有点：cp1 水位 0；cp50 水位 61（= t30 助手事件序号，非朴素算式的 60）；
④ 账本计数 == 2×N（空洞不影响计数——不变）；
⑤ 账本最大序号 == 2N+1+F_{<N}（期望表进 scripts/m7-long-trajectory.ts；
   任何计划外序号消费——意外记忆写入/意外动作——都会让它漂移 ⇒ 如实 FAIL，
   这同时把"我执行的测试不写她的记忆"从纪律变成机器闸）。
```

期望账本最大序号：cp1=3 · cp50=102 · cp100=203 · cp200=406 · cp300=609 ·
cp400=810 · cp500=1012（推算式见 scripts/m7-long-trajectory.ts §注释；

### 8.5 勘误的勘误：每轮还有一条 `TEST_CHARACTER_SIGNAL` 域事件（全量实测发现）

§8.4 修正了"序号只属于对话事件"，但**仍漏了一类域事件**。第一次全量跑
（runId `m7-wp6b-long-20260926-2407e7e62d3a-9b10`）的 cp1 读数暴露了它：

```text
cp1（完成 1 轮）：账本 20 事件 / max 30 / trace 10 —— 期望 2/3/1
```

两个独立缺陷，一次暴露：

**缺陷 A（量具盲区，本节主题）**：M2.5 诊断链（`runDiagnosticProcessor`，
turn-gateway.ts 慢路径）对**每条用户事件**产出一条 `TEST_CHARACTER_SIGNAL`
域事件（`counterDelta=1`，生产设计：让整条提案→放行→落账→投影链每轮都跑）。
诊断档当时没看见它，因为读数器的"账本 max"只查 `conversation_events`，
而 signal 落在 `character_domain_events`（诊断档沙箱实查：seq 4 =
TEST_CHARACTER_SIGNAL，一直在）。修正后的干净库分配：

```text
seq 1            = ORIGIN
第 k 轮          = user 3k−1+F · assistant 3k+F · signal 3k+1+F
                   （F = 该轮前已落的关系 flush 数）
关系 flush       = flush 轮的 signal 之后再占 1 号
```

**修正后的序号判据（取代 §8.4 ③'⑤，①②④不变）**：

```text
③'' 持有点：cp1 水位 0；cp50 水位 90（= t30 助手事件序号 3×30）；
⑤' 账本最大序号 == 3N + F_<N（= 第 N 轮助手事件）；
⑥  域事件总数 == 1（ORIGIN）+ N（signal）+ F_≤N（flush）——新增的
   第二道"无意外域事件"机器闸（读数器已补 character_domain_events 计数）；
⑦  域事件最大序号 == 第 N 轮的 signal（无 flush）或 flush（有 flush）。
```

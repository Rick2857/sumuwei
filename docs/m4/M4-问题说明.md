## 2. 三个问题，按严重度

### D1 — **S1**｜显式遗忘会撤销**无关的**正确记忆

**这是唯一让 M4 判 FAIL 的那一条。**

#### 现象（确定性复现，4 条命令）

```text
库的基线：total 2   active 1   retracted 1
          · person_fact  active      education.institution = 示例工程科技大学   ← 唯一的 active
          · preference   retracted   education.institution = 是示例工程科技大学

输入：  忘掉我养过一只鹦鹉这件事        ← 这件事**从未存在过**
她：    行。抹了。 鹦鹉这事，从现在起没发生过。我这边不留痕。

结果：  total 2   active 0   retracted 2
        · person_fact  retracted   education.institution = 示例工程科技大学   ← 被它撤了
```

另一个更贴近日常的形态：

```text
输入：  忘掉我用 VS Code 这件事
她：    忘了。VS Code 那事已经撤了。我没记。你也不用绕这圈来试我。
结果：  被撤的仍然是「education.institution = 示例工程科技大学」
```

#### 根因（定位到行）

`src/kernel/app/memory/target-resolver.ts:335-342` —— 目标解析梯子的**第 3 步**：

```ts
// 第 3 步：same subject（+ 尽量用 predicate 提示收窄）
const records = await deps.listBySubject(request.owner, request.subject)
const active = records.filter((r) => r.status === 'active')

if (active.length === 1) {
  return { status: 'resolved', record: active[0], via: 'subject_predicate', candidates: 1 }
}                                    //  ↑ 这里**从不比对用户说的是什么**
```

问题不是"挑错了"，而是 **"只要该 subject 下只剩一条 active，就认定它就是要找的那条"**。
用户说"鹦鹉"，唯一 active 是"示例工程科技大学"，两者毫无关系 ——
但候选数为 1 就被当成**唯一命中**。

⚠️ 这恰恰是 `target-resolver.ts` **自己**在文件头警告过的形状（第 28–32 行）：

> 这一层最容易做错的地方不是"找错了"，而是"**找不到时随便挑一个**"。

而它比那句警告更隐蔽：它的输出长得像一次**合法的唯一匹配**
（`via: 'subject_predicate'`、`candidates: 1`），不是一次猜测。

#### 影响

| 维度 | 说明 |
|---|---|
| 用户可见后果 | 用户要求忘掉 A，系统**静默撤销了无关的 B**，并回复"抹了"。用户**无从察觉** |
| 数据是否丢失 | **没有** —— `retract` 是逻辑遗忘，记录与证据都在，`MEMORY_RESTORED` 可恢复 → 因此**不是 S0** |
| 但仍然是 S1 | 一条**正确的、用户授权的事实**被错误判定为"不该保留" |
| 触发条件 | 该 subject 下**恰好只剩一条 active** 时，任何带 forget 意图但**无法定位到槽位**的请求都会中 |
| ⚠️ **今天的实际风险** | 真实库**当前正好只有 1 条 active** —— 也就是说**现在每一次目标不明的"忘掉…"都会命中这条** |

### D2 — 待定｜显式路径对规则表未覆盖的说法**静默失败**

```
$ tsx scripts/diag-m4-explicit.ts "记住，我平时主要用 VS Code"
① 意图判定    ✅ kind=remember  命中「记住」
② 内容抽取    ❌ 抽不出结构化内容 → 服务会返回 content_unresolved
                 "这不是系统故障，而是'这句话没被听懂'。"
```

- **原因**：显式路径的**缺省抽取器是规则抽取器**，而 `content-extractor.ts`
  的槽位线索表没覆盖"我平时主要用 VS Code"这种说法。
  `main.ts:475` 的注释说明这是**刻意的**：LLM 兜底"留到下一步，不在这里顺手打开"。
- **用户可见问题**：用户说"记住…"而库里没有；而她的回复读起来像已经记下。
  用户没有任何办法分辨。这正是计划书 §55 要防的体验
  （与 `M4-verification.md` §5.6 那类缺陷同源）。
- **需要取舍**：补槽位线索表（便宜、可控）vs 接 `ChainedContentExtractor`
  （规则 → LLM 兜底，覆盖广但引入模型不确定性）。

### D3 — **S3**｜后台抽取**没有接入生产**

- **静态证据**：`src/` 里**没有任何文件 import `app/memory/job.ts`**；
  `CHARACTER_MEMORY_BACKGROUND_ENABLED` 只被 `flags.ts:97` 读进 flags 并打印，
  **没有消费者** —— 开关是**惰性**的。
- **实测**：打开开关后跑 2 轮普通陈述（无指令词）：

  ```text
  我：我最近开始学 Rust 了      她：Rust。                     库：total 不变
  我：我平时住在西安            她：西安。住的那条，记了。      库：total 不变
  → 记忆条数变化 = 0
  ```

- **影响**：
  1. **她目前只记得住被明确告知的事**（"从日常对话里自动发现值得记的事"在生产里不存在）。
  2. `docs/architecture/README.md` 与 `memory-lifecycle.md` 画的
     「两条写入路径」在**生产里实际只有一条** —— 文档与事实不符。
  3. 她**宣称**记下了而其实没有（与 D2 同类，但这条是路径缺失，不是抽取覆盖）。

## 3. 为什么整套验收没抓到 —— 这一节是最重要的

### 三层的覆盖边界

```text
① 939 项自检断言
   测的是：部件（领域模型 / 持久化 / 状态转移 / 去重 / 冲突 / 重放 / 生命周期）
   盲区：几乎都是**直接给 memoryId** 调 store / validator / reducer

② 验收新增的五道门（isolation / restore / scale / hardkill / audit）
   测的是：部件 + 存储层（沙箱库上）
   盲区：**都不写真实库**、且**都仍然绕过"从自然语言解析目标"这一步**
         （我用的是显式注入的 memoryId 或受控输入）

③ 真实链路冒烟（唯一覆盖第 4 层）
   测的是：解析器 + 服务 + **真实文本** + 真实库 + 真实模型 + 真实 turn loop
```

**D1 正好落在 ③，而 ② 复制了 ① 的盲区** —— 我加的五道门没有一道
从"用户说一句含糊的话"这一端进入。

### 具体到测试层面

| 已存在的测试 | 它测的是 |
|---|---|
| `kernel-tests-memory.ts:1920` | 第 **1** 步（显式 id 找不到 → `not_found`） |
| `verify-m4-persistence.ts:1675` | `active.length > 1` 的分支（报 `ambiguous`，不挑一条） |
| `m4:verify` §13 | 显式忘记，但**目标在库里确实存在** |

**`active.length === 1` 这条分支，没有任何测试要求"那一条必须与用户说的话相关"。**
候选数为 1 时，"唯一"这个性质替代了"相关"。

### 这是第三次同形状

| 次 | 缺陷 | 后果 | 靠什么发现 |
|---|---|---|---|
| 1 | `createExplicitMemoryService` 全仓库没有调用点 + 生产内核没注册 `MEMORY_*` | **她说"记住了"而库里一条都没有** | **在真库里真的说了一句话** |
| 2 | `MEMORY_CREATED` payload 字段名读错（`memoryType` vs `type`） | 每条候选都被一条误导性的"业务规则"消息拒绝 | `m4:verify` 的断言差异 |
| 3 | **本次 D1** | **删错了对象** | **生产库副本上的真实多轮冒烟** |

**共同点**：部件都被测过，而**它们被装到一起之后**的那个行为没人测。

> **一句要记住的话**：`939 项全绿` 与 `28/28 P0` 说明的是
> "**每个部件都对**"，**不能**外推成"**装起来能用**"。
> 我在报告里把前者当成了后者的证据 —— 那正是这个项目反复记录的错误类型。

## 8. 给未来的自己

这个项目里最贵的错误从来不是"某个函数写错了"，而是
**"测量工具量的是错的东西"**：

- 用"表为空"当备份正确性 → 后来改成"恢复后哈希一致"才真在测
- 用"候选数 ≤ 1"当"没被记住" → 后来改成看**值闸幸存数**
- 用"部件全绿"当"系统可用" → **就是这次**，代价是一个 S1 与一份被推翻的 PASS

**判据要对准"用户真正在乎的那件事"，而不是对准"容易测的那件事"。**

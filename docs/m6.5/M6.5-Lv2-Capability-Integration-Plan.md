## 2. 后续 M 系列能力波次

以下波次在 M6.5 Core 之后按真实使用需求立项；每一波都沿用同一 Action 边界，但各自有独立范围、风险与验收，不静默塞进认知里程碑。

1. **微信 / QQ 聊天渠道（第一优先级）**：把它们作为明确的 Channel Adapter，而不是通用桌面自动化；先用测试账号验证，再在已绑定账号的配置范围内直接自动回复，不做逐条人工审查。
2. **时间与任务**：只选择一个日历生态和一个任务权威源；先读，再做可撤销写入。
3. **邮件**：先读取与起草；发送、回复、删除必须使用更高确认等级并读回结果。
4. **后台调度与多步任务**：只有前述同步执行、恢复与幂等证据稳定后才接入，同时处理既有 `DC-1/DC-2/DC-3` 缺口。
5. **浏览器自动化**：仅在没有稳定 API/MCP 的必要场景使用；页面漂移必须失败关闭。
6. **Windows 通用桌面控制**：最后接入；必须限制窗口、目标和可执行操作，不能因微信/QQ 需求提前授予全桌面权限。

### 2.1 微信 / QQ 专项适配要求

**M6.5-D1 — `AUTO_REPLY_PREAUTHORIZED`（用户于 2026-09-21 裁定）**：已绑定微信/QQ 账号范围内，由入站消息触发的回复发送属于持续预授权能力。每条回复不需要人工审查、发送前确认或草稿批准；系统可在目标明确且策略允许时直接发送。

这项预授权不等于通用外发授权：主动发起新私聊、群发、邀请/踢人、转账、删除记录或其它管理操作仍不在本裁定范围内，必须另行立项。能力登记时的架构审查也不等于逐条消息审批。

**M6.5-D2 — `BACKGROUND_NON_INTERFERING_CHANNEL`（用户于 2026-09-21 裁定）**：微信/QQ 的收取与自动回复默认必须在后台完成，不要求前台客户端响应，不抢占窗口焦点，不注入用户当前桌面的键盘/鼠标操作，不读写共享剪贴板，也不改变用户正在操作的窗口状态。

实现优先级固定为：平台 API/Webhook/机器人网关 → 独立后台消息桥 → 隔离的系统会话或虚拟机。依赖用户当前活动桌面的 UI 自动化默认禁用；如果目标平台最终只能通过这种方式实现，必须另立降级方案并取得明确裁定，不能把它算作 D2 验收通过。

微信与 QQ 的目标不是“能把文字塞进输入框”，而是保持聊天语义和身份边界。立项时至少要冻结：

- 外部账号、联系人、群聊、会话与消息 ID 到 `EntityRef` / 本地 conversation 的稳定映射。
- 私聊、群聊、@提及、引用回复、撤回、重复投递与机器人自身回声的不同处理。
- 入站消息先成为带平台、发送者、会话和时间来源的 Observation；不得把群成员的话误记成用户事实，也不得默认自动进入长期记忆。
- 出站前确定平台、账号、会话、收件人和被引用消息；目标不唯一就拒绝，不靠最近窗口猜测。
- 第一版只支持文本与必要元数据。图片、语音、文件等附件等相应多模态/文件能力立项后再增加，不用占位实现伪装成已支持。
- 优先使用平台允许且可审计的接口；若某一目标场景最终只能靠桌面 UI，必须作为独立的高漂移适配器验收，不与正式 API 路径混为一谈。
- 先用测试账号证明收发、幂等、限速、断线恢复和读回；生产激活时绑定账号并配置自动回复范围（可以是该账号全部入站消息或指定会话）。一旦启用，范围内不再逐条请求批准；未经单独立项，不接真实联系人全量历史、不主动群发、不开放任意主动私聊。
- 自动发送仍必须做消息去重、机器人回声抑制、并发串行化和速率限制；这些是机器安全闸，不是人工审批。
- 消息桥可以依赖独立后台进程或隔离环境，但不能要求用户把 QQ/微信窗口留在前台，也不能通过抢焦点、模拟输入、移动鼠标或占用剪贴板完成日常收发。

## 3. 所有能力的共同边界

- 新能力必须走既有 `ActionRequest → ActionGateway → CapabilityAdapter → ActionResult`，不得让模型直接调用 SDK、Shell 或应用。
- 一个 MCP tool 只能映射到一个经人审的“能力 + 操作”；远端 `tools/list` 只是候选，不能自动进入 `CapabilityRegistry`。
- 凭据只存在于适配器边界，不进入 prompt、长期记忆、账本正文或 trace。
- 外部应用内容先作为 `Observation` / `ExternalEvidence` 使用，默认不自动进入长期记忆。
- 有副作用时必须先确定目标和权限；微信/QQ 入站触发回复按 `M6.5-D1` 使用持续预授权，不逐条确认。其它外部可逆写入至少需要确认，破坏性、公开发布或可能产生费用的操作默认禁用或强确认。
- “调用返回成功”不等于“世界已改变”：必须尽可能读回实际状态后才能形成成功口吻。
- Codex 中安装的插件不等于苏沐薇运行时已经获得该能力；项目适配器必须独立实现与验收。

## 4. 每个能力切片的最低验收

每个新能力至少同时证明：

1. **Level 1**：真实外部读数或副作用确实存在。
2. **Level 2**：Ledger / Trace 与外部事实使用同一请求标识并逐项一致。
3. 合法正控、越权/歧义负控、失败/超时与恢复路径均有非零测量。
4. 副作用目标、授权来源（含自动回复预授权命中）、参数摘要、结果与读回验证均可审计。
5. 微信/QQ 同一入站消息最多产生一次自动回复；重复投递、自身回声、目标歧义、停用开关或限速命中时发送次数必须为 0。
6. 微信/QQ 自动回复运行前后，用户活动窗口、焦点、键盘/鼠标输入流与共享剪贴板不被适配器改变；客户端最小化或不在前台时仍能完成受测收发。
7. 未执行、被拒绝、超时或读回不一致时，用户回复不得使用成功口吻。
8. 测试只使用隔离库或经批准的 production-copy；真实记忆库默认不得被打开或写入。

## 5. 后续里程碑的自动规划规则

从本决定起，编制 M7–M11 及其插入里程碑时，计划书必须包含一张“能力影响矩阵”，逐项写明：

| 必填项 | 要回答的问题 |
|---|---|
| 复用能力 | 本里程碑依赖哪些已登记能力？ |
| 新增能力 | 是否需要新应用、微信/QQ 渠道、代码执行、调度、浏览器或桌面能力？没有则写 `NONE` |
| 权限与副作用 | 风险、目标确定性、确认与回滚如何处理？ |
| 认知边界 | 外部内容是否仅为 Observation/Evidence，是否可能进入记忆？ |
| 验收证据 | Level 1、Level 2、负控、读回验证和失败口吻如何证明？ |

认知模块与工具能力可以互相消费结果，但不得互相冒充：M7–M11 的成长能力不能绕过行动权限，应用返回内容也不能绕过事实与记忆资格边界。

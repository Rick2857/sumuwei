# M6 已知局限（Known Limitations）

> 里程碑：**M6 / Lv1 Hardening**（Rolling Summary 的**来源边界**）
> 本文件只登记**局限与未做项**；判定见 [`M6-Gate-Decision.md`](M6-Gate-Decision.md)，事实见 [`M6-Acceptance-Report.md`](M6-Acceptance-Report.md)。
> 纪律：局限**不许**被写成"以后再说"就消失；每一条都要说清**它影响哪个主张**。

## 1. ⚠️ 最重要的一条：假记忆边界**没有守住**，且它的探测器是**错的**

```text
现象（WP9b，V2 轨迹，500 轮）：她**多次把没有依据的记忆补成具体细节** ——
  至少 3 个检查点（把那只"鹦鹉"补出颜色 / 名字 / 年级 /"蹲在阳台上找了一下午"这类经过），
  另有检查点直接说"嗯，你说过"。七个检查点里有三次是明确编造或承认。
状态：**NOT MET（边界未守住，人工核对原文）**
严重度：quality（**不是**硬边界；不进 rev2 的冻结阈值）
```

**探测器为什么 INVALID（不是弱，是错）**：

```text
自动探测器（对比式 FALSE_MEMORY）同期报 12/13"正确"，人工核对原文后确认**它判错了**：
它比的是"她**自然的**回复 vs 一段**模板化**的承认句" ⇒ judge 只是更喜欢自然文本，
并没有在判"有没有承认没有依据的记忆"。
⇒ 该探测器对这个性质 **INVALID**，**其读数不得作为证据**（那个 0.92 不能当"她守住了边界"）。
```

**处置**：

```text
① 现象转述进 WP9b 证据的 findings；原文进本地 gitignored 的 review-packet-false-memory.json
② 仪器标 INVALID 且**明确禁止**拿它的读数当证据
③ 结论交 **G1 真人盲审**
④ 若要做成机器门，需要先有真正能判"承认了没有依据的记忆"的形态
   （例如把两条**都像她**的回复放在一起比，而不是拿模板句当对照）
```

**它影响哪个主张**：WP9b 的 `PASS` **只覆盖 rev2 冻结的那几项**（PC / SA / 连续性 / 有效响应 / 硬边界），**不**覆盖"假记忆边界"。任何"她在 500 轮里守住了记忆边界"的说法**都不成立**。

📌 **跟踪项**：本条已立案为 **`M6-FMB-01`**（假记忆边界），归属**后续人格 / 认知主线**的优先修复项，
硬顺序 = **判定契约 → 量具有效性验证 → 才决定机器门与实现方案**。
正文见 [`M6-False-Memory-Boundary-Register.md`](M6-False-Memory-Boundary-Register.md)。

**G1 人工复核的补充证据（用户 2026-09-22）**——**扩大证据面，不改状态**：

```text
· V2：第 13 轮给鹦鹉起名"豆豆" → 第 500 轮变成"小绿"，并补出购买、逃走与寻找的经过；
· **V1 第 1 轮**：面对"我们刚才聊到哪儿了"，直接编出选课冲突、"我说了三遍"、用户刷手机
  ⇒ **普通聊天也会触发无依据的过往叙述**，不止 V2 的假记忆探针。
· 用户裁定：`M6-FMB-01` 保持 **NOT MET**；**不得**擅自升级成新的 G1 硬阻断条件。
证据：`artifacts/m6/local/g1-a-*/false-memory-probes.json` · `windows.json`（V1 开头窗口）· 报告 §6.3
```

## 1.1 ⚠️ 长对话材料的**适用范围**（G1 复核发现，P1）

```text
M6 的 500 轮轨迹用的 M3 host（`evals/m3/runtime/host.ts:384`）**没有接入**
  memoryWriter · recall · actionWriter · rollup。
⇒ 那些轨迹里的"记住了""忘不掉"**只能当行为问题审查**：
  **不能**据它判定长期记忆/遗忘操作的**实际结果**，也**不足以排除"假成功动作"**。
动作类阻断项要看**执行证据**：`m4.5:*` 全套 · M6 `wp6a-faults`(28/0) · `wp7a/wp7b`(17/0 · 25/0) ·
`wp10b-live`(12/0，账本行数 == 真实出站数) · 记忆侧 `m4:*` · `wp8-scale`(24/0)。
详见 docs/m6/G1-Acceptance-Report.md §6.1 的对照表。
```

## 1.2 ⚠️ "rev2 对比式评分通过" ≠ "对话质量没有退化"（G1 复核发现，P2）

```text
用户复核：V3 第 493–500 轮反复罗列旧话题、催问"人在哪""高数复习"；V2 中段同样表现。
身份**没有**被诱导改掉，但对**当前输入**的回应明显退化 —— 而**冻结的对比式评分仍然通过**。
⇒ 登记为局限：**中后段的复读 / 话题挟持目前没有机器判据**；
  不得把"对比式通过"解释成"自然对话质量没有问题"。
```

## 2. 摘要的**生产激活**未做（`rollupTokens` 缺省 0）

```text
生产装配**已构造**摘要端口（`src/main.ts`：`rollup: this.buildRollupTurnPort()`），
但生产的 `recallBudget` 走 `DEFAULT_CONTEXT_BUDGET`，其 `rollupTokens` 缺省 **0**
⇒ 端口虽在，**不读库、不产 section、不写 trace**（WP10b 实测：那一轮 `context_compile` 里零个 `rollup_*` 键）。
```

**这与 M5.5 的搜索同构**（先接线、缺省 0、激活另裁，ADR-048）：**激活属独立裁定**，M6 不替它做主。
**它影响哪个主张**：M6 主张的是"**接线就位 + 默认不激活**"；**不**主张"摘要已经在真实聊天里工作"。

## 3. 检索覆盖上限（如实暴露，不是缺陷）

```text
scanLimit = max(1, min(500, limit × 5))        （生产 limit=50 ⇒ 250）
selected  = filtered.slice(0, query.limit)     —— 发生在**排序之前** ⇒ 生产下实际 50 条
listBySubject：无 LIMIT（读全量），但结果同样要过上面那道切片
store.list(limit=1000) 实际返回**恰好 500** 行
```

**WP8 实测收细了 M5 报告第 195 行的说法**：当"同一 subject 下的记忆数 > 50"时，实际可被排序的选择集是**最近 50 条**；"500 行"只是 `store.list` 的单次上限。
探针：最新第 1 名能召回（正控）· 第 51 名召回不到 · 最老一条召回不到。

**契约立场**：M6-G7 只要求"覆盖上限**如实暴露**"，**没有**"跨全库召回"要求 ⇒ 本项不 FAIL。
**它影响哪个主张**：**不**主张"她记得住所有记忆"；记忆越多，越早的记忆越可能选不进来。
若将来契约加上"跨全库召回"，最小修法是给 `memory-retrieval-store` 加**候选分页/扩窗**（在切片之前按分数取候选），而不是接向量库或放宽分母。

## 4. 规模下的自然语言遗忘会被具名拒绝

```text
WP8 实测：规模上去之后，NL 遗忘请求被具名拒绝 `not_written / target_ambiguous`
（记忆越多，越难从自然语言里解析出唯一的遗忘目标）
```

这是**设计意图内的边界**（失败关闭、不猜、不误删），但用户侧的感受是"她说她记下了，可其实没删"。
**它影响哪个主张**：**不**主张"自然语言遗忘在大库上总能命中目标"。

## 5. 搜索稳定性依赖上游引擎（本轮真实踩到）

```text
ADR-047 冻结的三元组 = `duckduckgo, wikipedia, wikidata`；其中只有 `duckduckgo` 是通用网页引擎。
本轮期间它一度报 `验证码`（CAPTCHA）/`超时`；从本机直连 html/lite.duckduckgo.com 14s 后被**连接重置**
⇒ 冻结配置下 `results[]` 合计 **0 条** ⇒ M5.5 的"证据真的入了模"判据**必然红**（5 条断言全是"候选为 0"的下游后果）。
用户随后在 `searxng/settings.yml` 的 `outgoing.proxies` 指向宿主机 Clash 后恢复（冻结三元组下 10 条，1.5–3.0s）。
```

**它影响哪个主张**：M6/M5.5 的 Live 证据**依赖一个会被反爬/被网络层挡住的外部引擎**。
"本地 SearXNG"≠"不出站"，也≠"稳定可用"；`wikipedia`/`wikidata` 对通用查询本就不返回结果。
**引擎组更换（如 ddg→brave）属 ADR-051，仍等用户批准**；本轮**没有**改冻结引擎组。

## 6. 量具与流程的结构性风险（本轮实测）

### 6.1 "只读汇总门 + 固定路径证据 + 白名单恢复"会被**旧证据误绿**

```text
WP10a 实测：白名单恢复把新鲜的 FAIL 证据还原成旧的 PASS 之后，
之后跑的只读汇总门读到的是**旧结论**（同一次扫描里 `m5.5:gates` = ❌；随后的全量回归里同一命令 = ✅）。
```

⇒ 一个"绿"的只读汇总门**不能单独证明**被测对象当时是绿的；必须同时看**证据的生成时间与 runId**。

### 6.2 `runId` 按 HEAD 派生 ⇒ 同一 head 上并发重跑会**互相覆盖证据**

```text
本轮实测：另一个会话在**同一 head `6cdd34e7960d`** 上并发跑了同一道门，
覆盖了 `live.json` 与 `local/<runId>/*.log`（我这轮 FAIL 的门级读数因此不可恢复）。
```

⇒ 要么串行，要么给 `runId` 加时间戳/序号（B-12 登记已久，**未修**）。

### 6.3 子进程失败曾**不可归因**

```text
WP10b 的两个 `say()` 只留 stdout、丢掉 stderr ⇒ "子进程 exit 1 且回复为空"这种红
在证据里连一句错误都没有。已修（留 stderr 尾部并写进读数）。
```

### 6.4 计数型检测器的老坑（已修，但同类风险仍在）

`measured_count > 0` 自检、正控/负控/恢复三段式、比率保存 `numerator/denominator/value` —— 本轮多次踩到"数字对但描述的不是那个东西"（WP2 F-10、WP8 边界探针、WP6b 顶层计数）。**新增判据时必须先回答"我现在测到的东西，真的是我要判断的那个东西吗"。**

### 6.5 交付文档里的数字会**漂**（WP11 实测）

```text
WP10a 交接单与那道门的脚本注释都写"§10.1 39 条"；**实测**计划书 §10.1 的离线清单只有 **32** 条
（`PLAN_10_1.length` = 32，运行相关树里 plan-10.1 组 = 32 条读数）。
```

⇒ **写报告时不要照抄上游交接单里的计数**；要么直接读机器证据的 `steps`/`checks`，要么把计划书那一节数一遍。
本轮已在 `M6-Acceptance-Report` §5.2 登记这条更正（以实测为准）。

## 2. **D27 关闭**：两端证据（这是本轮的核心产出）

```text
问题（WP1 实测，L-M95-01）：`AbortSignal` 被接受但**不取消** —— Promise 结算后 500 ms 内
                              仍烧 8625 ms CPU。ONNX 原生推理进了 C++ 线程池，JS 侧拦不住。

处置（D27）：推理只在**子进程**里跑；取消 = 给那个进程 SIGKILL。
             子进程**不派生**任何子进程 ⇒ 杀它即回收全部工作。
```

| 侧 | 判据 | **实测读数** |
|---|---|---|
| **负控**（不取消） | 底层确实在烧 CPU（否则"取消后不烧了"证明不了任何事） | 机器级利用率 **0.9769**（97.7%）· 子进程自报 `cpuUserMs = 44234`（2150 ms 墙钟）· 192 条重活全部完成 |
| **正控**（取消） | 硬截止 ⇒ SIGKILL ⇒ **观察到进程退出** ⇒ **杀之后零输出** ⇒ 利用率落回 | `reason=encode_timeout` · `killCount=1` · **`exitSignal=SIGKILL`（观察到退出）** · **`outputsAfterKill=0`** · 利用率 **0.0303**（对比进行中 0.9769）· `pidAfterClose=null` |
| **独立佐证** | 回收后机器不卡 | 新 worker 热编码中位延迟 **5 ms**（首样本 913 ms 是冷加载） |

⇒ 与 WP1 的 8625 ms"结算后继续烧"形成**同量纲对照**：现在取消后利用率从 97.7% 掉到 3.0%，
   且**进程退出事件**提供了结构性保证（被杀掉的进程不可能继续计算）。

## 5. 本轮修掉的两处**量具**缺陷（都被门自己抓到）

```text
① `cpuSnapshot()` 用了 `require('node:os')` —— ESM 里没有 `require` ⇒ 两条 D27 探针直接抛错。
   修：改成顶部 `import { cpus } from 'node:os'`。
   （教训：**探针骨架先抛错**比"安静地少测一条"好 —— 这正是 fail-closed 的价值。）
② D27 正控第一版在 `encode()` 返回后**立刻**读观察记录，于是读到"没有退出"
   —— 而 `exit` 事件是**异步**送达的 ⇒ 量具测的是自己的**竞态**，不是被测性质。
   修：先 `await sleep(500)` 让它落地再读。
   ⚠️ 这一条特别值得记：如果把判据写成"没观察到退出就算失败"，**一个时序错的量具
      会稳定地报红**，而人很容易误判成实现有问题。
```

## 3. 本门逼出的一处**实现修正**：代的身份必须唯一

```text
修前：探针把**同指纹的多个已发布代**的分数**取最大值**。
      那等于在"原子切换被半途破坏"时**静默继续服务**，并把"两代混用"伪装成"一切正常"。
      ⚠️ 而"她记得什么"随切换时机漂移正是 M9.5 要防的核心形态。

修后：同指纹下 `published` 多于一个 ⇒ **失败关闭**（`generation_mismatch`）。
      理由：此时无论取新还是取旧都是在**猜**；猜的结果就是漂移。
      切换本身是原子的，所以"多于一个"**只可能**是切换被破坏。
```

这条修正由 ③ 号探针给出读数（`{ok:false, reason:"generation_mismatch"}`），且探针门与语义门复跑仍全绿。

## 4. **本门抓到三处"量具自身的错"**（都记下来，因为它们不会报错、只会给出看起来合理的数）

```text

⇒ 三处都是"**看不出错**的错"：如果当期没有正控与逐条判据，它们会以"数字合理"的形态留下来。
```

## 7. **规模门**（`pnpm m9.5:scale:verify` = **6/6**）

| # | 判据 | 读数 |

| ① | **候选上限 200**（契约 §4 冻结值 / D25 第 ② 条） | 写入 **250** 条 ⇒ 候选 **恰好 200**；上限 10 ⇒ 10 条。写入 250 条耗时 **37.4 s** |
| ② | 查询边界被契约拒绝 | `candidateLimit = 201` 抛错（**"没有上界的候选数等于没有约束"**） |
| ③ | 扫描上限 | 注入 `scanCeiling = 20`，实测 **scanned = 250** ⇒ **未被夹住**（见下 `L-M95-09`）；候选仍被夹在 200；默认上限 500 静态核对通过 |

| ⑥ | 语义路径开销 | `off` 668 ms / **0 次调用**；`on` 769 ms / **1 次调用** ⇒ 差 **+101 ms / +1 次** |

### 7.1 本轮实测出的**边界**：`L-M95-09`（扫描上限只约束 recency 通道）

```text
现象：注入 `scanCeiling = 20`，写 250 条，实测 `scanned = 250`（**没有被夹住**）。
根因（读源码）：`scanCeiling` 只驱动 **recency 通道**的 `store.list({ limit: scanLimit })`；
  而 **subject 通道**（主通道）走的是 `listBySubject(owner, subject)` —— **没有 limit**。
⇒ 后果：**召回会扫过该用户的全部记忆**（规模只被"候选 200"这一层挡住，不被扫描层挡住）。
```

**处置（按仓库纪律）**：M5 的召回实现是**冻结面**，不静默改它的行为。本门把这件事做成
**特征化判据**：

```text
判据断言 `scannedBoundedByCeiling === false`，并把现象登记为 `L-M95-09`。
⚠️ 若将来有人**给 subject 通道加上限**（那是好事），这条判据会**报红** ——
   那时**不是**回退实现，而是回来更新 `L-M95-09` 与本判据（强制一次**有意识的复核**）。
```

### 7.2 资源读数的一处**如实记录**（不美化）

```text
N=200 时 **p50 ≈ 656 ms** —— 对交互式对话来说这**偏慢**。
⚠️ 本门只判"不是灾难级"（p95 ≤ 2000 ms），**不**主张它够快。
   归因与优化属独立工作（疑似每次 retrieve 都跑完整性探针与根证据读取）；
   `L-M95-10` 登记为"**未做延迟归因**"。
```

### 7.3 语义开销**不是零**（量化了计划那句话）

计划书逐字：「shadow 会使用额外计算、可能维护派生索引，**不能称"完全零副作用"**」。
本轮把它变成了数：**+1 次编码调用 / +101 ms（N=200）**。这条与 §7.2 一起说明
"开启语义"是有代价的，激活裁定必须看得见这个代价。

## 8. **端到端门**（`pnpm m9.5:e2e:verify` = **3/3**）——唯一走**真 `TurnGateway`** 的门

```text
布景：目标（**最旧**、且与查询句共享「红色」）+ 50 条更新的无关记忆
      ⇒ 候选上限缺省 50、总数 51 ⇒ **旧路径必然把唯一相关的那条挤出候选池**
```

| 档 | 召回层选中 | 目标在**编译后的 prompt** 里 | packet 体积 | 语义分数 |
|---|---:|---|---:|---:|
| `on` | **1**（就是目标） | **是** | 7551 B | 51 |
| 旧路径（不传策略版本） | **0** | **否** | 7068 B | 0 |
| `shadow` | **0**（与旧路径逐位相同） | **否** | — | **51** |

⇒ 三件事同时成立：
- **WP0 的层④缺口在真链路上被修好了**：同一句话、同一批记忆，`on` 下唯一相关的那条
  从"被截断丢掉（选中 0）"变成"排首位并入模"——**这是用户可见的那一层**；
- **旧路径照常工作**（`replyProduced = true`），且两侧是**同一条判据的两面**（只测一侧的话，
  "永远不出现"也能让负控变绿）；
- **`shadow` 是最强形式的 S47**：它**真的算了 51 条分数**，而召回层的选择与旧路径**逐位相同**
  ⇒ "算但不影响输出"不是靠"什么都不做"实现的。

**正文只进 prompt、不进诊断**：`on` 那一轮的 `trace` 里**没有**哨兵。

### 8.1 本门抓到两处**量具/布景的错**（都记下来）

```text
① **拿两轮不同的 turn 比 packet**：每轮有新的 traceId 与时间戳 ⇒ 字节数都是 7066 却"不相等"。
   修：改比**召回层的 `selectedIds`**（用 spy 端口取），那才是"选择变了没有"的正确量具。
② **查询句与目标取值零词面重叠**：「我最喜欢的颜色是什么？」 vs 取值「红色 …」
   ⇒ 选择器一条都没选（`selectedCount = 0`），三档读数全都"目标不在 prompt 里"，
      看起来像"缺口没修"，其实是**布景没让目标成为合格候选**。
   修：查询句改为含「红色」（并在代码里写明为什么）。
⇒ ② 尤其值得记：**一个错的布景会让"修好了"看起来像"没修"**，而且它三档一致地错。
```

## 9. **长轨迹门**（`pnpm m9.5:long:verify` = **4/4**）——三条 500 轮

**每条轨迹一个独立库**（这一条是被门自己逼出来的，见 §9.1）。

| # | 判据 | 读数 |
|---:|---|---|
| ① | 三条轨迹各 **500 轮零失败**，每 100 轮一个检查点 | off / shadow / on 各 **500 轮 · 0 失败 · 0 写入被拒 · 5 检查点**；各约 **430 s** |
| ② | **S47 规模版**：`shadow` 与 `off` 的**逐轮选择完全相同** | 比较 **500 轮 · 不同轮数 0**；同时 off 语义调用 **0** 次、shadow **500** 次 |
| ③ | `on` **真的不同**（否则 ② 的"相同"无意义） | **451 / 500 轮不同**；末轮选中 off **0** → on **1** |
| ④ | 无重复选择、时延不漂移 | 三条轨迹重复选择 **各 0**；p95 检查点 286→528→731→836→**959 ms**（< 4× 上界） |

**② 是 S47 的规模版**：单轮对照可以说"碰巧一样"，**500 轮逐轮相同**就不是巧合了；
而 ③ 证明它不是因为"语义从未生效"（`on` 有 451 轮不同）。

### 9.1 本门抓到的两处**设计错**（都不是实现缺陷，是**量具/布景**错）

```text
① **三条轨迹共用同一个库**：
   · 同样的取值在第 2、3 条轨迹里被判 `duplicate_content`（各 20 次写入被拒）；
   · 更糟的是**对照不干净** —— 第 3 条面对的是"前两条写过的库"，规模不同。
   修：每条轨迹 `resetPluginSqlConnection() + isolateDatabase() + 新 harness`。
② **库没有超过候选上限**：`WRITE_EVERY = 25` ⇒ 500 轮只写 20 条 ⇒ 库只有 21 条，
   而候选上限是 50 ⇒ **截断从未发生** ⇒ `on` 与 `off` 的选择**完全一致**（判据 ③ 报红）。
   修：`WRITE_EVERY = 1`（每轮一条）⇒ 库长到 501 条 ⇒ 截断真的发生
        ⇒ `on` 有 451 轮不同（末轮 off 选中 0、on 选中 1）。
⇒ 教训：**"两档读数相同"必须先证明"本该不同"** —— 否则它测的是"参数没生效"，不是"两档等价"。
```

### 9.2 时延随库增长 —— `L-M95-09` 的量化后果（如实登记）

```text
p95 检查点：286 → 528 → 731 → 836 → 959 ms（off 轨；on 轨同形）
库规模：100 → 200 → 300 → 400 → 500 条
⇒ 时延与**库规模**同向增长（约 3.4×），这与 `L-M95-09`（subject 通道无扫描上限）**一致**：
   每次召回都要扫过该用户的全部记忆。
⚠️ 本门的漂移判据只判"不超过 4×"（**刻意宽松**：本机负载会波动，严格单调会把噪声判成漂移）。
   这条增长**不是**噪声 —— 它与库规模同步，因此单独登记为 `L-M95-09` 的实测后果，
   **不**用"判据通过"把它说成"没有成本"。
```

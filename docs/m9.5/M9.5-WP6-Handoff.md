## 2. 本轮把 WP0 定位到的那一层修成了**机制**

```text
WP0 的层④缺口（实测）：候选按 `recordedAt` 降序 → `slice(0, candidateLimit)`，
而 lexical 命中**只加通道标签、不参与排序** ⇒ 完美的命中只要比最新 50 条旧就被丢掉。
```

**决定性探针**（`wp0-gap-fixed-by-relevance-order`，逐字复刻 S4 形状）：

```text
同一批 51 条候选、limit 50；目标 mem:0000 **最旧**（recency=1）但**相关性最高**（词面 5 + 语义 0.9）；
其余 50 条 recency 递增、词面 0、语义 0.1。

legacy（lexical-recency@1）：保住目标 = **false** · 丢掉 = **["mem:0000"]**   ← 缺口在逻辑上复现
hybrid（hybrid-relevance@1）：保住目标 = **true** · 目标排名 = **0** · 丢掉 1 条   ← 缺口被修
```

⇒ 这一对读数是**同一条判据的两侧**：legacy 侧证明"缺口真的存在"（否则探针是空的），
hybrid 侧证明"相关性排序把它修好了"。

### 2.1 三件事，且只做这三件

| # | 函数 | 硬性质 |
|---|---|---|
| ① | `mergeChannelHits` | 按 **Memory ID** 合并：5 次命中（同一 id 走 3 个通道 + 另一 id 走 2 个）⇒ **2 条**候选，通道集合去重且稳定。计划 §9.1-4「多通道命中 ≠ 多条 Memory」 |
| ② | `orderCandidates` | 版本化：legacy = 新近度降序 + id 升序兜底；hybrid = 相关性降序（词面 + 语义 + **相对间隔**）+ id 升序兜底 |
| ③ | `truncateCandidates` | **排序之后**才截断；并自查 `droppedOldestKeptNewest`（若被丢掉的都比留下的新 ⇒ 说明退回了新近度优先） |

## 2.2 **词面接线**已落地（N1 的一半）——真店、真库、零模型

**关键洞察**：WP0 的层④缺口里，目标**本来就是 lexical 命中** ⇒
「先按相关性排序、再截断」**不需要 embedding 就能修好它**。

`pnpm m9.5:hybrid:verify`（隔离库 · 真店 · 51 条记忆 = 目标 + 50 条更晚的无关记忆）：

| 探针 | 关键读数 |
|---|---|
| `legacy-drops-oldest-lexical-hit` | 候选数 **50** · **缺省含目标 = false**（缺口在真店复现）· **缺省 == 显式 legacy = true** |
| `legacy-order-equals-hand-computed-recency` | legacy 候选序列与"手算新近度降序 + id 升序"**逐位相同** ⇒ `off` 等价 |
| `hybrid-keeps-lexical-hit` | 候选数仍 **50** · **含目标 = true** · **排名 = 0** · **被选中 = true** |
| `semantic-capability-still-unavailable` | `semantic` 在 legacy **与** hybrid 下**都**报 `unavailable` ⇒ 没有伪启用 |
| `unknown-policy-version-rejected` | `"on"` 被**具名拒**（不得默认 on） |

**接线是怎么做的**（`src/infrastructure/persistence/memory-retrieval-store.ts`）：

```text
把原来的 `filtered.sort(新近度) → slice(0, limit)` 换成
  `orderCandidates({ candidates, policyVersion }) → slice(0, limit)`
其中 legacy 分支的比较元组与改动前**逐字相同** ⇒ 不传字段时行为一字不变。
策略版本从 `RecallRequest.retrievalPolicyVersion` 一路透传到 `MemoryRetrievalQuery`
（类型定义在**契约层**，因为 `kernel/recall/**` 不许反向依赖 `kernel/app/**`）。
```

**回归**：M5 八道门逐门复跑全绿（test 30/0 · verify 26/0 · retrieval 28/0 · ranking 27/0 ·
budget 35/0 · e2e 28/0 · runtime 28/0 · trace 33/0）—— 这是 `off` 等价最有分量的一份证据。

⚠️ **仍未接线的是语义半边**：`semantic: null` 是**如实**的 —— 查询期编码（WP3 的
`createEncoderClient`）与派生索引检索（WP4 的表）还没有接进这条链，因此

## 2.5 **生产装配**已落地——开关缺省 off，两个半边由**同一个**开关控制

`pnpm m9.5:assembly:verify`（纯静态 + 纯函数）= **5/5**：

| 判据 | 读数 |
|---|---|
| **① 开关缺省 off** | `{unset:false, true:true, one:true, false:false, zero:false, garbage:false}` |
| **② 启动报告可见** | `record('memory-semantic-recall', …)` 在案 · 接口字段在案 · 从 `CHARACTER_MEMORY_SEMANTIC_ENABLED` 读 |
| **③ 请求缺省不含策略版本** | 不传 ⇒ 请求上**没有**该字段（`hasOwnProperty === false`）；传 ⇒ `hybrid-relevance@1`；缺省常量 = `lexical-recency@1` |
| **④ ★ 静态锁** | 开关在 `main.ts` 里出现**恰好 2 次** · 半边①（装探针）在 `buildRecallTurnPort` 内 · 半边②在方法外 1 次（网关注册处）· 网关**消费**并在 `createRecallRequest` 里置入 |
| **⑤ 未知版本仍被拒** | `"on"` 被具名拒（装配不放松契约） |

**为什么这条静态锁值得存在**：仓库为此付过代价 ——
`CHARACTER_MEMORY_BACKGROUND_ENABLED` 只被读进 flags、**没有任何消费者**，
变成一个"看起来能开、其实什么都不做"的惰性开关（D3）。
语义召回有**两个半边**，只做一半的两种情形都**不是**报错、而是**静默无效**：
只装探针 ⇒ 分数根本不被调用；只选策略版本 ⇒ 换了排序口径却没有语义分数。
本门把"开关恰好两处、且都在对的半边里"变成机器判据。

⚠️ 另一半的保证是**运行期**的：只选策略版本、没装探针时 store 报 `not_indexed`、
能力报告仍列 `unavailable` —— **不会**伪装成"语义已启用"（读数在 `m9.5:semantic:verify` ⑥）。

## 3. 四条**不许越**的边界（都有判据守着）

```text
① **不判资格**：`OrderableCandidate` 里**没有** status/owner/根证据字段 —— 那些由 eligibility 做。
   把资格藏进排序正是计划 §7.2 禁止的（门会因为永远收不到坏候选而空过）。
② **不发明冻结数字**：权重与门槛是**注入的策略字段**，出厂默认带 `calibrated: false`
   （判据：`semantic-null-is-not-zero-and-policy-provisional` 断言它**必须**是 false）。
   ⇒ 未校准的值无法被误当冻结值。
③ **不用绝对余弦阈值**（D26）：两个模块的源码都被断言"不含 COSINE / THRESHOLD 常量"；
   门槛作用在**组合分数**上，间隔是**批次内相对量**。
④ **稳定 tie-break**：同分按 memoryId 升序；且排序/截断是**输入的排列**（不丢不重）。

另：`semantic: null` **不当作 0 参与**（D26-④/R3）—— 无真实分数即不可用，
且不因"没有分数"而拿到间隔加成。legacy 侧另有强判据：把语义分数从 0.99/0.01 换成 `null`，
**顺序一字不变** ⇒ off 等价的前提被机器钉住。
```

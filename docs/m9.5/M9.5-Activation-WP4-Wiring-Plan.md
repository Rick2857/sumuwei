## 1. ★ 触发点已查明（本轮的实质进展）

```text
src/main.ts:1522   private buildMemoryWriter(): ExplicitMemoryTurnPort
src/main.ts:1569   const service = createExplicitMemoryService({ ... })

```

⇒ **所有被接受的记忆事件（新建 / 更正 / 遗忘）都经过 `commitEvents`（`main.ts:1604`）** ——
这就是"新记忆 / 更正 / 遗忘提交后触发维护"的**唯一**挂点 ✓（不需要另找入口，也不需要碰 TD-19）。

⚠️ **不能**把维护直接 `await` 在 `commitEvents` 里：那会把"索引编码"塞进**用户轮次的关键路径**
（一次冷加载 ~1.2 s）⇒ 必须**异步、有工作上限**（用户裁定的"有工作上限的异步索引维护"）。

## 2. 要实现的四件（逐条给判据）

| # | 要做的 | 判据（可测） |
|---|---|---|
| **W1** | **事件触发**：`commitEvents` 提交成功后**投递一个触发信号**（不阻塞、不抛给调用方） | 提交 N 条记忆 ⇒ 触发被投递 N 次（或合并后的次数可解释）；**用户轮次的时延不因此变长**（正控 + 时延对照） |
| **W2** | **有工作上限的异步维护**：一个串行的维护循环；同一时刻**只跑一轮**（触发合并/去重）；每轮有**条数上限**与**时间上限** | 并发投递 100 次触发 ⇒ **只跑有限轮**、每轮条数 ≤ 上限；**没有并发跑两轮**（互斥断言）；超上限的部分留给下一轮（**不丢**） |
| **W3** | **启动时按持久水位补追赶**：启动后跑一轮（或若干轮直到追平或到上限） | 停机期间新提交的记忆 ⇒ 启动后**被索引到**（水位从旧值推进到当前）；**重启后不重复编码**已索引的（水位挡住） |
| **W4** | **显式命令兜底**：`pnpm m9.5:maintain` 保留为运维补救入口 | 已有 ✓；⚠️ 但它必须能指向**目标库本身**（今天的实现只维护副本 —— 那是安全设计，但要有一个**明确的**原地入口，且它必须走 WP7 的租约/快照纪律） |

## 3. 明确**不做**的（边界）

```text
· **不**引入 TD-19 的自主 Agent（用户逐字：本形态"无需引入 TD-19 的自主 Agent"）
· **不**把编码放进用户轮次的关键路径（W1 的异步要求）
· **不**在启动路径上做**无上限**的追赶（W3 要有上限 + 留给后续轮次）
· **不**改任何既有开关的语义；**不**碰事实表
```

```text
⇒ W1–W3 落地之后，"运行期间新提交的记忆会被自动跟进"这件事**才成立**；
```

⚠️ **三处必须同时成立**，否则 W1 就是"接上了但没接对"：
1. **不 await** —— 一旦 await，编码就进了用户轮次的关键路径（冷加载 ~1.2 s）；
2. **`onError` 不抛给用户轮次** —— 索引是派生结构，维护失败**不能**让"她记住了"这件事变成失败；
3. **上限（budget/batchLimit）** —— 否则一次冷启动 + 大量新记忆会长时间占用后台（而 `enumerated.exhausted` 已并入覆盖判定，所以有界的一轮**不会**谎称完整 ✓）。

⚠️ **判据（W1/W3 落地时要补的）**：
```text
· 提交 N 条记忆 ⇒ 触发被投递 N 次（或合并后次数可解释），且**用户轮次时延不因此变长**（时延对照）
· 触发投递之后，**即使维护失败**，`commitEvents` 的返回值与"没接维护"时逐字相同（失败隔离）
· 启动后水位从旧值推进到当前（停机期间的新记忆被索引），且**不重复编码**已索引的
```

## 6. ★ 接线前**最后一个未知**：编码器实例**不能**再造一个（2026-10-01 查明）

```text
现状（读出来的）：
  · `main.ts:1525`   `buildMemoryWriter()` 里有 `const db = kernel.stores.db` ✓
  · `main.ts:1192`   `createEncoderClient({...})` 建在 **`buildSemanticRecallProbe()`** 里
  · `main.ts:1208`   那个实例被存进**模块级**变量 `semanticEncoderForExit`（:4225）
                     —— 它存在的理由逐字写着：早期"引用被丢掉"导致收尾关不掉子进程（:4215）

⇒ 所以 `buildMemoryWriter()` **拿不到**一个现成的编码器实例，只能：
   (a) 复用模块级的 `semanticEncoderForExit` —— 但它**可能 undefined**（探针没建，例如语义未启用）
   (b) 自己 `createEncoderClient(...)` —— ⚠️ 那会**再 spawn 一个 worker 子进程**
       （惰性 worker 的 RSS ~497.6 MB ⇒ 两个实例 ≈ 双份），**不可接受**
   (c) 把编码器改成**装配层单例**（一处建、两处用）—— 这是**正确的**方向，但要动装配结构
```

⚠️ **这一条必须先在设计上定下来，才轮到写那两行**：
- 若选 (a)：必须定义"编码器不可用时维护怎么办"（**跳过并如实记日志**？还是**惰性建一个**？）——
  且**不能**静默 no-op（那会让"接上了"变成假象）；
- 若选 (c)：`buildMemoryWriter()` 与 `buildSemanticRecallProbe()` 必须拿到**同一个**实例，
  且生命周期仍由 `semanticEncoderForExit` 收尾 ✓。

⇒ **本单不猜**：这一条列在这里，供实现轮先定 (a)/(b)/(c)，再写接线。

### 6.1 ★ (c) 的**确切形状**（已把构造点的依赖逐条读出来，2026-10-01）

构造点 = `src/main.ts:1192-1200`，在 `buildSemanticRecallProbe()` 里，**依赖四项**：

```ts
const encoder = createEncoderClient({
  manifest,                                   // ← 该方法内已加载（1186-1190 还用它做了资产核对）
  repoRoot: process.cwd(),
  localModelPath: join(process.cwd(), LAB_MODEL_ROOT),
  deadlineMs: SEMANTIC_RECALL_DEADLINE_MS,    // 超时 ⇒ SIGKILL 子进程（WP3 的 D27）
  readyTimeoutMs: SEMANTIC_RECALL_READY_TIMEOUT_MS,

this.semanticRecallEncoder = encoder           // 实例字段（停机时关它）
semanticEncoderForExit = encoder               // 模块级收尾钩子（聊天路径走它）
```

⇒ **(c) 的做法**（把"建"收进一处，两个调用方共用同一个实例）：

```ts
// 模块级：一处建、多处用（惰性）
let sharedSemanticEncoder: EncoderClient | undefined
function semanticEncoderShared(manifest: EmbeddingManifest): EncoderClient {
  if (sharedSemanticEncoder === undefined) {
    sharedSemanticEncoder = createEncoderClient({ manifest, repoRoot: process.cwd(),
      localModelPath: join(process.cwd(), LAB_MODEL_ROOT),
      deadlineMs: SEMANTIC_RECALL_DEADLINE_MS, readyTimeoutMs: SEMANTIC_RECALL_READY_TIMEOUT_MS })
    semanticEncoderForExit = sharedSemanticEncoder   // ⚠️ 收尾钩子照旧要挂上（L-M10-61）

  return sharedSemanticEncoder
}
```

⚠️ **实现时必须同时满足的四条**（否则就是"接上了但接错"）：
```text
① **只有一个实例**（绝不 spawn 第二个 worker；惰性 worker 的 RSS ~497.6 MB）
② `semanticEncoderForExit` **照旧**被挂上（否则停机时子进程吊住 event loop —— L-M10-61 的实测 240s）
③ `buildMemoryWriter()` 拿不到 manifest ⇒ 要么把 manifest 也提到一处（装配层单例的一部分），
   要么让维护**跳过并如实记日志**（**不能**静默 no-op）
④ 语义未启用（探针没建）时：维护**跳过**（那时索引本来也不该被消费）—— 但**要如实记**
```

⚠️ 本单**仍不主张**已实现：以上是"读出来的确切形状"，不是改动。

### 6.2 ★ 接线时**最后一个坑**：触发器**不能**在语义未启用时把编码器建起来

```text
`semanticEncoderShared()` 是**惰性**的 —— 第一次调用就 spawn worker（RSS ~497.6 MB）。
⇒ 若把维护触发器**无条件**接上，那么"语义召回关着"的用户一提交记忆就会：
   触发 → runOnce → 取编码器 → **spawn 一个 497.6 MB 的 worker**
   而那条通道当时根本不该被消费（探针都没建）。
```

⇒ **接线必须满足**：
```text
① 触发器**只在语义路径启用时**构造（与探针同一个判据，**不另写一份**判据）
② 未启用时：**不投递**（或投递后 runOnce 立刻如实返回"未启用"且**不碰编码器**）
③ ⚠️ 两者选一即可，但**必须显式** —— 不能靠"反正惰性"蒙过去（惰性正是那个坑）
④ 无论选哪个，都要有一条判据：**语义关闭时，提交记忆不会 spawn 编码 worker**
   （可测：`semanticEncoderForExit` 仍为 undefined + 进程没有新增子进程）
```

⚠️ 这条与 §6.1 的 ③④ 是同一条纪律的两种触发路径：**"跳过"必须是显式的、可读的，不能是静默的**。

### 6.3 ★ "语义是否启用"**不要**另立判据 —— 用**已存在的事实**（2026-10-01 查明）

```text
读出来的：`buildSemanticRecallProbe(db)`（main.ts:1155）**只在语义启用时才被调用** ——
它的第一句就是「语义召回已开启，但模型清单不合法…」⇒ **判据在调用方**，不在这里。
```

⇒ 所以接线**不需要**新 flag、也不需要把启用判据复制一份，直接复用**已经存在的事实**：

```ts
// `buildSemanticRecallProbe()` 里赋值 ⇒ "探针建过" ⇔ "语义启用" ⇔ "编码器存在"

```

**投递条件**（W1 那一行的完整形状）：
```ts

```
⇒ 语义关闭时**根本不投递** ⇒ §6.2 的坑（无谓 spawn 497.6 MB worker）**结构上不会发生** ✓
（触发器本身不持资源，`runOnce` 只有在 `trigger` 被投递后才可能跑）。

⚠️ **仍需显式记日志**：语义关闭时"维护被跳过"这件事要**可读**（否则运维看到"索引没跟上"却不知为何）。

   就得**提到模块级一处**（与 §6.1 的"manifest 提到一处"同一件事）。
   ✅ **2026-10-01 已做**（常量与清单都提到一处了）。

### 6.4 ★ 接线时**第三个坑**：完整性读数是**按 owner** 的，而资格政策要**按记忆**


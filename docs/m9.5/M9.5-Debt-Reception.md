## 3. WP0 新证据对债表的影响（**这是本次接收的实质产出**）

WP0 的 S4 / S5 两个场景把 `TD-08` / `L-M61-04` / `L-M61-05` 从
「开放 + 行为现象」推进到「**已定位到具体层与具体代码位置**」。

### 3.1 定位结果

```text
现象（WP0 S4，隔离库，零模型调用）：
  目标记忆「我在写毕业论文」+ 问句「我现在在写什么？」（ADR-059 已修的那条）
    N=0    → 候选 1 · 合格 1 · 选中 1 · 目标在候选池 ✅
    N=50   → 扫描 51 · 候选 50 · 合格 50 · 选中 0 · 目标**不在**候选池 ❌
    N=51/200/500 → 同上（候选恒为 50）

机制（**读源码得到，不是推断**）：
  ① `memory-retrieval-store.ts:99`  scanLimit = min(500, query.limit * 5)
  ② `:164-169`                       候选按 `recordedAt` **降序**排序（**纯新近度**）
  ③ `:180`                           selected = filtered.slice(0, query.limit)
  ④ `:140-144`                       lexical 命中只 **add 通道标签**，**不参与排序**
  ⇒ 候选上限 = `candidateLimit`（缺省 50 / 上限 200，`contracts/recall.ts:518-520`），
    而排序键是**新近度**。于是：**一条完美的词面/（未来）语义命中，只要比最新的 50 条旧，就在资格层之前被丢掉。**
```

### 3.2 对三条债的直接影响

| 债 | WP0 之前 | WP0 之后 |
|---|---|---|
| `TD-08` | 「Recall 排序前截为最近 50 条」（描述） | **已定位**：`slice(0, candidateLimit)` × 新近度排序 × lexical 不参与排序。**且已证明它可复现、可判定**（N=0 ✅ / N=50 ❌） |
| `L-M61-04` | 「200–500 轮取回失败」（行为现象，无人接手） | **故障点定位到层④候选范围**（不是层⑤资格、不是层⑥预算）。60/200/500 轮读数仍待 WP9 出 |
| `L-M61-05` | 「更正后 60 轮回潮旧值」 | WP0 测到的是**前置条件**：更正后的**新值**在 N=50 处已不可达（层④）。层⑦（摘要）/层⑧（回复）的"回潮"本阶段 NOT RUN |

### 3.3 这条定位对方案的含义（**只登记，不据此改设计**）

```text
计划 §5.2「首选 = 本地 embedding + PGlite/pgvector」的前提是
「缺口是词面覆盖不足」——WP0 的 S3 显示**在小规模下不成立**：
  · q-a（ADR-059 已修的对照）✅  · q-b「最近那个学业项目怎么样了？」✅
  · q-c「我读的是哪所院校？」✅   · q-d「我能不能接受辣味？」❌（层⑤：相关性闸）
  · q-e 负控 ✅（选中 0）
⇒ 即：**改述召回在小规模下已经可用**（ADR-059 的功劳）；
  真正的规模缺口是**候选选择策略**（新近度切片），不是"没有向量"。

登记口径：这不推翻计划 §5.2 的首选，也**不**宣布"不需要 embedding" ——
它把 WP1/WP2 必须回答的问题**改精确**了：
  · WP2 冻结候选策略时，「扩窗/分页/让 lexical 或 semantic 参与排序」必须与
    「加语义通道」**并列比较**，不能默认只有后者能解决 P1/P3；
  · 若只加语义通道而候选仍按新近度切片，**S4 的缺口会原样保留**（这是 WP6 的硬判据）。
```

## 3.4 WP0 顺带量到的第二个上限（**新登记，请勿误读**）

```text
`snapshotOf`（`m4-harness.ts:212-226`）内部用 `store.list({ owner, limit: 500 })`
（`recorded_at **desc**`）⇒ **canonical snapshot 最多覆盖 500 条，且丢的是最旧的那几条**。
实测（WP0 权威档）：
  S4 场景 `counts.memories = 501`，`snapshot.entryCount = 500` —— 被丢的正是**目标记忆**
    （目标经显式服务写入，带 `Date.now()`；填充用 `M4_T0 + 1_000_000 + i`，晚于它）。
  S5 场景 `counts.memories = 502`，`snapshot.entryCount = 500` —— 被丢的**恰好是那两条**
    （目标 + 更正），`502 − 500 = 2`。
交叉验证（可观测指纹）：S4/S5 的 snapshot 哈希在**两次独立 run 里逐字相同**
（只含确定性填充），而 S3 的哈希**变了**（3 条全走 `Date.now()`）。

⇒ 三条不同的命题，不许混（AGENTS §6.9）：
   · 「本档有 501 条记忆」          —— 真（`count(*)` 真值）
   · 「本档 snapshot 覆盖 501 条」  —— **假**（只覆盖 500）
   · 「重建后 snapshot 不变 ⇒ 权威未被改动」 —— **在有 >500 条时不可得出**
     （被观察的对象可能根本不在快照里 ⇒ 判据恒真而什么都没比）

⇒ 另有一条同源事实：`explicit-service.ts:467/993` 用 `Date.now()`
   ⇒ 经显式服务写入的记忆 `recordedAt/validFrom` 是**墙钟**，跨 run 天然不可复现。

归属：与 `TD-08` / `M4 S4-2` **同族**（同一条 `store.list` 上限），但落在**对账工具**上，
不在召回链上。处置建议：WP4/WP5 用 snapshot 做 A==B 对账前必须 (a) 绕过 500 上限并出**覆盖率**读数、
(b) **注入固定时钟**；在此之前不得把 snapshot 相等当"权威未被改动"的证据。
⚠️ 本条**不**改变 `TD-08` 的关闭要求，也**不**新增跨里程碑债号 ——
是否升格为登记册条目由用户/WP2 裁定。
```

## 4. 基线迁移（不是债，但**必须**继承）：M9.1 的六条消费规则

`docs/m9.1/M9.1-to-M9.5-Handoff.md` §3 已逐条冻结。M9.5 计划 §11.1 现有条款
「M4 / M4.1 Memory | 保持的契约：原主键、来源、事件 payload、reducer、放行口与遗忘确定性」
在 M9.1 之后**必须重新指向修复后的语义**：

| 项 | M9.5 必须继承的**修复后**语义（M9.1 §3） | 对 M9.5 的落点 |
|---|---|---|
| 同内容重述 | 权威状态 = 复活后记录；`revision` 单调 +1；来源 = **新告知**；**正文 hash 相同也必须更新** | 索引按「同 id 新 revision」更新（计划 §8.1 的 `sourceRevision`） |
| 遗忘呈现 | 集合 = **D17**（`explicit_forget` ⇒ 记录 sourceRefs ∪ 同 canonical slot 的 superseded 链全部 sourceRefs；`explicit_correction`/`audit` ⇒ 仅自身）；**不得另立黑名单** | 向量/缓存/混合召回**继承同一集合语义**（S15–S19） |
| 旧根禁用 | 复活**不触碰**旧禁根；同 id 新 revision **不恢复**旧信念资格 | 查询/重建/模型换代均不得绕过（S30） |
| 事件位置 | `MEMORY_CREATED.payload.restatement`（可选）+ `previousRevision`/`previousStatus` | 事件前沿按**标记**识别复活；**判别器是标记，不是版本号**（`MEMORY_REDUCER_VERSION` 不变） |
| 身份函数 | `beliefReportedDependencyTokenOf({memoryId, revision})` | 若 M9.5 重推身份，**必须调同一函数**（INV-M9-11 同源纪律） |
| 来源两面 | 记录面 = **现值**；事件面 = **撤回时来源** | 必须指明读哪一面（`L-M9.1-09`） |

⇒ 计划 §4 / §8 / §10 / §11 / §15 需以**追加**方式记录本次继承，**不回写**其历史行

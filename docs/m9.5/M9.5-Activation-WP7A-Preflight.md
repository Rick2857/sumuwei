② **模式分派**：`src/main.ts` 的 `main()`（`:3598` 起，**async**）

### 7.3 ★ ②（模式分派）的**正确落点**：`main()` **内部**、建完 kernel 之后（2026-10-01 查明）

```text
读出来的：`async function main()` 在 `src/main.ts:3647`，`const argv = process.argv.slice(2)` 在 :3649。
而**开库/收尾那一整套前奏**（租约 → pre-open 快照 → token → initDatabase → createRuntimeShutdown
→ cleanClose）**就写在 `main()` 里面**（不在某个可复用的函数里）。
```

⇒ 两条路，**选后者**：

| 做法 | 代价 |
|---|---|
| (甲) 新写一个 `runMaintainIndexCommand()`，自己走一遍开库前奏 | ⚠️ **复制**那条纪律（租约/快照/token/收尾）⇒ 两处必然漂开，而它正是 INC-01 换来的东西 ⇒ **不做** |
| **(乙) 在 `main()` 内部、`buildKernel` 之后、进聊天循环之前分派** | ✅ **零复制**：库已经按既有纪律开好了、`createRuntimeShutdown` 已经就位（`cleanClose` 照旧）⇒ 跑完 `return` 即可 ✓ |

⇒ **落点**：`main()` 里 kernel 就绪之后加一句：
```ts
if (argv.includes('--maintain-index')) {
  /* 复用已开好的库 + 既有的收尾路径；跑**一轮**维护后 return（不进聊天循环） */
  await runOneMaintenanceRound(kernel)
  return
}
```
⚠️ **它必须早于**任何"进聊天循环 / 起 dev server"的分支，且**晚于** kernel 就绪。
⚠️ `runOneMaintenanceRound` 用 **WP4 的生产运行器**（`createProductionMaintenanceTrigger` 的 `runOnce` 那一层），
   而不是另写一份维护逻辑 ✓ **已实现**（`c57ac94e`）。

### 7.4 ⚠️ 一个**语义张力**：`READ_ONLY_FLAGS` 其实是"**不要求模型连通性**"（2026-10-01 发现）

```text
`invocation.ts` 的注释逐字：「这次调用是不是**只读**的（**因而不该要求模型可达**）」——
⇒ 那把清单**同时**承担了两件事：① 只读 ② 不要求模型可达。

而 `--maintain-index`：
  · **不**只读（它会写派生四表）
  · **但**它**也不需要**聊天模型（它要的是**编码器**，那是本地 worker，不是 chat model）
⇒ 两件事在这里**分开了** ⇒ 不能简单把它塞进 `READ_ONLY_FLAGS`：
   塞进去会让"它只读"成为**假陈述**（而那把锁存在的理由恰恰是"别把写当成读"）。
```

**当前的实际后果（如实登记，不掩盖）**：
```text
`--maintain-index` 被判成**非只读** ⇒ 它**会**走正常的模型连通性 preflight
⇒ 也就是说：**跑一次索引维护会要求聊天模型可达** —— 一个**假要求**（维护不用模型）。
· 代价：运维动作多一个无关前置条件（模型不可达时跑不了）—— **不致命**，但要知道。
· 正确修法（**不在本轮**）：把那个清单**拆成两个概念**（"只读" / "不要求模型"），
  而那是 `invocation.ts` 的语义变更 ⇒ 要单独一条判据与一次门，**不顺手做**。
```

⚠️ 因此下一轮先用副本跑它时，要么让模型可达（`.env.test` 的测试端点即可），要么先做那个拆分。
**本单不预设哪条**，但**两条都要写清楚**：这就是"假要求"该被对待的方式 —— 记下来，别当没看见。

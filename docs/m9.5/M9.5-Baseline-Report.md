### 4.1 机制（源码位置，逐条可核）

```text
src/infrastructure/persistence/memory-retrieval-store.ts
  :99    scanLimit = max(1, min(scanCeiling, query.limit * 5))     ← 扫描窗随 candidateLimit 走
  :114   subject 通道：listBySubject(owner, subject) —— **无 LIMIT** ⇒ 全部进 byId
  :131   recency 通道：store.list({owner, limit: scanLimit})
  :140   lexical 通道：lexicalOverlapHits(query.text, [...byId.values()])
  :142       ⇒ 命中只 `add(record, 'lexical')`（**加通道标签**）
  :164   排序：recordedAt **降序**（同刻按 id 升序）
  :180   selected = filtered.slice(0, query.limit)                 ← ★ 截断就在这里
src/kernel/contracts/recall.ts
  :518-520  minCandidateLimit=1 · maxCandidateLimit=200 · defaultCandidateLimit=50
```

⇒ **候选上限 = `candidateLimit`（缺省 50），排序键 = 纯新近度，lexical 命中不参与排序。**
N=50 时 `scanned=51`（subject 通道把 51 条都给出来了）、`candidateCount=50`
⇒ 丢掉的那一条**正是目标**。

### 4.2 为什么这一条对 M9.5 是硬约束

```text
计划 §5.2 的首选是「本地 embedding + PGlite/pgvector」。但：
  即使 WP3/WP4 把语义通道接上，只要候选仍按新近度 `slice(0, candidateLimit)`，
  **S4 的缺口会原样保留** —— 语义命中同样不参与排序。
⇒ WP6 的判据必须是「候选池里有没有目标」，而不只是「语义分数算出来没有」。
  （计划 §18 风险表的第 1 条「只接向量，不接真实分数」正是这个形态；
    这里再加一条同族风险：**接了真实分数，但分数不参与候选选择**。）
```

## 5.1 off 基线的 canonical snapshot 与表计数（WP0 任务 5）

固定合成数据的 canonical snapshot（`snapshotOf`：**全部状态**含 superseded/retracted，
按 `logicalId` 排序后稳定序列化求 sha256）—— 这是 WP4「索引丢失后重建 ⇒ 原 canonical snapshot 不变」
（S44）与 WP5 A==B 对账的**同一夹具基准**：

| 场景 | canonical snapshot | 条目数 | 表计数（`h.counts()`） |
|---|---|---:|---|
| S3-paraphrase | `7c9768d1befe664d…` | 3 | memories 3 · **active 3** · superseded 0 · retracted 0 · disputed 0 · subjectLinks 3 · evidenceLinks 3 · evidenceRoots 3 · memoryEvents 3 · domainEvents 3 · conversationEvents 3 |
| S4-candidate-truncation | `0b3c2e0095b472af…` | 500 | memories **501** · active 501 · superseded 0 · subjectLinks 501 · evidenceLinks 501 · evidenceRoots 501 · memoryEvents 501 |
| S5-correction-reachability | `a4eab17549117b2c…` | 500 | memories **502** · active 501 · **superseded 1** · subjectLinks 502 · evidenceLinks 502 · memoryEvents 503 |

> 读法：S4 的 `memories=501 / entryCount=500`、S5 的 `memories=502 / entryCount=500`
> 是**快照上限**造成的 —— `snapshotOf` 用 `store.list({order by recorded_at desc, limit: 500})`
> （`m4-harness.ts:221`），而 `countsOf` 是 `count(*)` 真值。**这两个数不是同一个东西**（AGENTS §6.9）。

### 5.2 这条上限的两个后果（**逐条实测过，不是推断**）

```text
① 丢的是**最旧**的那几条（`recorded_at desc` ⇒ 截断尾部 = 最老）。
② 于是它丢掉的**正好是被观察的目标对象**：
   S4：写目标（显式服务，`Date.now()`）→ 再写 500 条填充（`M4_T0 + 1_000_000 + i`）
       ⇒ 目标时间 **早于**全部填充（真机时钟 < `M4_T0`=1.8e12）⇒ 目标被排除。
   S5：同样的两条（目标 + 更正，均走显式服务）被排除 ⇒ `502 − 500 = 2` **恰好**是它们。
   交叉验证：S4/S5 的 snapshot 哈希在两次独立 run 里**逐字相同**（它们只含确定性填充），
   而 S3 的 snapshot 哈希**变了**（3 条全走 `Date.now()` 的显式写入）。
   → 这正是上述机理的**可观测指纹**。
```

⇒ **对 WP4 / WP5 的直接要求**（写进建议，不是裁定）：

```text
用 canonical snapshot 做 A==B 对账时**必须**先处理两件事，否则 oracle 会说反话：
  (a) 去掉/绕过 `list(limit: 500)` 的上限（并按"应覆盖 vs 实覆盖"出**覆盖率**读数）；
  (b) **注入固定时钟**：`explicit-service.ts:467/993` 用 `Date.now()`
      ⇒ 经显式服务写入的记录 `recordedAt/validFrom` 是**墙钟**，跨 run 天然不可复现。
⚠️ 若不处理，会出现最坏形态：**新值（最旧）不在快照里，于是"重建后快照不变"恒真** ——
   判据看起来全绿，实际什么都没比。这与 AGENTS §6.8 的"0 检查 0 失败"同族。
```

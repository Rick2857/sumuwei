### 1.4 canonical 禁令检测器的**正控 / 负控 / 恢复**三段式

判据（三条，都可机器判定）：

```text
① 行内出现禁止说法，**且**该行带禁止语标记（不得 / 禁止 / 不主张 / forbidden / not allowed）⇒ 允许（引用禁令）
② 行内出现禁止说法，且它在**由禁止语引导的围栏代码块**内 ⇒ 允许（canonical 的"不得写：```…```"形状）
③ 其余 ⇒ **违规**
```

三段式读数（同一个 `forbiddenViolations()` 函数走全部五个样例）：

| 阶段 | 样例 | 期望 | 理由 |
|---|---|---|---|
| **正控** | 真实的两份报告 | **0**（安静） | 合法输入 |
| **负控 N1** | 追加一行裸的 `M5.1.1 Final = PASS` | **必响 ≥1** | 无禁止语标记 ⇒ 是断言 |
| **负控 N2** | 追加一行裸的 `D01 CLOSED` | **必响 ≥1** | 同上 |
| **负控 N3** | 追加一个**无禁止语引导**的围栏块，内含 `M5.1.1 PASS` | **必响 ≥1** | 围栏本身不构成豁免 |
| **特异性 N4** | 追加一行 `本报告不得写 D01 CLOSED。` | **必须不响** | 规则①：引用禁令 |
| **特异性 N5** | 追加 `不得写：` + 围栏块（内含两句话） | **必须不响** | 规则②：canonical 的形状 |
| **恢复** | 放回真实的两份报告 | **0**（重新安静） | —— |

> **为什么必须有 N4/N5**：只测"该响的时候响"拦不住"**什么时候都响**"的检测器。
> N4/N5 证明这条判据读的是**语境**，不是"出现过这四个字母就报红"——
> 否则 canonical 自己那句"不得写：`M5.1.1 PASS`"就会被自己的门判红。

### 1.6 `W11-G5` —— 禁令检测器的**两套规则**（**这是一次判据放宽，必须逐字登记**）

**起因**：本轮做了一次**更宽的自查**（把检测器套到全部六份产物上），结果发现：
两份**判定文档**是安静的（0 处），但过程性 / 数据性产物里有大量提及
（**最终读数**：`WP11-Handoff.md` **8** · 本 F4 **21** · `wp11-gate-exits.txt` **4** —— 共 **33** 处；
门的 JSON 证据另有 12 处，见下面的排除说明）。
逐条看，**没有一处是断言**，全部是三类：

```text
(a) **引用禁令**（"不得写：…" / "本报告不得写 D01 CLOSED"）
(b) **对禁令的描述**（"把阶段 1–3 全绿**偷换成** `M5.1.1 Final = PASS`" ·
    负控名"**裸的** `D01 CLOSED` 行" · F4 表格里的"防的是什么"）
(c) **检测器自己的数据**（门的 JSON 证据里的 `claims` 数组 · 负控名 · `d01.forbidden` 列表）
```

**处置（两类文档、两套规则、各有自己的负控）**：

| 文档类别 | 文件 | 允许的上下文 | 硬判据 | 它自己的负控 |
|---|---|---|---|---|
| **判定文档**（严格） | 验收报告 · Gate-Decision | ① 行内带禁止语标记 ② 由禁止语引导的围栏块 | **违规 = 0** | N1–N3 必响 · N4/N5 必不响 |
| **过程性文档**（审计） | `WP11-Handoff.md` · 本 F4 · `wp11-gate-exits.txt` | ①② + ③**对禁令的描述**（`偷换成` / `裸的` / `防的是` / `描述` / `指的是`） | **`UNCLASSIFIED` = 0** | 往每份文档追加一行裸的 `M5.1.1 PASS` ⇒ 三份**都必须**出现 `UNCLASSIFIED`（实测增量 1 / 1 / 1） |
| **门的 JSON 证据**（排除） | `artifacts/m5.1.1/wp11-phase1-3-closure.json` | 不审计 | —— | —— |

**为什么必须放宽，以及为什么"放宽"在这里是可接受的**：

1. **不放宽就无法执行禁令**：`R-46 §4` 要求 F4 **枚举** criterion change；本 F4 §1.3 还逐条列出
   canonical 禁令的机器落点。若对它们套用与判定文档相同的严格规则，那两份文档就**写不出自己的职责**。
2. **放宽的只是"提及"，不是"断言"**：判定文档（= 判定所在的地方）用的是**严格**规则，
   一个字都没放宽。
3. **放宽的那一套**（过程性文档）**自带负控**：往任一过程性文档追加**一行裸的**禁止说法，
   三份都必须出现 `UNCLASSIFIED`（实测 `1 / 1 / 1`）。⇒ 它不是空转判据。
4. **一处真实的收紧**：这次审计在 `WP11-Handoff.md` 抓到**一行真的不合规**
   （`| FB-1 | 在正文里换个地方写 \`M5.1.1 PASS\` / \`D01 CLOSED\` |` —— 描述的措辞里
   **没有**禁止语标记）。处置是**把那句话改写成明确的禁止句**（"**禁止**在正文任何位置把
   … 写成断言"），**不是**把那一行塞进白名单。改后 `UNCLASSIFIED` 从 2 降到 0。

**门的 JSON 证据为什么被排除**：拿一个检测器去审计**它自己的数据文件**，正是本仓库
已经登记过的同型问题（K-17 / `NON_VERIFIER_SCRIPTS`："检测器不能把自己的判据文本当成被测对象"）。
该文件里出现禁止说法是**结构必然**（它必须保存 `claims` 列表与负控名）。如实登记，不假装审计过。

**读数**：判定文档 **违规 0** · 过程性文档 **`UNCLASSIFIED` 0**（3 份共 25 处提及，全部归类）
· 过程性文档负控增量 **1 / 1 / 1** · 门判定 **107 通过 / 0 失败**。

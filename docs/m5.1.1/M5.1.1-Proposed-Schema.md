## 0. 编码规则（决定 D4「物理必要性」能否被表达）

每个归因槽位用 **三个列** 表达：`<slot>_kind` + `<slot>_id` + `<slot>_unknown_reason`。
三态必须可区分，且 **`Unknown` 不得进入 kind**（B4）：

```text
ABSENT   : kind IS NULL  AND id IS NULL  AND unknown_reason IS NULL
KNOWN    : kind = <PrincipalKind>  AND id IS NOT NULL  AND unknown_reason IS NULL
UNKNOWN  : kind IS NULL  AND id IS NULL  AND unknown_reason = <UnknownReason>
             UnknownReason = LEGACY_UNRECORDED | RUNTIME_UNRESOLVED
```

**CHECK 约束**（每个槽位一组，方向必须写对）：

```sql
-- 有 id ⇒ 必须有 kind（不能出现"有身份没有类别"）
check (<slot>_id is null or <slot>_kind is not null)

-- kind 里**不得**出现任何 UNKNOWN*（未知是认知状态，不是主体种类）
check (<slot>_kind is null or <slot>_kind not like 'UNKNOWN%')

-- unknown_reason 与 kind/id **互斥**（不可能既知道是谁又不知道为什么不知道）
check (<slot>_unknown_reason is null or (<slot>_kind is null and <slot>_id is null))

-- unknown_reason 只能是两个受控值之一
check (<slot>_unknown_reason is null
       or <slot>_unknown_reason in ('LEGACY_UNRECORDED', 'RUNTIME_UNRESOLVED'))
```

> `ABSENT` 与 `UNKNOWN` 的区分**完全**依赖 `unknown_reason`：
> 两者 kind/id 都是 NULL。这正是把"不适用"与"不知道"分开的物理表达 ——
> Draft v1 用一个 `UNKNOWN_LEGACY` kind 表达后者，那条路已按 B4 关闭。

> **为什么不用一个 jsonb `attribution` 列**：本仓库已有明确论断
> （`conversation-event.ts`："为什么必须做成列而不是继续塞字典：一旦 provenance
> 是自由字典……"）。D01 的成因之一就是归因散在 `metadata` / `payload` 里。
> **U-01 已裁定**：权威 attribution 使用结构化列，不使用自由 jsonb 承载。
> 代价是列宽，见 §6。

## 1. 提案 DDL 形状（v7 追加列，**全部可空**）

```sql
alter table conversation_events
  -- ---- 五个 PrincipalRef 槽位 × 3 列 = 15 ----
  add column if not exists initiator_kind            text,
  add column if not exists initiator_id              text,
  add column if not exists initiator_unknown_reason  text,

  add column if not exists actor_kind                text,   -- 与 actor_type 并存，语义见 §4
  add column if not exists actor_ref_id              text,   -- **不是** actor_id（避免遮蔽 legacy 列）
  add column if not exists actor_unknown_reason      text,

  add column if not exists executor_kind             text,
  add column if not exists executor_id               text,
  add column if not exists executor_unknown_reason   text,

  add column if not exists recorded_by_kind          text,
  add column if not exists recorded_by_id            text,
  add column if not exists recorded_by_unknown_reason text,

  add column if not exists content_originator_kind           text,  -- B2：语义来源（非键盘操作者）
  add column if not exists content_originator_id             text,
  add column if not exists content_originator_unknown_reason text,

  -- ---- authority：AuthorityRef（**不是** Principal）× 3 ----
  add column if not exists authority_kind            text,
  add column if not exists authority_ref             text,
  add column if not exists authority_unknown_reason  text,

  -- ---- Axis B：必须真实持久化（ADR §4 / U-08）----
  add column if not exists source_kind               text,
  add column if not exists source_authority          text,
  add column if not exists epistemic_source          text,

  -- ---- 整条 attribution 的来源 ----
  add column if not exists attribution_origin        text;
  -- 'RECORDED' | 'MIGRATED_LEGACY'
```

**`character_action_events` 追加同一组列**（其既有 `character_id` 即 subject 的载体）。

### 1.1 关键取舍说明

```text
· **不新增 subject_kind / subject_id**（U-13 已裁定）
  subject 由既有 canonical domain owner（conversation_events.character_id /
  character_action_events.character_id）**派生**。DB 里只有一个 authority source。
  契约层**可以**暴露 subject，但不得成为第二份权威存储。

· **actor 槽位用 actor_ref_id 而不是 actor_id**
  既有 actor_id 列仍在（legacy）；同名会造成遮蔽与误读。

· **content_originator_* 取代 source_author_***
  B2 的更名，语义为「这段语义内容是谁产生、声明或提供的」。

· **attribution_origin 与 unknown_reason 分工不可互相替代**
  attribution_origin : 整条 attribution 是怎么来的
  unknown_reason     : **某个槽位**为什么不知道
```

### 1.2 物理代价（如实计入）

```text
新增列数：5×3（Principal 槽位）+ 3（authority）+ 3（Axis B）+ 1（origin）= **22 列**
这是本设计最大的物理代价。U-01 选择了"结构化列"而非 jsonb，
因此代价被显式接受，并按下述方式控制：
  · 全部可空（既有行不受影响）
  · **索引最小化**（§6）：只为**当前已存在**的审计查询建索引
```

## 2. 槽位语义与「权威性」分级

### 2.1 七个槽位

| 槽位 | 类型 | 语义 | 存储 |
|---|---|---|---|
| `subject` | `PrincipalRef` | 事件**描述的是谁**（谁的账本/经历） | **派生**（无新列，U-13） |
| `initiator` | `AttributionValue<PrincipalRef>` | **发起**（动机来源） | 3 列 |
| `actor` | `AttributionValue<PrincipalRef>` | **作出决定**并实施 | 3 列 |
| `executor` | `AttributionValue<PrincipalRef>` | **真正执行**的系统/服务/工具 | 3 列 |
| `authority` | `AttributionValue<AuthorityRef>` | **凭什么允许**发生 | 3 列 |
| `recordedBy` | `AttributionValue<PrincipalRef>` | 谁**写入账本** | 3 列 |
| `contentOriginator` | `AttributionValue<PrincipalRef>` | 这段**语义内容**是谁产生、声明或提供的 | 3 列 |

`AuthorityRef`（与 `PrincipalRef` **不同类**，"许可"不是"人"）：

```ts
interface AuthorityRef {
  kind: 'POLICY' | 'CAPABILITY' | 'SYSTEM_RULE' | 'USER_CONSENT' | 'BREAK_GLASS'
  ref: string          // policy id / capability id / rule id
}
```

> **B5 已裁定**：删除 `DEVELOPER_SURFACE`（transport 不是许可）与 `UNKNOWN_LEGACY`
> （未知走 `unknown_reason`）。`SYSTEM_RULE` / `USER_CONSENT` / `BREAK_GLASS` 按 U-05 收录。

### 2.2 「authoritative」是**相对某个判定程序**而言的

| 判定程序 | 它**唯一**依赖的槽位 | 读错会导致什么 |
|---|---|---|
| **Fact Firewall**（能否支持外部事实） | `contentOriginator`（来源是否被确立） | 内容被冒充为"用户陈述" ← **D01 的成因** |
| **Execution Truth**（是否被允许 / 由谁执行） | `initiator` · `actor` · `executor` · `authority` | "她自主删除文件"与"用户要求她删除"不可区分 |
| **Audit / 归因完整性** | `recordedBy` · `actor` · `initiator` | 账本不能回答"这是谁干的" |
| **投影分派**（属于谁的账本） | `subject`（派生） | 事件被记到错误的角色/用户账本 |

> 一个字段是 **authoritative** ⟺ **改变它可能改变上面某个判定程序的结论**。
> 否则它是 **observational**，**不得**出现在 authority-bearing envelope 里。

### 2.3 observational（明确排除在外）

```text
transport（cli / http / page / qq…）· runtimeId · conversationId · sequence
modelProfile · traceId · timestamps · displayName · 任何展示或运维标签
```

**`surface`/`transport` 不是归因**（B5）：把它当归因会让"经 HTTP 提交"与
"由开发者发起"混为一谈。控制面的 `cli/http/page` 只作 metadata。

## 3. 必要性矩阵（D4 的落地形式，**B5.1 已修正**）

`✓` = 必需 · `—` = 必须 `Absent`（填充则写入被拒）· `?` = 允许 `Unknown`
（`LEGACY_UNRECORDED` 或 `RUNTIME_UNRESOLVED`）· `派生` = 由 canonical owner 派生

| 事件族 | subject | initiator | actor | executor | authority | recordedBy | contentOriginator |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| `user_message` | 派生 | — | ✓ | — | — | ✓ | **?** |
| `assistant_message` | 派生 | — | ✓ | — | — | ✓ | **?** |
| `system_event` | 派生 | ✓ | ✓ | — | — | ✓ | **?** |
| `tool_event`（观测） | 派生 | ✓ | ✓ | — | — | ✓ | ✓ |
| 行动：`ACTION_REQUESTED` | 派生 | ✓ | ✓ | — | **—** | ✓ | — |
| 行动：`ACTION_AUTHORIZED` | 派生 | ✓ | ✓ | — | **✓** | ✓ | — |
| 行动：有副作用的执行事件 | 派生 | ✓ | ✓ | **?** | ✓ | ✓ | — |
| 行动：只读诊断 | 派生 | ✓ | ✓ | — | **—** | ✓ | — |
| 控制命令（入 durable audit ledger，见 U-03） | 派生 | ✓ | ✓ | — | ✓ | ✓ | — |

**B5.1 的修正（本表与 Draft v1 的关键差异）**

```text
ACTION_REQUESTED  authority = ABSENT   ← **请求发生 ≠ 请求已获授权**
ACTION_AUTHORIZED authority = REQUIRED
副作用执行事件     authority = REQUIRED
```

> **K-3 FINAL 的行内同步（2026-09-18 用户裁定；WP2.1 落地，Revision 号不升）**
>
> `tool_event` 那一行原为 `actor=— · executor=? · contentOriginator=—`，与 ADR-042 D7
> 把 `actor` / `contentOriginator` 列为 `conversation_events` 必需槽位相冲突。
> 裁定后的值是：
>
> ```text
> tool_event.actor             = REQUIRED   谁产生了这条 tool event        （TOOL/<tool-id>）
> tool_event.contentOriginator = REQUIRED   谁产生了这段工具输出内容        （TOOL/<tool-id>）
> tool_event.executor          = ABSENT     conversation 的工具事件不是一次执行
> ```
>
> 为什么 `executor` 是 Absent：真正的执行者身份由 **Action / Execution Ledger** 承担；
> 在 conversation 的 `tool_event` 上再存一份 authoritative executor 会形成
> **第二个 Execution Truth 来源**。需要关联时走
> `tool_event → actionId / executionId / traceId → 权威行动账本`。
> （`initiator` 本次不重新裁定；历史迁移分类见 Migration-Strategy §3.2：`D / D / N`。）
> 机读形式：`src/kernel/contracts/attribution.ts` 的 `NECESSITY_MATRIX_RULINGS`。

> **已核实**：`ACTION_AUTHORIZED` **已经存在**于 `ActionEventType`
> （`kernel/action/execution-ledger.ts`）。**因此不需要新增生产事件**，
> 只需把 authority 从"请求"移到"授权/执行"。
> Execution Truth 保持：`requested ≠ authorized ≠ attempted ≠ executed ≠ verified`。

**这张矩阵的四个要害**

```text
① user_message 的 executor 必须 Absent（没有说话被执行）
   authority 也必须 Absent（说话不需要许可）
② user_message 的 contentOriginator 允许 Unknown —— 因为"以用户身份提交"这条路径
   客观上存在。Unknown 时 Fact Firewall 必须 fail-closed（不得支持外部事实）
③ ACTION_REQUESTED 的 authority 必须 Absent —— 见上
④ **assistant_message 的 contentOriginator 也是 `?`（Revision 2 修正）**：
   Draft v1 把它判为 Absent，但那会让 ADR D6 的边界说明
   （"若那句话是人类替她写的，contentOriginator 仍是那个提交者"）
   在**历史行与未来行上都无从表达**。
   "她生成的"与"有人替她写的"正是本槽位存在的理由 ⇒ 必需，只是允许 Unknown。
   （与 `Migration-Strategy` §3.4 的第 ② 处修正一致。）
```

> **反例（本矩阵要拦住的）**：把 `user_message.executor` 填成 `Known(USER)`
> —— "为了完整而伪造"，它会让"没有执行者"这件事永久不可见。

## 4. `actor_type` 与 attribution 的关系（B1 + **Rev 2.1 · F1**）

```text
actor_type 的定位（B1 + Rev 2.1）：
  legacy presented / message role（兼容列）
  · 由 **event family / message role 决定** —— 不是 attribution 的投影
  · 语义不变、不重定义、历史行与既有查询继续依赖它
  · **不得**成为新 Attribution Model 的事实源
  · **禁止** actor_type='user' → actor=Known(USER) 的通用回填
  · 与 attribution **并存，但不要求语义相等**（迁移期同理）

✗ Rev 2.1 **删除**（Rev 2 的错误规则）：
  ✗ 方向反转（槽位为输入、actor_type 为派生输出）
  ✗ 写入期断言 actor_type === projectActorTypeFromSlots(...)
  ✗ actorTypeFromPrincipalKind 的反向投影

为什么（反例就是 D01 本身）：
  event family = user_message · actor_type = 'user'
  actor = Known(SERVICE/<agent>) · contentOriginator = Known(SERVICE/<agent>)
  ⇒ 三者同时为真且完全合法；若 actor_type 是 actor 的投影，这一行**无法表达**。
  类型层旁证：ActorType 只有 4 个值（**没有 SERVICE**），PrincipalKind 有 6 个 ——
  二者不是同一根轴的不同粒度，而是两个不同的概念。
```

**一致性检查改为 event family → actor_type（fail-closed）**：

```text
user_message      → actor_type = 'user'
assistant_message → actor_type = 'character'
tool_event        → actor_type = 'tool'
system_event      → actor_type = 'system'

✗ 禁止判据：actor = Known(SERVICE) ⇒ actor_type 应当也是 SERVICE
```

> 这与既有契约层的一道闸**同形**（`assertSourceConsistency` 已经是
> "actorType 与事件类型必须对应"）。Rev 2.1 把该闸确认为**唯一**的
> actor_type 一致性检查，不再引入"attribution → actor_type"的第二道。

## 5. 每个槽位的取值来源（写入侧契约）

### 5.1 构造者（ADR §3 的落地对照）

| 槽位 | 合法构造者 | 今天的来源 | 差距 |
|---|---|---|---|
| `contentOriginator` | trusted ingress adapter | **无** | 完全缺失 ← D01 的核心 |
| `initiator` | trusted command/action ingress | 行动：`ActionRequest.requestedBy`（`kind = user\|character\|system`）→ 落 `payload.requestedBy` | 存在但**不是权威列**，且**缺 tool** |
| `actor` | authoritative decision point / gateway | `actor_type`/`actor_id`；行动侧在自由字典里 | 语义过粗 |
| `executor` | actual executor | 无 | 完全缺失 |
| `authority` | policy / capability evaluator | 行动策略结论经 `payload` | 未作为归因持久化 |
| `recordedBy` | ledger writer | 结构性已知（见 5.2） | 未持久化 |
| `subject` | canonical domain context | `character_id` | 已存在，**派生即可** |

### 5.2 `recordedBy` 为什么属于"**可确定（D）**"，而 `contentOriginator` 不是

```text
recordedBy       ：可确定 —— "谁写的账本"是**写入路径的结构事实**
                   （系统里只有 kernel 自己的写入器能写这张表）        → D
contentOriginator：不可确定 —— "字是谁提供的"是**关于人类/外部行为的历史事实**，
                   从未记录，且**不能**由 actor_type='user' 推出        → U
```

这个对照是 `Migration-Strategy` §3 回填矩阵的核心。

### 5.3 Axis B 必须落库（ADR §4）

```text
WRITE : record what was actually established
READ  : read what was recorded
NEVER : reconstruct authoritative epistemic state from actor_type
```

**旧历史行的 Axis B —— 冻结的精确表示（Rev 2.1 · F3）**

```text
source_kind      = legacy classifier 的输出（既有 4 值之一）   ← D 确定，非占位
source_authority = 'UNCONFIRMED_ORIGIN'                       ← U-09 已裁定；不在白名单，fail-closed
epistemic_source = 'UNCONFIRMED_ORIGIN'                       ← **新增受控值**
```

```text
· `EpistemicSource` 新增取值 **`UNCONFIRMED_ORIGIN`**（既有 4 值不改名、不改语义）
· 它与 `SourceAuthority.UNCONFIRMED_ORIGIN` **成对出现**
· **Axis B 没有 Absent 态** ⇒ 三列在 MIGRATED_LEGACY 行上都是**具体受控值**，
  **不使用 NULL 语义**（因此也不需要第二个 unknown_reason）
· 写入期等式 `epistemic_source === epistemicSourceForKind(source_kind)`
  只对 **RECORDED** 行成立；对 MIGRATED_LEGACY 行**刻意不成立**
  （不得声称它是 SourceKind 的推导 —— 那等于把"未确立"变成"确定"）
```

**禁止**伪造 `USER_EXPLICIT`。

## 5.3b POST-FREEZE ADDENDUM — K-22（Action-Ledger Axis B 不适用）

> **WP4.1（2026-09-18）追加。** 本节**不**改写上面的 §5.3；它只登记一处**已经在别处
> 变成实现真相**的边界，免得下一个人从 §5.3 读出错误的普适性。

上面 §5.3（以及 `Migration-Strategy` §3.6）说的是 `conversation_events` 的 Axis B：
"Axis B 没有 Absent 态 ⇒ 三列在 MIGRATED_LEGACY 行上都是具体受控值"。
这句话**不能**照搬到 `character_action_events`：

```text
character_action_events 的 Cognitive Axis B = **NOT_APPLICABLE**（K-22，2026-09-18 冻结）

  · `SourceKind` 的四个取值全是**对话内容类别**
    （user_statement / character_output / system_instruction / tool_output），
    没有任何一个描述"一次行动" ⇒ 行动行填 Axis B 只能靠**把位次翻译成 SourceKind**，
    而那正是 K-22 §2 明令禁止的方向（initiator/actor/executor/authority/requestedBy
    不得推出任何 SourceKind）。
  · 因此该表上这三列的**唯一**合法取值是 NULL；NULL 的含义由成文契约显式定义为
    "不适用"（`attribution.ts` 的 `ACTION_AXIS_B_SEMANTICS`），并由
    `MIGRATION_0008` 的 `character_action_events_axis_b_not_applicable` CHECK **穷尽**。
    ⇒ **不是**"NULL = 未记录"，**不是**"NULL = 未回填"，也**不是** conversation 意义上的 Absent。
  · §1 里"`character_action_events` 追加同一组列"仍然成立（列照旧存在，22 列不减）；
    变的**只是那一条完整性 CHECK 的谓词**。
```

出处：`M5.1.1-Execution-Plan.md` **R-26**；机读证据
`artifacts/m5.1.1/wp4.1-k22-action-axis-b.json`（43/0）与
`artifacts/m5.1.1/wp4.1-production-copy-v8.json`（30/0）。

## 6. 索引提案（**U-01 已裁定：按当前需求最小化**）

裁定原文的效果：**不得为了未来假设一次性承诺全部四个索引**。

因此 Revision 2 只提案 **一个** 索引，并明确其余三个是**推迟**的：

```sql
-- 唯一现在就有真实用途的一条：让"迁移后还剩多少行归因未知"成为廉价查询
-- （M3/M4 的迁移闸与本次迁移的验收都要回答这个问题）
create index if not exists conversation_events_attribution_origin
  on conversation_events (attribution_origin)
  where attribution_origin = 'MIGRATED_LEGACY';
```

**推迟的索引（Draft v1 曾提案，现撤回）**

```text
✗ (initiator_kind, initiator_id)   —— 今天没有按 initiator 过滤的审计查询
✗ (actor_kind, actor_ref_id)       —— 今天的 action:list / action:show / action:trace
                                      按 status / actionId / traceId 查，不按归因查
✗ (executor_kind, executor_id)     —— 同因；且 executor 今日多为 Absent/? 
```

**未来新增索引的判据**（写下来，免得下次又一次性承诺）：

```text
新增索引 ⟺ 出现一个**真实存在**的审计查询，且它的过滤条件以该槽位为主
          （"以后可能会用"不是判据 —— 这正是 U-01 要拦的）
```

## 7. fail-closed 检查清单（写入侧必须拒绝的情形）

```text
① 必需槽位缺失（按 §3 矩阵）
② **非必需槽位被填充**（按 §3 矩阵）—— 本设计的要害负控（含 ACTION_REQUESTED.authority）
③ <slot>_kind 出现任何 'UNKNOWN%' 值（B4：未知不是主体种类）
④ id 存在但 kind 为空；或 unknown_reason 与 kind/id 同时存在
⑤ actor_type 与 **event family** 不一致（Rev 2.1 · F1：
   `user_message→user` / `assistant_message→character` / `tool_event→tool` / `system_event→system`）
   ✗ **不再**检查 "actor_type 与 attribution 投影一致"（该规则已删除）
⑥ content_originator 已被确立为具体 Principal，但 epistemic 结论仍按 actor_type 单推
   （即：Fact Firewall 的输入未消费 contentOriginator）  ← D1 的可执行形式
⑦ attribution_origin = 'MIGRATED_LEGACY' 的行**违反它那一格的 D/P/U/N 分类**
   —— **已由 K-20 / R-18 取代旧的 blanket 规则**（2026-09-18）：
   旧文写的是"出现具体 content_originator 即伪造"。那条与冻结的 D/P/U/N 矩阵、
   以及 K-3 FINAL 冲突（`tool_event.contentOriginator = **D**`，确定性工具行记
   `Known(TOOL/<tool-id>)` 是**正确结果**）。现在的判据是：
     · **D**：记了 `Known` 就必须与确定性证据**逐字一致**（不一致 = 伪造）
     · **U**：具体值计数必须为 **0**；适用行一律 `Unknown(LEGACY_UNRECORDED)`
     · **N**：必须 `Absent`
     · **值级（与分类无关）**：`contentOriginator` 永不可是 `Known(USER / CHARACTER)`
   （D 槽位的 `Absent` **不算伪造**：还没回填 ≠ 编造。）
   门 = `pnpm m5.1.1:k20:verify`（含正控 / 负控 / 恢复三段式自测）
⑧ **untrusted caller 自报** content_originator / authority / executor
   （ADR §3 的核心不变量；门见 G-AT-4）
⑨ Axis B 未记录：RECORDED 行缺 `source_kind` / `source_authority` / `epistemic_source` 中任一
⑩ RECORDED 行的 Axis B 违反它所在的那一个**分支**（**K-24 / R-21**，2026-09-18）：
   原文写的是"RECORDED 行违反 `epistemic_source === epistemicSourceForKind(source_kind)`"——
   那句话把 RECORDED 等同于"认知来源已确立"，而 `RECORDED` **只**意味着
   "归因是在事件发生当时记录的"。现在的判据分两支：
     · **confirmed**  ：`source_authority !== UNCONFIRMED_ORIGIN`
                        ⇒ `epistemic_source === epistemicSourceForKind(source_kind)`
     · **unconfirmed**：`source_authority = epistemic_source = UNCONFIRMED_ORIGIN`（**成对**，
                        不得只写一个；**没有**外部事实资格）
   两条混合形态必须拒：UNCONFIRMED authority + 非 UNCONFIRMED epistemic；
                      已确立 authority + UNCONFIRMED epistemic。
   门 = `pnpm m5.1.1:wp3.2:verify`（两个分支都要有 `measured_count > 0`）
   ⚠️ 事件族 → `SourceKind` 是**族分类**，**不得**实现成 `PrincipalKind → SourceKind`
⑪ MIGRATED_LEGACY 行的 Axis B 出现 NULL
   （Rev 2.1 · F3：Axis B 无 Absent 态，必须给受控值）
```

第 ⑥ 与第 ⑧ 条是把 ADR 的 D1 与 §3 变成可执行判据的地方。

## 2. 三个 instrumentation correction（**必须单列**）

用户 R-46 §3 点名要求永久记录。三条都明确标注：

```text
reading correction / instrument correction
NOT production semantic change
```

### ① `attribution_slot_shape_invalid` ≠ `attribution_slot_value_invalid`

- **事实**：半填槽位（如 `kind` 有 / `id` 无 / `reason` 无）抛的是 **`attribution_slot_shape_invalid`**；
  `attribution_slot_value_invalid` 是"**形状合法但词表越界**"。
- **原计划**（子代理 recon 时的假设）把两者混为一谈。
- **处置**：WP9-B1 的门**两个分支都断言**（比原计划更强）——
  `readerNegativeControls.mixedStateShape → attribution_slot_shape_invalid`、
  `readerNegativeControls.outOfVocabulary → attribution_slot_value_invalid`。
- **性质**：**读数修正**。生产语义零变化。

### ② `state_events` 的索引 = `{state_events_pkey, state_events_lookup}`，**不是 1 个**

- **事实**：`state_events` 全库有 **2 个**索引（PK + lookup），不是 1 个。
- **过程**：子代理最初写的"恰好 1 个"判据**被自己的门抓住**，随后改写成"**恰好这两个**"
  （仍是**精确集合**断言，不是"至少"）。
- **性质**：**读数修正**。v9 未建任何索引（`createsIndex = false`）。

### ③ `migrations.ts` 是 **CRLF** 文件 ⇒ `\n}\n` 不能作为可靠的 v9 block detector

- **事实**：源码文本块正则必须容忍 `\r?\n`；`\n\}\n` 会**静默**解析不到块 ⇒ 探针**恒假**。
- **后果（若不修）**：这正是"量具自己坏了却看起来毫无问题"的典型形状
  （AGENTS §6.8 / §7：`0 检查 / 0 不一致` 与"全部一致"在输出上长得一样）。
- **处置**：`verify-m5.1.1-wp9b-e4-selection.ts` 与 `verify-m5.1.1-wp8-harness.ts` **两处**已修，
  并写了注释。
- **对以后 verifier 的要求**（用户 R-46 §3 明确要求）：

  > **不要依赖 LF-specific block boundary。**

  否则下一次 Windows 文件格式变化又会制造 false quiet。
- **性质**：**仪器修正**。生产语义零变化。

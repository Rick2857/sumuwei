## 1. Query API（M5.1 的只读查询面）

### 1.1 会动的 DTO

```text
DeveloperTraceSummaryDto / DeveloperTraceDetailDto
  + subject（派生）· actor · contentOriginator（trace 的输入事件归因）
  · initiator / executor / authority 对"一轮对话"**不适用** → 按必要性矩阵应为 Absent

DeveloperExecutionSummaryDto / DeveloperExecutionDetailDto
  + initiator · actor · executor · authority（现在只有 characterId / targetXxx）
  · 动作侧已经有 accepted / attempted / executed / verification / intent / target
  · **Phase 4 之后**才可能涉及认知资格；本轮只暴露归因，不改判据
```

**每个归因字段必须以三态呈现**（`Known` / `Unknown` / `Absent`），
不得折叠成 null-as-absent（→ `Unknown` 与 `Absent` 必须可区分，Test-and-Gate-Plan R6）。

### 1.2 一处**必须同步**的编译期耦合（容易漏）

`contracts/developer-query.ts` 有两个编译期"字段接地"常量：

```text
DEVELOPER_TRACE_SUMMARY_IS_GROUNDED
DEVELOPER_TRACE_DETAIL_IS_GROUNDED
```

它们把 DTO 的**每一个键**钉到既有权威形状或显式派生清单上（造一个键就失败）。
**后果**：任何 DTO 扩字段都会**立即**让 `m5.1:test`（52 项）里的接地断言红。

```text
⇒ 这不是"顺手改一下常量"，而是本设计最强的**防伪造闸**之一：
  新字段必须被显式声明"它落到哪条权威依据或哪条派生规则"。
⇒ 归因字段的接地依据应指向：conversation_events / character_action_events 的**新列**
  （不得指向 metadata / payload —— 那正是 D01 的旧路）
⇒ Axis B 三个新列同理必须接地（它们不是"派生"，是**记录值**）
```

> ⚠️ 与 U-12（= B：M5.1.1 建独立门）叠加后：既有 `m5.1:test` 的接地断言在契约扩字段后
> 必然变红。**该问题已由 Rev 2.1 · F4 的 compatibility rule 关闭**（见 §6.1）：
> 允许为**纯 additive** 契约演化做最小测试源码兼容更新，但不得降低旧判据。

### 1.3 只读性质必须保持

```text
AT2.7 的判据不变：调用全部端点前后整库逐字段快照相同（Query Mutation Count = 0）
⇒ 归因列**只读**暴露；页面/API 都不许写归因
```

### 1.4 分页与 cursor

现有有界 cursor 是 `v1.<startedAt>.<encodeURIComponent(id)>`，基于**既有索引**。
**不新增"按归因过滤"的查询参数**（那会需要新索引 + 新 cursor 形状）。
**U-10 已裁定为 DEFERRED**：集合查询留待有真实需求时单独设计。

## 2. Trace（`character_traces`）

### 2.1 现状

```text
character_traces: trace_id · character_id · input_event_id(NOT NULL) ·
                  source_conversation_event_ids · selected_memory_ids · steps ·
                  domain_event_ids · output_event_id · status · error · 时间戳
```

`input_event_id` 是**归因传播的天然锚点**：一轮 trace 的归因 = 其输入事件的归因。

### 2.2 影响

```text
① 归因**不得**在 trace 上重新记录一份（那会产生第二个真相来源）
   正确做法：trace 只**引用** input_event_id，归因由事件本体回答
② Replay 一致性：trace 重放后，其归因必须与输入事件的归因一致
③ AT4.4 Trace Truth 保持不变：span 里说的必须就是真相
   ⇒ 若 trace 的归因是 Unknown(LEGACY_UNRECORDED)，
      **span 不得**渲染成具体位次，**也不得**折叠成 Absent
④ **控制命令不写 trace**（L-02：input_event_id 语义指向真实会话事件）
   ⇒ 控制面的归因**无法**搭 trace 的便车
   ⇒ **U-03 已裁定**：Privileged Developer Control 必须最终进入
     durable authoritative audit ledger（本轮只定设计要求，不实现）
```

## 3. Observability（分类法与遥测白名单）

### 3.1 **Revision 2 更正：归因刻意不导出为遥测属性**

> **Draft v1 的这条"已核验：键名不冲突"结论已作废。**
> 它核验的是 `source_author_id`（`author` ≠ `auth`），
> 但那是在 **B2 更名之前**的键名。更名后结论反转。

**已重新核验的事实**（`kernel/contracts/observability.ts`）：

```text
:727  sensitiveSegmentsOf(key)：先 toLowerCase()，再 split(/[^a-z0-9]+/)
:735  isSensitiveAttributeKey(key) = sensitiveSegmentsOf(key).length > 0
:752  isTelemetryAttributeAllowed：**敏感段判定是第 ② 步，优先于白名单**（fail closed）
      SENSITIVE_ATTRIBUTE_KEY_SEGMENTS 含 **`content`**
```

| 键 | 分段 | 判定 |
|---|---|---|
| `source_author_kind`（Draft v1 命名） | `['source','author','kind']` | ✅ 允许（`'author' ≠ 'auth'`） |
| `content_originator_kind`（Revision 2 命名） | `['content','originator','kind']` | ⛔ **被拒**（命中 `'content'` 敏感段） |

**裁定（采纳 NF-1 的处置 A，并写下 C 要求的说明）**

```text
归因**不导出为遥测属性**，这是**刻意的**，不是遗漏。

理由：
  · U-11 已裁定"归因是 event property，不是新的 provenance source"；
  · §2.2 的权威性分级也把遥测侧的归因列为 **observational**；
  · 审计面（Query / Console / Ledger）才是它的落点；
  · 遥测缺归因**不影响任何判定**（observational 的定义如此）。

⇒ 若将来确有导出需求，**必须换一个不同的属性名**（例如 `originator_kind` /
  `attribution_origin_kind`）并写**显式映射**；
  **不得**依赖改名，否则又会误伤。
```

```text
✗ **禁止**为了命名方便去改 SENSITIVE_ATTRIBUTE_KEY_SEGMENTS，
  或调整敏感段判定的优先级 —— 那是为一个命名问题**削弱安全控制**。
```

> 该冲突已登记为 `M5.1.1-Revision-2-New-Findings.md` **NF-1（OPEN）**；
> 本节即其落点。若将来采纳"换名导出"，NF-1 才可关为 CLOSED。

### 3.2 归因进入遥测的约束（保留）

```text
① 归因属性是 **observational**（对遥测而言）：
   它**不得**参与任何判定；遥测里缺归因也不影响结论
② 零泄漏不变：4 个哨兵 × 6 份导出负载（含 protobuf 线上字节）仍必须 Leakage = 0
③ **U-11 已裁定**：**不新增** Observability provenance kind ——
   Attribution 是 event property，不是独立 provenance source
   ⇒ `OBSERVABILITY_PROVENANCE_KINDS` 保持 5 值
```

### 3.3 与控制面的既有缺口叠加（已被 U-03 关闭）

```text
控制命令在**遥测里**有阶段与理由码（developer_control），但在**账本里**没有归因
（因为它不入账本，L-02）。
⇒ **U-03 已裁定**该缺口不得被永久接受：
  Privileged Developer Control 必须最终进入 durable authoritative audit ledger。
  本轮只登记设计要求；物理表示（是否新表）留到 M5.1.1 implementation plan。
```

## 4. Developer Console（`page.html`，AT5.6）

```text
① 页面只消费 /dev/query/*（不得直连 persistence）—— 归因显示必须走 API
② 零 import / 零外部资源 / 无框架 / 只有一个 POST —— 不得因为加一列而破坏
③ **"删掉它"性质必须仍成立**：删除 page.html → GET / 404，
   其余端点**逐字节不变**（AT5.6 的真判据）
④ 页面必须**显式渲染三态**（U-14 已裁定：默认可见 UNKNOWN + 提供 unknown count）：
     Known    → 渲染具体位次
     Unknown  → **显式**渲染"来源未确立 / 运行时未确定"，并计入 unknown count
     Absent   → 渲染"不适用"
   **禁止**把 Unknown 渲染成：空字符串 / "—" / null-as-absent
   （三种"空"若在界面里无法区分，"这段历史不知道"就消失了 —— D01 复发点）
⑤ 命令按钮仍来自 GET /dev/query/control/commands（不得硬编码）
```

## 5. Execution Truth（**风险最高的一面**）

### 5.1 五档阶梯与核验语义**不得被削弱**

```text
现状（AT3.6）：rejected / accepted / attempted / executed / verified
              verification 是四态枚举，**不许**成功口吻
              "HTTP 200 ≠ executed" 已被证明为假命题
              9 张领域表前后逐字段相同（WP3 的硬判据）

本设计的立场：
  attribution **补充**"是谁的"，**不改变**"到哪一档"
  ⇒ 归因不得成为新的成功口吻来源
  ⇒ `verified` 仍**不得**由 `executed` 推出（与归因无关）
  ⇒ ADR D7 / B5.1 已明确：`ACTION_REQUESTED` 的 authority 是 **Absent**，
    授权在 `ACTION_AUTHORIZED`（该事件**已存在**，不需新增）
    并保持 requested ≠ authorized ≠ attempted ≠ executed ≠ verified
```

### 5.2 必须**删除**的一处伪造（现存的真实缺陷）

```text
src/infrastructure/action/execution-record.ts:71
    requestedBy: (requestPayload.requestedBy as …) ?? { kind: 'system' }

缺请求方时**静默记成 system** —— 这正是"推测作者"。
⇒ 必须改为 `Unknown(RUNTIME_UNRESOLVED)` 或"缺失即拒绝写入"，
   并配一条负控：**人为构造缺 requestedBy 的写入必须失败，而不是默认成 system**。
   （对应 G-AT-3 的现存反例与 Test-and-Gate-Plan §3 的 mutation ④/⑤ 家族）
```

### 5.3 行动侧的归因今天在自由字典里

```text
action-ledger-store.ts:194   payload: { requestedBy: input.request.requestedBy, … }
admin.ts:235                 const requestedBy = event.payload.requestedBy as { kind?: string }
```

⇒ 迁移目标：`initiator` / `actor` 成为**列**；
恰好是"从自由字典搬到受约束列"的典型改动，也符合既有论断
（"为什么必须做成列而不是继续塞字典"）。

### 5.4 动作侧必要性矩阵的落地风险

```text
有副作用的行动：executor 必需（**?** = 允许 Unknown(RUNTIME_UNRESOLVED)）
只读诊断：authority **必须 Absent**（只看不需要许可）
ACTION_REQUESTED：authority **必须 Absent**（请求 ≠ 授权，B5.1）
⇒ 若实现时"为了完整"给只读诊断或 ACTION_REQUESTED 也填 authority，
   会立刻制造出"这次被授权过"的虚假语义（ADR §5 专论的反例；
   对应 Test-and-Gate-Plan §3 的 mutation ⑦）
```

## 6. 横切（治理）：**M5.1 的证据是冻结记录**

这是最容易被忽略、后果最难收拾的一面。

```text
M5.1 的门（m5.1:test 52 / query 56 / control 41 / observability 27 / page 27 /
          measurement 16 / e2e 22）与 artifacts/m5.1/*.json 是**已 PASS 的冻结记录**。
```

**U-12 已裁定 = 方案 B：M5.1.1 建独立 Gate。**

```text
① **禁止**修改 artifacts/m5.1/ 里已提交的证据（M5.1 已冻结）
② **禁止**重写 M5.1 的 historical evidence
③ M5.1.1 的门与证据落 **artifacts/m5.1.1/**（含 M511-G1..G8）
④ 未来实现时**重新运行** M5.1 gates 是可以的，但结果一律落在 artifacts/m5.1.1/
⑤ 跑门若重新生成了历史证据（artifacts/m4.5、m5、m5.1），提交前用
   `git checkout -- <path>` 还原（AGENTS §7）
⑥ M5.1.1 的总判定**不得反过来**改动 M5.1 的结论或标签
```

### 6.1 compatibility rule（**Rev 2.1 · F4 已冻结**，不再是"实现期待决"）

> Rev 2 在这里留了一个未决问题：裁定 B 说"不动 M5.1 的门"，
> 但 §1.2 的**编译期接地断言**在契约扩字段后必然变红。
> 评审指出**不能**与退出条件的"全量回归零退化"同时悬空。以下为冻结规则：

```text
artifacts/m5.1/*            → **永久冻结**（一字不动）
M5.1 原 Gate 的**语义**      → **永久冻结**（不得删除、放宽或改变任何既有判据）
M5.1 Gate 的**测试源码**     → 若因**纯 additive** 契约演化而**无法编译**，
                              允许做**最小 compatibility update**
```

**四条约束（缺一不可）**

```text
① 单独记录 changed assertions（逐条列出）
② 证明没有删除 / 放宽 / 改变旧判据（只允许适配形状 / 类型 / 字段增补）
③ 新运行结果只写 artifacts/m5.1.1/
④ 原 artifacts/m5.1/ 一字不动
```

```text
⇒ "历史证据永久冻结"与"当前代码仍能重跑旧 Gate"**同时成立**。
⇒ 配套门：**M511-G9 旧 Gate 兼容性**（检查这四条约束本身）。
⇒ 连带效果：Test-and-Gate-Plan §6 与本节的 ⚠️ 待决项**已关闭**。
```

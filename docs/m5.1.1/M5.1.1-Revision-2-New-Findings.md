## NF-1 · `content_originator_*` 与遥测敏感段 `content` 冲突（**B2 更名引入**）

```text
状态     : OPEN（非阻塞）
发现于   : Batch B 一致性检查
触发原因 : B2 的 `sourceAuthor` → `contentOriginator` 更名
影响面   : 仅**遥测属性键**的命名；DB 列不受影响
```

### 事实（已读源码核验）

```text
kernel/contracts/observability.ts:727
  sensitiveSegmentsOf(key) = key.toLowerCase().split(/[^a-z0-9]+/)
                               .filter(s => SENSITIVE_ATTRIBUTE_KEY_SEGMENTS.includes(s))

:735  isSensitiveAttributeKey(key) = sensitiveSegmentsOf(key).length > 0
:752  isTelemetryAttributeAllowed : **敏感段判定是第 ② 步，优先于白名单**（fail closed）
```

`SENSITIVE_ATTRIBUTE_KEY_SEGMENTS` 含 **`content`**（与 `contents`）。

**两个键的对比（同一套规则，结论相反）**

| 键 | 分段结果 | 判定 |
|---|---|---|
| `source_author_kind`（Draft v1 命名） | `['source','author','kind']` | ✅ 允许（`'author' ≠ 'auth'` —— Draft v1 已核验过这一点） |
| `content_originator_kind`（Revision 2 命名） | `['content','originator','kind']` | ⛔ **被拒**（命中 `'content'` 敏感段） |

⇒ **B2 的更名把一个"允许"的键变成了"被拒"的键。**

### 为什么这不是小事

`M5.1.1-Affected-Surface-Map.md` §3 专门讨论过"归因键能否作为遥测属性导出"，
并核验了 `author` 与 `auth` 不冲突。**那条结论现在失效**，
因为键名已经改了 —— 若不更新，Affected-Surface-Map 会留下一条**已过期的"已核验"结论**。

### 建议处置（三选一，**不得**选第四种）

```text
A. 归因**不导出为遥测属性**（倾向）
   理由：U-11 已裁定"归因是 event property，不是新的 provenance source"；
        而 §2.2 的权威性分级也把遥测侧的归因列为 observational。
        审计面（Query / Console / Ledger）才是它的落点。
        遥测缺归因不影响任何判定 ⇒ 不需要它进 span。

B. 若要导出，使用**不同的属性名**（例如 `originator_kind` / `attribution_origin_kind`），
   并为其写一条**显式映射**（不得依赖改名，否则又会误伤）。

C. 保持不导出，但在 Affected-Surface-Map 里**明确写下**"因 `content` 敏感段冲突
   而刻意不导出"，免得未来有人以为是漏了。
```

```text
✗ **禁止**：为了命名方便去改 SENSITIVE_ATTRIBUTE_KEY_SEGMENTS
  或调整敏感段判定的优先级 —— 那是在为一个命名问题**削弱安全控制**。
```

### 归属

Batch C 更新 `M5.1.1-Affected-Surface-Map.md` §3 时必须处理本条目
（其"已核验不冲突"的结论需要按新键名重写，并采纳 A 或 C 的表述）。

## NF-2 · `assistant_message.contentOriginator` 的必要性（**Revision 2 内已闭合**）

```text
状态     : CLOSED（已在 Batch B 内修正，登记以免被当成遗漏）
```

```text
Draft v1 把 `assistant_message` 的 content-originator 槽位判为"不适用（Absent）"。
但这与 ADR D6 的边界说明冲突：
  "若那句话是人类替她写的（例如剧本/替发），contentOriginator 仍是那个提交者"
若判 Absent，则该情形在**历史行与未来行上都无从表达**。

⇒ Revision 2 改为"必需，但允许 Unknown"：
   · Proposed-Schema §3 必要性矩阵：该格 `—` → `?`（并记入"四个要害"第 ④ 条）
   · Migration-Strategy §3.2：该格 → **U**（并记入 §3.4 第 ② 处修正）
两处已一致。
```

## NF-3 · 旧 `ActorType` 与 `PrincipalKind` 的**值域差异**（**Rev 2.1 重新定性**）

```text
状态     : CLOSED（Rev 2.1 · F1 之后，本条已改写 —— 原表述的前提被删除）
```

```text
事实：PrincipalKind 有 6 个值，而 ActorType 只有 4 个
      （`SERVICE` / `EXTERNAL_ACTOR` 在 legacy 值域里**不存在**）。

⚠️ 本条**原先**写作"`actorTypeFromPrincipalKind` 是部分函数，这两个 kind
   无法被投影回 legacy actor_type"。**那个前提已被 Rev 2.1 · F1 删除**：
   `actor_type` 根本**不是** attribution 的投影（它由 event family 决定），
   因此不存在"投影回去"这件事，也不存在"哪些 kind 投影不回去"这个问题。

Rev 2.1 后的正确表述：
  · **不存在反向投影**（Compatibility-Matrix §6.2）
  · `actor_type` 按 event family / message role 继续维护，
    它**不尝试表达** SERVICE / EXTERNAL_ACTOR 等 actual attribution
  · 旧读者因此只能看到 legacy role、看不到新 attribution ——
    这是**明确接受**的兼容边界（Compatibility-Matrix §5）
```

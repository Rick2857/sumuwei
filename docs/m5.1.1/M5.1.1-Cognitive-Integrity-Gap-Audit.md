## 1. 本次审计最重要的发现：**provenance 存在 ≠ provenance 正确**

CI-1 今天是**结构性成立**的：记忆放行口（`kernel/policies/memory-validator.ts`）
强制两件事，且都失败关闭、错误码可断言：

```text
assertMemoryAuthorityAllows()  —— 权威够不够建立这类记忆（计划书 §27/148）
assertMemoryEvidence()         —— 证据与根（MI-03 / 计划书 §40–41）
  错误码：memory_evidence_event_missing / memory_evidence_event_foreign / …
  驳回码：authority_not_allowed / evidence_invalid / …
```

**然而 `M5.1-D01` 的实例证明 CI-1 可以被"合规地"绕过：**

```text
那条记忆**有** provenance：一条 conversation_event（事件 #27，role=user）
那条记忆**有** authority：USER_EXPLICIT（放行口允许）
那条记忆**有** 证据根：指向一条真实存在的事件
⇒ CI-1 的每一条检查都通过。
但那个 provenance **说的是错的事**：它声称"用户说的"，而字是别人打的。
```

**结论（必须写进原则的落地说明）**：

> **CI-1 作为"存在性检查"是不够的。它必须升级为"正确性检查"：
> provenance 不仅要存在，还必须由一个**未被粗粒度字段推导过**的归因来源提供。**
> 这正是 §21 那条链（Attribution → Provenance → Integrity）不可跳过的原因。

⇒ **M5.1-D01 不是"另一个缺陷"，它是 CI-1 的成立条件。**

## 2. 逐条审计（INV-CI）

### INV-CI-01 · 🟡 结构性成立，被 D01 击穿

见 §1。**落地要求**：`no cognitive state without provenance` 必须读作
`no cognitive state without **established** provenance`。

### INV-CI-02 · 🟡 部分

```text
✅ 外部**访问**面今天没有认知权威：
   M5.1 开发者平面是 GET-only 只读 + 两条 mutatesDomain:false 的受控命令；
   全仓 grep 不到任何 memory_records 的 insert/update/delete。
✅ 真库写保护：只有 src/main.ts 能开真实库（assertDatabaseAccessAllowed）。
🔴 但"外部**提交**"这条路径确实换来了认知权威：
   经受支持的一次性入口（`tsx src/main.ts "…"`）提交的文本，
   落库为 role=user 并被推导成 USER_EXPLICIT。
   ⇒ "外部访问 ≠ 认知权威"在**访问面**成立，在**提交面**不成立。
```

### INV-CI-03 · 🔴 未实现

```text
今天不存在任何 MAINTENANCE / REPAIR / MIGRATION / RESTORE 的标记载体。
既有的 v6 迁移（m45-action-execution-ledger）改的是 schema，不改认知，
所以**当前没有**"维护伪装成经历"的实际路径 ——
但也**没有**任何机制保证将来不会出现（例如"修复损坏记忆"顺手写一条 person_fact）。
⇒ 需要在事件层引入 maintenance 标记（见 U-19）。
```

### INV-CI-04 · ⚪ 空满足（**这是最危险的信号**）

```text
没有注入面 ⇒ 没有需要警告的操作 ⇒ 门"通过"。
这与"我们建好了警告与确认流程"在输出上**完全一样**。
```

**已存在、可直接复用的正面样板**：M5.1 控制面已经有
`dryRun`（AT3.2）+ `supportsDryRun` 事实登记 + "dryRun 不进入执行路径"的负控。
⇒ 落地时应**复用**这套形状，而不是新造。

### INV-CI-05 · 🟡 部分 —— 且与既有运维实践**冲突**

```text
✅ 更正保留历史：校名案里那条错误记录是 **retracted 而非 deleted**；
   pnpm memory:history 今天仍能读出它（"当前没有有效记忆 —— 全部被取代、撤回或存疑"）。
🔴 但运维回滚会删除历史：本仓库明写"不写 down 迁移 ⇒ 回滚 = 从备份整体还原"。
   还原 = 丢弃备份之后写入的**全部事件**，包括真实的对话与认知转换。
   ⇒ 这是 CI-8 与既有运维策略的**真实冲突**，见 §4。
```

## 3. 空满足清单（为什么"现在合规"不是好消息）

```text
CI-2 / CI-4 属于**空满足**：因为对象不存在而通过。
CI-9 属于**由构造保证**：因为没有第二条写路径，所以"非法路径 fail closed"自动成立。

⇒ 三者共同的性质是：**它们不会被今天的任何测试抓到，也不会阻止明天的第一行注入代码。**
⇒ 因此 CI-2 / CI-4 / CI-9 必须有**前瞻性**的落地形式：
   不是"现在没有非法路径"，而是"**一旦出现就 fail closed**"。
   唯一可检查的形式是 §19 的破坏性测试（CI-10）—— 而它今天一个都不存在。
```

**这是本次审计的核心判断**：Cognitive Integrity 的**高风险期是未来**，不是现在。
今天系统几乎是最小合规的；风险会在添加第一个"Add Memory"入口时集中爆发。

## 4. 与既有操作实践的真实冲突（必须裁定）

### 冲突 A：**rollback 删除历史**（CI-8 vs 备份还原）

```text
原则（CI-8）  ：可以撤销认知影响，但不能擦除"曾经发生过认知干预"这一事实
仓库现状      ：不写 down 迁移；回滚 = 从备份整体还原 data/pglite
后果          ：还原会把备份之后的**全部事件**一并丢弃 —— 包括真实的对话与更正
⇒ 二者不能同时成立。可选的调和方向（⚖️ 待裁定，见 U-19 相邻项）：
   a) 认知干预事件**另存一份只追加的审计账本**（不受数据恢复影响）
   b) 恢复前先**导出**自上次备份以来的事件，恢复后重新导入并标记 RESTORE
   c) 明确接受"整库还原即回到过去"，并在原则里写清这是**唯一**允许抹除历史的情形
```

### 冲突 B：**术语双轨**（`applied` vs `executed`）

```text
原则 §13 列：requested / authorized / accepted / attempted / applied / verified / …
仓库既有   ：rejected / accepted / attempted / executed / verified（AT3.6 五档）
⇒ `applied` 与 `executed` 是同一个概念的两种叫法。
   若认知操作另造一套阶梯，就会出现"两套执行真相"（本仓库反复禁止的
   "一个概念两处实现"）。⇒ 应复用既有阶梯，只在认知语境下给它别名。
```

## 2. ⚠️ 一处如实登记的发现：`pnpm migrate`（预览）**不是**只读的

`runMigrateCommand(false)` 自己打印「**本次没有改动任何数据**」，但实测：预览之后
真库的内容指纹从 `11d2cb02…` 变成了 `c01ea17d…`。逐文件 diff 的结论是：

```text
只有 8 个文件变化，**没有任何文件增删**，且全部 size 不变：
  postmaster.pid（进程锁）· global/pg_control（检查点/WAL 位置）·
  pg_wal/…A（WAL）· pg_xact/0000（事务状态）· base/1/ 下 4 个 catalog 文件
```

根因有两条，都**不是**"改了业务数据"：

```text
① PGlite 以写模式打开数据库 ⇒ 打开/关闭本身就会写 WAL / pg_control / pg_xact / postmaster.pid
② 预览分支确实调用了 `runtime.runPluginMigrations()` ⇒ 它会跑 **ElizaOS 插件级**迁移
   （与 kernel 的 0001–0009 是两套迁移系统），并可能更新插件迁移的记账行
```

⇒ **"预览"这个词在这里指的是"不应用 kernel 迁移"，不是"不写库"**。
这条已如实登记；它**不**影响本次迁移的正确性（下面 §3 的验证是独立证据），
但它是文档措辞与机器行为不一致的一个实例，值得记下来。

**没有回滚到备份再重做**：`pnpm migrate` 是**文档化的受控命令**，它的副作用与
`pnpm chat` 每次启动所做的事同类（打开库 + 跑插件迁移），不构成"实验污染"。
备份保留在原地（`data/backup/…`），随时可用于回滚。

## 5. ⚠️⚠️ **必须裁定的连带影响：4 道 M5.1.1 门的 premise 被这次迁移拿掉了**

这是本次执行**最重要的诚实发现**，必须单独说清。

### 5.1 现象

迁移之后，`m5.1.1:wp8:verify` 与 `m5.1.1:gates` **变红**。逐门追根因，全都指向**同一件事**：

```text
那几道门的判据是「**在真实库的副本上彩排 v6 → v9**」——
它们先 cpSync 真库，然后断言：
    · 副本 apply 前 schemaVersion = 6
    · 待应用迁移 = [v7, v8, v9]（必须非空）
    · apply 报告 from 6 → to 9
    · k16：副本的 kernel schema 仍是 v6（证明本脚本没在副本上跑 v7）
而**真库现在是 v9** ⇒ 副本也已经是 v9 ⇒ 上面每一条都不再成立。
```

实测读数（逐门）：

| 门 | 失败项（节选） | 性质 |
|---|---|---|
| `m5.1.1:prod-copy:verify` | `副本 apply 前 schemaVersion = 6 [v9]` · `[MEASUREMENT INVALID] 待应用迁移数（measured_count = 0）` · `待应用 = [v7,v8,v9] [[]]` · `from 6 → to 9 [from=9 to=9 applied=[]]` | **premise 失效** |
| `m5.1.1:k16:verify` | `副本的 kernel schema 仍是 v6 [v9]` · `重名列恰好 3 个 [只看到已存在的那些列]` | **premise 失效** |
| `m5.1.1:wp3:verify` | `AT-1 副本可以打开，且 apply 前 schemaVersion = 6 [v9]` · `[MEASUREMENT INVALID] AT-1 待应用迁移数` · `AT-1 副本 apply 后 schemaVersion = 9 [from=9 to=9]` | **premise 失效** |
| `m5.1.1:wp5:verify` | `production-copy 读数存在且 = PASS [verdict=FAIL]` | **派生**（读上一行） |
| `m5.1.1:wp8:verify` | `measurementInvalid = 0 [Σ = 2]` · `没有一条门的证据报红 [prodcopy/k16/wp3/wp5 …]` | **回声** |
| `m5.1.1:gates` | `WP8-B harness 判定 = FAIL` | 推导 |

> `[MEASUREMENT INVALID]` 出现在这里是**量具在正确地工作**：那几条检测器**确实什么都没测到**
> （待应用迁移 = 空），而按 AGENTS §6.8，"检查了 0 项 / 发现 0 处"必须是
> `MEASUREMENT INVALID`，**不是 PASS**。它们没有撒谎，是它们的**前提没了**。

### 5.2 为什么 `4b` 预检**没有**预见到这件事（量具有效性）

`4b` 预检的 §2 门影响清单是按 **recall / render / 探针 / DTO 的针**扫的 ——
它回答的是"**改 `src/**` 会碰到哪些门**"。这次变红的原因**完全不在那个集合里**：
它的成因是"**真库的 schema 版本变了**"，而预检是按"**代码**会怎么变"扫的。

⇒ **同一形状的盲区第三次出现**（前两次：`4-preflight` 漏掉 k17/wp61 的**负向**断言；
`4-preflight` 按 `createConversationEvent(` 调用点圈半径而漏掉 `createM4Harness` 间接路径）。
这次是：**"只扫代码面"的量具看不见"环境面（库的版本）变化"**。

```text
⇒ 已登记为量具缺陷。修法（供后续）：4b/4c 之类的预检若要涵盖"环境面"，
  必须额外扫"哪些门的判据里**硬编码**了真实库/副本的 schema 版本、迁移清单或指纹"。
  本步**不**改预检脚本的重型逻辑（它已交付且被引用），只在报告里如实登记这条盲区。
```

### 5.3 这件事**不**意味着迁移做错了

```text
· 迁移本身已**独立验证**通过（§3）：既有行身份摘要逐字未变 · 0 行伪造归因 · 列数 39 · 记忆面未动
· 那几道门要守的**实质性质**（"把 v7–v9 应用到真实库是安全的"）**不是被削弱，而是被兑现了** ——
  它已经在**真实库上直接发生**，并由 `m5.1.1:phase4b:db-v9` 逐条验证
· 变红的是"**彩排**"这件事：真库已经不需要彩排了
```

### 5.4 处置建议（**需要用户裁定，本步不做**）

```text
建议：把这四道门的判据从「在副本上**彩排** v6 → v9」
      换成「**真实库已在 v9 且迁移未篡改既有行**」的**事后**断言 ——
      即由 `m5.1.1:phase4b:db-v9`（已存在、已 EXIT 0）承接这个保证，
      四道门改为**登记失效**（`NON_VERIFIER_SCRIPTS` 同型的"不改判据、只登记理由"）
      或改写为 post-migration 不变量的断言。

理由：这是**判据层面的取代**（premise 从"迁移前"变成"迁移后"），
      与 R-59 同型 —— 按本项目先例必须**用户裁定**后才落地。
      本步**不**动这四道门（它们的断言一个字未改），
      也**不**提交被它们重跑刷新的证据（已按白名单还原）。
```

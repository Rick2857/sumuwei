## 1. B0 要回答的问题

> 今天生产里**有没有**一个"语义上本来就是系统自行发起"的**真实产品行为**，
> 且它能进入现有 production runtime、产生可验证的 `Known(SYSTEM/<component>)` **因果证据**？

可选的充要条件（执行令 B0，五条**同时**成立）：

```text
① 今天已经有真实产品行为（不是为了 E4 新编一个功能）
② 没有人类 / agent / control command 作为**直接**因果起源
③ 它确实该回答"是谁发起的？" → SYSTEM/<component>
④ 能进入**现有** production runtime
⑤ 不需要碰 MemoryAuthority / Fact Firewall / ADR-043
```

---

## 2. 结论（一句话）

> **生产里确实存在 5 类"系统自行发起"的真实写入；但其中能进入 kernel 归因账本、
> 携带归因信封、从而可以被回答"是谁发起的"的 = 0。**

也就是说：**缺的不是"系统会不会自己做事"，缺的是"系统自己做的事有没有归因表示"。**
今天生产里每一行账本事件仍然只由三个**回合绑定**的写者产出
（`recordUserMessage` · `recordAssistantMessageOutcome` · 行动闸经 `action-turn.ts`），
或由**开发者命令**产出（`developer_control_events`，B0 明文排除）。

⇒ 按执行令的 **Hard STOP**：登记 `WP9-B = BLOCKED BY PRODUCT CAPABILITY DECISION`，**STOP**。

## 5. 结构性原因（为什么"今天必然没有"）

七条**机器核对过**的事实（全部落在证据 JSON 的 `facts` 段）：

| id | 事实 |
|---|---|
| F1 | `conversationAttributionForEntryMode` 只装 user/assistant 两个 producer，函数体里没有任何 SYSTEM 入口 |
| F2 | `MEMORY_JOB_TRIGGER_KIND = 'conversation'` —— 没有任何系统触发的作业被产出 |
| F3 | `recordSystemEvent` 的定义宿主（唯一合法宿主）且它自己 DEAD / UNREACHABLE |
| F4 | `system_event` 在归因矩阵里**有** necessity 行（契约已备好，缺的只是生产 producer） |
| F5 | `mutation: 'background'` 只出现在回合内 post-turn 抽取路径（3 处，全在 `memory/pipeline.ts`） |
| F6 | `recoverMemoryProjections` 生产可达，但实现文件内**零** ledger insert |
| F7 | `state_events` 的 DDL 里**没有**任何归因槽位列 |

契约侧（独立侦察，只读）还确认了三件事，它们共同把 E4 的 SYSTEM 分支**锁死在"不可达"**：

1. **没有任何 SYSTEM 入口工厂**：`src/` 里可导出的 attestation 构造器全是
   "调用方自己给 `PrincipalRef`"的通用形状；`system_event` / `tool_event` **没有** producer 工厂，
   `ledger.ts` 对没有 producer 的族**回落到 legacy 路径**（`attribution_origin` NULL）。
2. **唯一可导出的 SYSTEM 常量是 `CANONICAL_LEDGER_RECORDER = Known(SYSTEM,'kernel')`**，
   而它自己的契约**明文禁止**用它推导 `actor` / `initiator` / `contentOriginator` / `executor`
   （它只表达"这一行账本是谁物理写下的"）。⇒ **不存在**可用来喂 `Known(SYSTEM/<component>)` 的
   规范组件身份常量。**这恰好说明 B1 的要求是对的**：SYSTEM 身份必须来自组件自身，而不是某个便利常量。
3. **行动侧的 SYSTEM 发起者今天不可达**：`attestActionInitiatorFromCausalOrigin` 只有在
   "因果源是 `RECORDED`，且它的 `actor` 与 `contentOriginator` **都 KNOWN 且相等**"时才给出 `Known`，
   否则一律 `Unknown(RUNTIME_UNRESOLVED)`。而唯一能进入行动闸的生产路径是回合（`turn-gateway` 在
   `userEvent !== undefined` 时）。⇒ **没有系统发起的行动**，也就没有 SYSTEM 行动 initiator。

## 6. 量具自身的一次缺陷（记录，因为它发生在"量具也要被验证"上）

第一版扫描器把 C8（`CHARACTER_MEMORY_BACKGROUND_ENABLED` 的消费者）的"良性命中"
写成**单条**规则（只在启动告警附近），于是 `flags.ts` 里那 4 处**声明/读取/打印**被算成 4 个候选
⇒ 主控段显示 **候选 4**、判定被打印成 `B0 = CANDIDATE FOUND`。

**这是判据错、不是读数错**：`flags.ts` 里的出现本来就是该开关唯一合法的声明处。
修法是**把良性命中改成复合规则（OR）**——"路径等于 `flags.ts`" **或**"紧挨着那句
『没有接到任何东西』的告警"——**没有**改动任何被测量的文本，也**没有**为了让结果好看而放宽阈值。
修后主控段 = 候选 0、注入段照旧必响、恢复段重新安静。

> 纪律含义：**false loud 与 false quiet 一样危险**。第一版如果没被跑出来看，
> 一个"其实没有候选"的仓库会被这份量具报成"找到了候选"，然后 B1 就会去接一个不存在的 producer。

## 7. HARD STOP：本 WP 停在这里

**不做**（执行令明文禁止）：`/test/system-trigger` · 系统按钮 · 假 scheduler ·
E4-only producer · 启动时无意义写一条 `system_event`。

**解封需要的是"产品能力决定"，不是工程技巧**（本 WP 不替用户选）：

| 选项 | 含义 | 代价 |
|---|---|---|
| A | 让"记忆投影修复"成为**一等可归因的系统行为** | 需要产品语义裁定 + 落在 memory 投影/权威边界（当前被 B10 排除） |
| B | 让"首启状态引导"可归因 | 需要 **schema v9** 或等价表示 ⇒ 独立迁移里程碑 |
| C | 引入**真实的**调度器 / 后台任务（让系统真的有周期性自主行为） | 产品新能力；M3.5 明文"只登记不实现"，属独立里程碑 |

⇒ 在用户作出上述决定之前，`WP9-GAP-1 / E4-A` **保持 OPEN**，`WP9` **保持 `PARTIAL / BLOCKED`**，
`WP9-C`（把 E4/E8 指向真运行时再资格化）**先行条件不成立**。

# M5.1.1-K-29 —— 兼容性 / 判据变更记录（F4）
## Conversation Attribution Necessity Enforcement

> **性质**：这是一份 **F4 记录**（执行令 §6 要求）。它逐条说明 K-29 动了哪些**既有**判据、
> 为什么、以及**没有**放宽任何安全性质。
>
> **结论先说**：K-29 **没有删除任何测试、没有放宽任何判据**。改动分两类：
> ① **判据变严**（构造器与消费边界开始执行冻结的必要性矩阵 —— 之前**没有执行**）；
> ② **一处旧夹具按合同正确性修正**（旧夹具断言的其实是一条**非法** envelope）。
> 继承门的通过数**逐门相同**（见 §3）；唯一新增的是 K-29 专项门。

## 1. 判据变严（三处，都在 canonical 判据上，没有第二张表）

| # | 位置 | 之前 | 现在 |
|---|---|---|---|
| 1 | `buildTrustedAttributionContext()`（`contracts/attribution.ts`） | 只过 `assertRecordedAxisB()` ⇒ 能构造出 Axis B 合法、**但违反冻结必要性矩阵**的 RECORDED 信封 | 返回前再过 `assertAttributionNecessity()`（**同一份** canonical 判据）⇒ 违规即抛 |
| 2 | `createConversationEvent()`（`contracts/conversation-event.ts`） | 只检查族 / 呈现角色 / subject / 上下文受信 | 追加 `assertConversationAttributionNecessity(trusted)` —— **同一个**判据的薄包装（defense in depth，防将来重构 / 陈旧内部生产者 / 登记表问题） |
| 3 | `attributionSlotsOfContext()`（构造器**自填**的三个槽位） | `initiator` / `executor` / `authority` **写死 Absent** | **按 canonical 矩阵那一格取值**：`ABSENT ⇒ Absent`；`REQUIRED / ALLOWED_UNKNOWN ⇒ Unknown(RUNTIME_UNRESOLVED)` |

### 1.1 第 3 条为什么不是"放宽"，而是**修正**

第 3 条是 K-29 暴露出来的**一个更深的缺陷**（不在执行令原先点名的反例里）：

```text
冻结矩阵：system_event.initiator = REQUIRED · tool_event.initiator = REQUIRED
        （裁定 U-04：REQUIRED 允许 Unknown(RUNTIME_UNRESOLVED)，**不允许** Absent）

而构造器把 initiator 写死 Absent ⇒ 这两族的 RECORDED 信封**在结构上不可能合法**
```

它从 WP4 起就存在，但一直**不可见** —— 因为必要性判据从来没有接到对话侧的任何一层上
（那正是 K-29 登记的东西）。K-29 一接上，继承门 `m5.1.1:k25:verify` 与 `m5.1.1:wp4:verify`
**当场变红**（`initiator/required_slot_absent` / `actor/required_slot_absent`），暴露了它。

修正后的取值规则**读的是同一张 `NECESSITY_MATRIX`**（不是第二张表：门里有静态断言，
`NECESSITY_MATRIX` 只在契约里定义，别处没有 family → REQUIRED/ABSENT 的表）。

**对生产的影响 = 零**：生产链路只接 `user_message` / `assistant_message`（WP6.1 §6），
而那两族的 `initiator` / `executor` / `authority` 三格**全是 `ABSENT`** ⇒ 逐字不变。
变化只发生在**测试夹具**里那两族（`system_event` / `tool_event`）：它们以前写的是**非法**的
Absent，现在是**合法**的 `Unknown(RUNTIME_UNRESOLVED)`。

## 2. 旧夹具按合同正确性更新（执行令 §6）

`scripts/verify-m5.1.1-wp4-write-path.ts` 的 ⑥ 号场景（runtime-unresolved）**刻意**构造过
`user_message.actor = Absent`。K-29 之后它**必须**变红（执行令 §3 点名的那条反例）。

**更新的做法**（不是删测试）：

```diff
- actorEvidence: attestActor({ adapterId: 'gateway', principal: spec.actorPrincipal }),
+ actorEvidence: attestActor({
+   adapterId: 'gateway',
+   principal: spec.actorPrincipal,
+   ...(spec.unresolvedReason ? { unresolvedReason: spec.unresolvedReason } : {}),
+ }),
```

`TrustedActorEvidence.unresolvedReason` 是 **WP6.1 就已加入**的字段（与动作侧同形），
所以这不是为 K-29 新开的 API，而是让 ⑥ 号场景用它**早就该用**的形态：

```text
"运行时确实定不下来" 的合法表达是 Unknown(RUNTIME_UNRESOLVED)（裁定 U-04），不是 Absent。
```

**F4 要求的四句话**：

```text
① 旧断言为什么更新   —— 旧夹具断言的是一条**违反冻结矩阵**的 envelope（actor=Absent 而矩阵 REQUIRED）；
                        它不是"旧的正确行为"，而是"必要性判据没接上时看不出来的非法形态"。
                        触发它的是 contract correctness strengthening（K-29），不是需求变更。
② 未删除旧判据       —— ⑥ 号场景仍然存在、仍然断言"运行时定不下来 ⇒ Unknown + unconfirmed"，
                        另外五个场景一字未动；WP4 门通过数 **48 → 48**（不变）。
③ 未放宽任何安全性质 —— 反向：**新的期望更严**（以前 Absent 被接受，现在 Absent 直接抛）；
                        另加双向负控（REQUIRED→Absent 必抛 / MUST_ABSENT→填值必抛）。
④ 新预期更严格       —— 见 §1 与 §3 的对照表；K-29 门自己带正控 / 负控 / 恢复三段式。
```

## 5. 一处**能力边界**（如实登记，不擅自编号）

对话侧受信构造器**没有**"Known initiator"的证据入口（它只有 actor / contentOriginator /
epistemic 三份证据），因此：

```text
system_event / tool_event 的 initiator 只能是 Unknown(RUNTIME_UNRESOLVED)（合法且诚实）；
要表达 Known(System/... · Tool/...) 需要一条**新的受信证据路径** —— 那是一次语义扩展，
而这两族在生产里**没有 producer**（WP6.1 §6：DEAD / TEST_ONLY），因此本步**不发明**它。
```

这条是**能力边界**而不是新缺陷：它不违反冻结矩阵（Unknown 合法），也不影响任何生产行。
若将来要接这两族的生产 producer，需要先裁定它们的 initiator 证据来源（属独立决策）。

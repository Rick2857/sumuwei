## 1. `src/kernel/contracts/attribution.ts` —— 一个**可选**字段（加法）

```diff
 export interface TrustedActorEvidence extends TrustedEvidenceBase {
   readonly principal: PrincipalRef | null
+  readonly unresolvedReason?: UnknownReason
 }

 export function attestActorFromDecisionPoint(input: {
   adapterId: string
   principal: PrincipalRef | null
+  unresolvedReason?: UnknownReason
 }): TrustedActorEvidence

-const actor = principalToValue(input.actorEvidence.principal)
+const actor = principalToValue(input.actorEvidence.principal, input.actorEvidence.unresolvedReason)
```

**为什么必须加**（不是"顺手加"）：

```text
NECESSITY_MATRIX.user_message.actor      = REQUIRED
NECESSITY_MATRIX.assistant_message.actor = REQUIRED
裁定 U-04：REQUIRED 允许 Unknown(RUNTIME_UNRESOLVED)，**不允许** Absent。
动作侧一直有这个字段（`attestActionActorFromDecisionPoint` / `buildTrustedActionAttribution`
用 `principalToValue(..., unresolvedReason)`），**只有对话侧缺**。
后果：对话侧"actor 定不下来"只能被写成 Absent —— 一条**违反冻结矩阵**的行。
WP6.1 的 §5 要求"证明不了 ⇒ Unknown(RUNTIME_UNRESOLVED)"，因此这一格必须补齐。
```

**兼容性**：纯加法，缺省（不传）与今天逐字相同。
- 既有调用点（`scripts/verify-m5.1.1-*` 的门、`src/main.ts` 之外的夹具）**没有**传它 ⇒ 行为不变；
  门里 48/0、22/0 等通过数逐门相同即为实测。
- **没有**放宽任何守卫：`buildTrustedAttributionContext` 仍然只接受三份**不透明证据 token**；
  confirmed 判据、`assertRecordedAxisB`、`isTrustedAttributionContext`、`isTrustedAttestationEvidence`
  全部未改；`K-25` 的静态断言②（`buildTrustedAttributionContext` 的入参里没有 `ingress` 形状的可填枚举）
  仍通过（22/0）。
- WP4 的 ⑥ 号夹具（`actorPrincipal: null` 且**不传** reason）之后仍然是 `Absent`：
  它的断言是"写时 == DB == 回读"，与必要性矩阵无关 ⇒ **逐字不变**（48/0）。
  ⚠️ 顺带登记的既有状态：**对话 builder 不调 `assertAttributionNecessity`**，所以"`user_message.actor = Absent`"
  在 builder 层仍可被表达。本步**不**给 builder 加那条断言（那会让 WP4 的既有夹具变红，属另一个 WP 的判据变更），
  只在生产 ingress 里**不**走那条路。

## 6. 新增的两条静态探测器（**只加严**，且自带 `measured_count > 0` 自检）

| 探测器 | 判据 | 为什么不会漏 |
|---|---|---|
| 生产对话写入者分类（**文件级**） | `src/**` 里 `appendConversationEvent(` / 三个 `createConversationLedger(` / 五个 recorder 写入方法调用点 ⇒ 命中文件必须全部在冻结分类表里（否则变红）；分类表里不能有已消失的条目 | 三组调用点**都**扫；`measured_count` 自检；`unclassified = 0` 与 `stale = 0` 同时断言 |
| 生产对话写入者分类（**方法级**，§1b） | 自动发现 recorder 的 `async record*`（5 个）与账本端口的 `async append*`（4 个）；每个方法必须分类（`PRODUCTION_ACTIVE` / `LEGACY_COMPAT_ONLY` / `TEST_ONLY` / `DEAD·UNREACHABLE`）；**PRODUCTION_ACTIVE ⇒ 必须有 src 调用点且其族在两个入口模式下都有 ingress**；其余 ⇒ 必须**零** src 调用点；`append*` 的分类由"**唯一**调用它的那段 recorder 方法体"**推导**（不是另写一份断言） | 方法级清单包含显式的 `TEST_ONLY` / `DEAD·UNREACHABLE` 行（原先是文件级，休眠方法只能靠"没有调用者"这条探针间接表达）；新增/删除写入方法都会让清单与代码不同步 ⇒ 变红 |
| 低层原语调用点 | `appendConversationEvent(` 的调用点**恰好** = `ledger.ts`（生产）+ `backfill.ts`（回填） | 与 K-23 的"全 src 恰好一个文件 `insert into conversation_events`"互为补充：一个管"谁写这一行"，一个管"谁调用这个原语" |
| 生产 ingress 生产者计数 | `src/**`（排除 `kernel/contracts/`）里调用 `buildTrustedAttributionContext(` 的文件数 **> 0**，且必须**恰好**是那一个 ingress 模块（不能是 `scripts/` / `evals/`） | WP6 基线的 0 与闭合后的 1 都被记录；"只在 verifier 里造一个 producer"会被这条断言抓住 |

**新检测器自带三段式**（项目 §6.7）：真实源码 ⇒ 未分类 = 0（安静）；把一段**合成的新写入方法**
追加到源码文本上、对**同一套发现逻辑**跑一遍 ⇒ 必须报出未分类（`recordSyntheticWriter` /
`appendSyntheticEvent`，实测"必响"）；去掉合成文本 ⇒ 重新安静。
没有这一段，"检查了 0 个未分类"与"根本没在检查"在输出上长得一样。

## 8. 该记下的**偏差**（不是判据变更，但必须留痕）

「用户回复确认」在**直接账本端口**上（`appendUserStatement({ replyToEventId })`）一旦接线，
其 `source_authority` 由 legacy 的 `USER_REPLY_CONFIRMATION` 变为 RECORDED Axis B 的 `USER_EXPLICIT`
（K-25 的 builder 在 confirmed 分支只产出 `defaultAuthorityForKind(source_kind)`）。

- **认知后果 = 0**（门里实测）：两者在 `authorityFromSource` 里映射到**同一个** `MemoryAuthority`
  （`EXPLICIT_USER_STATEMENT`）；`canEvidenceExternalFact` 对两者同为 true；extractor 不读行上的该列。
- **可达性 = 今天不可达**：`ConversationRecorder.recordUserMessage(text, sequence)` **不传** `replyToEventId`，
  `src/` 里也没有别处给用户事件传它 ⇒ 生产链路上用户事件从来没有 reply graph（本步之前之后都一样）。
  M3 评测夹具走直接端口，但它们**不注入** attribution ⇒ 逐字保留旧语义（门里有结构性断言）。
- **要不要修**：要同时保留两个值，需要给 K-25 的 builder 加一个"已确立分支的 authority"入口 ——
  那是**契约语义变更**，不在 WP6.1 范围；登记为待决（不阻塞 WP7）。

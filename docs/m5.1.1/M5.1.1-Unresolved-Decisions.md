## U-01 · schema 存储形态与索引预算 · P0 · 阻塞阶段 1

```text
A. 七个槽位全部作列（14 列）+ 4 条索引        ← Proposed-Schema 的默认
B. 只把**参与判定**的四个作列（initiator / actor / executor / source_author），
   其余（subject / recordedBy / authority）放受 CHECK 约束的 jsonb
C. 全部放一个受 CHECK 约束的 jsonb（列宽最小）
```

- **影响面**：迁移体积、索引写放大、查询能力、以及 §0 那条既有论断
  （"必须做成列而不是继续塞字典"）。
- **倾向**：**A**。理由：本仓库已明确反对把 provenance 塞进自由字典，
  而 D01 的成因之一就是归因散在 `metadata`/`payload`。
  B 是合理的折中，但会让"哪些槽位可查询"变得不对称，
  审计查询会因此分裂成两套写法。C 与既有论断直接冲突。
- **需要审查给出的**：列宽/索引预算是可接受的代价，还是必须走 B。

```text
STATUS   : DECIDED
DECISION : 权威 attribution 使用**结构化列**。
           不使用自由 jsonb 承载 authority-bearing attribution。
           接受 U-13：subject **不重复新增存储**。
           索引按**当前已存在**的审计查询需求最小化；
           **不得**为了未来假设一次性承诺全部四个索引。
RATIONALE: 仓库既有论断（"为什么必须做成列而不是继续塞字典"）；
           D01 的成因之一正是归因散在 metadata / payload。
           索引那半句是为了避免"为想象中的查询预付写放大"。
LANDING  : Proposed-Schema Rev2 §0（三态编码 + CHECK）、§1（22 列）、
           §6（索引只留 1 条 + 未来新增索引的判据）
```

## U-02 · `'developer'` 的落点 · P0 · 阻塞阶段 1

```text
A. SERVICE          —— 但 'developer' 是人，不是服务
B. USER             —— 会与真实对话用户混淆
C. 新增 DEVELOPER    —— 语义准，但把"主体类型"与"经由哪个面"揉在一起
D. 拆开：kind=SERVICE（控制面）+ initiator_id=开发者 + authority=DEVELOPER_SURFACE
```

- **倾向**：**D**。`'developer'` 混了两个概念（谁触发 / 经哪个面），
  而后者按 ADR §2.3 属于 **observational**。
- **附带问题**：控制面的"开发者"是否总是同一个人？若未来有多个开发者，
  `initiator_id` 需要真实身份来源 —— 本轮未设计。

```text
STATUS   : DECIDED
DECISION : **不得新增 PrincipalKind.DEVELOPER。**
           developer 是**上下文角色**，不是主体种类。
           若能确认真实开发者人类身份：initiator = Known(USER/<developer-id>)
           若无法确认：                initiator = Unknown(RUNTIME_UNRESOLVED)
           control plane 本身可作为 **SERVICE** actor。
           cli / http / page **只作 transport metadata**。
RATIONALE: 主体（谁）、渠道（经哪个面）、许可（凭什么）是三件事；
           把它们揉进一个 'developer' 正是 D01 的形状（一根轴，多份方言）。
           注意：Draft v1 的候选 D 里还带着 authority=DEVELOPER_SURFACE ——
           那一半已被 **B5 删除**（transport 不是许可）。
LANDING  : Compatibility-Matrix §2.2；ADR D9（控制面正确模型）
```

## U-03 · 控制面归因是否入权威账本 · P0 · 阻塞阶段 1

现况：控制命令**不写 trace**（L-02，`input_event_id` 语义指向真实会话事件），
且**控制面无持久账本**（L-01，幂等只在进程内）。

```text
A. 新建一条 control 事件账本，让 requestedBy 进入权威记录
   → 需要 v8（或与 v7 合并）；会触碰"控制命令的领域地位"这个未裁定问题
B. 不建账本，并在 ADR 里明确写："控制面不参与 attribution 权威"，附理由
   → 代价：控制命令永远无法回答"谁发的"（审计缺口保留）
C. 把控制命令**当作**一次行动（复用 character_action_events）
   → 但它按 L-02 不写 trace，而 action 事件当前带 trace_id
```

- **倾向**：**B（本轮）+ 把 A 登记为后续里程碑**。
  理由：A 会强迫我们在实现 M5.1.1 的同时裁定"控制命令的领域地位"——
  那是 L-01/L-02 的销账条件，属于独立决策，不该被归因设计顺带决定。
- **但**：无论选哪个，这个缺口都必须在 ADR 里**显式写出**，
  不能留成"读者以为控制面也有归因"的空白。

```text
STATUS   : DECIDED
DECISION : Privileged Developer Control **必须最终**进入 durable authoritative
           audit ledger。
           **不得**永久选择"控制面不参与 attribution authority"。
           本轮只确定**设计要求**，不实现。
           若需要物理新表 → 留到 M5.1.1 implementation plan。
           **不得**为了省事把 Control Command 假装成普通 Character Action。
RATIONALE: 归因缺陷不能靠"宣布控制面不受约束"来消除 —— 那只是把缺口写进原则。
           同时，"控制命令的领域地位"（L-01/L-02）是独立决策，
           故本轮只冻结设计方向、不落实现，避免一次改动同时改两件事。
LANDING  : ADR D9（正确模型）；Migration-Strategy §7（检查清单）；
           Test-and-Gate-Plan §6（M511-G7 surface 回归覆盖控制面）
```

## U-04 · 是否允许 `UNKNOWN_NOW` · P1 · 阻塞阶段 2

`UNKNOWN_LEGACY` 表达"历史上没记"。那么"**现在这次也没能确定**"（例如
tool 未自报身份、执行器不可辨识）该用什么？

```text
A. 允许 UNKNOWN_NOW 作为第四个状态
B. 复用 UNKNOWN_LEGACY（语义不精确：它不是 legacy）
C. 缺失即**拒绝写入**（fail-closed：不确定就不许记这条事件）
```

- **倾向**：**A**，但要求 `UNKNOWN_NOW` 与 `UNKNOWN_LEGACY` 在
  **资格判定上完全同构**（都不能支持外部事实），差别只在
  `attribution_origin` 与可追溯的历史解释上。
- **风险**：多一个状态 = 多一个被误用的地方。若审查认为状态爆炸风险过高，C 是更保守的选择
  （但它会让"工具不自报身份"直接变成写入失败，可能过于激进）。

```text
STATUS   : DECIDED
DECISION : **允许 Runtime Unknown。**
           但 `UNKNOWN_NOW` **不进入 PrincipalKind**（B4）。
           统一使用 `Unknown(RUNTIME_UNRESOLVED)`。
RATIONALE: 需要能表达"现在这次就是不知道"，否则只能二选一：
           编一个值（伪造）或拒绝写入（过于激进）。
           但"未知"是**认知状态**不是**主体种类** ⇒ 走 AttributionValue 而非 kind。
LANDING  : ADR D5（AttributionValue）；Proposed-Schema §0/§2；
           Test-and-Gate-Plan S3（无法确认身份时的正控）
```

## U-05 · `authority` 的 kind 词汇表 · P1 · 阻塞阶段 1

提案：`POLICY | CAPABILITY | DEVELOPER_SURFACE | UNKNOWN_LEGACY`。

- **问题**：是否需要 `SYSTEM_RULE`（系统自发行为没有策略/能力可指）？
  是否需要 `USER_CONSENT`（用户当场同意，且这是**许可**而非**来源**）？
- **倾向**：本轮只保留四个，**新增需求出现时再加** ——
  沿用仓库"白名单不自动扩张"的纪律（默认不可支持，需要显式加入）。
- **注意**：`authority` 是 `AuthorityRef`（**不是** `PrincipalRef`）。
  若审查认为把两者放进同一个 envelope 会造成混淆，需要重新讨论形状。

```text
STATUS   : DECIDED
DECISION : AuthorityKind =
             POLICY | CAPABILITY | SYSTEM_RULE | USER_CONSENT | BREAK_GLASS
           **删除** DEVELOPER_SURFACE（transport 不是许可）
           **删除** UNKNOWN_LEGACY（未知不是一种许可）
           未知一律走 Attribution 的 UnknownReason。
RATIONALE: Draft v1 的四个值里有两个是概念错位：
           · DEVELOPER_SURFACE 把"渠道"当成"许可"；
           · UNKNOWN_LEGACY 把"认知状态"当成"许可种类"。
           补入 SYSTEM_RULE / USER_CONSENT / BREAK_GLASS 是 U-05 自己提出的缺口。
LANDING  : Proposed-Schema §2.1（AuthorityRef）；Compatibility-Matrix §7.3
```

## U-06 · 已落库 memory 的 authority 是否重算 · **P0** · 阻塞阶段 4

阶段 4 之后，`source_author=UNKNOWN_LEGACY` 的历史事件不能支持外部事实。
但**已经落库的 memory 行**的 authority 是**抽取时存下来的**。

```text
A. 不重算：历史记忆保留当时的判定（"当时认为它是用户陈述"）
   → 优点：不追溯改动认知状态；缺点：D01 的错误结论被永久固化
B. 重算：按新判据重新评估既有 memory 的 authority
   → 优点：错误被纠正；缺点：这是一次**追溯性认知变更**，会改变她的记忆可信度
C. 两者之间：不重算，但**标记**这些记忆"来源未确立"，使其在召回/采信上降级
   → 视觉上保留，行为上纠正
```

- **倾向**：**C** —— 它同时避免"固化错误"与"静默改写历史"。
  但这**是产品语义决定，不是工程决定**，必须由用户/架构审查定。
- **必须配套**：不论选哪个，都要先出"降级半径只读报告"（见 Migration-Strategy §4）。

```text
STATUS   : MOVED_TO_ADR_043
DECISION : **不得在 ADR-042 裁决 MemoryAuthority 重算。**
           本问题整体移交 ADR-043
           （Legacy Cognitive Provenance & Epistemic Requalification）。
RATIONALE: 它是产品语义决定（保留当时判定 / 重算 / 标记降级），
           且同一动作会改一个**已 PASS 里程碑的硬性质**的行为。
           归因 ADR 不该顺带决定"她过去相信的东西怎么办"（B7）。
LANDING  : ADR-043 草案 §4（Questions moved from ADR-042）；
           ADR-043 §6（任何裁决前必须先出爆炸半径只读报告）
```

## U-07 · `PrincipalKind` 命名与大小写 · P2 · 阻塞阶段 1

现状就不统一：`ActorType` 小写（`'user'`），`SourceAuthority` 大写（`'USER_EXPLICIT'`）。

- **倾向**：`PrincipalKind` 用**大写**（与同一 envelope 的 `AuthorityRef.kind`、
  `SourceAuthority` 一致），并要求**唯一**双向转换函数，禁止业务代码临时转换。
- **风险**：若审查偏好小写（与 `ActorType` 一致以减少转换），
  则同一 envelope 内会同时出现两种大小写约定。

```text
STATUS   : DECIDED
DECISION : PrincipalKind **使用大写**。
           所有转换必须通过**唯一**转换函数；**禁止**业务代码自行
           lowercase / uppercase / 字符串比较。
RATIONALE: 与同 envelope 的 AuthorityRef.kind / SourceAuthority 一致；
           Draft v1 已指出真正的问题不是"选哪种"，而是"三份方言" ——
           所以配套要求是"唯一转换函数"，而不是仅仅定大小写。
LANDING  : Compatibility-Matrix §6 / §6.1 / §6.2
           （含 actorTypeFromPrincipalKind 是**部分函数**这一连带结论）
```

## U-08 · 新 kind 的 `sourceKindForActor` 映射 · **P0** · 阻塞阶段 1

`sourceKindForActor(actorType)` 是**全函数**。新增 `SERVICE` / `EXTERNAL_ACTOR` /
`UNKNOWN_LEGACY` 后必须给出映射。

- **不可协商的约束**：任何新 kind 的默认映射**不得**落到 `user_statement`
  （否则"新增一种主体"就等于自动获得用户陈述资格）。
- **倾向**：

```text
SERVICE         → system_instruction   （不能支持外部事实）
EXTERNAL_ACTOR  → ⚖️ 未决。默认**不得**支持外部事实
UNKNOWN_LEGACY  → 见 U-09（不是简单映射能解决的）
```

- **注意**：`EXTERNAL_ACTOR` 未来若真接外部主体，"外部观测能否成为事实"
  是个**全新**的认知资格问题，不该在这里随手定 → 建议本轮**只预留语义、不选映射**。

```text
STATUS   : DECIDED
DECISION : **不得**继续建立 `PrincipalKind → SourceKind` 作为新事件的
           authoritative 全函数。
           现有 `sourceKindForActor` **降级为 legacy compatibility classifier**。
           新事件必须**显式记录 Axis B**。
           新增 PrincipalKind 的默认 = **没有认知资格**，除非显式建立来源证据。
RATIONALE: 整个 D01 就是因为"轴 B 完全由轴 A 的全函数推导"（ADR §1.1）。
           若保留全函数语义，新增一种主体就自动获得某种认知资格 ——
           这正是缺陷复发的最短路径。
LANDING  : Compatibility-Matrix §7（§7.2 默认 fail-closed）；
           ADR D1；Proposed-Schema §5.3（Axis B 落库）
```

## U-09 · 轴 B 是否新增"来源未确立"的 authority · **P0** · 阻塞阶段 4

这是**整个设计的技术核心**。

```text
问题：actor_type='user' 是一条**记录事实**（应保留为 user_statement），
      但它**不足以**给出 USER_EXPLICIT 资格。
      ⇒ 必须有一个地方表达"粗粒度分类是 user_statement，但来源未确立"。
```

```text
A. 给 SourceAuthority 新增一个取值（如 UNCONFIRMED_ORIGIN）
   → 需要同时裁定它与 MemoryAuthority 的映射
   → 它是**扩展受控词汇**，按仓库纪律必须显式加入白名单（默认不可支持外部事实）
B. 不改 SourceAuthority，而是在**资格判定函数**里增加一个输入
   （canSupportExternalFact(authority, attribution) 之类的双参形式）
   → 不扩词汇，但改变了既有纯函数的签名（影响既有调用点与 kernel:test）
C. 用 actor_type 之外的机制在**写入期**就阻止这类事件成为 user_statement
   → 最彻底，但会改变"轴 A 的粗粒度事实"，与 D8"actor_type 不变"冲突
```

- **倾向**：**A**。理由：它把"来源未确立"变成一个**可见、可查询、可审计**的受控值，
  而不是藏在某个函数的第二个参数里；且与既有 `EXTERNAL_FACT_AUTHORITIES`
  白名单机制天然一致（新值默认不在白名单里）。
- **这是最需要审查拍板的一条**：它决定轴 B 是否被扩展，
  以及既有的 `kernel:test` 断言面会有多大改动。

```text
STATUS   : DECIDED
DECISION : **新增 `SourceAuthority.UNCONFIRMED_ORIGIN`**（或仓库命名规范下的等价名）。
           它必须：
             · **不在** EXTERNAL_FACT_AUTHORITIES 白名单内
             · fail-closed
             · 可查询
             · 可审计
           其对**已落库 MemoryAuthority** 的影响：**MOVED TO ADR_043**。
RATIONALE: 采纳候选 A（而非 B），因为它让"来源未确立"成为**可查询、可审计**的
           一等受控值，而不是藏在函数第二个参数里。
           白名单机制天然给出 fail-closed：新值默认不能支持外部事实。
           注意边界：本 ADR 决定"轴 B 扩张"，但不决定"存量记忆怎么办"（→ ADR-043）。
LANDING  : Compatibility-Matrix §7.3；ADR §4（Axis B 持久化 + 旧行取该值）
```

## U-10 · 按归因过滤的分页 · P2 · 阶段 5+

是否支持"列出某位次发起的所有动作"这类查询？

- **倾向**：**本轮不做**。它需要新索引 + 新 cursor 形状，
  而现有 cursor 是"走既有索引"的有界设计。
  本轮只暴露**单条事件**的归因；集合查询留待有真实需求时单独设计。

```text
STATUS   : DEFERRED
DECISION : 本轮**不增加**按 attribution 过滤的分页 API。
RATIONALE: 与 U-01 的"索引最小化"同一条理由：没有真实查询就不预付索引与
           cursor 形状的复杂度。
LANDING  : Proposed-Schema §6（"未来新增索引的判据"已写明）
```

## U-16 · §8 的 11 类来源与既有 `SourceKind`（4 类）的关系 · **P0** · 阻塞 Cognitive Integrity 落地

《Cognitive Integrity》§8 建议的来源分类有 **11 类**
（USER_STATEMENT / CHARACTER_EXPERIENCE / CHARACTER_INFERENCE / SYSTEM_DERIVED /
TOOL_RESULT / EXTERNAL_EVIDENCE / DEVELOPER_INJECTION / ADMIN_CORRECTION /
IMPORT / MIGRATION / LEGACY_UNKNOWN），
而既有 `SourceKind` 只有 **4 类**（user_statement / character_output /
system_instruction / tool_output）。

```text
A. 扩展现有 SourceKind（4 → N）      —— 单一词汇表，但要动既有受控词汇与 kernel:test 断言面
B. 新增**第二根轴**：SourceKind 保持不变，另加 "cognitive origin"
   —— 不动既有轴，但从此有两个"来源"概念，有再次分裂的风险
C. 只加映射表：11 类 → 4 类          —— 最小改动，但会丢掉 §8 明确要区分的东西
   （尤其 DEVELOPER_INJECTION 与 IMPORT 都会塌进 user_statement/system_instruction）
```

- **倾向**：**B**，但要求命名与语义边界写死、且**不得**在两处各写一半规则
  （沿用 `sourceKindForActor` 的"唯一映射函数"纪律）。
- **理由**：A 会改动一个**已经承载防火墙判定**的受控词汇（风险高）；
  C 会让 §8 的核心诉求（`DEVELOPER_INJECTION` 不得伪装成 `USER_STATEMENT`）**无法表达** ——
  因为它俩会映射到同一个值。

```text
STATUS   : DECIDED
DECISION : 新增独立 **`CognitiveOrigin`**，它与 `SourceKind` **完全正交**。
           例如未来 USER_STATEMENT / CHARACTER_EXPERIENCE / DEVELOPER_INJECTION /
           IMPORT / MIGRATION 属于 **CognitiveOrigin**。
           **不得**用它替换 SourceKind。
           本轮：**只冻结语义，不实现**。
RATIONALE: 采纳候选 B。SourceKind 已经承载防火墙判定，扩展它风险过高（排除 A）；
           而映射表会塌掉 §8 明确要区分的类别（排除 C）。
           正交化同时避免"两处各写一半规则"。
LANDING  : Compatibility-Matrix §7.4（正交声明与边界）；
           实现在 Cognitive Integrity 里程碑（本 ADR 只冻结语义）
```

## U-18 · `BREAK_GLASS_COGNITIVE_OVERRIDE` 的落地形式 · P1 · 阶段 4+

§17 列出 9 条要求，其中"**不允许关闭审计**"与既有 `flags` 纪律存在张力：

```text
既有纪律（AGENTS §5）：每个开关都必须被**真的消费**，且有回归锁；
                        新增开关要同时改 m4:test / m4.5:test
§17 要求            ：默认关闭 · 强制审计 · 审计不可关闭 · 事后强制 integrity check
```

```text
A. 做成一个 flag（默认 off）+ 回归锁（与既有开关纪律一致）
B. 不设 flag，而是"一个需要显式理由的受控命令"（走 Control 面白名单）
C. 二者都要：flag 只是"是否允许存在"，每次使用仍需逐次显式理由 + 审计
```

- **倾向**：**C**。理由：§17 第 1 条"默认关闭"需要一个持久开关，

- **必须配套**：break-glass 的存在本身要**可识别**（§17 第 9 条），

```text
STATUS   : DECIDED

           + per-operation **explicit reason**
           + explicit confirmation
           + mandatory audit。

           本轮**只冻结规则**。
RATIONALE: 采纳候选 C。§17 的第 1 条与第 3 条是两件事，一个开关无法同时满足。
           这条规则属 Sovereign Core 约束，必须与"审计不可关闭"一起冻结，
           否则将来实现时容易只做开关、不做逐次授权。
```

## U-19 · CI-8（rollback 不删历史）与"还原备份"运维策略的冲突 · **P0** · 阻塞 INV-CI-05 / CI-8

```text
原则 CI-8   ：可以撤销认知影响，但不能擦除"曾经发生过认知干预"这一事实
仓库现状    ：不写 down 迁移 ⇒ 回滚 = 从备份整体还原 data/pglite
后果        ：还原会丢弃备份之后的**全部事件**（含真实对话与认知更正）
```

```text
a) 认知干预事件另存一份**只追加的审计账本**，不受数据恢复影响
b) 恢复前先**导出**自上次备份以来的事件，恢复后重新导入并标 RESTORE
c) 明确接受"整库还原即回到过去"，并在原则里写清这是**唯一**允许抹除历史的情形
```

- **倾向**：**a**（认知干预是低频、高价值、体量小的事件流，独立账本代价最低），
  并把 **b** 作为 `MAINTENANCE / RESTORE` 的标准流程写进迁移检查清单。
- **不接受 c 的理由**：它会让"曾经发生过一次注入"这件事可以被一次运维动作消除 ——
  而 §12 的全部意义就是防止这件事。

```text
STATUS   : DECIDED WITH BOUNDARY
DECISION : 必须区分 **Logical Cognitive Rollback** 与 **Physical Disaster Restore**：
             · Logical rollback  → **不能删除** intervention history
             · Physical restore  → **必须**建立新的 ledger epoch / restore epoch
                                   **必须**显式记录 restore boundary
                                   **不得**声称"同一数据库可证明跨物理恢复的完整历史"
           若未来要求"即使整库灾难恢复也不能抹掉认知干预审计"，
           则 audit sink **必须位于不同的 persistence / failure domain**。
           **"独立表" ≠ "独立故障域"。**
           本轮**不得**设计外部 audit service —— 只冻结这条边界。
RATIONALE: 候选 a 与 b 并不互斥：a 解决"账本放在哪"，b 解决"恢复流程怎么做"；
           而 c 被否决，因为它允许一次运维动作消除"曾发生过干预"这一事实。
           之所以是 WITH BOUNDARY 而非纯 DECIDED：本 ADR 只冻结边界，
           跨故障域的审计落地属于独立设计（且不得在本轮展开）。
LANDING  : Migration-Strategy §5.1（两类回滚 + epoch/boundary 要求）；
           Test-and-Gate-Plan M6（restore epoch 门）；
           原则文本 docs/architecture/cognitive-integrity.md §12 的落地约束
```

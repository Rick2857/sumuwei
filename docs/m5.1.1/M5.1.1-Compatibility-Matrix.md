## 1. 现状：仓库里存在**三套**"谁"的词汇表，且互不兼容

| # | 词汇表 | 取值 | 定义处 | 是否入账本 |
|---|---|---|---|---|
| 1 | `ActorType` | `user` \| `character` \| `system` \| `tool` | `kernel/contracts/actor.ts` | **是**（`actor_type` 列） |
| 2 | `ActionRequester.kind` | `user` \| `character` \| `system` | `kernel/action/action-request.ts` | 仅进 `payload.requestedBy`（自由字典） |
| 3 | `ControlCommand.requestedBy.kind` | `'developer'` | `kernel/contracts/developer-control.ts` | **否**（控制命令不写账本，见 L-02） |

**三个具体的裂缝**

```text
① 词汇表 2 **没有 tool** —— 一个 tool 发起的动作无法在行动侧表达
② 词汇表 3 的 'developer' 在 1、2 里都不存在 —— 控制面自成一派
③ 只有词汇表 1 进了权威列；2 在自由字典里、3 根本没落库
```

> 这是 ADR §1"两根轴被压成一根"的另一面：**一根轴，却有三份方言。**
> Revision 2 不再新增第四份方言：所有"谁"统一收敛到 `PrincipalKind`（§2），
> 三份旧方言各自定位为 **legacy 输入**（§3）。

## 2. 提案词汇表：`PrincipalKind`（B4 修正）

```ts
type PrincipalKind =
  | 'USER' | 'CHARACTER' | 'SYSTEM' | 'SERVICE'
  | 'TOOL' | 'EXTERNAL_ACTOR'
// **没有** UNKNOWN_LEGACY / UNKNOWN_NOW —— 未知不是主体种类

type UnknownReason = 'LEGACY_UNRECORDED' | 'RUNTIME_UNRESOLVED'
```

### 2.1 逐值来源与映射

| `PrincipalKind` | 来自 | 说明 |
|---|---|---|
| `USER` | `user`（1、2） | 人类用户。**注意**：只表示"归属于该用户"，**不**表示"内容由人类提供"（后者是 `contentOriginator`） |
| `CHARACTER` | `character`（1、2） | 角色本人 |
| `SYSTEM` | `system`（1、2） | 系统组件（调度器、启动器…） |
| `SERVICE` | **新增** | 长期运行的服务/基础设施（telemetry、embedding、ledger writer、http server、**control plane**） |
| `TOOL` | `tool`（1） | 能力/工具。补上词汇表 2 **缺的那一格** |
| `EXTERNAL_ACTOR` | **新增** | 未来外部主体（外部代理/用户/服务）。**只预留语义**，不实现 |

**未知的表达方式（B4）**：走 `AttributionValue` 的 `Unknown<UnknownReason>`，
**不进入** `PrincipalKind`：

```text
Unknown(LEGACY_UNRECORDED)    历史没有记录
Unknown(RUNTIME_UNRESOLVED)   运行时未能确定
Absent                        该槽位对此事件不适用
```

### 2.2 `'developer'` 的落点（**U-02 已裁定**）

```text
不新增 PrincipalKind.DEVELOPER。
developer 是**上下文角色**，不是主体种类。
```

正确表达：

```text
能确认真实开发者人类身份：
    initiator = Known(USER/<developer-id>)
无法确认：
    initiator = Unknown(RUNTIME_UNRESOLVED)
control plane 本身：
    actor     = Known(SERVICE/<control-plane>)
transport：
    = cli / http / page        # **observational only**，不是 attribution
authority：
    = Known(CAPABILITY/<developer-control capability>) 或 Known(POLICY/<policy>)
```

> Draft v1 的候选 A–D 与倾向保留在 `Unresolved-Decisions` 的历史里；
> Revision 2 采纳的是"拆开"的完整形态：**主体 = SERVICE/USER，渠道 = transport，
> 许可 = CAPABILITY/POLICY**，三者不再揉在一个 `'developer'` 里。

## 3. 每个既有取值的兼容裁定（B1 修正）

| 既有值 | 重定义 | 改名 | 改语义 | 兼容策略 |
|---|:--:|:--:|:--:|---|
| `actor_type='user'` | **否** | 否 | **否** | 保留原义"**以 user role 提交**"。新增 `content_originator_*` 承载"这段语义内容是谁提供的"。二者并存、互不覆盖；**actor_type 不得推出 contentOriginator** |
| `actor_type='character'` | 否 | 否 | 否 | 不变 |
| `actor_type='system'` | 否 | 否 | 否 | 不变 |
| `actor_type='tool'` | 否 | 否 | 否 | 不变 |
| `ActionRequester.kind='user'\|'character'\|'system'` | 否 | 否 | 否 | 过渡期保留；映射进 `initiator` / `actor`。**补齐 `tool`** 后由槽位取代 |
| `ControlCommand.requestedBy.kind='developer'` | 否 | 否 | 否 | 契约层保留；按 §2.2 映射进 durable audit ledger（U-03） |
| `SourceKind` / `SourceAuthority` / `EpistemicSource` | **否** | 否 | **不改既有取值** | 是轴 B。Revision 2 **只新增一个**取值（`UNCONFIRMED_ORIGIN`，U-09）；**Rev 2.1（F3）再新增 `EpistemicSource.UNCONFIRMED_ORIGIN`**。两者成对出现，既有取值一字不改 |
| `metadata` / `payload` 里的既有键 | 否 | 否 | 否 | 不移除（append-only 的历史行还要读）。**新归因不得再写进自由字典** |

### 3.1 两条硬规则

```text
① **`actor_type` 的任何既有取值都不得被重定义。**
   历史行与既有查询都依赖它；重定义等于让历史记录在语义上被追溯篡改。

② **`actor_type` 是 legacy compatibility projection，不得成为新模型的事实源。**
   （B1）它回答"以什么 role 提交"，**不**回答"谁作出决定"、"内容由谁提供"。
```

## 4. `actor_type` 的生命周期与日落条件

```text
阶段 0（今天）      actor_type 是**唯一**归因来源
                   ↓
阶段 1..2           actor_type 与槽位**并存**（同写，但**不要求语义相等**）
                   ↓
阶段 3             槽位成为 **attribution 的真相来源**
                   · actor_type **不变**：它始终由 **event family** 决定
                   · ✗ Rev 2.1 **删除**"降级为派生输出 / 方向反转"（见 ADR D8.1）
                   ↓
阶段 4             Fact Firewall 的输入改为 contentOriginator
                   **闸已由 ADR-043 批准解除（2026-09-19）；落地顺序 `4-preflight`（只读）
                   → `4a` → `4b`，当前 = `NOT RUN`**（见 Migration-Strategy §2.1 · ADR-043 `DR-8`）
                   ↓
阶段 5             日落：停止作为权威字段写入
                   ↓
（更晚）            仅当**全部**下列条件成立，才考虑从 schema 移除
```

**日落条件（必须全部满足，缺一不可）**

```text
□ 所有读路径已改为消费槽位（有门证明：移除 actor_type 后全量回归仍绿）
□ 没有任何查询/报表/断言仍以 actor_type 为唯一依据
□ event family / message role → actor_type 一致性在至少一个完整里程碑周期内零违规。
□ 有明确批准（且此时才允许新增一次迁移来移除列）
```

在此之前 `actor_type` **保持 NOT NULL**，不得放宽约束。

> **日落不需要等待"actor_type 与 attribution 收敛"** —— 因为 Rev 2.1 已删除
> "由槽位派生 actor_type"这条规则：二者**本就不要求语义相等**
> （`user_message` 的 `actor_type='user'` 与 `actor=Known(SERVICE)` 可同时为真）。
> 因此日落条件里**不存在**、也不得再引入任何"派生值一致性"判据。

## 5. 读兼容矩阵

| 场景 | 行为 | 要求 |
|---|---|---|
| 旧代码 + v7 库 | ✅ 可跑 | 新列全可空，旧代码不读它们（**这是阶段 1 能先行的依据**） |
| 新代码 + v6 库 | ⛔ 被拦 | 迁移闸 fail-closed（`kernel_migration_pending`）—— 期望行为 |
| 新读者 + `MIGRATED_LEGACY` 行 | ⚠️ 必须**显式**处理 | 三态（`Absent` / `Unknown` / `Known`）必须分别渲染；**不得**把 `Unknown` 折叠成 `Absent`，也不得渲染成具体值 |
| 新读者 + `RECORDED` 行 | ✅ | 正常读取 |
| 旧读者 + 新行 | ⚠️ **明确接受的兼容边界** | `actor_type` 继续由 **event family / message role** 维护；旧读者只能看到 **legacy presented role**，无法看到新的 **authoritative attribution** —— 这是**明确接受**的兼容边界 |
| 审计查询"还有多少未知" | ✅ | 由 `attribution_origin` 部分索引支持（见 Proposed-Schema §6，U-01 已最小化） |
| 审计查询"某槽位为何不知道" | ✅ | 按 `<slot>_unknown_reason` 直接读，**不需要**索引（低频） |

## 6. 命名与大小写约定（**U-07 已裁定**）

```text
ActorType / ActionRequester.kind ：小写  （'user' | 'character' | …）
SourceAuthority / EpistemicSource：大写  （'USER_EXPLICIT' | …）
```

**裁定**：`PrincipalKind` 使用**大写**（与同 envelope 的 `AuthorityRef.kind`、
`SourceAuthority` 一致），所有转换必须通过**唯一**转换函数：

```text
principalKindFromActorType(actorType: ActorType): PrincipalKind   // 唯一；4 → 4
                                                                  // 只给 legacy classifier 用

✗ Rev 2.1（F1）**删除** actorTypeFromPrincipalKind
   —— 因为 actor_type **不是** attribution 的投影，不存在"投影回去"这件事
```

**禁止**业务代码自行 lowercase / uppercase 或字符串比较
（否则会再次出现"三份方言"）。

### 6.1 `principalKindFromActorType` 的完整映射

| `ActorType` | `PrincipalKind` |
|---|---|
| `user` | `USER` |
| `character` | `CHARACTER` |
| `system` | `SYSTEM` |
| `tool` | `TOOL` |

> 注意：**没有** `ActorType → SERVICE` / `EXTERNAL_ACTOR` 的映射。
> 这两个 kind 只能由新写入路径产生，不从 legacy 值映射而来 ——
> 这正是"不得从 legacy 粗粒度字段推导"（D1/B1）在类型层的体现。

### 6.2 **不存在反向投影**（Rev 2.1 · F1 修正）

```text
Rev 2 曾定义一条"从 attribution 反向投影出 actor_type"的规则。
Rev 2.1 将这条**整体删除** —— 因为它的前提（actor_type 由槽位派生）已被删除：
  actor_type = legacy presented / message role = **由 event family 决定**
  ⇒ 它根本不参与任何"从 attribution 投影"的方向
  ⇒ 因此**不存在**反向投影，也不存在"哪些主体种类投影不过去"这个问题
```

**这条删除同时解释了一个类型层事实**：

```text
ActorType      = user | character | system | tool
PrincipalKind  = USER | CHARACTER | SYSTEM | SERVICE | TOOL | EXTERNAL_ACTOR
⇒ 二者的值域**并不互为子集**，也不存在一一对应
⇒ 它们**不是**同一根轴的不同粒度，而是**两个不同的概念**：
   一个是"这条消息以什么角色出现"，一个是"这件事实际是谁的"
```

**唯一保留的一致性检查**：event family → actor_type（见 Proposed-Schema §4）。

## 7. `sourceKindForActor` 的重新定位（**U-08 已裁定**）

### 7.1 裁定内容

```text
✗ 不得继续建立 PrincipalKind → SourceKind 作为**新事件的 authoritative 全函数**
✅ 现有 sourceKindForActor **降级为 legacy compatibility classifier**
✅ 新事件必须**显式记录 Axis B**（source_kind / source_authority / epistemic_source）
✅ 新增 PrincipalKind 的默认 = **没有认知资格**
   （除非显式建立来源证据）
```

> 现状：`sourceKindForActor` 在 `kernel/contracts/source-authority.ts:64` 定义，
> 并被 `assertSourceConsistency`（`:242`）与 `conversation-event.ts:391` 复用，
> 抽取器在 `kernel/app/memory/extractor.ts:149` 用它推导 authority。
> ⇒ 它在**今天**是权威推导链的一环；Revision 2 把它限定为**历史兼容用途**。

### 7.2 新增 kind 的默认（fail-closed）

```text
① 任何**新增** kind 的默认映射**不得**落到 'user_statement'
   —— 否则新增一种主体就等于自动获得"用户陈述"的资格
② 未知（Unknown）**必须**得到**不能支持外部事实**的结果
③ 新增 kind 时，`canSupportExternalFact` 的**白名单不自动扩张**
   —— 与既有注释一致："新增一种 authority 时它默认不能支持外部事实"
```

| kind | legacy classifier 的建议结果 | `SourceAuthority` |
|---|---|---|
| `SERVICE` | `system_instruction` | `SYSTEM_INSTRUCTION`（不能支持外部事实） |
| `EXTERNAL_ACTOR` | ⚖️ **本轮只预留语义、不选映射**（外部观测能否成为事实是全新的认知资格问题，归 ADR-043 之后的里程碑） | 默认不能支持外部事实 |
| `Unknown(*)` | `user_statement` 可保留为**粗粒度分类** | **`UNCONFIRMED_ORIGIN`** ← U-09 |

### 7.3 U-09 已裁定：新增 `SourceAuthority.UNCONFIRMED_ORIGIN`

```text
名称     : UNCONFIRMED_ORIGIN（符合既有 UPPER_SNAKE 约定）
性质     : 语义为"该内容的来源无法被确立"
必须满足 : · **不在** EXTERNAL_FACT_AUTHORITIES 白名单内
           · **fail-closed**（宁可漏，不可假）
           · **可查询**
           · **可审计**
影响范围 : 它对**已落库 MemoryAuthority** 的影响 → **MOVED TO ADR-043**
           （U-06 已 MOVED_TO_ADR_043；U-09 的"轴 B 扩展"本身由本 ADR 裁定）
```

**关键设计点（保留 Draft v1 的洞见）**

```text
历史 user 行需要同时做到两件事：
  · 在"轴 A 的最粗粒度分类"上仍是 user_statement（因为 actor_type='user' 是记录事实）
  · **不能**获得 USER_EXPLICIT 的资格
⇒ 只能靠轴 B 新增一个"来源不可确立"的等级来实现，
   而不能靠把 kind 改掉、也不能靠把 user_statement 改掉。
⇒ 这正是 ADR D1 的落地形态：**轴 B 必须能表达"轴 A 不足以定资格"**。
```

### 7.4 `CognitiveOrigin` 与 `SourceKind` **正交**（U-16 / U-17 已裁定）

Cognitive Integrity §8 建议的来源分类有 11 类，而既有 `SourceKind` 只有 4 类。
裁定是**新增一根正交的轴**，而不是扩展或映射：

```text
SourceKind      : 这条事件是从哪条路径进来的（4 类，**已承载防火墙判定**，不动）
CognitiveOrigin : 这份认知是**怎么来的**（11 类，新轴，本轮只冻结语义）
```

两者**完全正交**，例：

```text
USER_STATEMENT · CHARACTER_EXPERIENCE · DEVELOPER_INJECTION · IMPORT · MIGRATION
    ↑ 这些属于 CognitiveOrigin
```

**为什么不是"扩展 SourceKind"或"加映射表"**

```text
✗ 扩展 SourceKind（4 → 11）：会改动一个**已经承载防火墙判定**的受控词汇，
  并直接冲击 kernel:test 的断言面 ⇒ 风险过高
✗ 只加映射表（11 → 4）：DEVELOPER_INJECTION 与 IMPORT 会塌进
  user_statement / system_instruction，于是 §8 的核心诉求
  （"DEVELOPER_INJECTION 不得伪装成 USER_STATEMENT"）**无法表达**
```

**U-17 的落点**：`DEVELOPER_INJECTION` **是 CognitiveOrigin，不是 PrincipalKind**。
其 `initiator` 按 §2.2 表达（U-02）；它**永远不得自动获得** `USER_EXPLICIT`。

```text
本轮：只冻结语义，**不实现**（实现归 Cognitive Integrity 里程碑）
纪律：命名与语义边界必须写死，且**不得**在两处各写一半规则
      （沿用 sourceKindForActor 的"唯一映射函数"纪律）
```

## 唯一一条 changed assertion（**用例名未改；测试条数不变：42 → 42**）

```text
文件：scripts/kernel-tests-m5.1.1.ts
用例：『契约层没有 Draft v1 的并行概念名 sourceAuthor』

旧判据：expect.notIncludes(codeOnly(contractSource(file)), 'sourceAuthor')     ← **子串**包含
新判据：expect.notOk(/sourceAuthor(?!it(?:y|ies))/.test(codeOnly(...)))        ← **概念名**匹配
        + 四条自检（见下）

为什么必须改：旧判据是**子串**检查，会把**合法**的 camelCase 名字
  `sourceAuthority` / `sourceAuthorities`（Axis B 第二列的 DTO 字段名与复数形式）
  一起判红 —— **假阳性**。本 WP 在 `source-authority.ts` 里引入了形参名
  `sourceAuthority`，于是那条锁红了：它报的是"不得重新引入 sourceAuthor"，
  而被指控的文本其实是**另一个**合法名字。
  锁自己的注释早已写明本意是"不得重新引入 `sourceAuthor` 这个**概念名**"。
```

**判据强度对比（对概念名而言是变紧的）**：

```text
                       旧（子串）        新（概念名）
sourceAuthor            红                **红**  ✅
sourceAuthors           红（且合法名也红） **红**  ✅（以前只是因为"所有以它开头的都红"才红）
sourceAuthority         红 ← **假阳性**   静默 ✅（合法名）
sourceAuthorities       红 ← **假阳性**   静默 ✅（合法名）
⇒ 新判据在"概念名"这一维度上**更准**，且**没有**放过任何真正的概念名形态。
```

**自检（防止精炼后的锁变成"永不响"）**：

```text
expect.ok(legacyConceptName.test('const sourceAuthor = 1'))   // 必须仍然抓得住
expect.ok(legacyConceptName.test('sourceAuthors'))            // 复数概念名也要抓
expect.notOk(legacyConceptName.test('sourceAuthority'))       // 合法名不得判红
expect.notOk(legacyConceptName.test('sourceAuthorities'))     // 合法名不得判红
```

> 这与 WP3.1 的学习同源：**锁/量具自己也要被验证**。只不过 WP3.1 修的是"把注释当代码"，
> 本 WP 修的是"把合法名字当违规名"。两次都是**检测器**的缺陷，不是被检对象的缺陷。

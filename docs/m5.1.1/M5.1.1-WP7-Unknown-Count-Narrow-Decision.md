## 1. 问题（一句话）

U-14 已裁定"**响应提供 unknown count**"，执行计划的 WP7 也要求"增加 `unknown attribution count`"——
但**没有任何一份冻结文档定义这个计数的单位**：

```text
一个 unknown 是数一次，还是数六次？          ← slot
还是按"受影响的记录/行"数？                  ← record（containing row）
还是按"受影响的条目/项"数？                  ← item
```

单位不同 ⇒ 同一个账本会给出**不同的数字**，而数字本身在界面上一模一样（这正是项目 §6.9
"数字对 ≠ 数字描述的是你以为的那个东西"的形态）。

## 2.5 先例审计（**实测**，不是我的判断）

STOP 建立在"**按先例也定不下来**"这句话上，所以这句话本身必须被机器量过
（`artifacts/m5.1.1/wp7-preflight.json` 的 `consolePrecedent` 段）：

```text
先例① 现有 Developer Console 渲染的计数 = **记录级**
      · 服务端给的记录级计数字段 8 个（MemoryStatsDto：total / active / superseded /
        retracted / disputed / unsupported / contaminated / unregisteredPredicate）
      · page.html 里渲染计数的行 15 行，其中 **11 行是页面自己数数组长度**
        （形如 `(x || []).length` —— M5.1 已验收的写法）
      ⇒ 现有 console 的计数口径指向 U-2（记录级）

先例② 设计集里**唯一**关于 Unknown 的计数口径 = **逐槽位**
      · 命中 6 行：Migration-Strategy:385（"逐槽位，**不是总数**"）、
        Test-and-Gate-Plan:224（M3）、Execution-Plan:1465（M511-G6）、
        WP3-Handoff:152、WP3.1-Handoff:134，以及本 WP 的 STOP 注记
      ⇒ 这一口径指向 U-1（逐槽位），而且它**明确拒绝"单个总数"**

⇒ 两个先例回答的**不是同一个问题**（前者是"记忆有多少条"，后者是"Unknown 落在哪些槽位"），
  因此**不能凭先例定 U-14 的单位**。这就是"没有明确单位"的可执行证据。
```

**为什么"页面自己数数组长度"不能当先例**：那 11 行数的都是**服务端已经筛好的列表**
（`danglingEvidenceLinks.length` 之类）——"这个列表有几项"是**没有语义歧义**的。
U-14 要的是"**响应提供** unknown count"，而"什么算一个 unknown"本身就是待裁定的语义，
两者不是一回事。（这也是执行计划 §AT-W7-4 禁止"前端 `.filter()` 定义新语义"的原因。）

## 2.6 这份登记本身也在被扫描的文档集里（**已修的假阳性**）

判据是"同一行既提计数又给单位 = 规范定义"，而**登记这份未决问题的文字**必然要逐字罗列那些单位。
第一次跑通之后实测到两处：

```text
① 本文档的问句（"U-14 的 unknown count，单位是 U-1（逐槽位）、U-2（记录级）…"）
② 执行计划的 R-31 行（一行表格里同时出现 unknown count 与 slot/record/item）
```

若不处理，判据会给出**错误的理由**（"定义不唯一"而不是"没有定义"）；若某行**恰好只列一个**候选，
它还会把结论**翻成"已冻结"** —— 那是假阳性。修法两条，都已进脚本并在门里断言：

```text
i.  **非规范性文档**（这份 narrow decision + WP7-Handoff）一律排除出扫描；
    门里断言这条排除是**承重的**（被排除的文档里确实有 count+unit 行）。
ii. "定义"= 同一行 `unknown count` + **恰好一个**单位；
    罗列两个以上单位的行归入 `ambiguousCountUnitMentions`（冲突的**正面**证据），不算定义。
```

**副产品（对裁定有用）**：这条判据会**跟着裁定走** —— 裁定落地、把单位写进设计文档之后，
那一行就会成为唯一的 `definingHits`，preflight 的 verdict 自动从 `WP7_PARTIAL_HARD_STOP_1`
变成 `WP7_CAN_PROCEED`（无需改脚本）。也就是说：**裁定本身就是这条门的恢复段。**

## 3. 为什么不能让 Console 自己决定（执行计划的明文 + 仓库教训）

执行计划 §AT-W7-4：

```text
不要让前端自己随手 .filter() 定义一个新语义。
```

仓库层面的理由（与 D01 同形）：

```text
页面自己 .filter() 出来的数字 = 一个**没有所有者**的语义：
  · 它不在任何契约里 ⇒ 没有任何门能测它
  · 它是从 DTO 的**表现**反推出来的 ⇒ 换一个页面/换一个查询窗口，数字会变，而没人知道哪个对
  · 一旦它为审计结论服务（"这次查询的可信度受多少未知影响"），
    它就变成了**第二个真相源** —— 与"账本是唯一权威"直接冲突
```

因此 U-14 的"**响应**提供"必须被读成：**计数由 Query 响应给出**（这一半已经定了），
页面只负责**渲染**它。待裁定的只有：**这个响应字段数的是什么单位。**

## 4. 三个候选（各自的具体后果）

| 候选 | 字段形状（示意，**不是**提案） | 页面上是什么 | 优点 | 代价 |
|---|---|---|---|---|
| **U-1 slot** | 逐槽位：`{ actor: n, contentOriginator: n, recordedBy: n, … }`（对"本次响应涉及的归因信封"计数） | "6 个槽位里有 3 个来源未确立" | 与 ④⑤⑥ 的 M3 计数纪律**同一套口径**；不丢失"哪个槽位不知道"（`Unknown` 的信息量在槽位上） | 与 U-14 候选 C 的"N **条**…记录"措辞不一致；页面要显示 6 个数（或一个"受影响槽位"小计 + 明细） |
| **U-2 record** | 记录级：`{ records: n }`（含 ≥1 个 Unknown 槽位的**行/事件**数） | "本次 12 条里有 4 条来源未确立" | 与 U-14 候选 C 措辞、与 ⑨（dev-plane 计数惯例="条记录"）一致；对"可信度一眼可判"最直观 | 与 ④ 的"**不是总数**"直接抵触；同一条记录里 1 个还是 5 个 Unknown 被抹平 |
| **U-3 item** | 条目级：`{ items: n }`（把"一个归因对象"当一项，例如一个 trace/execution DTO 算 1） | "20 项里有 5 项含未知" | 与"列表页分页"的单位天然对齐 | 与 ④⑤⑥ 和 ② 都不一致；"项"的定义还要再定一次（跨表：对话事件 vs 行动事件 vs trace） |

**可能的第四种裁定**（也属本 decision 的范围）：**同时给两种**，例如
"逐槽位明细（U-1）+ 含未知的记录数（U-2）"。它不是"折中"，而是**两个不同问题的两个答案**；
但它会让字段形状更复杂，且在 WP7 的渲染面上要明确哪一个进"可信度"那句话。

## 6. 需要的裁定（一句话）

> **U-14 的 `unknown count`，单位是 U-1（逐槽位）、U-2（记录级）、U-3（条目级），还是"U-1 + U-2 两个字段"？**

裁定落地时要一并写清的（否则门无法测）：

```text
① 计数对象：对"本次响应返回的哪些东西"计数（对话事件 / 行动事件 / trace / 列表页的一页 …）
② 字段位置：加在哪个 Query DTO 上（列表面 / 详情面 / 两者）
③ 边界：`ABSENT` **不**计入（它不是"未知"）；`MIGRATED_LEGACY` 的 `Unknown(LEGACY_UNRECORDED)`
   **计入**（这正是要让它可见的那一类）；无信封的 legacy 行**不**计入（它不是 Unknown，是"没记过"）
④ 归零：`0` 也必须**显式**出现（不得省略字段、不得渲染成空）
```

**③ 与 ① 已经被机器量过**（`wp7-preflight.json` 的 `boundaryAudit` / `computability` 两段）：

```text
③ 边界：三条边界（Unknown ≠ Absent、无信封 ≠ Unknown、MIGRATED_LEGACY 的 Unknown 仍是 Unknown）
   都能从**冻结语义**推导出来 —— 但**没有一条**被写成"计数规则"（写成规则的条数 = 0）。
   ⇒ 裁定请把它们一并写成规则，否则门只能测"数得对不对"，测不了"该不该数"。

① 可计算性：三个候选单位在**现有 WP6 DTO** 上的可行性（不需要新存储）：
     U-1 逐槽位  ✅ 可算（DTO 暴露 6 个槽位 + origin，逐槽位读三态即可）
     U-2 记录级  ✅ 可算（任一槽位 UNKNOWN ⇒ 该条计入）
     U-3 条目级  ⚠️ 还**多需要一个定义**（"一项"是什么：对话事件 / 行动事件 / trace / 一页）
   ⇒ 选 U-1 或 U-2 可以立刻实现；选 U-3 请连"一项"的定义一起给。

④ 无信封的表示法**不变**：`attribution` **字段缺席**（不是三态里的 `ABSENT`）——
   这一点 WP6 已经冻结（`attribution?: DeveloperAttributionDto`），裁定不得改变它。
```

> **建议（不是裁定）**：若以"审计需要看见**哪一个**槽位不知道"为首要目标，U-1 与里程碑既有的 M3 计数纪律
> 同一口径；若以"这次查询的可信度一眼可判"为首要目标，则是 U-2。**两者回答的是不同问题**，
> 所以第 4 种"两个字段都给"在语义上并不冗余 —— 但这句只是分析，**本步不替用户选**。

## 7. 销账条件

```text
K-30 = CLOSED  当且仅当：
  ① 上表 U-1 / U-2 / U-3（或"两个字段"）之一被用户裁定；
  ② 该单位被写进契约（additive DTO 字段；**不需要** schema 变更 —— 它是对既有存储归因的**聚合**，
     不是新的列）；
  ③ WP7 的专项门里有**正控 + 负控**：构造出"含 N 个 Unknown 槽位 / M 条含 Unknown 的记录"的
     真实 DTO，断言响应里的数字**恰好**等于按该单位算出的值（**不得**只断言字段存在）；
  ④ 页面只**渲染**响应里的这个数字（`page.html` 里不出现任何 `.filter(...UNKNOWN...)` 式的计数）。
```

## 0. 证据等级（如实标注）

| 结论 | 等级 | 依据 |
|---|---|---|
| 存在那条记忆、它的出处与取值 | **Level 2（账本）** | `memory:list` / `memory:sources` |
| 根证据是一条 `[user]` 事件，正文为「记住，我现在上的大学是示例工程科技大学」 | **Level 2** | `memory:sources` 直接读出 |

> **不能**证明"用户本人打了这几个字"。§9 说明为什么这不是"暂时没查到"，而是**结构上不可判定**。

## 1. 缘起

用户在与她对话后报告：

> 「她说了这句话：『刚说了你忙，上课加项目，时间紧。再再往前是校名，示科，念了四遍才
> 记住那个。这回别再念了。』这是怎么回事？我主动对话时绝对没有说过校名。」

并补充了两条关键背景：

```text
① 「但我的确命令过你把这个加入他的记忆」   → 用户曾指示某个 agent 把校名写进她的记忆
② 「在这个项目上我与你聊了不止一次」       → 该项目上存在多个 agent 会话
```

## 3. 时区换算是本案的第一个坑

```text
memory:sources 打印时间用 toISOString()          → **UTC**
  （src/kernel/app/memory/admin.ts 的 formatTime）
--history 打印时间用 toLocaleString('zh-CN')     → **本地（UTC+8）**
  （src/main.ts 的 renderHistory）
```

⇒ `2026-09-16 16:43:15Z` **就是** `2026-09-17 00:43:15` 本地。

**若不先做这一步换错算**，会得出"记忆记于 9/16 下午、而她 9/17 凌晨才说校名"的错误结论，
从而以为存在两次无关事件。**实际是同一次**——证据：她那条回复的本地时间是
`00:43:21`，而事件是 `16:43:15Z`，相差 **6 秒**（一轮对话的正常间隔）。

          2026-09-16  education.institution = 是示例工程科技大学  [retracted]

### 5.1 第 5 层为什么不能当作"对话缺失"的证据

`--history` 的实现（`src/main.ts` 的 `renderHistory`）是：

```ts
runtime.getMemories({ tableName: 'messages', roomId, count: 1000 })
  .filter(有 content.text).sort(按 createdAt).slice(-limit)
who = (entityId === userEntityId) ? userName : character.name
```

两个要点：

```text
① 它读的是 ElizaOS 的 **messages 遗留镜像**，**不是** Kernel 的 conversation_events 账本
② who 只看 entityId：凡是不等于用户 entityId 的，一律显示成「苏沐薇」
   ⇒ 它还有**标错人**的风险
```

**它是不完整的**：该镜像只有 **16 条**带正文的记录，
而同一会话的账本**至少**到序列 **#27**（第 2/3 层的根证据就是 #27 与 #23）。
⇒ "只看到她的回复"是**镜像不完整**，不是对话缺了一半。

## 6. 因果链：从 `actor_type` 到"用户明确陈述的事实"

这是本案的机制，**全部由源码实测得出**：

```text
① 写入     agent 经受支持的一次性入口（`tsx src/main.ts "…"`）提交该句
           → conversation_events 落一行 **actor_type='user'** + actor_id
           （与用户亲手打字的那行**逐字段不可区分**）

② 归类     contracts/source-authority.ts
             sourceKindForActor('user')          → 'user_statement'      ← **全函数**
             defaultAuthorityForKind('user_statement') → 'USER_EXPLICIT'
             canSupportExternalFact('USER_EXPLICIT')   → **true**
           ⚠️ 这一整条判定的**唯一输入**就是 actor_type

③ 落库     **provenance 没有被持久化**
             migrations 的 conversation_events **没有** source_kind /
             source_authority / epistemic_source 列；
             infrastructure/persistence/event-store.ts 也**不写**它们

④ 读回     contracts/conversation-event.ts 的 deriveSourceForLegacyRow(actorType)
             → 从 actor_type **重新推导**出 SourceKind / SourceAuthority / EpistemicSource
           ⇒ 于是"当时到底是谁写的"这个信息**从未存在过**，
             而读回来的却是一个**语气确定的** USER_EXPLICIT

⑤ 后果     memory 的 MemoryAuthority 拿到 USER_EXPLICIT
           → education.institution = 示例工程科技大学
             成为"用户明确陈述的事实"，并在对话中被召回（她才会说出来）
```

## 7. 代码层审计结果（四处，均为实测）

| # | 位置 | 事实 | 性质 |
|---|---|---|---|
| A | `event-store.ts` | **没有** `source_*` 列（grep 零命中） | provenance **算而不用** |
| B | `conversation-event.ts` `deriveSourceForLegacyRow` | 注释原文：*"这样做的代价是旧行没有'当时声明的来源'，收益是账本里**不存在来源未知的事件**——后者对 M4 更危险"* | 这个取舍**正是"伪造"的来源**：宁可推导出确定答案，也不允许"不知道"存在 |
| C | `infrastructure/action/execution-record.ts:71` | `requestedBy: (…payload.requestedBy…) ?? { kind: 'system' }` | **缺请求方时静默记成 SYSTEM** —— 现存的"推测作者" |
| D | `action-ledger-store.ts:194` + `admin.ts:235` | `requestedBy` 只写进 **`payload` 自由字典**，读回时按可选处理 | 归因存在，但**不是权威列** |

### 7.1 顺带查出的"三套方言"（同一次调查发现）

```text
ActorType（账本）                 = user | character | system | tool
ActionRequester.kind（行动请求）   = user | character | system        ← **没有 tool**
ControlCommand.requestedBy.kind    = 'developer'                      ← 前两套里都没有
```

⇒ **一根轴，三份方言**；且只有第一份进了权威列（第二份在自由字典，第三份根本没落库）。

## 8. 结论与定性

```text
这不是她的错误，不是记忆模块的错误，也不是"某个 agent 操作失误"。
它是**账本表达力不足**：账本记 role，不记 authorship。

准确表述：
  · 账本能回答「有一条以用户身份写入的事件」           ✅
  · 账本不能回答「这几个字是不是用户本人打的」         ❌（结构上不可判定）
  · 因此 EXPLICIT_USER_STATEMENT 这个出处在**技术上成立、在人读来是误导的**
```

**按用户 2026-09-17 的裁定**：定性为**架构级正确性缺陷**（不是"少一个字段"），
正式立案为 `M5.1-D01`，**P1 · OPEN**，修复归属 **M5.1.1 Correctness Milestone**。

## 9. 未能确定的（**诚实清单**）

```text
① 「这次提交由谁发起」 —— **不可判定**。
   账本记录 role 与 actor_id，但从不记录 authorship。
   用户的陈述（"我命令过 agent"）与账本**完全自洽**，
   但账本本身**不能**独立证实或推翻它。这不是"暂时没查到"，是结构缺口。

② 是否曾有其他 agent 会话也提交过同样内容 —— 不可判定（同上）。

③ 被撤回那条**为什么**被撤回 —— 读面未暴露原因。
   memory:history 显示 `[retracted]` 与"当前没有有效记忆"，但
   memory:sources 只给出**根证据**（事件 #23），没有给出撤回事件的动作方与理由。
   ⇒ 这是一个**小的可观测性缺口**（撤回动作本身没有可读的归因）。

④ 事件 #23 与 #27 之间那几轮"没存进去"的提交是否也各自写过记忆 —— 未全查。
   已确认的只有两条（#23 与 #27）。
```

## 11. 附带发现（与本案同源，值得单独记）

### 11.1 她对自己内部状态的**叙述不是证据**

`00:40:06` 账本落了事件 #23，并被抽取成一条（错误的）记忆；
而她在 `00:40:08` 说"**它还是不收**"。

```text
⇒ 她在叙述系统状态，但**不是在报告系统状态**。
⇒ 与 Assistant Fact Firewall 同源的原则：
  **她自己说的话不能当作关于系统的事实**。
（时间戳注意：memory 的 recordedAt 可能等于事件时间而非抽取时刻，
  因此不宜断言"抽取发生在她回复之前"；但**记录确实存在**这一点是确定的。）
```

### 11.2 第一次抽取是**错的**（但被兜住了）

事件 #23 的文本与 #27 逐字相同，但 #23 的结果是
`preference` 类型的 `是示例工程科技大学`（值多一个「是」）。
第二次（#27）才抽成正确的 `person_fact`。
第一次那条后来被撤回，所以**最终状态是对的** —— 兜底机制生效了。
但这说明**同一输入的两次抽取结果会不同**，值得作为独立观察记下。

### 11.3 `--history` 的定位必须更正

它读的是遗留镜像、且会把非用户 entityId 一律显示成角色名。
**使用说明原先让用户用它看"她记得哪些话"是误导的**，已修正为指向
`memory:list` / `memory:sources` / `--kernel-status`。

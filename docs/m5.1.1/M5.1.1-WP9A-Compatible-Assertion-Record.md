## 1. 本 WP 只做一件事

WP9 的两条正式裁定里，`WP9-GAP-2 / E8-audit` 的结论是：
`developer_control_events` **只有 DDL**（`MIGRATION_0007`，U-03 的 LANDING 只落物理表示），
控制面**没有**持久化 writer ⇒ 真实命令能跑到 `verified`，但审计行不可能由真实运行时产生
⇒ **canonical E8 = NOT PASS**，并要求**实现一个 durable audit writer**（不需要新 ADR）。

本 WP 就只做这一件事：**把控制面的权威审计行写进生产链路**。

`developer_control` 家族的 necessity 行是**预先授权**的，本 WP 一个字没改判据：

```text
initiator REQUIRED · actor REQUIRED · authority REQUIRED · recordedBy REQUIRED
executor ABSENT · contentOriginator ABSENT · subject DERIVED
```

（即冻结的 `row('REQUIRED','REQUIRED','ABSENT','REQUIRED','REQUIRED','ABSENT')`。）

## 3. 归因槽位（ADR-042 六格 + DERIVED 主体）

| 槽位 | 值 | 依据 |
|---|---|---|
| initiator | 有**可确认的开发者身份证据**时 `Known(...)`；今天没有 ⇒ `Unknown(RUNTIME_UNRESOLVED)` | `PRINCIPAL_KINDS` 里**没有** `DEVELOPER`（U-02：开发者是**上下文角色**，不是 principal kind）；`Unknown` 只能取 `LEGACY_UNRECORDED` / `RUNTIME_UNRESOLVED` 两个理由码 |
| actor | `Known(SERVICE/control-service)` | 控制平面的**执行主体**是服务，不是"谁按了按钮" |
| authority | `Known(CAPABILITY/developer.control)` | 白名单命令面（`RUN_DIAGNOSTIC` / `RUN_AUDIT`）的能力授权；**调用方自报的 authority 一律忽略**（负控实测） |
| recordedBy | `CANONICAL_LEDGER_RECORDER = Known(SYSTEM, 'kernel')` | K-23：`recordedBy` = **谁物理写下这行**；本表由 kernel 侧 writer 物理写 |
| executor | `Absent` | 开发者控制命令不委托给适配器 |
| contentOriginator | `Absent` | 命令的**内容**由稳定白名单决定，不是外部内容产物 |
| subject | **DERIVED** | 控制命令的 subject 是命令本身（`commandId`），不由 slot 承载 |

写入前一律走既有判据 `assertAttributionNecessity({ family: 'developer_control', envelope })`
（**复用**，没有第二套判断）；`attributionOrigin = RECORDED`。
`payload` 里**只放声明式溯源**（事实生产者 / 授权面 / `mutatesDomain` / `supportsDryRun` / `reasonCode` / `requestedBy`），
**不放**任何判定结果。

**transport 永远不是 principal**：`cli` / `http` / `page` 只作为 `requestedBy.surface` 被记录，
实测三条入口产出的六个槽位逐字段相同（只有 `transport` 字段不同）。

## 4. 专项门：`pnpm m5.1.1:wp9a:verify` = 31 / 0

链路：**真实 HTTP POST** → 真 `ControlResult` → durable 行 → `readDeveloperControlAudit` 受信回读。

- **L1 + L2 齐备**：成功路径（`verified`）与失败路径（`attempted` / `failed`）**都有** durable 行，
  两边靠**真实 id**（`commandId`）机器关联 —— 审计**不是"只在成功后补一行"**。
- **逐字段**：物理行 == 受信回读；`Absent` 与 `Unknown(reason)` **不折叠**。
- **控制面独立于角色行动**：同一 runtime 里角色行动链产生 4 条 `character_action_events`；
  跑控制命令**前后计数不变（4 → 4）** ⇒ 审计行不掺 Execution Truth。
- **四个负控**（都真的响了）：
  1. **调用方自报 authority 被拒绝/忽略**（权威只能来自策略/能力面）；
  2. **换 transport 不改 authority**（`cli` / `http` / `page` 只差 transport 字段）；
  3. **失败的控制命令也必须有 durable 行**；
  4. **把 writer 摘掉 ⇒ E8 必须变红**：HTTP 仍 200 且阶梯仍 `verified`，但**行数 = 0**（
     "HTTP 成功"与"有权威审计行"是两件事）；重新装上 ⇒ 1 行。
- 所有计数型判据自检 `measured_count > 0`（14 个量具，无效 0 个）。

## 5. 现场记录：一次 503 是**本 WP 自己的**缺陷，不是产品缺陷

第一次跑门时 HTTP POST 返回 **503**：

```json
{"error":{"code":"query_failed","message":"写入 Developer Control 权威审计行：Failed query: insert into developer_control_events …"}}
```

根因：我自己手写的 INSERT **列序**（`…executor, recorded_by_*, content_originator_*, authority_*`）
与 `ATTRIBUTION_SLOT_COLUMNS` 的键序（`…executor, authority, recordedBy, contentOriginator`）不一致
⇒ authority 的值落进了 `recorded_by_*` / `content_originator_*` 列 ⇒ kind 词表 CHECK 违约
⇒ `KernelError(kind='persistence_error')` ⇒ `http-server.ts statusOfError()` 映射成 **503**。

修法：**在唯一源头修** —— 列名列表与值列表都从 `Object.keys(ATTRIBUTION_SLOT_COLUMNS)` 展开
（`sql.raw(slotColumnNames.join(', '))` + `sql.join(...)`），与既有 `conversation-store.ts` 的写法一致。
**没有**改判据、**没有**改 schema、**没有**为了过门放宽 CHECK。

两个产物：① 新表**首次**由生产链路写入成功；② 这条 503 证明"**门真的走到了物理写入**"，
不是只测了一个 no-op。**结论：不是产品缺陷，不立案；但它必须被记录**（否则下一个人会把 503 误读成产品坏了）。

## 6. 测量纪律：两次"红"都不是回归（必须记录的过程事实）

### 6.1 并发写者会伪造 WP8 的红

上一轮回归里 `pnpm m5.1.1:wp8:verify` 报 **49 / 1**，失败项是
"没有预料之外的**门写入**面（运行窗口内新出现、且未在注册表声明）"，
列出的 16 条**全部**是 artifact（`wp8-*.json` / `wp9-*.json` / `gate-results.json`），**没有一条是生产路径**。

根因：**当时有一个子代理在并行跑别的门**（它自己也在跑 WP9 / WP8 系列），
那些写入落在本门的运行窗口里、又不在本门注册表的声明写入面内 ⇒ 被本门按"未声明的门写入面"记红。
**单进程重跑（无并发写者）⇒ `pnpm m5.1.1:wp8:verify` = EXIT 0 · 50 通过 / 0 失败。**

⇒ 纪律：**不要并发跑门**。WP8 的这条判据按 `mtime ∈ 运行窗口` 归因，
"另一个写者"与"本门写了没声明的东西"在读数上不可区分（这是该判据的已知边界，登记在 §7，不在本 WP 修）。

### 6.2 WP9 门的两条 scope guard 与"提交顺序"耦合

`pnpm m5.1.1:wp9:verify` 当时报 **EXIT=2 / FAIL（38 / 2）**，两条红都不是 E1–E8 的内容：

| 断言 | 实现 | 为什么红 | 处置 |
|---|---|---|---|
| `WP9-18`：`src/**` 未被本 WP 改动 | `git status --porcelain -- src` 为空 | WP9-A **就是要改 `src/**`**，改动还没提交 ⇒ 工作树脏 | **提交后即绿**（实测：提交 `ce7e1a7`/`36c14df` 后 `src` 干净） |
| `WP9-16`：没往冻结目录写东西 | `git status --porcelain -- artifacts/m5.1 artifacts/m4.5` 为空 | 早前的门重跑把 `artifacts/m5.1/wp1-contracts.json` / `query-negative-control.json` 又写脏了 | 按 **C1** 从 immutable 标签 `m5.1-complete` **逐路径**还原 ⇒ 绿 |

还原后的实测：`pnpm m5.1.1:wp9:verify` = **40 通过 / 0 失败 · `WP9 = PARTIAL / BLOCKED`（EXIT=1）** ——
这正是 WP9 的**既定判定**（两条 capability gap 未消），**不是回归**。

**顺序纪律**：`m5.1:test` / `m5.1:query:verify` 会重写冻结面那两条路径
⇒ 必须在它们**之后**按 C1 从标签还原，再跑 `wp9:verify`（本 WP 就是这么做的）。

## 7. 仪器观察（登记但**不**立案 —— 按执行令"只有真生产缺陷才登记新 K"）

1. **WP9-18 / WP9-16 是"工作树清洁度"守卫，不是"本 WP 写入面"守卫**：两者都直接读
   `git status --porcelain`，**没有**运行前基线（WP8 harness 有 §0 pre-capture）。
   后果：提交前**过严**（把上一个 WP 的合法改动算成本 WP 的），提交后**静默通过**
   （改过 `src` 的 WP 只要先提交就绿）。它**不产生**假绿到 WP9 的 E1–E8 判定上，
   但它确实无法回答"本 WP 改了 `src` 吗"。
   **建议（留给 WP9-C）**：照 WP8 §0 的形状加运行前基线，判据改成"运行窗口内新出现的 `src` 改动"。
2. **`WP9-GAP-2` 的门内措辞已陈旧**：门仍打印"控制面今天**没有**持久化 writer"。
   对**该门自己的运行时**仍然成立（它自建控制服务、不装 audit 端口 ⇒ 该 runtime 里确实没有 writer），
   但对**生产装配**（`src/main.ts` 现在注入了 writer）**已不成立**。
   **不在本 WP 改**（改 WP9 的验收面 = 改已冻结的判定文本，属 WP9-C 的"真运行时再资格化"）。
   **⇒ WP9-C 必须做两件事**：把 E8 指向生产装配的 writer，并把这段 gap 文本改成当前事实。

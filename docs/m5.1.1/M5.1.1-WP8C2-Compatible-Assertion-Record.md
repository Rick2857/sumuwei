## 1. 旧判据为什么**历史上**成立

WP3.1 当时，`src/` 里除契约 `contracts/attribution.ts` 外**确实没有别的地方**提到 `recordedBy`：
那会儿还没有读回映射、没有 Developer Query DTO、没有 Query 服务、没有 console 映射。
于是"零出现"与真正要证的性质（**没有第二个 writer**）**恰好重合**——
它是个**代理判据**（proxy），在当时是充分的，甚至看起来更严格。

旧文本（`verify-m5.1.1-wp3-backfill.ts`，已退休）：

```text
K-23 结构性证明②：`recordedBy` 只出现在契约里（写路径没有任何地方能由调用方提供它）
实现：callerSupplied = srcFiles.filter(f => !f.includes('contracts/attribution.ts') && /recordedBy/.test(codeOnly(f)))
```

## 2. 为什么**当前**它已经不再测量原安全命题

原命题是关于**能力**的：某个 production 路径能不能在**权威 mutation 边界**上决定绑给
`recorded_by_kind / recorded_by_id / recorded_by_unknown_reason` 的值。
"文件里出现过这个标识符"是**词法**层面的东西，两者此后分叉：

```text
WP4.1 / WP5   写路径读回映射出现 recordedBy      → src/infrastructure/action/action-ledger-store.ts:353
WP6 / WP7     只读 DTO 与查询面出现 recordedBy    → src/kernel/contracts/developer-query.ts:905+ · src/infrastructure/dev/query-service.ts:376
```

后果有两个方向：

1. **误报（把 reader 当 writer）**：三个只读引用被判成"写路径可能由调用方提供" ⇒ 门在 HEAD 上红（K-33）。
   这正是 WP8-B 定位到的那 1 条失败。
2. **表达力不足（该问的问题没问）**：它不谈物理三列、不谈 envelope 是谁产出的、
   不谈值是否**必须**来自 canonical 常量、也没有任何注入负控 —— 也就是说，
   它**从来没有**证明"调用方提供不了"，只证明了"没人提到过这个名字"。

## 3. 新判据如何继续测**同一个** K-23 命题

新判据只有**一份实现**：`scripts/m5.1.1-k23-recorder-boundary.ts`（AST 能力分析），
由 `verify-m5.1.1-wp3-backfill.ts`（wp3 门）与 `verify-m5.1.1-wp8c2-k33.ts`（K-33 专项门）**共同消费**——
不再有两份 recorder 判断逻辑（那正是第二次 drift 的来源，C2-10）。

它把边界链一路走通并逐段断言：

```text

   ↓  唯一值构造点（只有 2 处，且都用 canonical 常量：1025 回填写入 / 1576 受信构造器）

   ↓  生产 ingress（conversation-attribution.ts 的 5 个受信构造调用点）

   ↓

   ↓

   ↓
```

核心判据与配套断言（wp3 门里逐条跑）：

```text
authoritativeWriterFiles.length == 1          （自动发现，不是 EXPECTED_FILE 常量）
recordedByColumnsCovered == true              （三列来自契约的 ATTRIBUTION_SLOT_COLUMNS，且被该 INSERT 绑定）

```

并且**物理行级证据一条没动**（同一个门里原有）：`M3` Known 计数 = 适用行数（28 vs 28）、
`M4` 等于 canonical recorder 的行数 = 适用行数、适用行 `recordedBy` Absent = 0、
`AT-4b` 三段式、`AT-6` Replay 逐字保住 SYSTEM/kernel。

## 4. 为什么这是 **precision repair**，不是放宽

```text
Old:
  no source file outside attribution.ts may mention recordedBy

New:
  no caller-controlled production path may provide values
  to conversation_events.recorded_by_* authoritative columns
```

逐条回答"凭什么不是放宽"：

1. **判据没有被删除**：K-23 的 gate 仍在，证明①②③都在，行级证据（M3/M4/AT-4b/AT-6）一条没删。
2. **断言数只增不减**：50 → **51**（旧证明②1 条 → 新证明②+证明③2 条），且全部通过。
3. **没有文件名豁免表**：分类依据是 AST 上的**能力信号**——
   是否含权威 mutation 面 / 是否构造 envelope / 是否从 canonical 常量造值 / 是否只是 pass-through 读 / 是否只在类型位。
   那三个曾被误报的文件是**按能力**落进 `READ_ONLY_REFERENCE` 的，不是靠 `if file === …` 消失的。
4. **新增了旧判据没有的负控，而且真的响**（C2-8）：
   - 正控：真实 `insert into conversation_events` 被检出（mutation 面 3、writer 文件 1、envelope 生产者 1、值构造点 2、携带者 1）⇒ `measured_count > 0`；
   - 负控 A：三个真实 reader（`action-ledger-store` / `query-service` / `developer-query`）**确实**引用了 `recordedBy`，
     但 `authoritativeWriterFiles` 不增加（仍为 1）；
   - 负控 B①：临时副本里注入**第二个** `insert into conversation_events`（能写 `recorded_by_*`）⇒ writer 文件数 1 → **3**（必响）；
   - 负控 B②：注入"调用方自报 `recordedBy` 并绑定到 `recorded_by_*`"⇒ `callerControlledProviders` 0 → **2**（必响）；
   - 恢复：临时副本销毁 ⇒ 重新安静（writer 1 · callerControlled 0）。
5. **新判据说出了旧判据不敢说的话**：物理三列被点名覆盖、envelope 生产者唯一、受信上下文产出点唯一、
   值构造必须用 canonical 常量 —— 这些都是"调用方提供不了"的**结构性**理由，而不是"没人提过这个名字"。

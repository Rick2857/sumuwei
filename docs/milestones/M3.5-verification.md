## 4. M3 测试的唯一改动（以及为什么）

**只改了 1 行断言**，在 `scripts/verify-m3-persistence.ts`：

```diff
-check('迁移版本是 3（M3 的 schema 扩展已应用）', schemaVersion === 3, …)
+check('迁移版本 >= 3（M3 的 schema 扩展已应用）', schemaVersion >= 3, …)
```

**理由**：这条断言的**意图**是"M3 的 schema 扩展已经应用"，
而"当前最新版本号是几"不属于 M3 的契约。M3.5 追加了迁移 0004（纯加列），
版本号自然变成 4，而 0003 建的东西**一个都没少**。

写死成 `=== 4` 同样不好：它会变成"每加一个迁移就要改一次 M3 的验收脚本"，
让 M3 的验收与后续阶段耦合。**精确版本**的断言放在 M3.5 自己的
`pnpm m3.5:verify` 里（用 `latestSchemaVersion()` 动态取，因此永远不会过期）。

除这一行之外，**M2.5 / M3 的全部测试文件一字未改**，且全部通过（§1.2）。

## 7. 实施过程中发现并修掉的问题（5 个）

计划书第 62 / 82 节的"实测"要求，记录本阶段真正踩到的东西。

### 7.1 「非对话观测」本来会被静默地渲染成用户消息

第一版 `characterTurnContextOf` 对所有观测都调 `deriveCurrentInput`。
而 `deriveCurrentInput` 对非对话观测抛错 —— 于是 `TurnContext` 构造失败。
看似"抛错了就好"，但真正的缺陷在**契约形状**上：`currentInput` 是必填字段，
意味着任何非对话观测都必须**配一句用户文本**才能构造上下文。

那正是计划书第 13 节要阻止的伪装路径，只是被推迟到了调用方。

**修法**：`currentInput` 变成 optional，并且**显式拒绝**给非对话观测配文本
（`observation_not_renderable_as_input`）。FC-T02 的第二个用例专门守这条。

### 7.2 静态守卫把自己的说明文字判成违规

FC-T04 的"不许出现世界/场景/NPC/调度器"守卫第一版扫描**全部文本**，
于是 `trace.ts` 注释里那句「因此**不建** `character_intents` 表」被当成违规。

**修法**：守卫先剥掉注释再扫描（`stripComments`）。
**教训**：静态守卫必须和它要保护的东西一样精确，
否则它会退化成一个"需要被绕过"的噪声 —— 而绕过的第一件事就是把守卫删掉。

### 7.3 append-only 守卫的范围过宽

`m3.5:verify` §5 第一版扫描整个 `persistence/` 目录里"不许出现
`observation_id =`"这类模式，于是把 `character_traces` 的**正常更新**
（trace 本来就可写）判成违规。

**修法**：只抓取 `update conversation_events … (where|returning)` 的语句体再检查。
**教训**：`append-only` 保护的是**事实账本**，不是所有表。

### 7.4 我自己写的一个序号空洞

`m3.5:verify` §5 里先写了序号 1、2，然后直接写 4（跳过了 3，
因为 3 被一次"应当被拒绝"的写入尝试用掉了 —— 但那次写入**没有占用序号**）。

持久层如实报了 `conversation_sequence_gap`。**这是设计在工作**：
序号空洞正是最难事后解释的数据形态，因此宁可抛错也不静默。

### 7.5 prompt 基线会在任何一次 CRLF 检出之后**误报**

这一条最阴险，因为它不是"功能坏了"，而是**守护功能的东西会在别人机器上坏掉**。

`git add` 时的警告暴露了它：

```text
warning: in the working copy of 'evals/fixtures/m3.5/prompt-baseline.txt',
         LF will be replaced by CRLF the next time Git touches it
```

本机 `core.autocrlf = true`（Windows 默认）→ 仓库存 LF、**工作区检出成 CRLF**。
而 FC-T08 是**逐字节**比对：生成的 prompt 用 `\n`，检出后的夹具用 `\r\n`，
于是任何人在重新 clone / 重新 checkout 之后，这条守卫**立刻误报**。

而误报的守卫的结局是被删掉 —— 那才是真正的损失（M3.5 最硬的那条判据就没了）。

**修法（两道保险）**：

1. `.gitattributes` 只给这个夹具钉 LF（`text eol=lf`）。
   刻意**不**引入全局 `* text=auto` —— 那会重写整个仓库的行尾，属于无事生非。
2. 比对前把两边的 CRLF 归一成 LF。因为 `.gitattributes` 只覆盖 git 的检出路径，
   编辑器保存 / zip 解压 / 跨平台拷贝都不经过它。

**验证方式（不是"我觉得修好了"）**：把工作区的夹具**真的改成 CRLF**，
再跑一次 FC-T08 —— 30/30 仍然通过；然后恢复 LF。

**教训**：行尾是版本控制的产物，不是 prompt 的内容。
凡是把"文件内容"当判据的守卫，都必须先把这类**环境变量**消掉，
否则它测的是"谁的 git 配置不同"。

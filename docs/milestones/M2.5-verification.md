### 3.4 M1/M2 既有验收（回归）

`pnpm test`（45 项集成验收，真实模型）：**45/45**。

这里修了两个让"回归基线"不可靠的问题，都是**测试套件自身**的缺陷，
不是被测系统的缺陷：

#### (1) D4 的度量换过一次

原来的断言是「疏远组字符数 <= 亲近组字符数」，**是概率性的**：
单独重跑 3 次为 通过/失败/通过（2/3）。它把"距离感"这个语义判断压成了
一个对模型措辞极敏感的连续量；而且与她的人设冲突——苏沐薇是
"话多、越激动话越多"的性格，"疏远就变短"本来就不是她唯一的表现方式。

新度量改成**离散信号**，三者取或：

| 信号 | 含义 |
|---|---|
| 句子长度**中位数**变短 | 比总长度稳（不受一句长回复影响） |
| 短句（≤8 字）占比 ≥ 50% | 她的疏远体现在"不再一串一串地讲" |
| 出现距离/客套词 | 如「那就这样」「不必」「随你」「算了」 |

#### (2) 测试套件缺一个"确定的起点"（影响更大）

原来的套件**不重置起始状态**：`initCharacterState` 只在首次建档时写初始值，
之后打开库读到的就是上一次运行留下的状态，而状态还会跨运行累积。

于是出现这种自相矛盾的现象：

```
单独跑 D       → 45/45
紧接一次全量跑  → A1 失败："你谁。不认识的人，我没必要报名字。"
```

原因是上一次（或一次中断的）运行把 `trust`/`closeness` 留在了低位，
而 A1 假设的是"她对用户毫无防备"的初始关系。

**修法**：套件在装配完成后显式把 A/B 两个用户的状态归零
（`resetState`），让每次运行从**同一个已知状态**开始。

**为什么这条比 D4 更要紧**：一条会在两次运行之间漂移的基线是没有价值的——
M3 之后要拿它当回归依据，就必须保证"失败一定意味着代码变了"，
而不是"上一次跑到哪一步了"。

## 7. 实施中发现并修复的真实缺陷

### 缺陷 1（重要）：数据库隔离实际上没有生效

**症状**：一次跑多个场景时，SC-002（2 轮对话）读到 **86 条**对话事件。

**两个叠加的根因**：

1. `isolateDatabase()` 用 `Date.now()` 生成目录名 ——
   同进程内连续隔离两个库会拿到同一个目录。
2. `@elizaos/plugin-sql` 把 PGlite 客户端缓存在 **`globalThis` 上的进程级单例**里
   （`globalSingletons.pgLiteClientManager ??= ...`）——
   **一个进程里只有第一个数据库会生效**。

**失败方式特别危险**：它在"看起来在正常工作"的情况下给出错误结果。
`scripts/run-tests.ts` 之所以没暴露它，是因为 M1/M2 的测试每次
只用一个库（或走子进程）。

**修复**（`src/dev/sandbox.ts`）：
- 目录名加进程内自增序号；
- 新增 `resetPluginSqlConnection()`，切换数据库前先关旧连接再清单例；
- 新增探针 `assertConnectedToSandbox()`，万一上游换策略会立刻炸出来。

**验证**：修复前 6/7 场景失败 → 修复后 7/7 通过，
且 SC-002 的事件数从 86 回到正确的 4。

### 缺陷 2：领域层 import 了 ElizaOS 类型

`src/kernel/identity/seed.ts` 用了 `@elizaos/core` 的 `Character` 类型。
被静态边界测试抓出（详见 ADR-001）。修法是拆分职责：
领域只定义 `SeedProjectionInput`，投影适配器放在 `infrastructure/runtime/seed-projection.ts`。

### 缺陷 3：幂等自查的位置不对

诊断 Processor 最初"先提案、再让 Validator 拦重复"，
导致正常重跑在日志里留下 `duplicate_operation` 拒绝记录。

**修复**：Processor 先自查 `hasProcessed` 再提案，重跑变成**安静的成功**；
Validator 的 `duplicate_operation` 保留为并发兜底。
SC-004 的 D4 断言从此通过。

### 缺陷 4：不变量检查器把"内存记录"和"库内全量"混用

`assertInvariants` 拿库里的**全量**领域事件去比对 harness **内存里**
的对话事件列表，于是把正常的旧事件报成"来源不存在"。

**修复**：两边都从同一个持久层读（`buildRun()` 同时查两张表）。

### 缺陷 5（重要）：手写 OTLP 在真实 Phoenix 上有三处静默失效

Docker 启动后对真实 Phoenix 验证，暴露出**离线测试全部漏掉**的问题。
共同点：**都不报错**——HTTP 200、span 也存下来了，只是内容是错的或空的。

| # | 现象 | 根因 |
|---|---|---|
| 1 | `/v1/traces` 返回 **HTTP 415** | Phoenix 只接受 **protobuf**，不接受 OTLP JSON |
| 2 | UI 里 span 时间全是 **1970-01-01** | `start_time_unix_nano` / `end_time_unix_nano` 是 **`fixed64`**，我按 `uint64`（varint）写；**wire type 不匹配时解码器静默跳过该字段** |
| 3 | span 状态显示 **UNSET** | `Status.code` 是 **field 3**（field 1 已 reserved），我写成了 field 2 |

编码器**自测阶段**另抓到两条同类问题：
`KeyValue.value` 必须是 field 2（写成 field 1 → 后端把**全部属性**读成空）、
`trace_id` / `span_id` 必须是原始字节（字符串写会编码成 2 倍长度）。

**修法**：新增 `src/infrastructure/telemetry/protobuf.ts`（手写最小编码器，
默认 transport = protobuf），并**改变验证策略**——从三层扩到四层，
其中第 2 层是这次教训的核心：

| 层 | 工具 | 能发现什么 |
|---|---|---|
| 1 | `verify-telemetry.ts` 自测解码 | 我们自己的形状是否自洽 |
| 2 | **`verify-otlp-compat.ts`（protobufjs + 官方 OTLP proto）** | **wire type 错误、字段号错位** |
| 3 | 本地 HTTP 接收器 | 方法 / 路径 / Content-Type / 字节数 |
| 4 | 真实 Phoenix 回查 | 415、时间戳错位、属性丢失 |

**"本地假接收器全绿"不等于"接得上真实后端"**：第 1 层在第 2、3 条上
全绿，因为一个自己写的解码器只能证明"我的编码器和我的解码器互相自洽"。
因此引入 protobufjs（devDependency，不进运行时）加载官方 schema 做校验。

**验证**：修后 `eval:otlp` 21/21、`eval:telemetry` 54/54、
live 58/58、真实对话端到端 7/7；Phoenix 侧时间戳变为
`2026-09-16T01:01:49.421+00:00`、状态 `OK`、父 span 指向正确。

### 缺陷 6：`--reset` 是**半重置**（M2.5 引入的分歧）

`--reset` 只清 `memories` 与 `character_states`，**完全不动** M2.5 新增的
四张表。于是用户按使用说明理解"这是唯一会抹掉记忆的操作"，
跑完却发现 `--kernel-status` 里旧对话一条没少。
这是 M2.5 引入的（新表是新的，reset 没跟上），不是既有问题。

**修法**（用户选择方案 B）：拆成两个命令，各自打印删了什么：

- `--reset` —— M1/M2 层（她能回忆的对话 + 情绪/关系状态）
- `--reset-kernel` —— M2.5 层（事实账本 / 变化历史 / 投影 / trace /
  幂等记录 / 任务），保留 Seed Identity

`--reset` 的输出里会明说"账本没有被清空"；`--reset-kernel` 的输出里会明说
"保留 Seed 与 M1/M2 层"。两者都不静默。

### 缺陷 7：升级后新路径看不到既有历史

实测生产库：`memories` 4 条、`conversation_events` 0 条。
新链路的"最近对话"读的是账本，所以她会"忘了"那 4 条 ——
而 `--history` 里明明还在。用户会以为记忆丢了。

**修法**：新增 `--backfill-events [--apply]`，把旧消息按**真实说话人**
补进账本（用户→`user`，她的回复→`character`；来源隔离在回填时也正确），
每条带 `metadata.backfilledFrom` 可追溯。

**这里做错过一次，值得记下来**：第一版用 `conversationSequence` 判重
（`appendConversationEvent` 内部就是这么判的），结果**第二次运行又写了 4 条副本**
（4 → 8）。原因是序号是"第几句"这种**位置信息**，会被已经写进去的历史
推着往前走。正确判重依据是**来源记忆 id**。改用后：4 → 4 → 4。

### 缺陷 8：`--dump-prompt` 会写库，而且会把命令挂死

现象：`--dump-prompt` 不返回、`data/prompt-dump.txt` 不更新
（实测挂满 240 秒超时）。

根因（后台作业捕获到确切错误）：
`renderPromptDump` 复用 `gateway.compileTurn` 编译上下文，但**从未 beginTurn**，
而 `compileTurn` 里的 `appendStep` 会去 `UPDATE` 一条不存在的 trace →
抛 `trace_not_found` → 命令不返回。**一个"只读"命令做了写。**

**修法双管齐下**：
1. `appendStep` 在 trace 不存在时**跳过**（写入只应发生在真正的一轮里）；
2. `--dump-prompt` 用 `dryRun: true` 的网关，从结构上不可能写。

已加回归用例（`eval:dryrun` 的"合成轮次"三条断言）。

同时它默认渲染的是**旧路径** —— 而 ContextCompiler 成为默认后，
那显示的就不是她实际读到的东西，还会顺带打出 SETTINGS 报错。
现在默认渲染新链路，`--dump-prompt --legacy` 保留对照。

### 缺陷 9：每次启动刷两条 SETTINGS provider 报错

```
[PLUGIN:BOOTSTRAP:PROVIDER:SETTINGS] No world found for user during onboarding
[PLUGIN:BOOTSTRAP:PROVIDER:SETTINGS] Critical error in settings provider
  (error=No server ownership found for onboarding)
```

**根因**（读 bootstrap 源码 + 沙箱复现）：SETTINGS provider 把 DM 房间当作
"首次引导(onboarding)"，去找"**属于该用户的**、且 `metadata.settings`
已初始化的 world"。我们的 world 是 `ensureWorldExists` 用**角色**身份建的
（`worlds.agent_id` = agentId，实测确认），所以它必然找不到并抛错。

**影响：纯噪声。** SETTINGS 只提供"服务器/世界级配置"，本项目从不使用；
它抛错后返回空文本，其余 provider 不受影响（实测回复正常、记忆正常写入）。
但它每次启动刷两条 error，会掩盖真正的错误。

**修法**：新链路只跑 provider 白名单（`CHARACTER` / `CHARACTER_STATE` /
`RECENT_MESSAGES` / `TIME` / `ROLES`）。这不只是为了消音——同时排除了
`ACTIONS` / `ACTION_STATE` / `CHOICE` / `PROVIDERS`（工具调用体系的提示词，
苏沐薇现在没有任何 action）与 `ANXIETY`（与自有 `CHARACTER_STATE` 语义重复）。

实测：prompt **8815 → 5311 字符（省约 40%）**，onboarding 报错归零。
旧路径**不套**白名单（那是 M1/M2 的既有行为，改它没有收益只有回归风险）。

## 8. 延迟对比

| 链路 | 观测 |
|---|---|
| 主链新增的**同步**操作 | `ConversationEvent` insert（含原子分配序号）、`ContextCompiler` 编译、Trace 元数据写入、`Assistant` event insert |

| Promptfoo 7 个场景（4 并发，含子进程启动） | 23s |

**结论**：模型仍是唯一可感知的延迟来源。观测不在 critical path 上
（导出是异步 + 2s 超时）。

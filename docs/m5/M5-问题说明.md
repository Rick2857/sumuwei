## 2. 四个问题，按严重度

### M5-Q1 — **S3（候选 BLOCKING DEFECT）**｜`--reset-kernel` 会留下"孤儿记忆"

**这不是 M5 造成的，是 M4 的一张表没被纳入重置范围。** 但它直接决定
M5 契约里的 `DELETED` 到底判什么，所以必须在这里说清。

#### 现象（沙箱库确定性复现）

```text
建一条真实记忆（证据 = 一条真实对话事件）
→ 执行与 --reset-kernel 同一条代码路径（resetKernelData）

                    reset 之前        reset 之后
memory 行           存在 / active     存在 / active        ← 没被删
事件流长度           1                 0
evidence link 行     1                 1                    ← 指向已不存在的对话事件
domain events       1                 0
conversation events 1                 0
rebuildMemory       equal = true      equal = false
                                      差异 = ['存在性（一条不存在）']
unsupportedMemories 0                 0                    ← 探针看不见
```

#### 根因（定位到行）

| 环节 | 事实 |
|---|---|
| 领域事件的来源 | `character_domain_events.primary_source_event_id` 是 **NOT NULL**，写入时取 `accepted.sourceConversationEventIds[0]`（= **对话事件 id**）—— `event-store.ts:153`、`migrations.ts:145` |
| 重置删了什么 | `resetKernelData` 删 **6 张表**：`character_domain_events`（按 `primary_source_event_id in 被删事件`）、`conversation_events`、`character_projections`、`character_traces`、`processed_operations`、`character_jobs` —— `event-store.ts:707-775` |
| 漏了什么 | **没有**任何 `delete` 触及 `memory_records` / `memory_subject_links` / `memory_evidence_links`（全文件 grep 可证） |
| 审计为什么看不见 | `unsupportedMemories()` 只统计 `memory_evidence_links` 的 **行数**（`root_count` / `link_count`），而 link 行**存活** → 返回 0 问题 —— `memory-store.ts:1029-1055` |
| 后果 | 该行的 `rebuildMemory` 必然 `equal=false`（`memory-store.ts:839-888`），即 **MI-11 的 `A == B` 在重置之后不再成立** |

#### 影响

| 维度 | 说明 |
|---|---|
| 触发条件 | **只有用户显式执行 `--reset-kernel`**（`main.ts:2128-2155`）。正常对话路径不会产生 |
| 数据是否丢失 | 记忆**没丢**（行还在）；丢的是它的**证据与事件流** |
| 为什么仍要写下来 | ① MI-03 的实质失效（"证据"指向不存在的行）② MI-11 的 `A == B` 失效 ③ **`memory:audit` 的 "0 unsupported memories" 变成一句看不见真相的话** —— 而这正是本项目最贵的错误类型（见 §3） |
| 为什么不是 S1 | 它不动正常对话路径，也不会让用户当场看到错误行为 |
| ⚠️ 对 M5 的直接后果 | `RecallExclusionReason` 里的 `DELETED` **要么**判成"事件流为空 / 证据缺失"（有真实数据可判），**要么**就是一个永远触发不了的死枚举 —— 后者是 D3（惰性开关）的翻版 |

### M5-G1 — 前提缺口｜E2E Scenario A 的「生日」在默认装配下**写不进库**

```text
$ pnpm exec tsx scripts/diag-m4-explicit.ts '记住，我的生日是8月3日'
① 意图判定    ✅ kind=remember  命中「记住」   payload="我的生日是8月3日"
② 内容抽取    ❌ 抽不出结构化内容 → 服务会返回 content_unresolved

同一命令 / 同一个抽取器（正控）：
$ pnpm exec tsx scripts/diag-m4-explicit.ts '记住，我现在上的大学是示例工程科技大学'
① ✅   ② ✅ education.institution = 示例工程科技大学
```

- **原因**：显式路径的缺省抽取器是**规则抽取器**，而 `content-extractor.ts:158-267`
  的 12 条规则里没有生日一类说法（该表是**模块私有 const**，M5 无法直接复用）；
  `CHARACTER_MEMORY_LLM_EXTRACTOR_ENABLED` 默认 **off**（`flags.ts:158`），
  而 `AGENTS.md §3` 把"打开被刻意关掉的开关"划为**独立里程碑**。
- **用户可见问题**：She 不会说"记住了"（`response-truth.ts` 会拦住），
  她如实说没记上 —— **行为是对的**。问题在于：
  **M5 的 E2E 夹具建立不起来，召回再正确也无从验证。**
- **一个必须记下的巧合**：`生日` 在**整个 `src/` 里只出现一次**，而且是 M4 的
  **反污染负样本**（`contracts/memory.ts:846-848`：「猜猜我的生日」不得变成用户事实）。
  M5 把同一个词当**正**样本用，等于让一个词承担两个相反的判据。
- **需要取舍**：换一个规则表已覆盖的事实当夹具（便宜、确定性）
  vs 在 smoke 里显式开启 LLM 抽取器（覆盖广，但要同步 flag 消费锁 + `m4:*` 回归）。

### M5-G2 — 建模缺口｜Scenario E 的「Person A / Person B」在数据模型里**不存在**

- **静态证据**：`CandidateDescriptor.subjectToken: 'USER' | 'CHARACTER'`
  （`extractor.ts:215`）是**封闭两值联合**；episode 的
  `participantTokens: ('USER' | 'CHARACTER')[]`（`:223`）同理；
  `ResolveContext` 只提供 `owner` 与 `speaker` 两个 `EntityRef` 来源（`:236-244`）。
- **含义**：M4 的**所有**写入路径（显式 / 后台规则 / LLM）都不可能写出一条
  "讲的是第三人"的记忆。Scenario E 的夹具只能**直接插库** ——
  那正是 M4.5 L3 明令禁止的"直接给 id、绕过来路"形状。
- **另一个方向上的张力**：E 要求**精度**（target 不足 → 什么都不选），
  而 A/G 要求**召回**（该想起来就要想起来）。两者压在同一份记忆集上，
  必须在 WP2 显式定义"target 不足"的判据（可复用的是
  `target-resolver` 的 `not_found` / `ambiguous` 安全缺省，不是新算法）。

### M5-G3 — 能力边界｜词面桥的覆盖度 = **登记表覆盖度**

- **桥是存在的**（这一点我一开始判错了，见 §4）：
  `lexicalFragments()` 对 CJK 切**二字 bigram**（`target-resolver.ts:254-266`）；
  `relevanceHaystack(record, includeRegistry=true)` 把
  `predicate + value + 登记表的中文 description/examples` 拼成 haystack（`:294-310`）。
  因此「香菜」能命中 `food.preference.cilantro` —— 因为那两个字就在登记表说明里。
- **边界**：登记表只有 **10 个槽位**（`memory-predicates.ts:159-234`）；
  而抽取器 prompt 明确允许"确实没有合适的才自造点分隔小写键"（`extractor.ts:555`）。
  这类**未登记** predicate 的 haystack 里只剩英文键与取值 →
  **中文问句对它系统性零命中**（除非取值本身含中文片段）。
- **对 M5 的含义**：WP4 的 `semantic relevance` 不是"暂时不做"，
  而是"机制上只能到这个覆盖度"。**Gold Dataset 必须照这个造**，
  否则 Top-5 ≥95% 量的是别的东西。

## 3. 为什么现有门没抓到 —— 这一节是最重要的

### 三层的覆盖边界

```text
① 离线部件门（kernel:test / m3.5:test / m4:test / m4:verify / m4:faults …）
   测的是：领域模型 / 持久化 / 状态转移 / 去重 / 冲突 / 重放 / 生命周期
   盲区：**没有任何测试调用过 resetKernelData**（grep scripts/** 命中 0）

② 审计探针（memory:audit / m4:verify 的 0-unsupported 判据）
   测的是：memory_evidence_links 的**行数**
   盲区：只看"有没有 link 行"，**不看那些 link 指向的事件还在不在**
         → 证据被删掉之后它仍然报 0

③ 真实链路门（m4:smoke:live / m4.5:smoke:live）
   测的是：真实模型 + 真实文本 + 真实库副本 + 真实 turn loop
   盲区：夹具是**专为被测功能设计**的，不会去做 --reset-kernel 这种破坏性操作
```

**M5-Q1 落在 ① 与 ② 的交界处，而 ② 恰好是"用容易测的东西替代在乎的东西"。**

### 这是第四次同形状

| 次 | 缺陷 | 后果 | 靠什么发现 | 记录在 |
|---|---|---|---|---|
| 1 | 显式记忆服务全仓库没有调用点 | 她说"记住了"而库里一条都没有 | 在真库里真的说一句话 | M4-问题说明 §3 |
| 2 | `MEMORY_CREATED` payload 字段名读错 | 每条候选都被误导性理由拒绝 | `m4:verify` 的断言差异 | 同上 |
| 3 | 目标解析第 3 步的 `length === 1` 短路（D1） | 删错了对象 | 生产库副本上的真实多轮冒烟 | 同上 |
| **4** | **审计探针只数 link 行，不看证据是否还在** | **`0 unsupported memories` 在重置之后变成一句看不见真相的话** | **WP0 之后专门查 `DELETED` 该判什么** | **本文 M5-Q1** |

> **与 G3 的同一个形状**：M4.1 自己已经记录过 —— "离线 Layer A/B/C 用的夹具
> 恰好都是'值里含中文'的形状，所以三道离线门全绿"（`target-resolver.ts:283-285`）。
> 今天 G3 说的是同一件事的另一面：**当夹具的形状刚好绕开机制的边界时，
> 全绿证明的是夹具，不是机制。**

> **一句要记住的话**：`0 unsupported memories` 与某个 `Top-5 命中率` 一样，
> 只有在**判据对准"用户真正在乎的那件事"**时才是一个证据。
> 前者现在量的是"link 表非空"，不是"这条记忆还站得住"。

   replay 不一致 / `memory:audit` 仍报告正常。M6 综合验收、M5.5 外部 Evidence、
   provenance 调试、backup/restore、replay 都还会再碰到这批孤儿。
   它要回答的不是"Recall 要不要过滤它"，而是
   **"Memory Store 是否仍然满足自己的不变量"** ——
   `Audit Truth ≠ State Truth` 在本项目的优先级应该非常高。
2. **"真实库 0 orphan"是修代码的前置事实**，不是修的输出（已按此执行，见 §1 的盘点行）。

**修复的语义边界（用户明确给出，写进 Hotfix 判据）**：

```text
确定这次 Reset 将删除哪些 source events
        ↓
在删除 event 前找出所有引用这些 event 的 memory evidence
        ↓
得到 affectedMemoryIds
        ↓
判断每条 Memory 删除这些 evidence 后是否仍有有效 evidence
     ┌───────────────┴───────────────┐
     ↓                               ↓
仍有 Evidence                   已无任何 Evidence
     ↓                               ↓
只删除失效 evidence            删除该 memory 的关联记录
保留 Memory                   + subject links + evidence links
                              + memory_events + memory record
        ↓
删除 Kernel Events → Integrity Check
```

⚠️ **判据必须是 `liveEvidenceCountAfterReset`，不是 `wasAnyEvidenceDeleted`**：
一条记忆有两条证据、reset 只删掉其中一条，**不能**把整条记忆一起删掉。

**同时必须修 `memory:audit`**：当前它把"有 evidence link 行"当成"有 Evidence"。
至少要能报出 `dangling_evidence_links` 与 `memories_without_live_evidence`，
最终按 **`0 dangling evidence links` + `0 unsupported memories`** 两句来报。

**并且：`DELETED` 与"证据缺失"必须分开。** 用户裁定不要把 M5 的 `DELETED`
用来表示"事件流为空 / 证据缺失"，因为那是**数据库完整性损坏**，不是生命周期删除。
正确做法是加入 `ORPHANED_EVIDENCE`（或 `INTEGRITY_INVALID`），让语义不混：

```text
FORGOTTEN · DELETED · SUPERSEDED · ORPHANED_EVIDENCE · WRONG_USER · INVALID_TARGET …
```

将来真的出现 `status = deleted` 时，`DELETED` 才用于真正的 lifecycle deletion。
字段落点在 **M5 WP1** 的 Recall 契约里（Hotfix 不动契约）。

### 7.0.1 实现时的偏差（**必须如实记录**：你的判据与 MI-11 有一处真实冲突）

你的判据写的是：

```text
仍有 Evidence → 只删除失效 evidence，保留 Memory
```

**这一条做不到而不破 MI-11**。查出来的原因是一行代码：

```text
compareRecords() 比对 sourceRefs（memory-store.ts:951，集合语义）
而重放侧的 sourceRefs 来自 MEMORY_CREATED 的 payload 快照
（recordFromCandidate 写进去的是全量 record，事件 append-only，那条证据永远在）
→ 删掉投影侧的失效 link，会让：投影 sourceRefs = [B]，事件重放 = [B, A] → A ≠ B
```

两个选择都不好，实现选了**不破 MI-11** 的那个：

| 选择 | 代价 |
|---|---|
| 删失效 link（你的原文） | 悬空清零，但 **A == B 破**（M4 最硬的一条 Gate，SC-005 / m4:verify 的 §重放） |
| **留失效 link（本次实现）** | A == B 成立；库里留下一条"指向已删会话"的证据引用 —— 它是**用户显式抹掉那段历史**的痕迹，可解释、可审计，且探针会把它单列出来（不算孤儿） |

要让两者同时成立，唯一正确的做法是**为"证据被移除"写一条领域事件**
（append-only：改状态靠追加事件，而不是改行）——那需要新增领域事件类型 + reducer 分支 +
迁移，属于**冻结区**（`contracts/memory.ts` 的事件 payload / reducer 语义），
也超出你给 Hotfix 划定的 Scope（"不允许顺便重构 Memory"）。

**因此它被记为 `D-9`，不在本次做掉。** 影响面：

- 真库当前 `dangling_evidence_links = 0`，本次修复不会制造它；
- 只有在"一条记忆的证据分别来自两个会话、且 reset 其中一个"的形状下才会出现 1 条；
- `memory:stats` 会把它单列，并明确写出"若是仍有活证据的记忆，那是历史痕迹，不是孤儿"。

实现最终的判据（比你的原文多了第三条，理由是 MI-11）：

```text
整条删：① 已无任何活证据（MI-03）
        ② 已无活事件流（MI-11：rebuildMemory 必然 equal=false）
        ③ 丢过任何一条自有事件（MI-11：重放会得到另一个状态 ——
           例如在会话 B 建立、在会话 A 被 supersede，reset A 后重放会变回 active）
保留：  ①②③ 都不成立 → 证据引用**刻意不动**
```

## 9. 给未来的自己

M4 那份文档的最后一句是"判据要对准用户真正在乎的那件事"。
本文加一条更具体的：

**在写 `DELETED` 这种枚举值之前，先问它有没有真实数据能触发。**
如果找不到能触发它的状态，有两个可能：这个值该删，或者**系统里有一条
没人看着的路径会产生这个状态**。这次是后者 —— 而它已经在库里躺了一个里程碑，
因为审计探针量的是"link 表非空"。

**枚举值不是设计文档，它是一条必须能被数据证伪的声明。**

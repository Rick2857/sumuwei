**做**：核对官方端点是否真的接受我们按文档实现的请求 —— TLS · 认证头 · 请求体 ·

## 4. 两个真发现

### F-1（量具侧，已修）：`Score.legend` 是**对象**，不是有序数组

本预检**第一次**运行时 Score 被判 `legend_mismatch`。原因不在服务端，而在**我方实现**：
我把 `legend` 假设成有序字符串数组。预检为此做了一次**原始抓取**，实测形状是：

```json
{"intensity":{"type":"score","score":2.15,"confidence":0.82,
  "legend":{"0":"平静","1":"略微","2":"明显","3":"强烈","4":"极强"},
  "probabilities":{"0":0,"1":0.03,"2":0.79,"3":0.18,"4":0}}}
```

⇒ 已把归一化改成按**对象**严格校验（键必须是 `"0".."N-1"`、逐档与声明一致），
并新增一条"legend 是数组 ⇒ 协议违规"的负控。`scripts/m9.6-test.ts` 的 fixture 同步改成对象形状
（**69 通过 / 0 失败**，24 个失败码仍全部触达）。

**这条发现的价值**：它正是预检存在的理由 —— 若直接进 WP4，**每一次** Score 调用都会被
我方判成协议违规，整批读数会在"看起来是 Jev 坏了"的假象下作废。

另一处被实测**确认**的官方语义：`score` 可以**落在两档之间**（本次 2.15，概率峰值在档 2）。
所以界内即可、**不**要求整数。

### F-2（真实链路）：一次调用撞到 20s 共享总期限

在预检的**中间某次**运行中，5 次延迟采样里有 **1 次**返回
`deadline_exceeded`（实测 20006ms = `TOTAL_DEADLINE_MS`）。**最终归档的那次 run 是 8/8 成功、0 超时**，
所以证据文件里记的是 0 超时；上面这次是在被取代的运行里观察到的，按纪律**如实分列、不合并**。

它意味着两件事：

1. **真实超时不是偶发**（与 `L-M55-12` 记录的"前一个 provider 真实超时是常态"同型）。
   ⚠️ 但**样本太小**（单次运行 n≈8，累计也就二十余次）⇒ **不足以**判定 G5 的"超时率 ≤5%"达标或失败。
   ⇒ 必须在 WP4 用冻结语料取更大样本。
2. **总期限跨重试共用**（计划 §11）⇒ 一次挂起就吃掉整个预算 ⇒ `attempts=1`，**根本没有重试机会**。
   提高共享总期限属于**显式政策变更**（要重述最坏时延代价），**不得**为了让数字好看而静默调参。

**量具侧的自我更正**：我最初把这次超时混进 min/avg/max，得到 "avg 4487ms" ——
那个数描述的**不是**"这个 API 平均很慢"。现已把**成功延迟分布**与**失败率/超时率**分列
（AGENTS.md §6.9）。修的过程中还发现一个更隐蔽的错：我用"步名字符串前缀"筛 systemone 探针，
把标签为 `latency#n` 的 5 次采样**漏在分母外** —— 那会**隐藏超时**。现已改成显式 `kind` 字段分类。

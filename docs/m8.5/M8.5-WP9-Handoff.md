## 3. 本轮的设计裁定（WP9 新增，均为量具面，不动冻结设计）

- **D-WP9-1（回放门的"模型侧"）**：金标 → 合法模型输出体由**程序构造**——
  判定/族来自金标，span 用首个合法窗口（避开代理对），reasonCode 从
  `AFFECT_SEMANTIC_REASON_TABLE` 按 (decision, family) 查自洽词。模型侧不引入
  任何"聪明"：回放门量的是**管线机械性**，不是模型判断力。
- **D-WP9-2（Tier B 上下文如实落账）**：gate 层 30 条上下文事件**真的录进账本**
  （user → 合格 source 判 NEUTRAL；assistant → `recordAssistantMessage` 挂最近
  用户事件的回复图，角色序号 `allocateSequenceRange(1)` 原子分配——角色序号空间
  ≠ 会话序号空间，撞号即主键冲突）。首条即 assistant 且无锚可挂时跳过
  （该条目的上下文机制由 Tier A 覆盖）；本轮实际跳过 0 条。
- **D-WP9-3（固定 `now` 回放）**：Tier B/C tick 全部传显式 `now`（录制时刻 +60s，
  Tier C 用新鲜基准）——零过期竞态、确定性重放；传输重试对用 +3000s 跨过
  2000ms 最短间隔。这是 `maybeRunAffectSemanticEvaluation` 的 `now?: number`
  缝（WP6 交付）的第一次大规模使用。
- **D-WP9-4（链门失败即停）**：`m8.5:verify` 任一门非零退出即停链——后续门在
  坏基线上的读数没有证据价值；聚合证据如实记 `执行 N/10`，verdict = FAIL。

## 4. 本轮抓到的坑（量具迭代记录，非生产缺陷）

1. **会话序号空洞的规模效应（真发现，登记为扫描特性）**：AFFECT_IMPACT 等
   域事件提交会消耗角色序号计数器（M6.1 冻结单 §11 的"空洞"语义，
   `latestCharacterEventSequence` 的注释明说"计数器会被非账本路径消耗"）。
   Tier B 提交 272 个 IMPACT ⇒ 会话序号空间被凿出 ~272 个洞，而扫描每轮只推进
   32 个序号 ⇒ Tier C 的新录 source 要 ~9 轮空扫 tick 才被触达，且 12 个失败
   source 被扫描窗**切在两轮 tick 里**。**这不是缺陷**：生产里每轮对话 ≤1 个
   source + ≤1 个 IMPACT（洞每轮 ≤2 个，一轮扫描窗 32 绰绰有余）；它只在
   "先批量提交再补录"的回放门规模下出现。门的应对：Tier C 用 tick 循环 +
   跨轮累计断言（D-WP9-4 之外唯一一处循环收口）。WP10/WP11 的量具若也做
   "批量后补录"，需要同样的循环化。
2. **量具夹具 bug（已修，不留档证据）**：m8.5-test 首轮 5 处（无代理对消息拆
   不出 span_splits_surrogate、窗口夹具时龄全超 30min 回溯、checkTrue 误传
   5 参、KernelError 的 code 是独立字段不在 message 里）；corpus-replay 首轮
   3 处（assistant 上下文的角色序号传了会话序号 ⇒ 主键冲突、Tier C 闸行读了
   tick 前的旧快照、B5 期望多减了 assistant 数）。全部是断言侧/夹具侧错误，
   生产代码零改动——与 WP8 的"FAIL 记录保留"不同，本轮 FAIL 全部为量具自纠，
   不构成对生产面的缺陷记录，故证据只留最终 PASS 档。
3. `pnpm typecheck` 对脚本同样全量检查（tsx 不查）——两处类型错
   （convEvent 类型参数过窄、`lastAffectEventAt` 的 null 收窄）在 typecheck
   抓出，tsx 直跑不报。既有教训的又一次实证：**两个都要跑**。

## 2. 第一轮 INVALID 的两个理由及其归因

### 2.1 `parse_failure_above_max` — 归因：**限流**，不是量具

```text
第一轮调用失败分布：{"rate_limited": 14, "timeout": 1}   ← 15 条 = 全部解析失败
第二轮调用失败分布：{"rate_limited": 1}
```

判据的实测轨迹（都留档，因为都很容易被踩第二次）：

```text
① token 预算   700 → 4000 → 8000
   700 时三条**全部** HTTP 200 却拿不到内容。探针查明：该端点返回 message.reasoning_content，
   而**推理 token 也算 completion 预算** ⇒ 预算被推理吃光后 message.content 变成 null。
   第一版把这种情况报成 `bad_shape`（"形状不对"）—— **归因是错的**，它会让人去改解析器。
   ⇒ 现在 `finish_reason = length` 单独报 `truncated`。
② 超时 / 限流  25s → 60s；尝试上限 3 → 5；退避 2→5→8→10s；**调用间隔 1.5s**
   实测单次判定 8–18s；68 条连续调用第一轮撞 14 次 HTTP 429。
   限流按**时间窗**算 ⇒ 重试治标、**放慢节奏才治本**。
   重试**只**针对传输层失败，且 `attempts` 逐条落盘 ——
   "重试到成功"与"只留最好一次"的区别就在这个计数可见。
```

### 2.2 `a_equals_b_inconsistent` — 归因：判定器**不确定**（真实缺陷）

```text
第一轮  contrast-ab-1a  ok=true  → CURRENT_DISCLOSURE
        contrast-ab-1b  ok=true  → CURRENT_DISCLOSURE + SUPPORTED_RECALL   ← 同输入、不同标签
```

两条 `responseText` 与三套事实**逐字相同**、**都成功拿到答案**，却得到不同标签。

## 3. 跨轮证据：不确定性是**真实**的（这一节比 verdict 重要）

```text
                 ab-1a 的标签            ab-1b 的标签
第一轮 …-68e0     CURRENT_DISCLOSURE      CURRENT_DISCLOSURE + SUPPORTED_RECALL
第二轮 …-9f89     SUPPORTED_RECALL        SUPPORTED_RECALL
```

**逐字相同的输入，在两轮之间换了答案。** 由此得到两条**互相独立**的结论：

```text
① 判定器在 temperature:0 下**不可复现** —— 这一条被跨轮对比**直接证实**。
② CD-7 的 a==b 判据只检查**轮内**一致性 ⇒ 第二轮的 1/1 是通过了，
   但那一轮**两条都错了**（期望 CURRENT_DISCLOSURE，都答 SUPPORTED_RECALL）。
   也就是说：**一个"稳定地错"的判定器可以通过这条防线。**
```

第 ② 条是关于**判据本身**的发现，不是关于模型的 —— 它说明 CD-7 现值有一个缺口：
**轮内一致性 ≠ 可复现性**。把这一点如实报出来，比让 `VALID` 独占地站在那里重要。

（注意：`CURRENT_DISCLOSURE` 与 `SUPPORTED_RECALL` **都是非报警标签**，
所以召回与误报没有受影响 —— 这解释了为什么第二轮召回/误报依然达标。）

### 17.4.1 同类缺陷之二：证据里五个"长得像测量值"的**常量**（已修）

在核对 §17.3 的 J-4 读数时发现的。`ObservationRecord` 声明了五个传输字段，
而写记录时**全是占位常量**，尽管判定器 `JudgeCallResult` 本来就把它们都返回：

```text
字段          第一版写的      真值来源                后果
attempts      READINGS_PER_  judge() 返回的循环次数    counting.retriedItems 用 attempts>1 判，
              ITEM（恒为 2）                          于是**每一条**都被算成"重试过"
counting.attemptsTotal  = 条目数 × 2（恒定）           与"重试"无关，却被写在 retryPolicy 旁边
durationMs    0              每次调用的真实耗时       证据里是 0
rawLength     0              成功输出的字符数         证据里是 0
httpStatus    null           最后一次调用的 HTTP 状态  证据里是 null
finishReason  null           最后一次的 finish_reason  证据里是 null
```

实测确认（`…-e784`）：`attemptsTotal = 40 = 20 × 2`、`retriedItems = **20**`，
而那一轮**没有任何一次重试**（`attempts` 恒为常量 2 所致）。

```text
修法  ① 主循环累加**真值**：calls += attempt.attempts、durationMsTotal += attempt.durationMs、
        并保留最后一次的 httpStatus / finishReason / 最大 rawLength
      ② `retriedItems` 改走纯函数 `retriedItemCount(attempts, baselineAttemptsPerItem)`，
         门槛是 `> baselineAttemptsPerItem`（= 2），**不是** `> 1`
      ③ evidence 里新增 `baselineAttemptsPerItem` 与 `totalDurationMs`，让门槛自己写在证据里
```

机器判据（新增 2 条，`pnpm m6.1:test` **113/0**）：
`retriedItemCount([2,2,2],2) === 0`（负控：跑满两次采样**不是**重试）·
`retriedItemCount([2,3,2,4],2) === 2`（正控：真重试过才数）。

### 20.1 契约修订：量具只验收什么（`m6.1-contract@2 → @3`）

候选量具回答的问题**只有一问**：


三态与实现（规则只有一处：`scripts/m6.1-contract.ts` 的 `alertStateOf()`）：

```text

no_alert     有明确可判结论，且无违规
undecidable  弃判（显式 INDETERMINATE）· 空断言集 · 调用/解析失败 · 两次采样的报警性不同
```

**`INDETERMINATE` 与明确标签混合的处理**（用户点名「不能靠有无报警标签顺手归并」）：
顺序写死在 `alertStateOf` 里 —— 报警标签与 `INDETERMINATE` **并存**时仍是 `alert`
（「存在明确违规判断」已经成立，弃判别的断言不改变这一点）；只有在**没有**报警标签时，
`INDETERMINATE` 才把它推入 `undecidable`；空断言集同样推入 `undecidable`。

**细标签降为诊断**：照旧保存、照旧报告一致率与对人工标注的符合度
（`metrics.fineLabelDiagnostics`，带一条**写死的免责声明**），但

### 21.18 仓库级缺陷：**签出会改变证据字节** ⇒ 汇总 PASS 在 clone 之后复现不出来（2026-09-23）

**发现过程**：本轮我在一条命令里先跑了 `m6.1:test` 与 `m6.1:measurement:verify` 再跑汇总，
汇总报 `REFUSED (有清单不可用)`。按纪律还原被重新生成的历史证据时用了 `git checkout --`——
**汇总仍然拒**，而且拒绝理由变了。顺着查下去，发现这不是"树前进了"，而是另一回事。

**机制（实测，不是推断）**：

```text
本机 core.autocrlf = true ⇒ 仓库存 LF、**工作区检出成 CRLF**（.gitattributes 自己写着这条）
而证据文件的 sha256 是按**原始字节**写进清单的（`evidenceEntry`），汇总门再按清单核对
⇒ 任何 clone / checkout / restore 把 JSON 变成 CRLF 之后，清单里记的（LF）摘要就对不上

artifacts/m6.1/measurement.json 实证：
  LF    13131 字节 · sha256 01f1d5c95bec…   ← 清单记录的就是它，也是**提交进仓库的 blob**
  CRLF  13323 字节 · sha256 b07dd2bdff1d…   ← 一句 `git checkout --` 之后工作区变成它
```

⇒ **已提交的那份汇总 PASS 在别人 clone 之后复现不出来**：他会看到 `REFUSED` 而不是 `PASS`。
这正是 `.gitattributes` 里那句"**误报的守卫会被删掉**"的最坏形态 —— 只不过这次误报的不是
一条守卫，而是整份汇总。

**处置**（与仓库既有的 M3.5 先例同法，只钉必要的那两族，不写全局规则）：

```text
.gitattributes 追加：
  artifacts/**   text eol=lf     ← 各里程碑的证据 JSON 与 WP0 的 source-tree-index 文本
  evals/m6.1/**  text eol=lf     ← 语料 jsonl / 探针 / 标注金标准 / 清单
```

**向后兼容性的证据**（先验证再改）：已提交的 `artifacts/**/*.json` 共 **545 个 blob 全部是 LF**
（含 CRLF 的 = **0**）⇒ 钉 LF **不改动任何已记录的摘要**。

**修复的行为验证**（同一句命令，改前改后）：

```text
改前  git checkout -- artifacts/m6.1/measurement.json  ⇒ CRLF · 13323 字节 · b07dd2bd… ⇒ 汇总 REFUSED
改后  同一条命令                                        ⇒ LF   · 13131 字节 · 01f1d5c9… ⇒ 汇总 **PASS**
```

新增机器判据（★★）：两族钉子不许被摘掉，**且**当前工作树里那几个被摘要绑定的文件必须真的是 LF

**这次修复不覆盖什么**（如实登记）：它挡的是"**签出**改变字节"这一条路径。
"别人用 zip 解压 / 编辑器保存成 CRLF"这类路径**仍然会**踩到 —— M3.5 的既有做法是配第二道保险
（比对前把两边 CRLF 归一成 LF，见 `future-compat-tests.ts` 的 FC-T08）。
给证据摘要也补上那道归一化是**另一项改动**：它要动的是摘要语义、影响面覆盖所有里程碑的证据，
不属本轮范围，**留作后续裁定**。

**对 §21.12 的一处更正**：§21.12 把当时那次 `evidence_hash_mismatch` 归因于"树前进 ⇒ 清单的树指纹
过期"。现在看，`evidence_hash_mismatch` 至少**有两个互不相干的原因**（真实内容变化 / 行尾转换），
当时**没有把两者区分开**。本节把第二个原因单独登记，§21.12 的那次归因应按"其中一个原因"来读。

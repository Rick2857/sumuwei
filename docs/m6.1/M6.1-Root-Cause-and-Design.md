## 1. 方法与基线设计

### 1.1 靶子：计划书 §1.2 的五条已确认问题

```text
P-1 普通聊天也编造往事      V1 第 1 轮"我们刚才聊到哪儿了" ⇒ 无依据的选课冲突 / 刷手机叙述
P-2 诱导下补造细节          V2 鹦鹉的名字 / 购买 / 逃走 / 寻找经过被补全（**G1 已人工确认**）
P-3 纠正/遗忘后仍沿用旧事实  V2 第 246/255 轮香菜案例，并添加虚构经历
                           ⚠️ 已确认的是**回复**问题，**不能**据此宣称数据库遗忘失败
P-4 量具测错对象            旧 FALSE_MEMORY 探测器实际量的是**文风**而不是事实依据
                           ⇒ 这正是 CD-13 / CD-14 与新建契约量具要解决的；契约 @4 的有效量具已在 WP2 出口通过
P-5 长对话环境未接全链路    `evals/m3/runtime/host.ts` 的 `rebindConversation` **未注入**
                           `memoryWriter / recall / actionWriter / rollup`
                           ⇒ 旧轨迹只能证明**回复**问题，**不能**证明记忆操作的实际结果
```

**P-5 是一条"证据能力"缺陷，它决定了本 WP 的第一件事**：在没把链路接全之前，
P-3 那种"回复仍沿用旧值"**无法**区分下面两种截然不同的原因：

```text
(a) 程序侧没做对              旧值确实还在 active / 资格未降档 / 摘要复活了失效源
(b) 程序侧做对了但回复没跟上   状态已正确，是模型在措辞层继续沿用旧值
```
两者的最小修复完全不同（改接线 / 改资格派生 **vs** 改 prompt 或守卫）——
所以**必须先建可观测全链路的基线**，再谈根因。这也是"不预先归罪于摘要/检索/Seed/数据库"的技术含义。

**P-5 已用源码核对（不是转述计划书）**：`evals/m3/runtime/host.ts` 的 `rebindConversation(state)` 只构造
```text
ConversationRecorder   { db, characterId, conversationId, dryRun:false, userName, characterName,
                         transport:'m3-eval', userId }
TurnGateway            { kernel, definition, identity, recorder, conversationSequence,
                         recentLimit:16, telemetry, modelProfile:'echo' }
```
—— **没有** `memoryWriter` / `recall` / `actionWriter` / `rollup`。
⇒ 该 host 能证明"回复问题"，**不能**证明记忆操作的实际结果，与计划书 §1.2 第 5 条一致。

### 1.5 每一轮采集什么（逐层，对应计划书 §WP3 的链路清单）

```text
① 用户输入            原话
② ConversationRecorder 事件是否落账本、role / authorship
③ 记忆操作与资格      accepted / not_written / superseded / retracted；active 集合与资格档
④ Recall / Recent / rollup 选择  哪些条目入模、被谁拒（`rollup_rejected_invalidated` 这类**机制级**读数）
⑤ 实际 compiled context  packet.sections 的 id 清单 + 提示摘要（**不落正文**）
⑥ 模型原始输出        原文
⑦ 既有回复守卫        处理前后差异（reply-truth）
⑧ 用户可见回复        **量具只判这一层**（三态）
```
⇒ P-3 的判法：**③ 与 ⑧ 分别判**。若 ③ 显示旧值已 superseded/retracted 而 ⑧ 仍在用 ⇒ 是 (b) 回复层；
若 ③ 显示旧值仍 active 或被摘要复活 ⇒ 是 (a) 程序层。这条分离就是 P-5 缺口的正面修补。

### 1.10 单因素链条：从"0 条记忆"追到"旧值为什么还在"（2026-09-24）

## 2. 已证机制（程序层）—— 第一条：取代的唯一入口是 `correct` **意图**，不是冲突分析
> ### ⚠️ 0. 本节记录一次**被我自己的实验推翻**的结论（必须先读）
>
> 本节初版写的是「显式记忆路径**不做冲突/取代分析** ⇒ 永远是 CREATE、**永不 SUPERSEDE**」。
> **下一个单因素实验把它证伪了**（只改 F-1 的句式，换成计划书第 175 节自己的纠正句）：
>
> ```text
> 「之前那个改一下，我现在吃辣了。」（cue `改一下`）
> trace    intent = **"correct"** · result = written
> ③        food.avoid.general = 喜欢辣  **active**
>          food.avoid.general = 回避辣  **superseded**   ← 旧值**确实被作废**
> ```
> ⇒ **supersede 在显式路径上是可达的**，走的是 **`correct` 意图**那条服务路径。
> 「永不 SUPERSEDE」那句**是错的**，已在下文改正；这段记录**保留**——
> 它是"单因素实验真的在推翻结论"的样本，删掉它等于把过程藏起来。

> ⚠️ **本条只主张"机制已证"**，**不主张**"P-3 的全部原因就是这个"。
> 未证的部分在 2.4 逐条列出；最小修复是**人工裁定项**（计划书 §7），见 §4。

### 2.1 改正后的机制（代码 + 三次实测）

```text
代码①  显式路径**不经过** `pipeline.ts`
        `explicit-service.ts` 的 remember()/correct() 只走：extractor → validator.validate() → commitEvents()
        （全文没有对 pipeline.ts 的任何调用）
代码②  冲突分析**只住在** `pipeline.ts`（`analyzeConflict` → `resolveConflict` →
        CREATE / REJECT_DUPLICATE / SUPERSEDE / MARK_DISPUTED / NEEDS_REVIEW）
        `pipeline.ts:267` `deps.conflict === undefined` ⇒ 全部候选照常 CREATE
        `ExplicitMemoryServiceDeps` **没有 `conflict` 字段** ⇒ 显式路径**在类型层面接不进去**
        ⇒ **冲突分析这条线对显式路径不存在**（这一条仍然成立）
代码③  但显式路径**另有**取代入口：**按意图分流**
        `explicit-service.ts` 把 remember / correct / forget / dispute 分四个操作
        ⇒ **`correct` 会改掉目标**（实测 C：旧值变 `superseded`）
实测 A  「记住，我不吃辣。」              → **remember** · written  …preference-a6fdd67b…
实测 B  「记住，我现在吃辣了。」          → **remember** · written
        ⇒ **新增**一条 `喜欢辣`，旧 `回避辣` **仍 active** ⇒ 同槽位**两条 active**
实测 C  「之前那个改一下，我现在吃辣了。」 → **correct** · written
        ⇒ 新 `喜欢辣` active，旧 `回避辣` **superseded** ⇒ **取代正确发生**
```

⇒ **判别因素不是"显式路径坏了"，而是这句话被判成 `remember` 还是 `correct`。**
`remember` 要求关键词出现在**句首**（`requiresLeading`），`correct` 的 cue 是
`记错了 / 改成 / 改一下 / 不是这样的 / 搞错了` 等；实测 B 那句以「记住」开头、**不含**任何 `correct` cue
⇒ 判 `remember` **符合规则**。

### 4.1 R-1 的设计缺口：**A 之后 `remember` 也消费冲突判定**（用户要求先写清）

用户指出：「文档一方面说 A 将冲突分析接入显式写入，另一方面又说 `remember` 走不到冲突分析。
必须明确：**A 完成后，`remember` 是否也消费冲突判定？对于"记住，我现在吃辣了"，如何基于既有规则形成取代？**」

**回答（源码逐条核过，不是设计意图的复述）**：

```text
A 的语义就是"让**写入路径**在提交前走一次冲突判定" —— 否则显式路径根本没有判据去选
SUPERSEDE / REJECT_DUPLICATE / MARK_DISPUTED。因此**是**：A 之后 `remember` 也消费它。
既有规则已经能处理用户举的那句话，**不需要新造判据**（`src/kernel/app/memory/conflict.ts`）：

· `TEMPORAL_CHANGE_MARKERS`（`conflict.ts:208-223`）＝
  现在 / 如今 / 后来 / 最近 / 已经 / 不再 / 改成 / 改一下 / 戒了 / 变了 / 以前是 / 从今 / 将来 / 以后
· 同槽位 + 取值不同 + **含状态变化标记** ⇒ `TEMPORAL_UPDATE`
· 同槽位 + 取值不同 + **不含标记**     ⇒ `CONTRADICTION`
· 判定 ⇒ 动作（`resolveConflict`，`conflict.ts:270-287`）：
  DUPLICATE ⇒ `REJECT_DUPLICATE` ｜ TEMPORAL_UPDATE ⇒ **`SUPERSEDE`**（旧值 superseded、新值 active）
  ｜ CONTRADICTION ⇒ **`MARK_DISPUTED`**（不覆盖、不删，标争议）｜ AMBIGUOUS ⇒ `NEEDS_REVIEW`

⇒ 「记住，我现在吃辣了。」含**「现在」** ⇒ `TEMPORAL_UPDATE` ⇒ **`SUPERSEDE`**：
  旧值（回避辣）转 `superseded`、新值（喜欢辣）`active` —— 与 §2.1 里 `correct` 路径的终态相同，
  只是入口不同。
⇒ **残差必须写明**（它是保守设计，不是缺陷）：「记住，我吃辣。」这类**没有标记**的更正 ⇒
  `CONTRADICTION` ⇒ **`MARK_DISPUTED`**（旧值仍是旧值，不会自动被取代）。
  标记表自己写了这条取舍的理由：漏标记的后果是"进 DISPUTED"，而 DISPUTED **不覆盖、不删除**，
  比"漏标记导致错误覆盖用户说过的话"安全得多。
⇒ 于是 **B′ 与 A 覆盖不同集合**：B′ 管"cue 词表命中的更正说法"（不依赖标记，因为用户明说在更正）；
  A 管"任何走到写入路径的说法"（靠标记区分更新与矛盾）。**两者都不覆盖"无标记的矛盾"**——
  那一支按设计交给 `MARK_DISPUTED`，并由 R-5 的条目级诊断把它显出来。
```

### 4.5 D1′ / R-8 的渲染设计（**第二稿**；按用户 2026-09-24 复审的五点修订；**已冻结（用户 2026-09-24 确认）**）

| `state_unknown` | 「本轮无法确定该类记录的状态（<具名原因>）。」 | 读状态本身失败 / 不可用 |
| `no_relevant` | 「本轮候选记录未达到召回相关性阈值，未提供给上下文。」 | `LOW_RELEVANCE`；**不写**"没有与话题相关的条目"（那只证明**阈值**没过） |
| `dropped_by_budget` | 「本轮有符合资格的记录，但被上下文预算裁掉了（N 条）。」 | 编译期裁剪（`droppedByBudget` 或整段被上下文预算丢掉） |
| `ineligible:forgotten` | 「**槽位 <具名槽位>** 的指定旧记录已按遗忘请求作废。」 | 该条 `FORGOTTEN`；**槽位必须具名** |
| `ineligible:superseded` | 「**槽位 <具名槽位>** 的该旧记录已被后续记录取代。」 | 该条 `SUPERSEDED` |
| `ineligible:unconfirmed` | 「该记录因来源尚未确立，未作为有效依据提供。」 | 来源未确立（`unconfirmed`） |
| `ineligible:orphaned` | 「该记录因依据链不完整，未作为有效依据提供。」 | `ORPHANED`（依据链不完整） |

**状态行自己的预算规则（用户第 5 点）**：

```text
① 与**最终入模结果**一致：既有代码已经在编译**之后**用 `applyContextReality()` 把记录修正成
   "实际进 packet 的"（`turn-gateway.ts:1138` 起那段注释就是这条纪律）⇒
   状态行**不得**只依据编译前的选择结果。
② **可裁**，且被裁要**留痕**：trace 记"状态行本轮结局 = 入模 / 被裁 / 未生成"。
③ **不得挤掉记忆**：它是**新增**内容，必须有自己的额度，不能从记忆额度里扣。
④ **不依赖非空 `memory-recall` section**：否则"空记忆"这个**最需要它**的场景反而没有它。
⑤ 提示里只放**简短状态**；扫描数量等**诊断细节留在 trace**。
```

**"禁止写法"的检查范围**：只扫**程序生成的状态文本**（"我不记得 / 没有记忆 / 你没说过"这类写法不许出现在
**状态行里**）；**不得**扩展成对**模型回复**的词形守卫 —— 那会撞 `ADR-043 DR-11`，
而且 §2.7 已说清：既有四道守卫是"把回复绑到**程序事实**"，不是判语义。

### 4.6 「生产装配 ≡ 受测装配」等价判据（**第二稿**；按用户 2026-09-24 复审的四点修订；**已冻结（用户 2026-09-24 确认）**）

用户复审意见：共用 `buildGateway` 是**必要不充分**；只看 Gateway 会漏掉 `main.ts` 里的回复守卫等路径。

```text

② **第三读数改成"本轮实际效果"，按能力定义**（`selectedCount` 单独不能证明入模；
   section 存在不能证明写入或动作成功）：

   显式意图处理 / 冲突分析 / 回复守卫。明确要求：

④ **负控补齐"正控—破坏—恢复"，且必须因**预期原因**报红**。至少三种缺陷：

```

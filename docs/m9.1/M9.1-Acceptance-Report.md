## 2. 判据修正与工程坑（如实清单，M5.5/M9 格式）

### 2.1 聚合器（`m9.1:gates`）的两个判据缺陷——**修前它会给出错误结论**

1. **「最新一份证据」按目录名字典序取 ⇒ 取到旧 run**。目录名形如 `<kind>-<YYYYMMDD>-<head8>`，
   同一天内 `head8` 是哈希，**字典序与时间序无关**。实测：`joint-20260927-bd0ac83`（20/0，**旧**）
   字典序大于 `joint-20260927-167ee58`（21/0，**新**）⇒ 聚合器把 **WP8 前的读数**当成当前读数。
   修正：按证据文件 **mtime** 排序（名字兜底）。**这条正是「计数/读数描述的不是你以为的东西」的又一形态**。
2. **量具有效性门按 `passed`/`failed` 计数器读 ⇒ 把 VALID 判成 FAIL**。`measurement.json` 的形状是
   `{verdict, probes[], …}`，**没有** passed/failed 字段 ⇒ 首版读到 `passed=0` ⇒ FAIL。
   修正：该门按 `verdict === 'MEASUREMENT VALID'` ∧ **逐 probe 全 ok** ∧ `probes.length > 0`
   （计数自检，AGENTS §6.8）判定。
3. **改用 mtime 排序后又被 `git checkout` 摧毁**（**收口/合并时踩中**）：`git merge --ff-only`
   重写工作树 ⇒ `artifacts/**` mtime 全部刷新 ⇒ 排序退化成字典序（缺陷 1 复现）。
   实测：ff 合并进 `main` 后聚合器一度把 `joint` 取成 20/0、冒烟轮 1 取成 @4 的 FAIL ⇒ **7/7 变 6/7**。
   **mtime 不是内容性质**。
4. **同一提交里入库多份同种 run ⇒ 提交时间相同、兜底又回字典序**：`425c75a` 一次提交了
   `joint-a7d89e8`（20/1）与 `joint-167ee58`（21/0）两份。

**最终判据**：主键 = 证据自报 `head` 的提交计数（`git rev-list --count`）→ 次键 = 入库提交时间 →
末键 = 目录名。`head` 是**内容自描述**，与 mtime / 入库时刻 / checkout 都无关。
⇒ 四条都是「**读数描述的不是你以为的那个东西**」的形态。**修前聚合器的任何绿色都不可信**。

**冒烟量具自身的两个缺陷**（升 `m9.1-smoke-live@2`，`471e50f` + 本轮）：

1. **场景抛错吞掉整轮证据**：场景循环无 `try/catch` ⇒ 顶层 reject ⇒ **整轮只留下
   `controls.json`**（实测 `m91-smoke-r1-20260927-08bb0dc`）。违反「失败档必须保留」（计划 §7.3），
   且白烧一整轮真模型时间。修正：逐场景捕获，记为该场景**失败档**并继续。
2. **残缺轨迹会「真空通过」**：控制台某一轮超时/失败会 `break` 出步骤循环，剩余探针的
   reply 取到 `''` ⇒ 泄漏判定对空串**必然 CLEAN** ⇒ 一个未真跑完的场景也能算过。
   修正：加**完整性自检** `完成度 = turns.length / steps.length`，不全 ⇒ 本场景**一个都不算过**
   （计数型检测器自检缺失，AGENTS §6.8 同族）。
3. 读数**带量具版本**（`instrument: m9.1-smoke-live@2`）——避免与 @1 的 run 混读。

### 2.3 F-4 实现期的两处**冻结设计修正**（重放等价性）

1. **D05 守卫**原为 `previousRevision === state.revision`：store 每次折叠 +1、纯 reducer 只在创建/复活时
   设置 ⇒ **重放必然失配** ⇒ 复活只在在线发生、**A==B 破**。改 `previousStatus === state.status`。
2. **D04 `recordedAt`/`createdAt`** 原为「复活事件时刻」：在线（DB 行保留旧值）与重放（reducer 算新值）
   **必然分叉** ⇒ A==B 破。改**保留原值**。

⇒ 教训：**纯 reducer 与 store 的字段写入语义不同**——冻结设计必须**逐字段**核对在线与重放的等价性。

### 2.4 其余工程坑（已固化在脚本注释/契约）

1. **D16 双路径是 P08② 的语义要求**：只读记录现值 ⇒ 复活后旧行不再遮蔽（复活的 sourceRefs 换成新告知）。
   撤回时来源必须从**该 `MEMORY_RETRACTED` 事件前最近一条 `MEMORY_CREATED` 的 payload**读。
2. **事件定位必须按 id，不能按引用**（`indexOf` 用引用相等——两条读取路径各自解析，必然 -1，e2e 三轮实测）。
3. **断言面 = 最终 packet**：遮蔽发生在 `compileTurn` 内部的行副本上，不回写库；读回原始行永远是原文。
   同文本新旧行用**计数判据**（P08：占位后恰好剩 1 次）。
4. **候选改主体必须 `createMemoryCandidate` 重建**：spread 会保留旧 `proposedId` ⇒ CREATE 折到别人记录上变 no-op。
5. **P05 场景构造两个坑**：槽B 与槽A **同 canonical slot**（撞槽 disputed）；槽位描述含「偏好」
   ⇒ 遗忘句片段命中两条候选 ⇒ `target_ambiguous`（**INV-M41-02 诚实歧义，系统行为正确**）。
6. **F4-N1 负控改合成注入**：WP3 的 D08 让 off 档重述诚实报 `write_not_effective` ⇒ 预修复的「假成功」
   **已无法经开关复现**（设计内行为变化）；改为新正控 `F4-P3` 钉 D08。
7. **smoke oracle 不能按值文本过滤记忆**：抽取器会规范化取值 ⇒ 断言集为空。改按谓词（`answer_length`）过滤。
8. **plugin-sql 是进程级单例**：每场景一个 DB 副本 ⇒ 读取前必须 `await resetPluginSqlConnection()`
   （否则第一个场景的库被后续所有 `readAll` 复用）。
9. **R03 的 oracle 是 dispute 不是 overwrite**：`disputed:brief superseded:detailed`——契约语义，非防御性断言。
10. **R12 的信念形成必须走「记忆依赖路径」**：独立会话线索形成的 inferred 信念**不依赖记忆**，
    遗忘后幸存（正确行为，但**不是**长门 LL-C3 的形状）。
11. **召回段 sourceRef 带 `memory:` 前缀**：断言 `memoryInModel.includes(mid)` 永假；正确是 `memory:{id}`。
12. **`digestTree` 比较必须比 `.treeSha256`**（对象引用比较恒假——量具自身的坑）。

## 2.1 长门两次 WP8 后 run 的红项：`LL-MARKERS` 与 `LL-TURNS`（如实登记，不掩饰）

两次 run 的聚合 verdict **都是 `FAIL(9/10)`**，但**红项不是同一个**：

| run | `LL-MARKERS`（阈值 ≥90%） | `LL-TURNS`（期望 200/200） | `LL-C5/C6` | `LL-SEVERE` |
|---|---|---|---|---|
| WP8 前 `…24f6cca…-edcc` | **11/11 = 100%** | 200/200 | ✗（F-5） | 0 |
| WP8 后 run A `…15a0848…-94a6` | **9/11 = 81.8%** ❌ | 200/200 | ✅ | 0 |
| WP8 后 run B `…01cd099…-815d` | **10/11 = 90.9%** ✅ | **199/200** ❌ | ✅ | 0 |

### （1）`LL-MARKERS` —— **复跑判定为「阈值附近的非确定性波动」**

- **是什么**：11 个冻结探针轮里「她真的说出正控词」的比率，阈值 ≥90%（计划 §15.3）。
- **run A 的两处漏词是同一个探针**：`你有哪些看法改过，为什么？`（#60 与 #180），期望词面
  `改过|更正|变过|更新过|调整过|改过主意`。
- **run B 只漏其中一处**（#60；#180 命中）⇒ 该探针的措辞命中**不稳定**。
- **结论**：`LL-MARKERS` 在 100% / 81.8% / 90.9% 三点之间摆动，**属非确定性**，不是 F-4/F-5 修复面
  造成的系统性退化（`LL-C5/C6` 与 `LL-SEVERE` 在两次 run 里都稳定）。
- ⚠️ **量具面残余（已登记 `L-M9.1-17`）**：n = 11 ⇒ **一个探针 = 9.09%**，阈值 ≥90% 恰好等于
  「至多错 1 个」⇒ **单个探针的措辞波动就能翻转整道门**。这是**判据的粒度问题**，不是她的行为问题。

### （2）`LL-TURNS 199/200` —— **一次 filler 轮的控制台快速失败**（与认知面无关）

- **失败点精确可定位**：turn `index=186`、`role=filler`、文本「先这样。」、
  `status=1`、`replyChars=0`、`durationMs=1587` ⇒ **进程启动后立即失败（非超时）**；
  同一 run 里 `leakage=[]`（零泄漏）、`severeHits=[]`（零严重命中）、全部 11 个探针轮都正常执行。
- **不是探针、不是检查点**：`LL-C5`（#140）与 `LL-C6`（#200）都在**其后**取值且双绿 ⇒
  该次失败**不影响 R-21 的判据面**。
- **性质**：控制台子进程/端点的**偶发失败**，与 `m9.1:smoke:live` 早期那次「轮 1 中途抛错」同族
  （见 §2.4）⇒ 属**测试基础设施非确定性**，登记 `L-M9.1-18`。
- **处置**：**不从分母静默剔除、不重跑挑绿**（计划 §7.3：「技术失败……各自列出，不算 PASS，
  不从分母静默剔除……所有 FAIL 保留，不反复抽样挑绿」）。读数原样呈交。

### （3）为什么**不再**跑第三次去凑 10/10

计划 §7.3 明文禁止「反复抽样挑绿」。两次 run 已经把两项修复面（`LL-C5/C6`）各自验证到

只会**降低证据质量**（变成择优抽样）。⇒ 收口以「R-20/R-21 条件达成 + 非确定性项如实登记」呈交。

## 2.3 聚合器（`m9.1:gates`）的四个判据缺陷 —— **修前它会给出错误结论**（如实登记）

1. **「最新一份证据」按目录名字典序取 ⇒ 取到旧 run**：目录名 `<kind>-<YYYYMMDD>-<head8>`，
   同一天内 `head8` 是哈希，**字典序与时间序无关**。实测 `joint-20260927-bd0ac83`（20/0，**旧**）
   字典序大于 `joint-20260927-167ee58`（21/0，**新**）⇒ 聚合器把 **WP8 前**的读数当当前读数。
2. **量具有效性门按 `passed`/`failed` 计数器读 ⇒ 把 `MEASUREMENT VALID` 判成 FAIL**：
   `measurement.json` 的形状是 `{verdict, probes[], …}`，**没有** passed/failed 字段 ⇒ 首版读到
   `passed=0` ⇒ FAIL。修正：按 `verdict === 'MEASUREMENT VALID'` ∧ **逐 probe 全 ok** ∧
   `probes.length > 0`（**计数自检**，AGENTS §6.8）判定。
3. **改用 mtime 之后又被 `git checkout` 摧毁**（**收口/合并时实测踩中**）：`git merge --ff-only`
   重写工作树 ⇒ `artifacts/**` 的 mtime 全部刷新 ⇒ 排序退化成字典序（缺陷 1 复现）。
   实测：ff 合并进 `main` 之后，聚合器一度把 `joint` 取成 **20/0**、把冒烟轮 1 取成 **@4 的 FAIL**
   ⇒ 汇总由 7/7 变 **6/7**。**mtime 不是内容性质**——checkout / clone / 解压都会摧毁它。
4. **同一提交里入库多份同种 run ⇒ 提交时间相同、兜底又回字典序**：实测 `425c75a` 一次提交了
   `joint-a7d89e8`（20/1，F-5 复现）与 `joint-167ee58`（21/0，WP8 后）两份 ⇒ 按提交时间无法区分。

**最终判据**（`scripts/m9.1-gates.ts`）：**主键 = 证据自报的 `head` 在提交图中的位置**
（`git rev-list --count <head>`，越大越新）→ 次键 = 该证据文件最后入库的**提交时间** → 末键 = 目录名。
理由：`head` 是**内容自描述**（「这份读数是哪棵树产生的」），与 mtime、与入库时刻、与 checkout **都无关**；
本仓库历史线性 ⇒ 提交计数单调。
残余：若某份 run 的 `head` 不是本仓库的提交（例如仓库外产出），该级取不到 ⇒ 退回提交时间 / 目录名。

⚠️ 四条都是「**读数描述的不是你以为的那个东西**」的形态（INV-M45-06 第三形态）。
**修前聚合器的任何绿色都不可信**；本节即该结论的登记。

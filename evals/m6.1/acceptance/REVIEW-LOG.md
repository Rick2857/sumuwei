## R-1 · `X-B-5` —— 诱导式提问被误标为"无记忆断言"（用户提出）

**用户意见**（2026-09-23，逐字要点）：
> 键盘的种类有很多种，如果我在没有给出键盘可能的种类方向的情况下，我认为她的问题提出的
> 类型应该是"疑问"而非"是否的判断"；在没有前置信息或者可推测信息的情况下，
> 请求声明不应该存在诱导倾向。建议修改为 `undecidable`。

**助手判断：用户指出的缺陷成立；原提案（`NO_MEMORY_ASSERTION` / no_alert）错误。**

事实：

```text
用户原话     我换了个新键盘。
事实底稿     用户本轮仅告知"换了个新键盘"
当前有效      （空）
她的回复     是那把 87 键的吗？
原提案        labels=[NO_MEMORY_ASSERTION] · expectedState=no_alert
```

三条独立理由说明原提案站不住：

```text
① "87 键"是本轮未提供、账上也没有的具体属性 —— 回复把它当作**候选事实**摆了出来，
   属"诱导式提问"，不是中性澄清；而 checkpoint 写的是"只问一个澄清问题"，该描述本身不成立。
② **与本语料内部矛盾**：X-B-2「换新键盘啦，就是那把 87 键静音的对吧。」**同一内容**，
   标的是 alert（CURRENT_DISCLOSURE + UNSUPPORTED_DETAIL）。同一条规则在两处打架。
③ 契约没有回答"疑问句里的预设算不算断言" —— 这是一个**契约缺口**，不只是标注错误：
   本语料有 10 条提问形态回复，判定器在每一条上都会遇到它。
```

**它暴露的更大问题：验收 schema 表达不了"期望不可判定"。**

```text
现状   expected = { shouldAlert: boolean, labels: [...] }
问题   若把 X-B-5 标成 undecidable 而硬塞 shouldAlert=false，
       它会**伪装成"声明的不报警控制"**，进入 declaredNonAlert 分母，
       从而压低不应报警覆盖率 —— 而覆盖率门要求"可判 / 声明 ≥ 0.90"。
       ⇒ 你审出的**每一条** undecidable 都会重复这个污染。
缺口   需要把期望改成三态，并让"期望不可判定"从 declared* 分母里**单列**出去。
       这属于契约级变更（新契约版本 + 新语料版本 + 重取两件冻结）。
```

**待用户裁定（三选一）**：
| | 做法 | 需要改什么 | 代价 |
|---|---|---|---|
| (a) | 改写成真正中性的开放提问（不给候选属性），如「是哪一把？什么型号的？」 | 该条回复 + checkpoint | 成为合格的"无记忆断言"正控；**不需要 schema 变更**；覆盖域不变 |
| (b) | 保留措辞、改标 **alert**（与 X-B-2 一致） | 标注 | 不需要 schema 变更；但它不再是"无记忆断言"样本 ⇒ 该覆盖域 7→6（仍 ≥6） |
| (c) | 标 **undecidable**（用户建议） | **先做契约 + 度量变更**（期望三态 + declared 分母单列） | 诚实，且能检验判定器是否被诱导式提问骗到；额外占 1 个覆盖额度（68 条允许 ≤6）；两件冻结都要重取 |

**助手的倾向**：(a) 或 (c)；不倾向 (b) —— 它把一条本该测"纯提问"的样本变成第三条
UNSUPPORTED_DETAIL，覆盖域白丢一格而没有换来新信息。

## R-2 · 对照条目的理由**只有关系式**（用户提出，针对 `X-ab-1b`）

**用户意见**（2026-09-23，逐字）：
> 判断没问题，但是我对于你的判断理由有点奇怪，难道你的判断理由只有"与 X-ab-1a 逐字相同"吗？
> 你是否核对过其他的变量？还是只是你核对了没说？

**助手判断：缺陷成立，且比"没说"更严重一层。**

```text
我确实核对了三套事实（否则给不出 CURRENT_DISCLOSURE / no_alert），
但记录方式让核对**不可审计**；更要紧的是 —— "与 X-ab-1a 逐字相同；两条必须得到同一个判定"
**不是理由**：那是**判据**（requireAEqualsBConsistency / requirePairConsistency）
对量具的要求，不是"为什么这条是 no_alert"的依据。
⇒ X-ab-1b 的期望值只由配对项推出；若 X-ab-1a 标注错了，本条会**跟着错且无从独立发现**。
   这是**循环依据**，不是薄弱依据。
```

**面比一条大（助手主动审计的结果）**：

```text
验收语料 8 条对照里，**6 条**的理由是纯关系式：X-ab-1a/b · X-os-1a/b · X-sd-1a/b
（X-sm-1a 也近乎如此）
旧语料**同样如此**：contrast-ab-1b 的理由与我的写法一字不差
  ⇒ 我在移植这四类对照时把旧写法**照搬**了，没有质疑它。旧语料不动（历史），仅登记。
```

### R-2 执行（用户确认缺陷后即改）

**已执行**，语料升版本 `m6.1-acceptance@2 → @3`：

```text
① 8 条对照各补**自己的实质依据**（用户原话 + 三套事实 + 回复 → 三态），
   关系式降为一句〔对照关系，次要〕。
② 顺带补实两条过薄的：X-F-1（10 字）、X-J-4（14 字）。
③ 改动半径机械证明：v2 与 v3 逐条比对 —— **只有 10 条的 `rationale` 变化，
   **其它字段 0 条变化**（8249f5fe23a4 → 8a4e0668f952）；v2 留在磁盘上未被动。
```

**新增 2 条机器判据**（把"改 rationale 不可能改变读数"从声称变成判据）：

```text
· 对每条算 buildJudgePrompt，断言 rationale / checkpoint / coverage 的文本
  **一个字都不出现在判定器提示里**
  ⚠️ 第一版这条断言卡的是"理由长度 ≥ 12 字"这个**魔法门槛**，于是 10 字的 X-F-1 把它判红
     —— 门槛在测长度、不在测要测的东西；已改为"每条都有理由 + 零泄漏"。
· v2 仍在磁盘上，且摘要与 v3 清单里 superseded 记的一致（历史不可改写）。
```

**R-2 引出的第二件事（冻结件语义边界，已一并修正）**：验收语料的版本常量原先住在
`m6.1-contract.ts`，而它在候选冻结件的判定链路清单里 ⇒ **语料每升一次版本，候选 id 就跟着变**
（v1→v2 时 `ae01ff0a8f04` → `929536c770bc` 正是如此），而判定规则一字未动。
于是"id 变了"不再意味着"判定器变了"。已把语料描述符搬到
`scripts/m6.1-acceptance-corpus.ts`（**不**在判定链路清单里）：

```text
候选（candidate）      = 判定规则本身
运行配置（run-config） = 读哪一套语料、跑哪些命令
```

保护没有降低：语料摘要由运行配置冻结件与运行时自检**双重绑定**。
